三層責務分離マップ — 全体地図

基本

JP1（ジョブ運用管理）・JSR-352（概念モデル／業界標準語彙）・VB.NET共通基盤（実装）を 三層に分離 し、 それぞれが何を担うかを一望する。設計議論で「これはどの層の話？」と迷ったとき最初に開く図。

┌─────────────────────────────────────────────────────────┐ │ [L1] JP1/AJS3 ★ ジョブの "外側" │ │ │ │ • スケジュール起動 • ジョブネット (依存・並列・順序)│ │ • リモートホスト実行 (jpqjobsub等) │ │ • 戻り値判定 (しきい値) • リカバリ・先行後続制御 │ │ • 運用カレンダー • 履歴集約 • JP1/IM 通報 │ └─────────────────────────────────────────────────────────┘ │ EXE 起動 + 引数 + 戻り値 ▼ ┌─────────────────────────────────────────────────────────┐ │ [L2] JSR-352 ★ 概念モデル / 共通言語 │ │ │ │ Job ─ Step ─ Chunk(Reader/Processor/Writer) │ │ │ │ │ └ Batchlet / Listener / Partition │ │ │ │ Checkpoint Restart Skip Retry ExitStatus JSL │ │ ※「業界標準語彙」として設計議論・ドキュメントで使う │ └─────────────────────────────────────────────────────────┘ │ 概念を実装に落とし込む ▼ ┌─────────────────────────────────────────────────────────┐ │ [L3] VB.NET 共通基盤 ★ ジョブの "中身" │ │ │ │ • 引数解析 / 設定読込 • DB接続・Tx制御 │ │ • Chunk/Batchlet テンプレート │ │ • Checkpoint テーブル • 冪等性キー │ │ • 共通ログ (相関キー埋込) • DLQ │ │ • 戻り値マッピング (例外→ExitCode) │ └─────────────────────────────────────────────────────────┘
🔰 三層分離の意義
JP1とアプリ基盤を独立した層として設計すると、(1) JP1製品自体の入替え影響を局所化でき、(2) アプリ基盤を他案件で再利用しやすく、(3) 中央のJSR-352概念層を共通言語として持つことで国際的な議論にも耐える。 
  方針:  JP1は "WHEN/WHERE"   → いつ・どこで動かすか
         JSRは "WHAT"          → 概念モデルで何を意味するか
         VB は "HOW"           → 具体的にどう実装するか

01

ジョブ粒度の対応関係 — 「Job」って誰のJob?

基本

JP1の「ジョブ」「ジョブネット」と、JSR-352の「Job」「Step」、VB.NET実装の「EXE」「クラス」は 名前は似ているが粒度が違う。 ここを揃えないとレビューで永遠に話が噛み合わない。

[ JP1/AJS3 ] [ JSR-352 ] [ VB.NET 実装 ] ───────────────────── ────────────── ────────────────── ルートジョブネット ├ ジョブネット │ ├ ジョブ A ─────▶ Job A ─────▶ AppA.exe │ │ ├ Step 1 ──▶ クラス: LoadStep │ │ │ └ Chunk ──▶ Reader/Processor/Writer │ │ └ Step 2 ──▶ クラス: AggregateStep │ │ └ Batchlet ──▶ クラス: AggregateBatchlet │ ├ ジョブ B ─────▶ Job B ─────▶ AppB.exe │ └ ジョブ C ─────▶ Job C ─────▶ AppC.exe └ ジョブネット (並列) ├ ジョブ D ┐ └ ジョブ E ┴ ─▶ 別Jobとして並列実行
⚠ 落とし穴： JP1の「ジョブ」とJSR-352の「Job」は同じ言葉だが指す範囲が異なる。 JP1ジョブ = OS/EXE実行単位、JSR-352 Job = アプリ内のバッチ処理単位。
→ 通常は 1 JP1ジョブ = 1 EXE = 1 JSR-352 Job の対応にすると混乱が少ない。
JP1 / 起動コマンド例（ジョブネット内のジョブ定義）
REM JP1/AJS3 ユニット定義 — UNIX/Windowsジョブ
REM ジョブ定義の "実行ファイル名" として共通基盤EXEを指定

scriptpath="D:\Batch\AppDailySales.exe"
prm="/jobid=%JP1_JOBID% /executionDate=%JP1_TODAY% /mode=normal"
env="BATCH_ENV=PROD"
jd="and"          REM 終了判定: 戻り値AND
tho=0              REM 警告しきい値
abh=8              REM 異常しきい値 (8以上で異常)
JSR-352 / Job XML (JSL) — 概念モデル表現
<!-- 同じ業務をJSR-352 JSLで表現すると -->
<job id="dailySalesJob">
  <step id="loadStep" next="aggregateStep">
    <chunk item-count="100">
      <reader    ref="salesCsvReader"/>
      <processor ref="salesValidator"/>
      <writer    ref="salesDbWriter"/>
    </chunk>
  </step>
  <step id="aggregateStep">
    <batchlet ref="salesAggregateBatchlet"/>
  </step>
</job>
VB.NET / 共通基盤Main — 上記2つに対応する実装
' AppDailySales.exe のエントリポイント
' 1 EXE = 1 JSR-352 Job として扱う

Module Program
    Sub Main(args() As String)
        Dim ctx = JobContext.Parse(args)   ' /jobid=, /executionDate=
        Dim job = New JobBuilder("dailySalesJob", ctx) _
            .AddStep(New ChunkStep("loadStep",
                reader:=New SalesCsvReader(),
                processor:=New SalesValidator(),
                writer:=New SalesDbWriter(),
                itemCount:=100)) _
            .AddStep(New BatchletStep("aggregateStep",
                New SalesAggregateBatchlet())) _
            .Build()

        Dim exitCode = job.Execute()
        Environment.Exit(exitCode)   ' ← JP1がここを判定
    End Sub
End Module
✓ 設計の鉄則： 1 JP1ジョブ = 1 EXE = 1 JSR-352 Job の1:1:1対応を基本とする。 複数のEXEを1ジョブネット内で並べて表現することで、JP1の依存制御の力を最大限活かせる。
逆に1 EXEの中で5つも6つもStepを持たせるのは、JP1の制御外になり運用が辛くなる。
02

Chunk vs Batchlet — どちらで実装すべきか

中級

JSR-352の2つの実行モデル Chunk と Batchlet は、 「件数ループがあるか／ないか」 で使い分ける。 この判別を間違えると、Checkpoint/Restartが効かない or 過剰実装になる。

判別軸Chunk向きBatchlet向き
処理形態レコード単位ループ単発処理
典型例CSV→DB登録、DB→DB集計、ファイル変換FTP転送、外部コマンド起動、DDL発行
件数概念ありなし
Checkpoint自動で効く不要/不可
Tx境界item-count件ごとprocess()全体で1Tx
Skip/Retryレコード単位で可処理全体のリトライのみ
VB.NET実装3クラス(Reader/Processor/Writer)1クラス(IBatchlet実装)
VB.NET / Chunk実装パターン
' 大量レコードを「100件読む→加工→100件書く」でループ
Public Class SalesCsvReader
    Implements IItemReader(Of SalesRecord)

    Private _stream As StreamReader
    Private _position As Long

    Public Function ReadItem() As SalesRecord _
        Implements IItemReader(Of SalesRecord).ReadItem
        Dim line = _stream.ReadLine()
        If line Is Nothing Then Return Nothing   ' 終端
        _position += 1
        Return SalesRecord.Parse(line)
    End Function

    ' Checkpoint用: 現在位置を返す
    Public Function Checkpoint() As Object
        Return _position
    End Function
End Class
VB.NET / Batchlet実装パターン
' FTPで1ファイル転送する単発処理 — 件数ループ概念がない
Public Class FtpUploadBatchlet
    Implements IBatchlet

    Public Function Process() As String _
        Implements IBatchlet.Process

        Try
            FtpClient.Upload(_localPath, _remotePath)
            Return "COMPLETED"          ' ← ExitStatus
        Catch ex As FtpTimeoutException
            Return "RETRY"              ' ← JP1がジョブ再実行する目印
        Catch ex As Exception
            Logger.Error(ex)
            Return "FAILED"
        End Try
    End Function

    Public Sub Stop_() Implements IBatchlet.Stop_
        ' JP1からの停止指示を受けて中断
        FtpClient.Cancel()
    End Sub
End Class
⚠ よくある誤用： 「件数ループがあるけど単純だからBatchletで」と書いてしまうと、 Checkpoint/Restart が効かない ため、 100万件処理中の99万件目で落ちたら最初からやり直し。これはJP1再実行時に致命的な遅延になる。
→ 件数ループ＝Chunk一択 をルール化する。
📘 判別フローチャート：
(1) この処理は「N件のレコードを1件ずつ処理する」？ → Chunk
(2) この処理は「ファイル/コマンドを1回実行して結果を返す」？ → Batchlet
(3) 両方に見える？ → 件数の側を主軸にChunk、外部コマンド呼び出しはChunk内のWriter側に閉じ込める
03

Checkpoint / Restart — 二段階の再開戦略

中級

Checkpoint/Restartは 「ジョブ全体の再実行（JP1）」と「レコード単位の続行（アプリ）」 の二段構造で設計する。 JP1のリカバリ機能だけに頼ると、100万件処理を毎回最初からやり直す羽目になる。

[ 失敗発生時の選択肢 ] ▼ JP1 リカバリ実行 └ ジョブ全体を最初から再実行 │ ├─ 副作用なしジョブ → そのまま再実行OK │ └─ 副作用ありジョブ → ❌ 二重登録・整合性破壊リスク └ 冪等性キー or Checkpoint参照が必須 ▼ アプリ Restart ★推奨 └ Checkpointから続行 │ ├─ 100万件中90万件処理済 → 90万件目から再開 └─ 副作用は冪等性キーで防止
VB.NET / Checkpointテーブル設計
-- 共通基盤がジョブ実行ごとに自動でI/Oする管理テーブル
CREATE TABLE BATCH_CHECKPOINT (
    JOB_NAME       VARCHAR(64)   NOT NULL,
    EXECUTION_KEY  VARCHAR(64)   NOT NULL,  -- JP1ジョブID等
    STEP_NAME      VARCHAR(64)   NOT NULL,
    READER_POS     BIGINT        NULL,      -- Reader位置
    READ_COUNT     BIGINT        NOT NULL,  -- 累計読込件数
    WRITE_COUNT    BIGINT        NOT NULL,
    SKIP_COUNT     BIGINT        NOT NULL,
    BATCH_STATUS   VARCHAR(16)   NOT NULL,  -- STARTED/COMPLETED/FAILED/STOPPED
    LAST_UPDATED   DATETIME2     NOT NULL,
    PRIMARY KEY (JOB_NAME, EXECUTION_KEY, STEP_NAME)
);
VB.NET / Chunk処理ループ (Checkpoint付き)
Public Class ChunkStep
    Public Function Execute(ctx As JobContext) As String
        ' 1. Checkpoint復元 (前回中断位置から)
        Dim cp = CheckpointRepository.Load(ctx.JobName, ctx.ExecutionKey, _stepName)
        If cp IsNot Nothing AndAlso cp.BatchStatus <> "COMPLETED" Then
            _reader.Restore(cp.ReaderPos)   ' 続きから読む
        End If

        ' 2. Chunk ループ
        Do
            Using tx = _db.BeginTransaction()
                Dim buffer As New List(Of SalesRecord)
                For i As Integer = 1 To _itemCount   ' 100件
                    Dim rec = _reader.ReadItem()
                    If rec Is Nothing Then Exit For
                    Dim processed = _processor.ProcessItem(rec)
                    If processed IsNot Nothing Then buffer.Add(processed)
                Next
                If buffer.Count = 0 Then Exit Do

                _writer.WriteItems(buffer)

                ' 3. Checkpoint保存 (Tx内で永続化)
                CheckpointRepository.Save(ctx, _stepName, _reader.Checkpoint())

                tx.Commit()  ' ← データ + Checkpoint が原子的に確定
            End Using
        Loop

        Return "COMPLETED"
    End Function
End Class
Before — Checkpointなし
100万件のCSV取込で99万件目に異常 → JP1リカバリ実行 → 最初の1件目から再開 → 99万件分の重複登録 or 全件削除&再実行で4時間ロス
After — Checkpoint+冪等性キー
99万件目で異常 → JP1リカバリ実行 → 共通基盤がCheckpoint読込 → 99万件目から続行 → 1万件処理して数分で完了
🚫 アンチパターン： Checkpoint保存を別Txで行う実装。データ書き込みとCheckpointが別Txだと、片方だけ成功した場合に整合性が崩れる。 必ず同一Tx内で保存する（VB.NETなら同じ SqlTransaction）。
04

戻り値・ExitStatus 設計 — JP1との契約

中級

JP1はEXEの 戻り値（ExitCode）でジョブの正常／警告／異常を判定 する。 ここを社内標準化しないと、ジョブネット定義のしきい値がプロジェクト毎にバラバラになり、 運用引継ぎで必ず事故る。

ExitCode意味JP1判定JSR-352 ExitStatus典型ケース
0正常終了正常COMPLETED全件処理成功
1警告終了警告COMPLETED_WITH_WARNINGSkipありで完走
4業務エラー異常FAILED業務データ不整合(再実行不可)
8システムエラー異常FAILEDDB接続断・タイムアウト(再実行可)
16致命的エラー異常ABANDONEDCheckpoint破損・即時停止
100+起動前エラー異常—引数不正・設定ファイル無し
VB.NET / 例外→ExitCode マッピング
Public Module ExitCodeMapper
    Public Function Map(ex As Exception) As Integer
        Select Case ex.GetType()
            Case GetType(ArgumentException),
                 GetType(ConfigurationException)
                Return 100   ' 起動前エラー

            Case GetType(BusinessRuleException)
                Return 4     ' 業務エラー (再実行しても直らない)

            Case GetType(SqlException),
                 GetType(TimeoutException),
                 GetType(IOException)
                Return 8     ' システムエラー (再実行で復旧可能性あり)

            Case GetType(CheckpointCorruptedException)
                Return 16    ' 致命的 (人手介入必須)

            Case Else
                Return 8     ' デフォルトはシステムエラー扱い
        End Select
    End Function
End Module
JP1 / ジョブ定義のしきい値設定
REM JP1/AJS3 ユニット定義 — しきい値は社内標準で固定

tho=1          REM 警告しきい値: ExitCode 1以上で警告(色変化&通報なし)
abh=4          REM 異常しきい値: ExitCode 4以上で異常(JP1/IM通報)
jd="and"      REM 終了判定: しきい値による判定

REM ★ 全ジョブで tho=1 / abh=4 を必須とすることで運用が統一される
REM ★ ExitCode 8 と 16 はリカバリ手順が違うので、JP1/IMで色分け通報
✓ 設計の鉄則： ExitCode 4 と 8 を分ける意味は 「JP1の自動リカバリ可否を区別するため」。
・ExitCode 8 → 自動リカバリで再実行可能 (DBが復旧していれば次回成功)
・ExitCode 4 → 人間がデータを修正しないと再実行しても同じエラー
この区別をJP1のリカバリ設定（自動再実行回数）に反映させる。
⚠ 注意： .NETの Environment.Exit(code) は終了コードに signed 32bit を渡せるが、JP1で扱えるのは慣例的に 0〜255。 256以上を返してもJP1側で下位8bitだけ取られて誤判定になる。2桁台に収めるのが安全。
05

ログ相関キー設計 — 横串で追えるログ

中級

JP1ログ・アプリログ・DB処理履歴が 同一キーで突合可能 でないと、障害解析時間が桁違いに伸びる。 設計初期に「相関キーは何か」を決め、全ログに必須プレフィックスとして埋め込む。

[ 相関キーで横串 ] JP1/AJS3 ログ アプリログ DB処理履歴 ───────────── ───────────── ───────────── JOBID=A2024001 [JOBID=A2024001] INSERT_HIST Step:loadStep EXEC_KEY=A2024001 StartTime=... Chunk:42回目 INSERTED_AT=... ItemRead:4250 EndTime=... ExitCode=8 ERROR: SqlEx ROLLBACK record → ExitCode=8 ───────────── ───────────── ───────────── ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ └──┴──┴── 同一キー A2024001 で結合 ──┴──┴──┘
JP1 / 起動引数で相関キーを渡す
REM JP1がEXE起動時に必ず渡す3つの標準引数

prm="/jobid=%JP1_JOBID%"            REM JP1ジョブID(JP1組込変数)
   + " /executionDate=%JP1_TODAY%"  REM 業務日付
   + " /netname=%JP1_JOBNETNAME%"    REM ジョブネット名

REM ★ JP1組込変数: JP1_JOBID, JP1_TODAY, JP1_JOBNETNAME 等
REM ★ %JP1_JOBID% は1ジョブ実行ごとにユニーク値が自動生成される
VB.NET / 全ログに相関キーを自動埋込 (NLog/log4net例)
' 起動時に MDC (Mapped Diagnostic Context) にセット
Public Class JobContext
    Public Sub InitLogContext()
        log4net.ThreadContext.Properties("JOBID") = Me.JobId
        log4net.ThreadContext.Properties("NETNAME") = Me.NetName
        log4net.ThreadContext.Properties("EXECDATE") = Me.ExecutionDate
    End Sub
End Class

' log4net.config — フォーマットに必ず埋め込む
' <conversionPattern value="[%date] [%property{JOBID}] [%level] [%property{STEP}] %message" />

' 出力例:
' [2026-05-05 10:23:14] [A2024001] [INFO] [loadStep] Chunk #42 committed (4250 items)
' [2026-05-05 10:23:18] [A2024001] [ERROR] [loadStep] SqlException: timeout
SQL / DB処理履歴テーブルにも相関キー
-- 業務テーブルに監査列として最低限これだけは持つ
CREATE TABLE SALES_HEADER (
    SALES_ID       VARCHAR(32)   PRIMARY KEY,
    -- ... 業務列 ...
    EXEC_KEY       VARCHAR(64)   NOT NULL,  -- ★ JP1ジョブID
    INSERTED_AT    DATETIME2     NOT NULL,
    INDEX IX_EXEC_KEY (EXEC_KEY)              -- 障害時の絞込用
);

-- 障害時はこれ1発で「このジョブが登録した全レコード」が取れる
SELECT * FROM SALES_HEADER WHERE EXEC_KEY = 'A2024001';
Before ▶︎ 相関キーなし
「昨夜のジョブで重複登録があった」→ JP1ログから時刻特定 → アプリログをタイムスタンプで突合 → DBはタイムスタンプ範囲検索 → 同時刻に複数ジョブが動いていて切り分け不能 → 半日の調査
After ▶︎ 相関キーあり
「ジョブA2024001で重複登録」→ JP1ログ・アプリログ・DBを WHERE EXEC_KEY='A2024001' で一発検索 → 5分で原因レコード特定
📘 相関キー三種の使い分け：
・JOBID = JP1の1回の実行を識別 (運用視点・障害切分け)
・NETNAME = ジョブネット名 (業務視点・どの業務か)
・EXECDATE = 業務日付 (データ視点・何日分か)
3つすべてをログとDB監査列に埋め込んでおくと、運用/業務/データの3軸で集計できる。
06

リトライ戦略の二段構え — 粒度を分ける

中級

リトライは 「JP1のジョブ単位リトライ」と「アプリのレコード単位リトライ」 の二段構造で設計する。 混同すると「DB一時障害でも全件最初から」「業務エラー1件でジョブ全体停止」など極端な運用になる。

[ 二段リトライ階層 ] 例外発生 │ ┌─────┴─────┐ ▼ ▼ 一時的か? 永続的か? │ │ ▼ ▼ ┌──────────┐ ┌──────────────┐ │レコード単位 │ │ジョブ単位 │ │ Retry │ │ Skip + Log │ → DLQへ │ (アプリ層) │ │ (アプリ層) │ └──────────┘ └──────────────┘ │ Retry上限超過 ▼ ┌─────────────────────────────┐ │ ExitCode 8 で終了 │ │ → JP1が "ジョブ全体" を再実行│ │ (Checkpointから続行) │ └─────────────────────────────┘
リトライ階層担当粒度典型ケース制御方法
レコード単位VB.NET1レコード個別レコードの一時的エラーRetry例外指定+回数
レコード単位VB.NET1レコード業務エラーで該当行スキップSkip例外指定+DLQ転送
Step全体VB.NETStep単位Checkpointから続行Restart API

多重起動制御 — 二重実行を絶対防ぐ

上級

JP1が二重起動を防いでくれる、と思って油断すると刺される。 JP1管轄外の経路（手動実行・障害復旧時の応急実行）からの二重起動 はアプリ側でしか防げない。

SQL / 排他制御テーブル
CREATE TABLE BATCH_LOCK (
    JOB_NAME       VARCHAR(64)  PRIMARY KEY,
    LOCKED_BY      VARCHAR(64)  NOT NULL,   -- JP1ジョブID + ホスト名
    LOCKED_AT      DATETIME2    NOT NULL,
    HEARTBEAT_AT   DATETIME2    NOT NULL,   -- 死活確認
    EXPIRES_AT     DATETIME2    NOT NULL    -- 失効時刻 (ゾンビ対策)
);
VB.NET / 起動時のロック取得
Public Class BatchLockService
    Public Function TryAcquire(jobName As String, lockedBy As String) As Boolean
        Using tx = _db.BeginTransaction(IsolationLevel.Serializable)
            ' 1. 期限切れロックを除去 (ゾンビ対策)
            _db.Execute("DELETE FROM BATCH_LOCK WHERE EXPIRES_AT < SYSDATETIME()", tx)

            ' 2. INSERT試行 — 既存ロックがあれば一意制約違反で失敗
            Try
                _db.Execute(
                    "INSERT INTO BATCH_LOCK (JOB_NAME, LOCKED_BY, LOCKED_AT, HEARTBEAT_AT, EXPIRES_AT) "  &
                    "VALUES (@j, @b, SYSDATETIME(), SYSDATETIME(), DATEADD(MINUTE, 60, SYSDATETIME()))",
                    New With {.j = jobName, .b = lockedBy}, tx)
                tx.Commit()
                Return True
            Catch As SqlException
                Return False   ' 既に別実行中
            End Try
        End Using
    End Function

    Public Sub Release(jobName As String)
        _db.Execute("DELETE FROM BATCH_LOCK WHERE JOB_NAME = @j", New With {.j = jobName})
    End Sub
End Class

' Main内での使用
If Not _lockSvc.TryAcquire(jobName, lockedBy:=$"{ctx.JobId}@{Environment.MachineName}") Then
    Logger.Error($"二重起動検知: {jobName}")
    Environment.Exit(101)   ' 起動前エラー扱い
End If
⚠ ゾンビロック問題： ジョブ強制Kill時にロックが残り、次回正常起動を阻害する。 対策は2つ併用:
(1) EXPIRES_AT による失効 (上記コード)
(2) Heartbeat更新スレッドで HEARTBEAT_AT を1分毎更新、5分以上更新が止まったら別プロセスから強制解放可
🚫 やってはいけない： JP1の多重度制御だけで二重起動防止が完了していると主張する設計書。 JP1停止中の応急対応・別ホストからの実行・テスト環境の検証実行など、JP1管轄外経路で必ず破綻する。 「全経路で1つしか動かない」 をDB制約で保証する。

上級

バッチ並列化には2つのアプローチがある。 JP1ジョブネットで並列ジョブを並べる方法 と、 1ジョブ内でJSR-352 Partitioningを使う方法 。それぞれ得手不得手がある。

VB.NET / アプリ内Partitioning実装
Public Class PartitionedStep
    Public Function Execute(ctx As JobContext) As String
        ' 1. PartitionMapper: 分割計画を作成
        Dim partitions = _mapper.MapPartitions(ctx)   ' [{1-25},{26-50},{51-75},{76-100}]

        ' 2. 各Partitionを並列実行
        Dim tasks = partitions.Select(Function(p)
            Return Task.Run(Function()
                Return ExecutePartition(p, ctx)
            End Function)
        End Function).ToArray()

        Task.WaitAll(tasks)

        ' 3. Reducer: 結果集約
        Dim totalProcessed = tasks.Sum(Function(t) t.Result.WriteCount)

        If tasks.Any(Function(t) t.Result.Status = "FAILED") Then
            Return "FAILED"
        End If
        Return "COMPLETED"
    End Function
End Class
✓ 設計の指針： 「JP1がある」前提なら原則アプローチA(JP1並列)を採用。 個別失敗時のリカバリ・運用可視性・別ホスト分散の容易さで圧倒的に有利。 アプローチB(アプリPartitioning)は 「分割数を動的に決めたい」「ホスト1台で完結させたい」 場合の限定採用。
📘 ハイブリッド： 大規模案件では「JP1で4分割並列起動」×「各ジョブ内でさらに2スレッド並列」のような二段並列もあり得る。 ただし運用・障害解析が複雑化するため、性能要件が単段で満たせるなら絶対に単段に留める。

上級

JP1は強力なため、ついジョブネット内に業務ロジックを書きたくなる。これは 方式設計の最大の落とし穴 。 責務境界を死守するため「JP1でやらないこと」を成果物に明記する。

🔰 まとめ — 三層分離の効能
この対応表が示すのは、 「JP1とアプリ基盤は守備範囲が補完関係にある」 ということ。 JP1にしかない用語(ジョブネット・運用カレンダー)はジョブの外側を、 JSR-352/VB.NETにしかない用語(Step・Chunk・Checkpoint)はジョブの中身を表現している。 
  JP1のみ ──────  ジョブの外側 (運用)
                     ── 戻り値・相関キー (契約)
  JSR-352/VB.NETのみ  ジョブの中身 (処理品質)
この補完性を理解すれば、 「どの層で何を解決すべきか」 が機械的に判定できる。
