SKILL形式の発見（v0.7→v0.8の差異）

発見

Lab手順書は v0.7.x（スラッシュコマンド形式）想定だが、実機で入った Spec Kit は v0.8.4.dev。 .claude/commands/ ではなく .claude/skills/ 配下に SKILL.md 形式 で配置されていた。 これは Anthropic の Claude Skills 公式仕組みに合わせた進化。

観点v0.7（旧）v0.8（実機）
ファイル形式.md（シンプル）SKILL.md（YAML+構造化）
配置場所.claude/commands/.claude/skills/{name}/

コマンド数6個14個（Git連携追加）

Git連携ブランチ作成のみコミットまで自動化可

# SKILL.md の YAML フロントマター（実機で確認）
---
name: "speckit-constitution"
description: "Create or update the project constitution..."
user-invocable: true          # /コマンド名で起動可
disable-model-invocation: false  # 自然文でもAIが自律起動

🔰 SKILL とスラッシュコマンドの違い

スラッシュコマンドは「テンプレート展開」が中心。SKILL は「能動的な振る舞いを記述」できる。 たとえば「.specify/extensions.yml を読んで条件付きフックを実行する」というロジックを SKILL.md 内に書ける。 Tom が普段書いている ~/mnt/skills/user/ のカスタムスキルと同じ仕組み。

Constitution — 不変原則6条

仕様策定

Spec Kit 最初のステップは「憲章 (Constitution)」。プロジェクト全体に常に適用される不変原則を定める。 これがあると AI が勝手にフレームワーク導入や過剰抽象化をしなくなる。 

/speckit-constitution

このプロジェクトは Python 3.12 で作る最小TODO CLI です。
以下を不変原則として明文化してください:

1. テストファースト（実装前にpytestを書く）
2. 標準ライブラリ優先、外部依存は必要最低限
3. 型ヒントを全関数に付ける
4. 1ファイル100行を目安に分割
5. README に使い方を必ず書く
6. CLI は --help で全機能が分かる設計
📘 生成物の質が高かった理由: AI は RFC2119 の MUST/SHOULD/MAY を使い分け、各原則に __post_init__ や mypy --strict など具体的な検証手段まで提示した。 Tom が指示しなくても「Test-First (NON-NEGOTIABLE)」のような強度を自動で付与。
⚠️ Technology Constraints がやや先走り: 生成された Constitution に「Storage: JSON file」など Lab08 plan で決めるべき技術選定が含まれてしまった。許容範囲だが、本来は plan 領域。 Lab学習としては「過剰原則の検出」を体験する機会と捉えた。

Clarify — 5問対話で曖昧解消

仕様策定

/speckit-clarify は 仕様の曖昧さを AI が質問形式で洗い出す。最大5問。 Plan に進む前にここで詰めるとAIの暴走リスクが減る。初回は必ずやるのが推奨。

#質問領域選択趣旨
1保存場所BXDG準拠、~/.local/share/todo/
2バリデーションB200文字、空白拒否、絵文字OK
3破損時挙動Bエラー停止、ユーザに委ねる
4並行アクセスAlast-write-wins、ロックなし
5出力形式Aプレーンテキストのみ
 
# 5問完答後、AI が spec.md に「明確化事項」セクションを自動追記
## 明確化事項

### セッション 2026-04-30

- Q: データ永続化の保存先は？ → A: XDG Base Directory 準拠...
- Q: タイトルの入力バリデーション制約は？ → A: 最大200文字...
- Q: データファイル破損時の挙動は？ → A: エラーメッセージで...
- Q: 複数プロセス同時起動時の挙動は？ → A: Last-write-wins...
- Q: 一覧表示の出力フォーマットは？ → A: プレーンテキストのみ...
📘 賢い設計判断: 質問4で AI が fcntl.flock / msvcrt.locking を提示しつつ 「複雑さに対して得られる安全性が釣り合わない」と選択肢A（ロックなし）を推奨した。 これは Constitution の「最小」原則と整合する妥当な判断。

Plan — 多層成果物の連鎖生成

設計と分解

/speckit-plan でついに技術スタックを決める。plan.md だけでなく関連ファイル群が芋づる式に生成される。 これらが「契約」として後段の tasks.md 生成に効く。Spec Kit の真価はこの多層成果物の連動にある。 

# /speckit-plan で生成される全ファイル
specs/001-todo-cli/
├── plan.md                     # アーキテクチャ概要
├── data-model.md               # データ構造とJSONスキーマ
├── quickstart.md               # クローンから動作確認まで
├── research.md                 # 技術選定の検討メモ
└── contracts/
    └── cli-commands.md         # CLI入出力契約（v0.8追加）
ファイルサイズ役割
plan.md5.5KB（〜200行）5モジュール構成、Constitution Check表
data-model.md3.3KBJSONスキーマ + 不変条件5項目 + 状態遷移図
quickstart.md1.8KBuv/pip インストール、5コマンドワークフロー
research.md5.5KBargparse vs click vs typer など6項目の比較
contracts/cli-commands.md2.3KB4コマンドの stdout/stderr/exit code 契約
✓ AI が spec.md にない設計判断を追加: research.md の最終セクションで AI は Atomic File Writes（tempfile.NamedTemporaryFile + os.replace）を 自発的に追加。last-write-wins の腐敗リスクを軽減する保険として、後段で正式タスク化される。
🔰 「契約 (Contract)」とは

contracts/cli-commands.md はCLI の完全契約書。各コマンドの stdout / stderr / exit code を 正確な文字列レベルで定義する。これが pytest の期待値そのものとして使える:

contracts          tests              implementation
─────────          ─────────          ─────────────
"Added task 1: x"  → assert "Added"  → print(f"Added...")
                       in stdout         in cli.py

仕様→テスト→実装が1本の文字列でつながる。これが Spec-Driven の追跡性の真髄。

Sledgehammer問題と業務適用の判断

検証と振り返り

Tom は Lab 完走後に「前回手書きで2時間で作れた、これ Sledgehammer だった？」と問うた。 鋭い問い。答え: 学習目的としては適切、業務として同じ規模なら過剰。 機能規模に応じて Spec Kit のフローを取捨選択するのが実務的。

項目前回（手書き）今回（Spec Kit）
所要時間約2時間約6〜8時間
テスト数数個〜10個49個
ドキュメントREADMEのみ10ファイル
明示的設計判断即興7件（research.md）
実装の堅牢性普通アトミック書込・XDG・破損検出
💡 業務適用時の規模ベース判断
  • バグ修正・小改修（1〜2h）: Spec Kit 不使用、通常の Claude Code
  • 中規模機能（半日〜2日）: constitution + specify + plan + implement のみ。clarify と tasks はスキップ
  • 大規模機能（数日〜数週間）: 全フロー使用、本Lab通り
  • 新規プロジェクト: 全フロー使用、特に constitution に時間をかける
こう見えたら使えるサイン:
  • 「設計書を残さないと3ヶ月後の自分が困る」と思った
  • チーム内で機能の振る舞いに認識ズレが起きた経験がある
  • 仕様→実装の追跡性を監査で求められる
