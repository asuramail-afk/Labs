00

OIDCが解決する問題

概念

なぜ OIDC が生まれたのか。「自前でログイン機能を作る」方式と比較して、何が問題で、OIDCがどう解決するかを理解します。

BEFORE OIDC — 自前ログインの世界
各アプリが自分でユーザーテーブル・パスワードハッシュ・セッション管理を実装する。
問題は3つ:
① パスワードの散在: ユーザーはサービスごとに別のパスワードを管理（or 使い回す）
② 実装ミスのリスク: パスワードの保存方法、ブルートフォース対策、MFAなどを各開発者が正しく実装する保証がない
③ 統合不可能: 社内で複数アプリを使うとき、ログインが別々で統合管理（SSO）ができない
OIDC の発想: 「認証は専門のサーバー（IdP）に任せ、アプリはその結果だけを受け取る」。
アプリはパスワードを一切扱わず、IdPが発行したIDトークン（「この人は確かに tom です」という証明書）を受け取るだけ。
観点自前ログインOIDC
パスワード保管各アプリが保管 → 漏洩リスクが分散IdP だけが保管 → 1箇所で厳重管理
MFA 対応各アプリで個別実装IdP で一元設定、全アプリに適用
SSO不可能（アプリ間でセッション共有できない）IdP のセッションで複数アプリにログイン
アプリ開発者の負担認証ロジック全て自前リダイレクト + トークン検証のみ
ユーザー体験サービスごとに登録・ログイン1回のログインで複数サービス利用
なぜ OAuth 2.0 だけでは不十分か: OAuth 2.0 は「認可」（APIアクセス権の委譲）の仕様。「この人は誰か」（認証）を安全に伝える仕組みがなかった。OIDC は OAuth 2.0 の上にIDトークンという「認証の証明書」を追加した拡張仕様。
POINT — ここを押さえる
  1. OIDC = OAuth 2.0 + IDトークン（認証レイヤー）。OAuth 2.0 が「鍵の貸し借り」なら、OIDCは「身分証明書の発行」を追加したもの
  2. アプリ（RP = Relying Party）はパスワードを一切知らない。IdPにリダイレクトして、結果のトークンだけ受け取る
  3. IdP を差し替え可能（Keycloak → Auth0 → Entra ID）にする標準プロトコル。ベンダーロックインを避けられる
01

全体アーキテクチャ

概念

今回構築するシステムの登場人物と、なぜこの構成にするのかを図で確認します。

登場人物（3者）
① ブラウザ（エンドユーザー）: ログインしたい人。パスワードを入力する先は IdP の画面だけ。
② Node.js アプリ（RP: Relying Party）: 認証を IdP に「頼む」側。トークンを受け取ってセッションを作る。
③ Keycloak（IdP: Identity Provider）: 認証を「引き受ける」側。ユーザーDBを持ち、トークンを発行する。

│  Windows ノートPC (localhost のみ)                │
│                                                  │
│  ┌──────────┐                ┌────────────────┐ │
│  │ Browser   │  ──Cookie──►  │ Node.js App    │ │
│  │           │               │ (Express)      │ │
│  │           │               │ :3000          │ │
│  │           │               │                │ │
│  │           │  ◄─redirect─  │   ──HTTP──►    │ │
│  │           │               │            ┌───┴──────────┐
│  │           │  ──ID/PW──►   │            │ Keycloak     │
│  │           │               │            │ (IdP)        │
│  │           │               │            │ :8080        │
│  └──────────┘               └────────────┴──────────────┘
│                                                  │
│  全通信が localhost 内で完結 → 機密データが外に出ない   │
└─────────────────────────────────────────────────┘
なぜ Keycloak か: 完全にローカルで動く OSS の IdP。Docker 1コマンドで起動でき、本番レベルの機能（Realm, Client, MFA, SSO）を無償で試せる。データが外部に出ないため、客先の機密環境でも安心して検証できる。
なぜ Node.js + Express か: openid-client ライブラリが OIDC の全手順（Discovery, 認可URL生成, トークン交換, ID トークン検証）を隠蔽せずに使えるため、各ステップで「今何のHTTP通信が起きているか」を観測しやすい。
構成要素ポート役割なぜ必要か
Keycloak:8080IdP（認証サーバー）ユーザーDB + ログイン画面 + トークン発行
Express:3000RP（Webアプリ）ログイン/コールバック/セッション管理
ブラウザ—エンドユーザーリダイレクトの起点と終点
POINT — この構成のメリット
  1. ¥0: 全て OSS / 無償。Docker Engine（WSL2）なら商用ライセンスも不要
  2. 外部通信なし: localhost で完結するため、VPN 不要・機密環境OK
  3. 本番に近い: Keycloak は Red Hat SSO のアップストリーム。本番で使われる IdP そのもの
  4. 差し替え容易: .env の Issuer URL と Client 情報を変えるだけで Auth0 / Entra ID に切り替え可能
02

Keycloak 起動

環境構築

IdP（認証サーバー）を1コマンドで起動します。なぜ開発モードか: 本番ではHTTPS必須・DB設定必須ですが、学習目的では HTTP + 組み込みDB で十分。start-dev はその簡易起動フラグです。

Docker（WSL2 Ubuntu 上で実行）
docker run -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:26.0 start-dev
パラメータ値なぜ必要か
-p 8080:8080ポートマッピングWindows のブラウザから localhost:8080 でアクセスするため
KC_BOOTSTRAP_ADMIN_USERNAMEadmin管理コンソールの初期管理者。未設定だとログインできない
KC_BOOTSTRAP_ADMIN_PASSWORDadmin同上のパスワード。学習用なので簡易値でOK
start-dev開発モードHTTP許可 + 組み込みH2 DB。本番では start + DB設定 + HTTPS
Docker Desktop vs Docker Engine: Docker Desktop は従業員250人以上 or 年商$10M以上の企業では有償ライセンスが必要。WSL2 + Docker Engine（CLI版）なら完全無償・商用利用OK。
Docker が使えない場合: Keycloak ZIP版 + JDK 17（Temurin等、無償）で代替可能。
keycloak-26.x/bin/kc.bat start-dev で同じように起動する。Node.js アプリ側は一切変更不要。
実機確認
  1. コンソールに Keycloak 26.0 ... started と表示されることを確認
  2. ブラウザで http://localhost:8080 を開き、Keycloak のウェルカムページが表示されることを確認
  3. admin / admin で管理コンソールにログインできることを確認
  4. ログイン後、左上に「master」というRealm名が表示されていることを確認（これがデフォルトRealm）
03

Realm・Client・User 設定

環境構築

Keycloak 管理コンソールで「誰が」「どのアプリに」「どうやって」ログインするかを登録します。各設定項目のなぜを理解することが重要です。

Step 1: Realm 作成

なぜ Realm を分けるか: Realm は「テナント」に相当する隔離単位。master Realm は Keycloak 自体の管理用なので、アプリ用には専用 Realm を作る。ユーザー・Client・設定が Realm ごとに完全に分離される。
Keycloak 管理コンソール操作
左上のドロップダウン（「master」と表示）→ Create realm
  Realm name: testrealm
  → Create

Step 2: Client 作成

なぜ Client を登録するか: IdP は「どのアプリからのリクエストか」を識別する必要がある。未登録のアプリからの認証リクエストは拒否される。Client ID と Client Secret がアプリの「身分証明」になる。
設定項目値なぜこの値か
Client typeOpenID ConnectOIDC プロトコルを使うため（SAML も選べるが今回は不要）
Client IDtest-app認可リクエストの client_id パラメータに使われる識別子
Client authenticationONConfidential Client（サーバーサイドアプリ）として Client Secret を発行。OFF だと Public Client（SPAなど）
Standard flowONAuthorization Code Flow を許可。最も安全なフロー
Valid redirect URIshttp://localhost:3000/callback認可コード送信先を限定。これがないと攻撃者が自分のサーバーにコードを送れてしまう
Web originshttp://localhost:3000CORS 許可。ブラウザからの直接API呼び出し時に必要
redirect URI の制限はセキュリティの要: もし *（ワイルドカード）にすると、攻撃者が redirect_uri=https://evil.com/steal で認可コードを奪取できる。本番では完全一致で登録すること。

Step 3: Client Secret をコピー

Keycloak 管理コンソール操作
作成した test-app → Credentials タブ → Client secret をコピー
→ .env ファイルの OIDC_CLIENT_SECRET= に貼り付け
なぜ Client Secret が必要か: トークン交換（後述 Lab 08）で、「このリクエストは正規のアプリから来た」ことを証明するため。ブラウザには渡さず、サーバー間通信でのみ使う。

Step 4: テストユーザー作成

Keycloak 管理コンソール操作
Users → Create user → Username: tom
作成後 → Credentials タブ → Set password
  Password: 任意
  Temporary: OFF（OFFにしないと初回ログイン時にパスワード変更を強制される）
実機確認
  1. 左上のドロップダウンに testrealm が表示され、選択されていることを確認
  2. Clients 一覧に test-app が存在し、Credentials タブに Client Secret が表示されていることを確認
  3. Users 一覧に tom が存在することを確認
  4. .env ファイルの OIDC_CLIENT_SECRET に正しい値が入っていることを確認

05

Discovery（自動検出）

フロー

node server.js 起動時に最初に起きる通信。なぜ Discovery があるか: IdP のエンドポイント URL をアプリにハードコードしなくて済むようにするため。

Discovery の仕組み
OIDC の仕様で、全ての IdP は /.well-known/openid-configuration というURLに自分の情報を公開することが決められている。
アプリは Issuer URL（http://localhost:8080/realms/testrealm）さえ知っていれば、そこに /.well-known/openid-configuration を付けて GET するだけで、認可エンドポイント・トークンエンドポイント・署名鍵の場所など全てが分かる。 
アプリ起動時:
  Issuer URL を知っている
       │
       ▼
  GET /.well-known/openid-configuration
       │
       ▼
  JSON で全エンドポイントが返る
  ┌─ authorization_endpoint  ← ログイン画面はここ
  ├─ token_endpoint          ← トークン交換はここ
  ├─ userinfo_endpoint       ← ユーザー情報はここ
  ├─ end_session_endpoint    ← ログアウトはここ
  └─ jwks_uri                ← IDトークンの署名検証鍵はここ

対応するコード

server.js — initOidc()
const issuer = await Issuer.discover(process.env.OIDC_ISSUER);
// 内部で GET http://localhost:8080/realms/testrealm/.well-known/openid-configuration
// → JSON レスポンスからエンドポイントURLを自動取得

Discovery の恩恵: IdP を Keycloak → Auth0 に差し替えるとき、.env の OIDC_ISSUER を https://tenant.us.auth0.com/ に変えるだけ。コード内のエンドポイントURLを一切書き換える必要がない。
なぜこれが重要か — 実務での意味
  • 開発環境（Keycloak localhost）→ ステージング（社内IdP）→ 本番（Entra ID）と環境ごとに IdP が変わるのは日常
  • Discovery があるから OIDC_ISSUER 1つの差し替えで全エンドポイントが追従する
  • Discovery がなかったら: authorize URL, token URL, userinfo URL, logout URL, JWKS URL を全て個別に設定ファイルに書く必要がある
実機確認

  2. ブラウザで http://localhost:8080/realms/testrealm/.well-known/openid-configuration を直接開き、JSON が返ることを確認
  3. JSON 内の authorization_endpoint token_endpoint userinfo_endpoint のURLを目視で確認。これらが後続の全通信で使われる
06

認可リクエスト（① /login）

フロー

「ログイン」リンクをクリックした瞬間に何が起きるか。ブラウザが Keycloak にリダイレクトされるまでの通信を分解します。

このステップで起きること
ブラウザ              Node.js(:3000)              Keycloak(:8080)
  │                       │                          │
  │  GET /login           │                          │
  ├──────────────────────►│                          │
  │                       │ PKCE 生成                │
  │                       │ state 生成               │
  │                       │ セッションに保存          │
  │  302 Location:        │                          │
  │  keycloak/auth?...    │                          │
  │◄──────────────────────┤                          │
  │                                                  │
  │  GET /auth?client_id=...&code_challenge=...      │
  ├─────────────────────────────────────────────────►│
  │                                                  │
  │  ◄── Keycloak ログイン画面 HTML ──               │
  │◄─────────────────────────────────────────────────┤

対応するコード

server.js — GET /login
app.get('/login', (req, res) => {
  // ① PKCE: code_verifier（ランダム文字列）を生成
  const code_verifier = generators.codeVerifier();
  // ② code_verifier の SHA-256 ハッシュ = code_challenge
  const code_challenge = generators.codeChallenge(code_verifier);
  // ③ CSRF対策: state（ランダム文字列）を生成
  const state = generators.state();

  // ④ セッションに保存（コールバック時に照合するため）
  req.session.code_verifier = code_verifier;
  req.session.state = state;

  // ⑤ 認可URLを組み立ててリダイレクト
  const url = client.authorizationUrl({
    scope: 'openid profile email',
    code_challenge,
    code_challenge_method: 'S256',
    state,
  });
  res.redirect(url);
});

各パラメータの「なぜ」

パラメータ値（例）なぜ必要か
client_idtest-appKeycloak が「どのアプリからのリクエストか」を識別
response_typecodeAuthorization Code Flow を使うことを宣言。トークンを直接返さず「認可コード」を返す
scopeopenid profile emailopenid: OIDC であることを示す必須値。profile: 名前等。email: メールアドレス
redirect_urihttp://localhost:3000/callback認可コードの送り先。Keycloak に登録済みの URI と完全一致しないと拒否される
state6f4KKvPH...CSRF 対策: コールバック時にセッションの値と照合。不一致なら攻撃と判断して拒否
code_challenge0VH23JUQ...PKCE: code_verifier の SHA-256 ハッシュ。認可コード横取り攻撃を防ぐ
code_challenge_methodS256ハッシュアルゴリズムの指定（SHA-256）
なぜ PKCE が必要か: 認可コードがネットワーク上で傍受された場合、攻撃者がそのコードでトークンを取得できてしまう。PKCE があると、トークン交換時に code_verifier（元のランダム文字列）が必要になるため、コードだけ盗んでもトークンは取れない。
仕組み: 認可リクエストでは「ハッシュ値（code_challenge）」だけを送り、トークン交換では「元の値（code_verifier）」を送る。Keycloak 側でハッシュを再計算して一致を検証する。
なぜ state が必要か: 攻撃者が自分のアカウントの認可コードを被害者のブラウザに送り込む「CSRF攻撃」を防ぐ。state はセッションに紐づいたランダム値なので、攻撃者は正しい state を知ることができない。

ユーザー認証と認可コード（②③）

フロー

Keycloak のログイン画面でパスワードを入力してから、アプリに認可コードが届くまで。ここでアプリはパスワードに一切触れないことが OIDC の核心です。

このステップで起きること
ブラウザ                              Keycloak(:8080)
  │                                       │
  │  ② POST /login-actions/authenticate   │
  │     username=tom, password=***         │
  ├──────────────────────────────────────►│
  │                                       │ ユーザーDB照合
  │                                       │ → 認証OK
  │                                       │
  │  ③ 302 Location:                      │
  │     localhost:3000/callback            │
  │     ?code=a66fcd16-...                 │
  │     &state=6f4KKvPH...                │
  │◄──────────────────────────────────────┤
  │                                       │
  │  GET /callback?code=...&state=...     │
  ├──────► Node.js(:3000)                 │
セキュリティ上の核心: パスワードは「ブラウザ → Keycloak」の直接通信でのみ送られる。Node.js アプリはパスワードを中継しない・保存しない・見ることすらできない。アプリが受け取るのは「認可コード」という一時的な引換券だけ。
なぜ「認可コード」という間接方式か: トークンをブラウザに直接返すと、ブラウザの履歴やリファラーヘッダーからトークンが漏洩するリスクがある。認可コードは1回限り・短寿命（数秒〜数分）の引換券で、これ自体では何もできない。サーバー間通信でトークンに交換して初めて意味を持つ。

認可コードの特性

特性値なぜそうなっているか
有効回数1回限り使用済みコードでの再トークン交換を防ぐ
有効期限数十秒〜数分傍受されても時間切れで使えなくなる
送信経路URL の query パラメータブラウザのリダイレクトで受け渡すため
単体での価値なしトークン交換には client_secret + code_verifier が別途必要

トークン交換（④⑤）

フロー

認可コードをトークンに交換するサーバー間通信。ブラウザを経由しないため、DevTools には映らない最も重要なステップです。

このステップで起きること
Node.js(:3000)                           Keycloak(:8080)
  │                                          │
  │  ④ POST /token                           │
  │     grant_type=authorization_code        │
  │     code=a66fcd16-...                    │
  │     redirect_uri=.../callback            │
  │     client_id=test-app                   │
  │     client_secret=7PvAjm...              │
  │     code_verifier=ZeHNbr...              │
  ├─────────────────────────────────────────►│
  │                                          │ 検証:
  │                                          │  code 有効？ ✓
  │                                          │  client_secret 正しい？ ✓
  │                                          │  code_verifier → SHA256
  │                                          │    = code_challenge？ ✓
  │                                          │  redirect_uri 一致？ ✓
  │                                          │
  │  ⑤ 200 OK                               │
  │     { id_token, access_token,            │
  │       refresh_token, expires_in }        │
  │◄─────────────────────────────────────────┤
なぜサーバー間通信か: client_secret をブラウザに渡すと、ユーザーが DevTools で読めてしまう。秘密値はサーバー間でのみやり取りするのが鉄則。

対応するコード

server.js — GET /callback（トークン交換部分）
const params = client.callbackParams(req);
// ↑ URL の query から code, state を抽出

const tokenSet = await client.callback(
  `${process.env.APP_BASE_URL}/callback`,
  params,
  { code_verifier: req.session.code_verifier, state: req.session.state }
);
// ↑ 内部で POST /token を実行し、以下を検証:
//   1. state の一致（CSRF防止）
//   2. id_token の署名検証（JWKS で取得した公開鍵で）
//   3. id_token の iss, aud, exp 等のクレーム検証

Keycloak が検証する4つの条件

検証項目何を確認しているか失敗するとどうなるか
code発行済みで未使用かinvalid_grant エラー
client_secret登録された Client の秘密鍵と一致するかunauthorized_client エラー
code_verifierSHA-256 → 認可リクエスト時の code_challenge と一致するかinvalid_grant エラー（PKCE検証失敗）
redirect_uri認可リクエスト時と同じ URI かinvalid_grant エラー

3つのトークンの役割

トークン形式用途有効期限
id_tokenJWT（署名付き）「この人は誰か」の証明書。クレーム（sub, name, email等）を含む短い（数分）

IDトークンのクレーム

フロー

ID トークン（JWT）をデコードして中身を見ます。クレーム（claim = 主張）とは「IdP がこのユーザーについて主張する事実」です。

なぜ JWT か: JSON に電子署名を付けた形式。受け取った側が IdP の公開鍵で署名を検証すれば、内容が改竄されていないことを確認できる。IdP に問い合わせることなく、オフラインで検証可能。

対応するコード

server.js — クレーム取得

// openid-client は内部で署名検証済み → 信頼できるデータ

Access Token の利用（⑥ UserInfo）

フロー

ここまで access_token は「取得しただけ」でした。このLabで初めて Authorization: Bearer ヘッダーに付けて API を呼びます。

id_token vs access_token — 何が違うのか
id_token: 「この人は誰か」の証明書。アプリが読むためのもの。API に送るものではない。
access_token: 「この人は何ができるか」の許可証。API サーバーに提示するためのもの。

今回は access_token を Keycloak の UserInfo エンドポイントに提示して、ユーザー情報を取得する。実務では自社の API サーバーに提示してリソースにアクセスする。 
id_token の使い方:
  アプリ内で tokenSet.claims() → ユーザー表示に使う
  → 外部には送らない

access_token の使い方:
  GET /api/resource
  Authorization: Bearer eyJhbG...
  → API サーバーがトークンを検証してリソースを返す

対応するコード

server.js — GET /api/userinfo
app.get('/api/userinfo', async (req, res) => {
  const token = req.session.tokens?.access_token;

  // Discovery で取得済みの UserInfo エンドポイント URL
  const userinfoUrl = client.issuer.metadata.userinfo_endpoint;

  // access_token を Authorization ヘッダーに付けて GET
  const response = await fetch(userinfoUrl, {
    headers: { Authorization: `Bearer ${token}` },
  });

  const userinfo = await response.json();
  res.json({ userinfo });
});
なぜ Cookie ではなく Authorization ヘッダーか: Cookie はブラウザ ↔ 同一ドメインのサーバー間でしか使えない。API サーバーが別ドメイン（マイクロサービス構成等）の場合、Cookie は送れない。Authorization: Bearer ヘッダーならどのドメインの API にも送れる。これが OAuth 2.0 / OIDC が Bearer トークン方式を採用した理由。
通信の流れ
ブラウザ              Node.js(:3000)              Keycloak(:8080)
  │                       │                          │
  │ ボタンクリック         │                          │
  │ GET /api/userinfo     │                          │
  ├──────────────────────►│                          │
  │  (Cookie: connect.sid)│                          │
  │                       │ GET /userinfo             │
  │                       │ Authorization: Bearer eyJ.│
  │                       ├─────────────────────────►│
  │                       │                          │ access_token 検証
  │                       │  200 { sub, name, ... }  │
  │                       │◄─────────────────────────┤
  │  200 { userinfo }     │                          │
  │◄──────────────────────┤                          │

ログアウト（⑦ RP-Initiated Logout）

フロー

ログアウトは「アプリのセッション破棄」だけでは不十分です。なぜか: Keycloak 側のセッションが残っていると、再度 /login にアクセスした瞬間にパスワード入力なしでログインされてしまうから。

2つのセッションを両方破棄する必要がある
アプリのセッション破棄だけの場合:
  ブラウザ → /login → Keycloak（セッション残存）→ 自動ログイン → /callback
  → ユーザーから見ると「ログアウトしたのにすぐログインされる」

両方破棄した場合:
  ブラウザ → /login → Keycloak（セッションなし）→ ログイン画面表示
  → 正しいログアウト挙動

対応するコード

server.js — GET /logout
app.get('/logout', (req, res) => {
  const id_token = req.session.tokens?.id_token;

  // ① アプリ側のセッションを破棄
  req.session.destroy(() => {

    // ② Keycloak の end_session エンドポイントにリダイレクト
    const url = client.endSessionUrl({
      id_token_hint: id_token,
      // ↑ 「どのユーザーのセッションを終了するか」を特定するため
      post_logout_redirect_uri: process.env.APP_BASE_URL,
      // ↑ ログアウト後にリダイレクトされる先
    });
    res.redirect(url);
  });
});
パラメータなぜ必要か
id_token_hintKeycloak が「どのユーザーのセッションを終了するか」を特定するため。これがないとKeycloakはログアウト確認画面を表示する
post_logout_redirect_uriログアウト後の戻り先URL。Keycloak に事前登録が必要（未登録だとリダイレクトされない）

全通信一覧（From / To / URL / パラメータ / なぜ）

#From → ToMethod / Endpoint主なパラメータなぜこの通信が必要か
—Node.js → Keycloak GET /.well-known/openid-configuration なし エンドポイントURLの自動検出。ハードコード不要にする
①ブラウザ → Keycloak GET /auth client_id, redirect_uri, response_type=code, scope, state, code_challenge, code_challenge_method 認証フローの開始。IdP に「このアプリのユーザーを認証してほしい」と依頼
②ブラウザ → Keycloak POST /login-actions/authenticate username, password ユーザー認証。パスワードはブラウザ↔IdP間のみで流れる
③Keycloak → ブラウザ 302 → /callback code, state, iss 認可コード（一時引換券）をアプリに渡す。トークンを直接返さないことでセキュリティ確保
④Node.js → Keycloak POST /token grant_type=authorization_code, code, redirect_uri, client_id, client_secret, code_verifier 認可コードをトークンに交換。client_secret + code_verifier で正規アプリを証明
⑤Keycloak → Node.js 200（④の応答） id_token(JWT), access_token, refresh_token, expires_in, token_type=Bearer 認証結果（id_token）と API アクセス権（access_token）の発行
⑥Node.js → Keycloak GET /userinfo Header: Authorization: Bearer {access_token} access_token を使って API を呼ぶ実例。Bearer トークン方式の実践
⑦ブラウザ → Keycloak GET /logout id_token_hint, post_logout_redirect_uri IdP 側のセッションも破棄。アプリだけのログアウトでは不十分なため

ブラウザ ↔ Node.js の認証は Cookie

全体像の整理:
・ブラウザ ↔ Node.js: Cookie（connect.sid）でセッション管理 → Authorization ヘッダーは出ない
・Node.js ↔ Keycloak: Authorization: Bearer ヘッダー（⑥ UserInfo 取得時）
・トークン交換（④）: client_secret を POST ボディに含めて送信（サーバー間通信）

「Authorization ヘッダーが見当たらない」のは正常。セッションベースの Web アプリでは Cookie が主軸で、Bearer トークンはサーバー間通信で使われる。

セキュリティ対策の総まとめ

攻撃対策どのステップで機能するか
認可コード横取りPKCE（code_verifier / code_challenge）① で challenge 送信、④ で verifier 送信して照合
CSRF（リクエスト偽造）state パラメータ① で state 送信・セッション保存、③ で照合

Client 偽装client_secret（Confidential Client）④ でサーバー間通信のみで送信
IdP 偽装iss クレーム検証⑤ で openid-client が iss と Discovery の issuer を照合
