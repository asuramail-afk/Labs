なぜErrorが必要か（文字列throwとの差）

基本

throw は何でも投げられるが、ただの文字列には stack（発生地点）・instanceofによる分類・構造化されたmessage が無い。Errorはこの3点を備えた「エラーを値として扱う器」。

// ① 文字列を投げると…
try { throw "失敗しました"; }
catch (e) {
  console.log(typeof e);   // "string"
  console.log(e.stack);    // undefined ← スタックが無い
}
// ② Errorを投げると…
try { throw new Error("失敗しました"); }
catch (e) {
  console.log(e instanceof Error);    // true ← 分類できる
  console.log(e.message);             // "失敗しました"
  console.log(e.stack.split("\n")[0]); // "Error: 失敗しました"
}

    

  


  
  

    
01
Errorの構造（nameはprototype・他は非列挙）
基本

    

      
name はインスタンスではなく Error.prototype 上にある。message / stack / cause は own だが enumerable:false。この「非列挙」がLab08のJSON問題の根本原因。

      

        
プロパティ所在列挙可能

        
nameError.prototype—（継承）

        
messageインスタンス(own)false

        
stackインスタンス(own/V8)false

        
causeインスタンス(own)false

      

      
const e = new Error("boom", { cause: "root" });
console.log(e.hasOwnProperty("name"));  // false ← 自分は持たない
console.log(e.name);                    // "Error" ← prototype経由
console.log(Object.getOwnPropertyDescriptor(e,"message").enumerable); // false
console.log(e.cause);                   // "root"
console.log(Object.keys(e));            // [] ← 全部非列挙

基本

    

      
なぜ型を分けるか＝catch側で意味的に分岐するため。全型は Error を継承するので instanceof Error は常に true。

  () => null.foo,                 // TypeError
  () => notDefined,               // ReferenceError

];
cases.forEach(fn => {
  try { fn(); }
  catch (e) { console.log(e.constructor.name, "/ Error?", e instanceof Error); }

03
new有無とカスタムError
基本

    

      
Error("x") は new 無しでも同じ（仕様で吸収）。だがサブクラスは new 必須。カスタムでは super()（messageとstack生成）と this.name上書き（既定は"Error"のまま）が要。

      
console.log(Error("a").message === new Error("a").message); // true

class ValidationError extends Error {
  constructor(message, options) {
    super(message, options);        // ① messageセット+stack生成
    this.name = "ValidationError";  // ② 名札を上書き
  }
}
const v = new ValidationError("入力不正");
console.log(v instanceof ValidationError); // true
console.log(v instanceof Error);           // true
console.log(v.name);                       // "ValidationError"
console.log(String(v));                    // "ValidationError: 入力不正"

      

    

  


  
  

    
04
error.cause（ES2022エラー連鎖）
発展

    

      
高レベルなエラーで包んでも { cause: e } で根本原因を失わない。野良の err.original=e 慣習を言語標準に統一したもの。

      
function low() { throw new Error("DB接続失敗"); }

try {
  try { low(); }
  catch (e) { throw new Error("ユーザー登録失敗", { cause: e }); }
} catch (top) {
  console.log(top.message);        // "ユーザー登録失敗"
  console.log(top.cause.message);  // "DB接続失敗" ← 辿れる
}

      

    

  


  
  

    
05
AggregateError（Promise.any）
発展

    

      
Promise.any は全部失敗したとき複数の理由を .errors 配列で束ねる。単一Errorでは情報が落ちるから専用型が要る。非同期なので出力は一瞬遅れて表示される。

      
Promise.any([
  Promise.reject(new Error("A失敗")),
  Promise.reject(new Error("B失敗"))
]).catch(err => {
  console.log(err instanceof AggregateError);   // true
  console.log(err.errors.map(x => x.message));   // ["A失敗","B失敗"]
});

      

    

  


  
  

    
06
防御的catch / finally / optional binding
発展

    

      
catchには何が来るか保証されない（文字列も来る）ので instanceof Error で防御。finally は return/throwを跨いでも必ず走る。ES2019で catch{}（束縛省略）も可。

      
function safe(fn) {
  try { fn(); }
  catch (e) {
    if (e instanceof Error) console.log("Error:", e.message);
    else console.log("非Error:", typeof e, JSON.stringify(e));
  }
  finally { console.log("finally は必ず走る"); }
}
safe(() => { throw 42; });                  // 非Error: number 42
safe(() => { throw new Error("ちゃんとError"); });

      

    

  


  
  

    
07
stackはnewの瞬間にキャプチャ
発展

    

      
stack は throw時ではなく new した瞬間のコールスタックを固定する。だからErrorは投げるその場で生成するのが鉄則（使い回すと発生地点とズレる）。

      
function makeErr() { return new Error("作成時点でキャプチャ"); }
const e = makeErr();
// stackの先頭数行を見る → makeErr が含まれる
console.log(e.stack.split("\n").slice(0, 3).join("\n"));

      

    

  


  
  

    
08
JSON.stringify(error)が{}になる
発展

    

      
既定の JSON.stringify は 列挙可能なownプロパティしか拾わない。message/stackは非列挙なので結果は {}。許可リスト（replacer配列）を渡すと [[Get]] 経由で取得され非列挙でも入る。

      
const e = new Error("boom");
console.log(JSON.stringify(e));                       // {} ← 空！
console.log(JSON.stringify(e, ["name", "message"]));  // {"name":"Error","message":"boom"}
console.log(JSON.stringify({ name: e.name, message: e.message })); // 明示変換

      

    

  


  
  

    
09
realm跨ぎとError.isError
発展

    

      
iframe等の別realmのErrorは instanceof Error が false になりうる（Errorコンストラクタが別物）。内部スロットを見る Object.prototype.toString や近年追加の Error.isError が堅牢。

      
const e = new Error("x");
console.log(e instanceof Error);                     // true（同一realm）
console.log(Object.prototype.toString.call(e));      // "[object Error]"
console.log("Error.isError:",
  typeof Error.isError === "function" ? Error.isError(e) : "(この環境は未対応)");

      

    

  


  
  

    
10
catch(e)の正体＝制御の反転
制御の反転

    

      
catch(e) の e は「自分が名前だけ決め、値はランタイムが注入する束縛点」。throwするとスタックが巻き戻り、throw後の行は実行されずcatchへ制御が飛ぶ。

      

        
🔰 制御とデータの流れ

        
a() ─呼ぶ→ b() ─throw @Error→ ┐
                              │ throw後の行は実行されない
                              ▼ スタック巻き戻し(unwinding)
              try が捕捉 → catch(e) に  e = @Error  を「注入」
                              ▼
              catchの後の通常処理へ復帰

      

      
function a() { console.log("a: 入る"); b(); console.log("a: ここは実行されない"); }
function b() { console.log("b: 入る"); throw new Error("bで投げた"); console.log("b: ここは実行されない"); }

try { a(); }
catch (e) { console.log("catch: 注入された e =", e.message); }
console.log("catchの後: 処理は継続する");

      

    

  


  
  

    
11
コールバック注入（mapの反復）
制御の反転

    

      
catchと同じく「名前は自分・値は呼ぶ側」。違いは 反復ごとに何度も (el, idx, arr) が注入される点。DOMの addEventListener("click", e => …) のEvent注入も同型。

      

        
🔰 反復ごとのデータ推移

        
map が cb(要素, 添字, 元配列) を反復注入し、戻り値を新配列へ積む
 反復1: el=10 idx=0 → 戻り10 → [10]
 反復2: el=20 idx=1 → 戻り21 → [10,21]
 反復3: el=30 idx=2 → 戻り32 → [10,21,32]

      

      
const out = [10, 20, 30].map((el, idx, arr) => {
  console.log(`idx=${idx}: el=${el}, arr=${JSON.stringify(arr)} → 戻り値=${el + idx}`);
  return el + idx;
});
console.log("結果:", JSON.stringify(out)); // [10,21,32]

      

    

  


  
  

    
12
setter＝代入が呼び出しに化ける
制御の反転

    

      
box.value = 42 は内部で [[Set]] → setter関数を this=box, v=42 で呼ぶ。関数呼び出しの形をしていないのに、代入が引数注入になっている。

      
const box = {
  _v: 0,
  set value(v) { console.log("setter発火 v =", v); this._v = v; }
};
console.log("代入前 _v =", box._v);  // 0
box.value = 42;                       // ← この代入がsetterを呼ぶ
console.log("代入後 _v =", box._v);  // 42

      

    

  


  
  

    
13
generator yield 双方向注入
制御の反転

    

      
const a = yield "first" の yield 式は「出す」と「受け取る」を別タイミングで担う。停止地点に 次の .next(x) の x が注入される（＝await と同型）。

      

        
🔰 双方向のデータ推移

        
it.next()    ──"first"──▶  外へ出力（ここで一時停止）
it.next(10)  ◀────10────  停止中のyield式の値=10 → a=10
it.next(20)  ◀────20────  停止中のyield式の値=20 → b=20
※ 最初のnext()の引数は「入れる先の停止yield」が無いので捨てられる

      

      
function* g() {
  console.log("本体: start");
  const a = yield "first";
  console.log("本体: a =", a);
  const b = yield "second";
  console.log("本体: b =", b);
  return "done";
}
const it = g();
console.log("next()   →", JSON.stringify(it.next()));    // {value:"first",done:false}
console.log("next(10) →", JSON.stringify(it.next(10)));  // {value:"second",done:false}
console.log("next(20) →", JSON.stringify(it.next(20)));  // {value:"done",done:true}

      

    

  


  
  

    
14
new.target / this / arguments（魔法束縛）
制御の反転

    

      
命名すらせず、関数に入った瞬間に固定名で存在する束縛。new.target は new で呼ばれたか（コンストラクタ or undefined）、arguments は実引数の集合をランタイムが注入する。

      

        
🔰 呼び方が値を決める

        
F(1,2)     → new.target = undefined,  arguments = [1,2]
new F(3,4) → new.target = F,          arguments = [3,4]
            （呼び出し地点がnew.target/thisを注入する＝制御の反転）

      

      
function F() {
  console.log("new.target:", new.target ? new.target.name : "undefined");
  console.log("arguments :", JSON.stringify(Array.from(arguments)));
}
F(1, 2);       // new.target undefined
new F(3, 4);   // new.target F

制御の反転

    

      
p.name というただのプロパティ読み取りが、裏でエンジンにより handler.get(target, prop, receiver) 呼び出しに化け、3引数が注入される。box.value=42→setter と同じ構造。

      
const target = { name: "Tom" };
const p = new Proxy(target, {
  get(t, prop, receiver) {
    console.log(`getトラップ: prop=${String(prop)} ← エンジンが注入`);
    return Reflect.get(t, prop, receiver);
  }
});
console.log("p.name =", p.name);  // トラップ発火 → "Tom"
console.log("p.age  =", p.age);   // トラップ発火 → undefined

      

    

  


  
  

    
16
generatorの初期値とプライミング
制御の反転

    

      
Lab13の続き。最初の .next() の引数は「停止中のyieldが無い」ため捨てられる。最初から使う値は普通の引数で渡し、1回目の.next(v)から注入したいときだけ「プライミング」で最初の.next()を内部消費する。

      

        
🔰 プライミングが「ズレ」を吸収する

        
素のまま : next(A)=起動  next(B)→Aの位置  next(C)→Bの位置 …1つズレる
           └─捨─┘
priming  : [内部でnext()起動] next(A)→先頭yield  next(B)→2番目yield …ズレ解消
            └─捨てる回を肩代わり─┘

      

      
// 方法A: 初期値は「普通の引数」で渡す（yieldを経由しない）
function* counter(start) {
  let cur = start;
  while (true) { const step = yield cur; cur += step ?? 1; }
}
const it = counter(100);
it.next();   // {value:100} ← start が即使える
it.next(5);  // {value:105}
it.next(10); // {value:115}

      
// 方法B: プライミング（1回目の next(v) から注入したいとき）
function prime(genFn) {
  return (...args) => { const it = genFn(...args); it.next(); return it; };
}
function* echo() { while (true) { const r = yield; console.log("受取:", r); } }

const it = prime(echo)();
it.next("A");  // 受取: A ← 1回目から使える！
it.next("B");  // 受取: B
