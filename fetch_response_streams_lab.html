00

fetch は「即座にbody全部」を返さない — 2段階パイプライン

基本

fetch() が返す Promise は「全レスポンス受信」ではなく レスポンスヘッダを受信した時点で resolve する。body はまだネットワーク上を流れている最中かもしれない。 だから .json() や .text() も Promise を返す ―― 残りのストリームを読み切る非同期処理だから。 

fetch(url)
   │
   ▼
[Promise<Response>]  ← ★ヘッダ受信時点で resolve（body は未受信）
   │
   ▼
Response オブジェクト
   ├─ status / headers / ok ...  ← 即利用可能（メタデータ・同期）
   └─ body                       ← ReadableStream（中身はまだ流れ得る）
        │
        ▼
   .json() / .text() / .blob() / .getReader()
        │
        ▼
   ここで初めて body 全体 or チャンクを消費（非同期）
JS — ヘッダ受信と body 消費は別ステップ
const res = await fetch('/api/data');  // ← ヘッダ受信でここに到達
console.log(res.status, res.ok);          // ← 同期で即読める
const data = await res.json();          // ← body を最後まで読み切る（別の待ち）
▲ Before / After / Δ
Beforefetch =「リクエスト→完全なレスポンス」のブラックボックス
Afterfetch =「ヘッダ受信」と「body消費」が分離された2段階パイプライン
Δ最初のバイト到達時点で処理開始可（TTFB活用）／巨大bodyを全展開せず逐次処理／進捗・中断・逐次パースが可能に
01

Response.body は ReadableStream — Streams API への入口

基本

Response.body の型は ReadableStream<Uint8Array>。 これが Response と Streams API をつなぐ唯一の接続点。getReader() で reader を取り出し、 read() を { done, value } が返るまでループして1チャンクずつ受け取る。

JS — getReader でチャンクを逐次受信
const res = await fetch('/large-data');
const reader = res.body.getReader();   // ReadableStream → reader

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  // value は Uint8Array（このチャンク分のバイト列）
  console.log('受信チャンク:', value.length, 'bytes');
}
⚠ HTTP の chunked transfer encoding のチャンク境界と、JS の read() が返すチャンク境界は 1:1 対応しない。データが「ある程度」溜まったら流れてくる、という挙動。
擬似ストリームを read() ループで消費
「実行」を押すと read() ループのログが出ます
02

メタデータ系プロパティ全解説 — なぜ同期で即読めるのか

中級

HTTP レスポンスは「ステータスライン＋ヘッダ」と「body」の2部構成で、ヘッダが先に届く。 Response はこの物理順序をAPIに反映した ―― だからメタデータ系は全部同期・即時・読み取り専用。

プロパティ型なぜ存在するか / 利用シーン
statusnumberHTTP意味論の中核。fetchは4xx/5xxでrejectしないので、これを見ないと失敗を検知できない
okboolean200〜299か。status>=200&&status<300を毎回書く冗長さの除去。fetchの「エラーでrejectしない」設計の埋め合わせ
statusTextstring理由フレーズ。HTTP/2では事実上廃止＝空文字になりがち。ログ表示以外で依存しない
headersHeadersヘッダ名は大小無視・同名複数値あり。素のObjectでは表現不可なので専用クラス
typestringCORS境界の可視化。opaqueならstatus=0・body読めず・headers空
urlstringリダイレクト追跡後の最終URL。実際にどこから来た応答かを知る唯一の手段
redirectedbooleanリダイレクトを経たか。改ざん検知などセキュリティ判断に
bodyUsedbooleanbody消費済みか。「一度しか読めない」制約を消費前にガードするフラグ
bodyReadableStream｜null未受信かもしれないbodyをStreamで公開。HEAD/204等ではnull

// type 値の意味

type === "basic"          → 同一オリジン、全部読める
type === "cors"           → 別オリジンだがCORS許可あり、中身読める
type === "opaque"         → 別オリジン no-cors取得、status=0/body空（キャッシュ目的等）
type === "opaqueredirect" → redirect:'manual' のリダイレクト応答
type === "error"          → ネットワークエラー（Response.error()由来）
📘 headers が Headers 型である理由: Content-Type と content-type は HTTP仕様上同一。素の Object はこの大小無視を表現できない。さらに Set-Cookie のような同名複数値もある。 Headers クラスはこの仕様を正しくカプセル化する。
httpbin.org に投げて status/ok/type/url 等を表示
ネットワーク接続が必要です。押すと実レスポンスのメタデータが出ます
03

body 消費メソッド全解説 — なぜ5つ以上あり、全部 Promise なのか

中級

body はネットワーク上ではただのバイト列。それを「何として解釈するか」はアプリしか知らない。 だから解釈方法ごとにメソッドを分けた。全部 Promise なのは「body最後の1バイトが届くまで結果が確定しない」から。

メソッド戻り値なぜ使う / 利用シーン
.json()objectAPI応答。内部でUTF-8デコード＋JSON.parse。最頻出
.text()stringHTML/プレーンテキスト/自前パースしたいJSON
.blob()Blob画像・PDF等のバイナリ。URL.createObjectURLで表示/DL
.arrayBuffer()ArrayBufferバイナリを自前解析（バイト操作・WebAssembly・Audio）
.formData()FormDatamultipart/form-data応答の構造化取得
.bytes()Uint8Array新しめ。arrayBufferより直接バイト配列が欲しいとき
🔰 なぜ「1つの汎用メソッド＋引数」にしなかったか
メソッドを分けることで戻り値の型が静的に確定し、内部で最適な変換経路を取れる。 fetch(...).then(r => r.json()) の .json() が string ではなく object を返すと 型推論が効くのはこのため。 
body（バイト列 Uint8Array）
   │
   ├─ .text()        → UTF-8デコード        → string
   ├─ .json()        → UTF-8デコード+parse  → object
   ├─ .blob()        → そのまま包む          → Blob
   ├─ .arrayBuffer() → 生バッファ            → ArrayBuffer
   └─ .formData()    → multipart解析         → FormData
        ↑ どれも「body を最後まで読み切る」点は共通（だから全部Promise・一度きり）
❌ .json() 等を呼ぶと body Stream は消費し尽くされる。2回目は TypeError: body stream already read になる。Lab 04 の clone() で回避する。
同じ body を2回読もうとして TypeError を出す
押すと「一度きり」制約が TypeError として出ます
04

clone() と「一度きり」制約 — なぜ複製が必要なのか

中級

body は ReadableStream で、Stream は消費されると枯れる。clone() は body消費前に呼ぶと Stream を内部で tee（分岐） し、同じデータを2系統で読めるようにする。 

         res.body (ReadableStream)
               │  clone() = 内部で tee()
         ┌─────┴─────┐
         ▼           ▼
    Cache保存用   ブラウザ返却用
  （Service Worker での典型シーン）
JS — clone は body 消費の前に
const res  = await fetch('/data');
const res2 = res.clone();        // ★ どちらかを消費する前に
const a = await res.json();
const b = await res2.text();   // res2 は独立した系統なので読める
現在: After（clone あり）
✓ After: clone() してから消費 → 2系統とも成功。SWで「片方Cache保存・片方ブラウザ返却」が成立
✗ Before: clone なしで2回 .json() → TypeError: body stream already read。Streamは枯れて再読不可
⚠ clone 後は両系統がメモリにバッファされ得る。巨大 body で消費が偏ると（片方だけ速く進む等） その差分がメモリに溜まり圧迫する。巨大データでは clone より「1回だけ getReader で読む」を検討。
clone なし＝失敗 / clone あり＝両方成功 を並べて表示
押すと clone の有無で結果が変わる様子が出ます
05

静的メソッドと Response 生成 — なぜ自分で Response を作れる必要があるのか

応用

Response は「受け取る」だけでなく「生産する」側にも回れる。 Service Worker / エッジ関数でネットワークを介さず応答を組み立てる ―― これが静的メソッドの存在意義。

APIなぜ存在するか
new Response(body, init)SWでネットワークを介さず応答を自作。オフライン対応・モックの入口。bodyにReadableStreamも渡せる
Response.json(data, init)new Response(JSON.stringify(d),{headers:{'Content-Type':...}})の定型句が長すぎた＋Content-Type付与忘れ多発。それを1行に
Response.redirect(url, status)SW/エッジでリダイレクト応答を返す定型。Locationヘッダ手書き回避
Response.error()SWがネットワークエラーを意図的に表現。主にAPI対称性のため
JS — Service Worker で応答を生産する
// 旧: 長い定型句
new Response(JSON.stringify({ ok:true }), {
  headers: { 'Content-Type': 'application/json' }
});

// 新: ショートカット（Content-Type 自動付与）
Response.json({ ok: true });

// 受信Streamを変換して新しいResponseとして返す（SWの定番）
const transformed = res.body.pipeThrough(new TextDecoderStream());
return new Response(transformed);
new Response / Response.json をその場で生成・消費
押すと自作 Response の status/headers/body が出ます
06

Stream は3種類しかない — 3レイヤで整理する

中級

Streams API の名前が多く見えるのは、Stream本体と操作する道具と 具体的な変換器の実装が混在して目に入るから。レイヤを分ければ本体は3つだけ。 

レイヤ1：Stream本体（これだけが「種類」）
   ReadableStream  … データの「出口」（読む対象） ← Response.body はこれ
   WritableStream  … データの「入口」（書く対象）
   TransformStream … 入口＋出口を持つ「変換器」

レイヤ2：Streamを操作する道具
   ReadableStreamDefaultReader / WritableStreamDefaultWriter
   ReadableStreamDefaultController など

レイヤ3：TransformStreamの「具体実装」
   TextDecoderStream / TextEncoderStream
   CompressionStream / DecompressionStream
🔰 TransformStream の正体
TransformStream は「writable プロパティ（入口）」と「readable プロパティ（出口）」を持つだけの箱。 書き込むと変換されて読み出せる。TextDecoderStream は新種ではなく「TransformStream に バイト→文字列の変換ロジックを実装したもの」。 
            ┌─────── TransformStream ───────┐
write() ──▶ │ writable    [変換]    readable │ ──▶ read()
            └────────────────────────────────┘
   ＝ { writable: WritableStream, readable: ReadableStream }
3種の本体役割身近な例
ReadableStream読み出せる（出口）Response.body
WritableStream書き込める（入口）File System Access の書き込み先
TransformStream変換（入口＋出口）TextDecoderStream
📘 新しい XxxStream という名前を見たら「レイヤ1〜3のどこか」で即分類できる。 TextDecoderStream → レイヤ3（TransformStream実装）、 ReadableStreamDefaultReader → レイヤ2（道具）。
07

reader / writer とロック — なぜ Stream を直接 read() できないのか

応用

ReadableStream に read() メソッドは無い。getReader() で reader を取得してから読む。 この間接化の理由は排他ロック ―― getReader するとStreamはロックされ、他の誰も読めなくなる。 「2か所から同時に読んで順序がぐちゃぐちゃ」を防ぐ。 

ReadableStream
   │ getReader()  ← ここで Stream がロックされる
   ▼
ReadableStreamDefaultReader  ← read() はこちらが持つ
   │
   ▼
{ done, value } を done:true まで繰り返し取得
道具取得元役割
ReadableStreamDefaultReadergetReader()read()でチャンク取得（使う側）
ReadableStreamBYOBReadergetReader({mode:'byob'})自前バッファに直接読む省コピー（高度）
WritableStreamDefaultWritergetWriter()write() close()（使う側）
ReadableStreamDefaultControllernew ReadableStream(...) 内enqueue()でデータ供給（作る側）
🔰 reader/writer は「使う側」、controller は「作る側」
reader・writer は既存のStreamを使う道具。controller は new ReadableStream で Stream を作るときに「データを流し込む」道具。役割が反対側。 
作る側： new ReadableStream({ start(controller){
            controller.enqueue(chunk);  ← データ供給
            controller.close();        ← 終端
         }})
                    │
                    ▼
使う側： stream.getReader() → reader.read()  ← データ消費
⚠ getReader 後の Stream はロック中。releaseLock() を呼ぶまで pipeThrough や 2つ目の getReader はできない（TypeError: locked）。
getReader 済み Stream にもう一度 getReader → 失敗
押すとロック衝突の TypeError が観察できます
08

Stream をつなぐ3メソッド — pipeThrough / pipeTo / tee

応用

Stream は「つなげる」のが本質。接続メソッドは3つだけ。 pipeThrough は中継（出口がまた ReadableStream）、pipeTo は終端、 tee は分岐。

メソッドつなぎ方戻り値 / 性質
pipeThrough(T)Readable に TransformStream を噛ます新しい ReadableStream（数珠つなぎ可）
pipeTo(W)Readable を WritableStream に注ぐPromise（流し終わると解決＝終端）
tee()Readable を2本に分岐[streamA, streamB]（clone の正体）
 
pipeThrough … 中継：出口がまた ReadableStream → さらにつなげる
   res.body
     .pipeThrough(new DecompressionStream('gzip'))
     .pipeThrough(new TextDecoderStream())   ← 数珠つなぎ

pipeTo … 終端：出口は WritableStream → ここで完結
   res.body.pipeTo(someWritableStream)  // → Promise

tee … 分岐：1本を2本に
   const [a, b] = res.body.tee();
JS — pipeThrough で逐次テキスト処理
const res = await fetch('/stream-endpoint');

// バイト列Stream → 文字列Stream に変換
const textStream = res.body.pipeThrough(new TextDecoderStream());

// ReadableStream は asyncIterable なので for await で回せる
for await (const chunk of textStream) {
  console.log('文字列チャンク:', chunk);
}
⚠ マルチバイト文字（日本語等）はチャンク境界で分断され得る。TextDecoderStream は これを正しく結合してくれる。自前の TextDecoder を使う場合は decode(buf,{stream:true}) の {stream:true} を忘れると文字化けする。
バイト列 → TextDecoderStream → 文字列チャンクを表示
押すと pipeThrough を通った文字列チャンクが出ます
09

Response × Stream の接点 — すべて res.body に集約される

応用

Response と Streams API の関係は1点に集約される ―― Response.body が ReadableStream である、という事実。status/headers 等はStreamと無縁。 

Response オブジェクト
   ├─ status / headers / ok ...  ← Stream と無関係（メタデータ）
   └─ body : ReadableStream<Uint8Array>  ★ここが Streams API の入口
Response の操作内部の Stream 操作結果
.json() / .text() / .blob()res.body を read() ループで読み切るbodyUsed=true
res.body.getReader()Streamをロックして自前read()bodyUsed=true・進捗取得可
res.body.pipeThrough(...)Streamを変換器に接続変換後Streamを取得
res.clone()res.body を内部で tee()2系統に分岐・両方読める
new Response(readableStream)ReadableStreamをbodyとして渡す自前Streamから応答生成
🔰 .json() は「Streamを読み切る糖衣」
.json() の中身は実質「res.body を最後まで read() ループ → 全バイト結合 → デコード → JSON.parse」。 だから .json() でも getReader() でも同じ1本のStreamを取り合う。片方を使うと もう片方は使えない。これが Lab 03/04 の制約の正体。 
res.json()  ≒  res.body を read() ループ → 結合 → decode → JSON.parse
res.text()  ≒  res.body を read() ループ → 結合 → decode
                          ↑ 同じ Stream。先に使った方が枯らす
✓ new Response(stream) で「作る側」にも接続あり。 受信Streamを pipeThrough で変換 → new Response で返す、が Service Worker の定番。Response と Stream は読む側・作る側の双方向でつながっている。

進捗付きダウンロード実装 — Stream の威力が出る典型例

応用

.blob() 一発では進捗が取れない。getReader() で自前ループするから途中経過が見える。 Content-Length ヘッダ（メタデータ）と read() ループ（Stream）の組み合わせ。

JS — 進捗バー付きダウンロード
const res = await fetch('/big-file.zip');
const total = +res.headers.get('Content-Length');  // メタデータ
const reader = res.body.getReader();                  // Stream

let received = 0;
const chunks = [];
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  chunks.push(value);
  received += value.length;
  updateBar(received / total);              // ← 途中経過が取れる
}
const blob = new Blob(chunks);
Before ▶︎ .blob() 一発
受信完了まで何も分からない。ユーザーは「固まった?」と感じる。中断もできない。
After ▶︎ getReader ループ
チャンク到達ごとに % 更新。進捗バー表示・AbortController での中断・逐次パースが可能。
擬似的なチャンク受信を進捗バーで可視化
押すと read() ループで進捗が更新される様子が出ます
📘 この構造はそのまま SSE / LLMストリーミング応答の土台。OpenAI/Anthropic API の text/event-stream も getReader() ループ＋TextDecoderStream で 1トークンずつ受け取っている。
