Step 0 — SpringBoot起動と自動構成

起動

main() から SpringApplication.run() を呼んだ瞬間に Spring Batch の中核Beanが自動登録される。 ここで誰がいるかを把握しておくと、後続Labで「どこから来たBean?」と迷わない。 

@SpringBootApplication
public class BatchApplication {
    public static void main(String[] args) {
        SpringApplication.run(BatchApplication.class, args);
    }
}

起動時に自動で用意される登場人物:

🔰 起動直後のBean構成図
ApplicationContext
  ├── DataSource              (H2 等、組み込みなら自動)
  ├── PlatformTransactionManager   ← chunk commit を担う
  ├── JobRepository           ← BATCH_* テーブルを操作
  └── JobLauncher             ← Job 起動口
       │
       └─ デフォルトで起動時に Job Bean を自動実行
          (spring.batch.job.enabled=false で停止可)
Bean役割Spring Boot 5での扱い
JobRepositoryBATCH_*テーブル読み書き自動構成
JobLauncherJob実行のエントリ自動構成
PlatformTransactionManagerchunk単位のtx境界自動構成(DataSource由来)
BATCH_JOB_INSTANCE 他メタデータDDL組み込みDB時は自動実行

Step 1 — @Configuration の読み込み順

起動

BatchConfig 内の @Bean はソースコードに書いた順ではなく 依存関係順に呼ばれる。これを理解すると「なぜここでNullPointerが出ない?」が腑に落ちる。 

@Configuration
public class BatchConfig {
    // @Bean reader, processor, writer, step1, importPersonJob ...
}
🔰 依存グラフと呼び出し順
  Job ──→ Step ──→ Reader     (Reader は親が要求した時に作る)
              ├──→ Processor
              ├──→ Writer ──→ DataSource
              └──→ JobRepository, TxManager (自動Beanを参照)

呼び出し順:
  ① reader()        ← 依存なし、最初に作れる
  ② processor()     ← 依存なし
  ③ writer(ds)      ← DataSource(自動Bean)を要求
  ④ step1(jr,tx,r,p,w)  ← 上3つ + 自動2つを要求
  ⑤ importPersonJob(jr, step1) ← 最後
✗ 誤解: ソース順に呼ばれる
// 「上から順に呼ばれる」と勘違いすると、
// step1 が reader をどう取るか説明できない。
@Bean Job job(...) { ... }
@Bean Step step1(...) { ... }
@Bean ItemReader reader() { ... }
✓ 正解: 依存解決順
// Spring が依存グラフを解析して
// reader → processor → writer → step1 → job
// の順に @Bean メソッドを呼ぶ。
// ソース順は無関係。

Step 2 — ItemReader (FlatFileItemReader) を1行ずつ

起動

FlatFileItemReaderBuilder の各メソッドが何のために呼ばれているか、5項目を分解する。 特に .name("personReader") は Restartの要。 

@Bean
public FlatFileItemReader<Person> reader() {
    return new FlatFileItemReaderBuilder<Person>()
        .name("personReader")                              // ① ★Restart key
        .resource(new ClassPathResource("persons.csv")) // ② file
        .delimited()                                       // ③ CSV
        .names("firstName", "lastName")                  // ④ columns
        .targetType(Person.class)                       // ⑤ bean
        .build();
}
#メソッド意味
①name()STEP_EXECUTION_CONTEXT に保存するキー。Restart時にこの名前で「次に読む行」を復元する
②resource()ClassPathResource なら src/main/resources 配下、FileSystemResource なら絶対パス可
③delimited()カンマ区切り解釈。固定長なら fixedLength()
④names()列を識別子に命名。Personのsetterにマップする橋渡し
⑤targetType()new Person() してsetterで値投入
現在: After(Step実行時)
✓ After: Step実行時の reader.read() 動作 reader.open(ctx) // ファイルOPEN, 行カウンタ=0 read() → Person("John","Doe") // 1行目 read() → Person("Jane","Smith") // 2行目 ... read() → null // EOF = ループ終了シグナル reader.close()
✗ Before: @Bean生成直後の状態 new FlatFileItemReader 完了 ファイルはまだ開かれていない .read() を呼ぶとエラー ↓ Step実行時に reader.open() が 呼ばれて初めて動く
03

Step 3 — ItemProcessor の3つの役割

起動

Processor の責務は「変換 / 検証 / フィルタ」の3つ。 null を返すと「フィルタ」、例外なら「Skip or Job失敗」、それ以外は「Writerへ」。 

@Bean
public ItemProcessor<Person, Person> processor() {
    return person -> {
        person.setFirstName(person.getFirstName().toUpperCase());
        person.setLastName(person.getLastName().toUpperCase());
        return person;
    };
}
🔰 Processor の判断フロー
受け取った item
   │
   ├─ 変換して return    → Writer へ送る
   ├─ null を return     → そのitemは捨てる(filter, エラーではない)
   └─ throw 例外         → faultTolerant設定次第で Skip or Job失敗
⚠ 副作用は禁物: Processor内でDB書き込みやAPI呼び出しをしてはいけない。 chunk commit境界が崩れ、Restart時に二重実行になる。書き込みは Writer に集約する。
✗ Before: Processor で副作用
return person -> {
    person.setFirstName(...);
    auditDao.log(person);  // ★悪い: 副作用
    return person;
};
// → chunk失敗時、auditだけ残ってDB不整合
✓ After: 純粋関数として書く
return person -> {
    person.setFirstName(...);
    return person;  // ★pureな変換のみ
};
// 監査ログは別Step or 別Writer で。
// commit境界が一致して整合性が保てる。

Step 4 — Writer / Step / Job の組み立て

起動

JdbcBatchItemWriter は内部で addBatch() + executeBatch() を使い、 chunk内の全件を1回のJDBC呼び出しでまとめて送る。これがスループットの肝。 

@Bean
public JdbcBatchItemWriter<Person> writer(DataSource dataSource) {
    return new JdbcBatchItemWriterBuilder<Person>()
        .dataSource(dataSource)                                    // ① 自動Bean
        .sql("INSERT INTO person (first_name, last_name) " +
             "VALUES (:firstName, :lastName)")                  // ② named param
        .beanMapped()                                              // ③ getterに自動マップ
        .build();
}

Step = Reader/Processor/Writer + chunkサイズ + tx境界 を束ねる。

@Bean
public Step step1(JobRepository jr, PlatformTransactionManager tx,
                  ItemReader<Person> r, ItemProcessor<Person,Person> p,
                  ItemWriter<Person> w) {
    return new StepBuilder("step1", jr)              // ① BATCH_STEP_EXECUTION key
        .<Person,Person>chunk(10, tx)                // ② chunk=10 + tx境界
        .reader(r).processor(p).writer(w)            // ③ DI連結
        .build();
}

@Bean
public Job importPersonJob(JobRepository jr, Step step1) {
    return new JobBuilder("importPersonJob", jr)
        .start(step1).build();
}
📘 chunk(10, tx) の意味: 「10件処理ごとに1回commit」を宣言している。 chunk(10) = read×10 + process×10 + write(10) + commit が1サイクル。 失敗時はそのサイクル分だけrollback、それまでのcommitは確定。
chunkサイズ失敗時のロススループット用途
1最小(1件)低(commit多発)クリティカルだが遅くてOK
10〜100小〜中中標準
1000+大高大量データ高速処理

Step 5 — JobLauncher.run() で実行開始

実行

Spring Boot の batch 自動構成は、起動時に Job Bean を自動実行する。 手動実行する場合は JobLauncher を直接呼ぶ。JobParameters が冪等性キーになる。 

JobParameters params = new JobParametersBuilder()
    .addString("inputFile", "persons_20260505.csv")
    .addLocalDateTime("ts", LocalDateTime.now())
    .toJobParameters();

jobLauncher.run(importPersonJob, params);
✗ Before: 毎回同じparams
// 毎回同一params → 同一JobInstance
// 1回成功すると2回目は
// JobInstanceAlreadyCompleteException
JobParameters p = new JobParametersBuilder()
    .addString("file", "a.csv")
    .toJobParameters();
✓ After: timestamp混入
// ts が毎回変わる → 別JobInstance扱い
// 何度でも実行可能
JobParameters p = new JobParametersBuilder()
    .addString("file", "a.csv")
    .addLocalDateTime("ts",
        LocalDateTime.now())
    .toJobParameters();
⚠ Restart vs 別実行の使い分け: 失敗JobをやりなおしたいときはあえてSAMEparamsで実行する(=Restart)。 新しい処理として実行したいときはts等で差別化する。設計時にどちらが正解か明確にしておく。

Step 6 — JobInstance の決定とJobExecution作成

実行

JobLauncher.run() の最初の仕事は「このparamsはRestartか新規か」の判定。 JobRepository がDBを問い合わせて分岐する。

🔰 JobLauncher 内部のフロー
jobLauncher.run(job, params)
   │
   ├── JobRepository.createJobInstance(jobName, params)
   │     │
   │     ├─ 既存JobInstance + 前回COMPLETED
   │     │     → JobInstanceAlreadyCompleteException
   │     │
   │     ├─ 既存JobInstance + 前回FAILED
   │     │     → 既存を再利用 = Restart
   │     │
   │     └─ 見つからない
   │           → 新規JobInstance作成
   │
   ├── JobExecution作成 (status=STARTING)
   ├── BATCH_JOB_EXECUTION INSERT
   └── 実行スレッドへ制御を渡す

DB上の状態(初回実行時):

-- BATCH_JOB_INSTANCE
id  | job_name           | job_key (params hash)
----+--------------------+---------------------------
1   | importPersonJob    | a3f9c1d2...

-- BATCH_JOB_EXECUTION
id  | instance_id | status   | start_time
----+-------------+----------+--------------------
100 | 1           | STARTING | 2026-05-05 09:00:00
📘 JobInstance vs JobExecution: JobInstanceは「論理的な1回」、JobExecutionは「物理的な1回の試行」。 失敗してRestartすると JobInstance:1 → JobExecution:2 になる(1対多)。

Step 7 — Step開始と ExecutionContext 復元

実行

Step開始時、ItemReaderの open(executionContext) が呼ばれる。 Restartの場合、ここで 前回の読み取り位置にseek される。これがCheckpoint復元の正体。

🔰 Step起動シーケンス
1. StepExecution作成
     → BATCH_STEP_EXECUTION INSERT (status=STARTING)

2. ItemReader.open(executionContext)
     ├─ 新規実行: ファイルOPEN、行カウンタ=0
     │
     └─ Restart: BATCH_STEP_EXECUTION_CONTEXT から
                 {"FlatFileItemReader.read.count": 20} を読む
                 → 21行目までskipしてseek

3. StepExecution.status = STARTED
4. Chunk Loopへ
現在: After(Restart)
✓ After: Restart時の reader.open() DBから読む: STEP_EXECUTION_CONTEXT ↓ {"FlatFileItemReader.read.count": 20} ↓ ファイルOPEN → 20行スキップ ↓ 21行目から read() 開始 ↓ 20件目までは前回commit済みなので DBに二重INSERTされない
○ Before: 初回実行時の reader.open() DBには ExecutionContext なし ↓ ファイルOPEN(行カウンタ=0) ↓ 1行目から read() 開始 (普通の動作。Restartではない)
📘 Tomさん自作VB.NET基盤の Checkpoint との対応: 自作基盤で「ジョブテーブルにlast_processed_idを保存→再起動時に読む」をやっていたなら、 まさにそれが BATCH_STEP_EXECUTION_CONTEXT として標準化されている。

Step 8 — Chunk Loop 本体 ★最重要

実行

Spring Batchの心臓部。read×N → process×N → write(N) → commit のサイクルを readがnullを返すまで繰り返す。chunkサイズが10、CSVが23行なら3回のcommitに分かれる。 

// 疑似コード(StepのChunk指向実装の本体)
while (true) {
    TransactionStatus tx = txManager.getTransaction(...);
    List<Person> items = new ArrayList<>();

    // (a) read を chunk-size 回
    for (int i = 0; i < 10; i++) {
        Person item = reader.read();
        if (item == null) break;       // EOF
        items.add(item);
    }
    if (items.isEmpty()) {
        txManager.commit(tx); break;     // ループ終了
    }

    // (b) process を全件
    List<Person> processed = new ArrayList<>();
    for (Person p : items) {
        Person out = processor.process(p);
        if (out != null) processed.add(out);  // null=フィルタ
    }

    // (c) write をまとめて1回
    writer.write(new Chunk<>(processed));

    // (d) ExecutionContext更新 (read.count を保存)
    // (e) commit → INSERT確定 + Restart位置永続化
    txManager.commit(tx);
}
🔰 chunk=10、CSV=23行 の時系列
t=0  ┃tx開始┃read×10┃process×10┃write(10)┃ctx更新┃commit┃ ← 1〜10件確定
t=1  ┃tx開始┃read×10┃process×10┃write(10)┃ctx更新┃commit┃ ← 11〜20件確定
t=2  ┃tx開始┃read× 3┃process× 3┃write( 3)┃ctx更新┃commit┃ ← 21〜23件確定
t=3  ┃tx開始┃read=null → empty → commit → break┃         ← ループ脱出

  total: read=23, write=23, commit=3
Before(commit境界の理解前)
・「失敗したら全部やり直し」
・どこまで処理されたか不明
・冪等性は自前で実装する必要あり
After(理解後)
・chunk単位で確定/巻き戻し
・read.countでどこまで処理済か明確
・冪等性はSpring Batchが保証
✓ commit境界 = chunkサイズ。これがSpring Batchの設計上の核心。 「どこから再開できるか」が「どこでcommitするか」と一致する。 自作基盤を作るときも、この対応を崩さないことが信頼性の基盤になる。

Step 9 — Job終了とメタデータ確定

実行

Chunk Loopが正常終了したあと、ItemReaderクローズ → 各種カウンタDB更新 → Job終了 の順で締める。 最終的にDBに残る情報を確認する。

🔰 終了シーケンス
1. ItemReader.close()      → ファイルハンドル解放

2. StepExecution更新
     status = COMPLETED
     readCount = 23
     writeCount = 23
     commitCount = 3
     filterCount = 0
     skipCount = 0
     → BATCH_STEP_EXECUTION UPDATE

3. JobExecution更新
     status = COMPLETED
     end_time = ...
     → BATCH_JOB_EXECUTION UPDATE

4. JobLauncher.run() がリターン

最終的なDB状態:

-- BATCH_JOB_INSTANCE  (1行)
id=1, job_name=importPersonJob

-- BATCH_JOB_EXECUTION  (1行)
id=100, status=COMPLETED, start=09:00:00, end=09:00:05

-- BATCH_STEP_EXECUTION  (1行)
id=200, step_name=step1, status=COMPLETED,
read_count=23, write_count=23, commit_count=3

-- BATCH_STEP_EXECUTION_CONTEXT  ★Restartの根拠
{"FlatFileItemReader.read.count": 23}

-- person  (アプリのテーブル: 23行)
1, JOHN, DOE
2, JANE, SMITH
...
📘 監視のポイント: 本番運用ではこれらカウンタを監視ダッシュボードに出す。 read_count != write_count ならフィルタやSkipが発生している(意図通りか確認)。 commit_count から「想定chunk数とズレてないか」を見るとパフォーマンス劣化の早期検知になる。
10

失敗→Restart シナリオ(全体観)

応用

Step 8の chunk3 (13件目以降の3件) でWriter例外が発生したケースを追う。 なぜRestart時に重複INSERTが起きないのか、ここで完全に腑に落ちる。

🔰 失敗発生時のロールバック
[1回目実行]
chunk1: tx commit済    → person: 10件確定
chunk2: tx commit済    → person: 20件確定
chunk3: write中で例外発生
    │
    ├─ tx ROLLBACK     → 21〜23件目のINSERT巻き戻し
    ├─ STEP_EXECUTION.status = FAILED
    └─ STEP_EXECUTION_CONTEXT に
         {"FlatFileItemReader.read.count": 20}
       が確定保存されている (chunk2のcommit時点)

[Restart: 同じJobParametersで再実行]
    │
    ├─ JobRepository: 既存JobInstance + FAILED → Restart判定
    ├─ reader.open(): ctxから20を取得 → 21行目にseek
    └─ chunk loop再開:
         read 21,22,23 → process → write → commit
         read=null → 終了
         → person: 23件、二重INSERTなし
Before: Spring Batchなし(自作)
・どこで失敗したか手動確認
・どこから再開すべきか業務ロジックで判定
・冪等性キー設計を自分で
・状態テーブルを自分で設計
After: Spring Batchあり
・状態は STEP_EXECUTION_CONTEXT に自動保存
・Restartは「同じparamsで再実行」だけ
・冪等性はchunk commit境界で自動担保
・状態テーブルは BATCH_* 標準
✓ Tomさんの自作9フェーズ基盤との比較: Phase「Checkpoint/Restart」「DLQ」「ETL/ELT」「Staging Table」は、 Spring Batchでは chunk commit + SkipListener + ItemReader→Processor→Writer + 後続Step に ほぼ1対1で対応する。設計判断の答え合わせができる。
