00

参照アーキテクチャの定義と目的

基本

参照アーキテクチャ (Reference Architecture / RA) とは、ある領域・業界・技術スタックで「典型的に有効」とされる構造・要素・関係性をテンプレート化したもの。具体システムではなく 抽象パターン を提示する点で ソリューションアーキテクチャ と区別される。SIerでは新規案件の初期構成のたたき台・レビュー基準・標準化教材として使う。

🔰 そもそも「参照」とは？
抽象度を3段階で押さえると混乱しない：
① エンタープライズアーキ（経営戦略×IT全体図）→ ② 参照アーキ（特定ドメイン/技術の汎用構造）→ ③ ソリューションアーキ（個別案件の具体設計）。
参照アーキは ②。具体プロダクト名は最小限、図と原則と非機能要件中心。 
  抽象度 高
    ↑   ┌──────────────────────────┐
    │   │ Enterprise Architecture  │  経営×IT 全社マップ（TOGAF等）
    │   ├──────────────────────────┤
    │   │ Reference Architecture   │  ★ ココ：ドメイン/技術の汎用構造
    │   ├──────────────────────────┤
    │   │ Solution Architecture    │  個別案件の具体設計
    │   └──────────────────────────┘
  抽象度 低
軸参照アーキ (RA)ソリューションアーキ (SA)
対象ドメイン/技術の汎用パターン個別プロジェクト
顧客複数案件の母集団1案件1顧客
具体度製品名は最小限製品・バージョン・台数まで
寿命3〜10年案件の稼働期間
所有者標準化チーム/CoEプロジェクトアーキ
 
// 参照アーキの「最小単位」を擬似テキストで表す
ReferenceArchitecture {
  name: "Web系業務システムRA v3",
  scope: "社内向け業務Web、〜500並行ユーザ、Azure前提",
  drivers: ["開発期間6ヶ月以内", "運用人数2名", "監査ログ7年保管"],
  layers: ["Presentation", "Application", "Domain", "Infrastructure"],

💡 利用シーン
  • 新規案件キックオフで「ベース構成案」を1日で出したい
  • 顧客提案時の概念図／非機能要件のたたき台
  • 新人/中途のオンボーディング教材（共通言語の確立）
  • 監査・セキュリティレビューの観点リスト
  • 調達(製品選定)時の「外せない条件」抽出
📍 こう見えたら出番:
  • 「毎案件、最初の1ヶ月が構成議論で消える」
  • 「アーキテクチャレビュー会の指摘がプロジェクト毎に違う」
  • 「人が増えても新人が独自設計を始めてしまう」
現在: After（RAあり）
✓ After: RAあり [新規案件P] └→ RAを参照「Web系業務RA v3」採用 ├ 構成: Presentation/Application/Domain/Infra (確定) ├ 非機能: 7年監査・OIDC認証 (確定) └ 議論: 案件固有の20%だけに集中 → 1週間で初期構成FIX
✗ Before: RAなし [新規案件P] └→ ゼロから議論 ├ 構成: 「DBは何？」「認証どうする？」「ログ保管期間は？」 ├ メンバー毎に経験差で意見対立 └ 1ヶ月過ぎても初期構成FIXせず → 設計工数膨張
01

業界標準・フレームワークとの関係（TOGAF/Zachman）

基本

参照アーキは TOGAF・Zachman といったエンタープライズアーキテクチャ (EA) フレームワーク内では「Architecture Continuum」上に位置づけられる中間生成物。Foundation（基礎）→ Common Systems（業界横断）→ Industry（業界特化）→ Organization-Specific（社内特化）という連続性で抽象→具体に下りていく。

📘 TOGAF ADM上の位置: Phase B(Business)/C(Information Systems)/D(Technology) で参照アーキを参照しながら自社/案件用に具体化する。RAは「Solutions Continuum」の入口となるテンプレ群。 
// Architecture Continuum の階層（TOGAF）
Foundation Architecture        // TRMなど最も汎用
   ↓ より具体
Common Systems Architecture    // 業界横断（例: 一般的なWebアプリ三層）
   ↓
Industry Architecture          // 業界特化（例: 金融オンラインバンキングRA）
   ↓
Organization-Specific          // 自社特化（例: A社向けWeb業務RA v3）
フレームRAの位置づけ用途
TOGAFArchitecture Continuum / Solutions ContinuumADM Phase B-D の入力
Zachman各セル（What/How/Where/Who/When/Why × 6視点）の標準解網羅性チェック
IT4ITValue Stream毎のリファレンス運用プロセス標準化
ArchiMate記法（モデリング言語）RAの図示・関係表現
NIST CSF / ISO 27001セキュリティ観点RA非機能要件のチェック
⚠️ 誤解しがちな点: TOGAFやZachmanはRAそのものではなく、RAを作る・配置する・運用するためのメタフレームワーク。「TOGAF採用」=「RAができる」ではない。RAは別途設計が必要。
✗ Before（混同あり）
// 提案書での誤った表現
"本案件はTOGAF準拠のため、
 マイクロサービス構成とします。"
// → TOGAFはRA選択を強制しない
//   論理が飛躍している
✓ After（正しい）
// 正しい論理連鎖
"TOGAF ADMに従い分析した結果、
 ビジネス要件と非機能要件から
 弊社RA カタログ中の
 『MSA-参照アーキ v2』を選定。"
// ← フレーム/RA/個別案件 の関係明示
💡 利用シーン
  • RFP/提案書で「業界標準準拠」を語るときの引用
  • 監査対応で「設計プロセスの正当性」を示す
  • 大企業との取引でEAフレームに揃える必要があるとき
  • 社内RAカタログを整備する際の階層設計
📍 こう見えたら出番:
  • 「TOGAF準拠と書きたいが、何を準拠と呼ぶか曖昧」
  • 「監査でアーキ決定の根拠を聞かれている」
02

参照アーキの構成要素 — 何を必ず書くか

基本

RAドキュメントが必ず備えるべき構成要素は概ね 5+1。① コンテキスト ② 構成図 ③ コンポーネント定義 ④ 非機能要件 ⑤ 意思決定記録(ADR) + ⑥ 適用ガイド。これらが揃って初めて「再利用可能」と呼べる。

🔰 RAの中身マップ
┌─────────── Reference Architecture Document ───────────┐
│                                                        │
│ ① Context（誰のための・どこまでの範囲か）             │
│    └ Drivers / Constraints / Out of Scope             │
│                                                        │
│ ② Structure（構成図 — 論理/物理/配備）                │
│    └ コンポーネント図・配置図・データフロー           │
│                                                        │
│ ③ Components（各部品の責務・I/F・代表製品）           │
│                                                        │
│ ④ Quality Attributes（非機能要件マトリクス）          │
│    └ 可用性・性能・セキュリティ・運用性 など          │
│                                                        │
│ ⑤ ADR（採用理由・却下理由・トレードオフ）             │
│                                                        │
│ ⑥ Adoption Guide（適用手順・テーラリング指針）        │
└────────────────────────────────────────────────────────┘
要素書く内容抜けると起きる問題
① Context適用対象・前提・対象外適用範囲外の案件に流用され炎上
② Structure論理/物理構成図絵が無く議論が空中戦になる
③ Components責務とI/F定義境界が曖昧で実装が肥大化
④ NFR性能/可用/セキュ目標値機能だけ作って本番で爆発
⑤ ADR採否の根拠「なぜこれ?」を毎回再議論
⑥ Adoptionテーラリング手順RAが「飾り」になる
 
// ④ NFR（非機能要件）マトリクスの例
| 観点         | 目標値                    | 検証方法            |
|--------------|---------------------------|---------------------|
| 可用性        | 99.9% (月43分以内停止OK)  | SLO監視ダッシュボード |
| 応答時間      | p95 < 1.0sec / Top画面    | 性能試験 (JMeter)   |
| 同時接続      | 500並行                  | 負荷試験            |
| RTO / RPO    | 4時間 / 1時間            | DR訓練              |
| 監査ログ保管  | 7年                       | ストレージライフサイクル |
| 認証          | OIDC (社内IdP)           | ペネトレーション試験 |
✅ 抜け漏れチェックの簡易テスト: RAドキュメントを読んだ別チームが「自分の案件で使うか」「使わない場合何を変えるか」を判断できるか? できれば合格、無理なら ① Context か ⑥ Adoption Guide が不足。
💡 利用シーン
  • 新規RA策定時のテンプレート（章立て）
  • 既存RAの抜け漏れ監査
  • RAレビュー会のチェックリスト
  • 新人にRAの読み方を教える教材
📍 こう見えたら出番:
  • 「RAはあるが構成図しか無い」
  • 「NFRが書かれていない or 数値が無い」
  • 「適用範囲が不明で何にでも当てはめられている」
03

4+1ビューモデル — 多視点でアーキを記述する

中級

Philippe Kruchten が提唱した 4+1 View Model。Logical(論理) / Process(プロセス) / Development(開発) / Physical(配備) の4ビュー + Scenarios(ユースケース) でアーキを多角的に記述する。RAでも「1枚絵」では足りない時に必ず使う基本枠組み。

🔰 4+1ビューの全体像
                    ┌────────────────┐
                    │   Scenarios    │  ユースケース・要件
                    │  (+1 ビュー)    │  → 他4ビューを駆動
                    └───────┬────────┘
                            │
            ┌───────────────┼───────────────┐
            │               │               │
   ┌────────▼─────┐  ┌──────▼──────┐  ┌────▼──────────┐
   │  Logical     │  │  Process    │  │  Development  │
   │  論理構造     │  │ 並行性・通信 │  │ コード/モジュール │
   │ (機能要件)    │  │  (性能/可用) │  │ (開発の利便性)  │
   └──────────────┘  └─────────────┘  └───────────────┘
                            │
                    ┌───────▼────────┐
                    │   Physical     │
                    │  配置・トポロジ  │
                    │  (運用性)        │
                    └────────────────┘
ビュー関心事主な読者代表的記法
Logical機能・責務・継承業務SE/分析担当クラス図・コンポーネント図
Process並行性・性能・可用性性能担当・SREシーケンス図・アクティビティ図
Developmentモジュール分割・依存開発者・ビルド担当パッケージ図・レイヤ図
Physicalサーバ配置・NWインフラ・運用配置図・NW構成図
Scenariosユースケース駆動全員（共通言語）ユースケース図・シナリオ
📘 Tomさんの現場対応: OutSystemsの場合、Logical = モジュール責務マップ、Process = BPT/Timer のフロー、Development = アプリ/モジュール構成図、Physical = 環境構成図 (DEV/QA/PROD/フロントエンドサーバ数) にマッピングできる。 
// 4+1 を OutSystems文脈に当てはめた例
[Logical View]
  - CoreServicesモジュール: 業務エンティティ + Public Action
  - UI Library: 共通テーマ + ブロック

[Process View]
  - BPT「申請承認フロー」: 並行3000件想定、Timer夜間バッチ
  - 同期API: Server Action経由で平均<200ms

[Development View]
  - Cross-Cutting: Auth, Audit, Logging (CS層)
  - Foundation: Theme, Reusable Patterns (FW層)
  - End-User: HR_Portal, Approval_App

[Physical View]
  - Front-end Server x2 (Azure VM Standard_D4s_v5)
  - Database: Azure SQL Business Critical
  - Cache: Redis Cache Standard

[Scenarios] - これらに対し各ビューが整合してるか検証
  - UC01 ログイン (Auth)
  - UC02 申請投稿 (BPT起動)
  - UC03 月次集計 (Timer)
⚠️ よくある失敗: Logical View だけ書いて他を省略 → 性能問題(Process欠如)・運用事故(Physical欠如)が顕在化。RAでは必ず4ビューを最低1枚ずつ。
現在: After（4+1完備）
✓ After: 4ビュー完備 レビュー会: 「機能はLogicalで明確、性能はProcessで秒レベル合意、 配置はPhysicalで2台冗長確認、ビルド単位はDevelopmentで分離」 → 30分で承認、リリース後トラブルなし
✗ Before: Logicalだけ レビュー会: 「機能図はあるが、サーバ何台?」「タイマーの並行数は?」 「モジュール境界が運用と整合してる?」 → 質問祭りで2時間延長、後日資料追加で再レビュー
💡 利用シーン
  • RA文書の章立て（4+1で章を切る）
  • レビュー会で「視点漏れ」を指摘するチェック軸
  • 新人に「アーキ図の読み方」を教える
  • 顧客説明資料での視点切替（経営層=Scenarios、運用=Physical）
📍 こう見えたら出番:
  • 「アーキ図が1枚しか無く、議論で言葉が噛み合わない」
  • 「ステークホルダー毎に欲しい情報が違うのに同じ図を見せている」
04

レイヤード参照アーキテクチャ

中級

最も古典的・普及度の高いRA。Presentation / Application / Domain / Infrastructure の4層が標準。上位は下位のみに依存 という依存方向の制約がコアルール。違反すると保守時に副作用が広範に伝播する。OutSystems の Architecture Canvas (Lab09) もこのレイヤード思想の派生。

🔰 4層の責務と依存方向
       ┌──────────────────────────────┐
       │  Presentation Layer          │  画面・APIエンドポイント
       │  (Web UI / REST Controller)  │
       └──────────────┬───────────────┘
                      ↓ depends on
       ┌──────────────▼───────────────┐
       │  Application Layer           │  ユースケース・トランザクション制御
       │  (Use Case / Service)        │
       └──────────────┬───────────────┘
                      ↓ depends on
       ┌──────────────▼───────────────┐
       │  Domain Layer                │  業務ルール・エンティティ
       │  (Entity / Value Object)     │
       └──────────────┬───────────────┘
                      ↓ depends on
       ┌──────────────▼───────────────┐
       │  Infrastructure Layer        │  DB・外部API・メッセージング
       │  (Repository / Gateway)      │
       └──────────────────────────────┘

  ★ 矢印は「上→下」の一方向。逆向き依存は禁止。
層典型的なクラス例VB.NET / OutSystems対応
PresentationHomeController, OrderViewModelScreen / Block / Exposed REST
ApplicationOrderService, RegisterUseCaseServer Action (CS層)
DomainOrder Entity, Money VOEntity + 業務Action (Core)
InfrastructureOrderRepository, SapGatewayIntegration Studio / Consumed REST
✗ Before（依存逆流）
' Domain層がInfraに直接依存
Public Class Order
  Public Sub Save()
    Dim con As New SqlConnection(...)
    con.Open()
    ' ↑ Domainが具象DBを知っている
    '   テスト不能・差替不能
  End Sub
End Class
✓ After（DIで反転）
' DomainはInterfaceに依存
Public Class Order
  Private _repo As IOrderRepo
  Public Sub New(repo As IOrderRepo)
    _repo = repo
  End Sub
  Public Sub Save()
    _repo.Persist(Me)
  End Sub
End Class
' Infra層でIOrderRepoの具象実装を提供
⚠️ レイヤードの落とし穴: 厳密にすると「DTOコピーだらけ」「全部4層通す」で生産性が落ちる。CRUD系の単純機能はBypass(Pres→Repoの直結)を許容するなど、テーラリング指針をRAに明記すべき。
📘 OutSystems文脈の対応: Architecture Canvas の End-User Layer = Presentation+一部Application、Core Services = Application+Domain、Foundation = Cross-cutting、Library = Infrastructure に概ね対応する。
💡 利用シーン
  • 業務Webアプリの初期設計テンプレ
  • 新人教育で「責務分離」を教える教材
  • レビューで「依存逆流」を検出する基準
  • VB.NETバッチ共通基盤の層設計
📍 こう見えたら出番:
  • 「Domainクラスに SqlConnection や HttpClient がある」
  • 「ControllerからRepoを直接呼んでビジネスロジックが散在」
  • 「テスト時にDBに繋がないと動かない」
05

ヘキサゴナル / クリーンアーキテクチャ

上級

Hexagonal (Ports & Adapters) = Alistair Cockburn 1995、Clean Architecture = Uncle Bob 2012 が代表。両者の核心は「業務ルール（Domain/UseCase）が外側（DB/UI/外部API）に依存しない」という依存性逆転。RAとしては「ビジネスロジックを長く生かしたい」「複数フロント/DBを差し替えたい」案件で採用される。

🔰 同心円で見る依存方向
       ┌──────────────────────────────────┐
       │      Frameworks & Drivers       │  ← UI / DB / Web / 外部
       │   ┌──────────────────────────┐   │
       │   │   Interface Adapters     │   │  ← Controller / Presenter / Gateway
       │   │   ┌──────────────────┐   │   │
       │   │   │  Application     │   │   │  ← Use Case
       │   │   │  ┌──────────┐    │   │   │
       │   │   │  │  Domain  │    │   │   │  ← Entity / 業務ルール
       │   │   │  └──────────┘    │   │   │
       │   │   └──────────────────┘   │   │
       │   └──────────────────────────┘   │
       └──────────────────────────────────┘

  依存方向: 外 → 内 のみ。内側は外を一切知らない。
  ★ Domainが最も安定し、変更頻度が低い設計。
観点レイヤードヘキサゴナル/クリーン
依存方向上→下（一方向）外→内（同心円）
Domainの位置下から2番目中心（最も安定）
テスト容易性中（モック必要）高（Domain単体で動く）
差替容易性低〜中高（Adapterだけ作れば良い）
学習コスト低中〜高
適合案件短期業務Web長期コア・複数フロント
 
// Port (interface) と Adapter の対応 — TypeScript
// === Domain（依存無し） ===
class Order {
  constructor(public id: string, public total: number) {}
  isHighValue() { return this.total > 10000; }
}

// === Port（Application層が定義） ===
interface OrderRepo {
  findById(id: string): Promise<Order>;
  save(o: Order): Promise<void>;
}

// === Use Case（Portにのみ依存） ===
class PlaceOrderUseCase {
  constructor(private repo: OrderRepo) {}
  async exec(o: Order) {
    if (o.isHighValue()) { /* 承認フロー */ }
    await this.repo.save(o);
  }
}

// === Adapter（外側で具象実装） ===
class SqlOrderRepo implements OrderRepo { /* SQL実装 */ }
class InMemoryOrderRepo implements OrderRepo { /* テスト用 */ }
📘 Ports & Adaptersの命名: Inbound Port = UIから入る I/F (Use Case)、Outbound Port = DBや外部APIへ出る I/F (Repo/Gateway)。「P&A」「Hexagonal」は同義語として使われる。
⚠️ 適用判断: 全案件に適用すると過剰設計。「コア業務ロジックが3年以上生きる」「複数チャネル（Web/Mobile/Batch）から共有」「DB/フロント技術を将来交換予定」のいずれかに該当しなければレイヤードで十分。
💡 利用シーン

  • 同一業務ロジックをWeb/Mobile/Batchで共有
  • DBをOracle→PostgreSQLに将来交換する前提の設計
  • ユニットテスト網羅率を高く保ちたいプロジェクト
📍 こう見えたら出番:
  • 「業務ロジック修正のたびにフロントとDBが同時に壊れる」

イベント駆動参照アーキテクチャ (EDA)

上級

Event-Driven Architecture (EDA)。コンポーネント間のやり取りを同期API呼び出しではなくイベントの発行/購読で行う。Producer → Broker → Consumer という基本3点セット。疎結合と非同期スケールを最大化できる一方、順序保証・冪等性・スキーマ進化の難しさを伴う。

🔰 EDAの最小構造
  ┌──────────┐    publish    ┌────────────┐    subscribe   ┌──────────┐
  │ Producer │  ───────────→ │  Broker    │  ───────────→  │ Consumer │
  │ (Order)  │  OrderCreated │ (Kafka)    │  OrderCreated  │ (Notify) │
  └──────────┘               └─────┬──────┘                └──────────┘
                                   │ 永続化(retain)
                                   ▼              subscribe ┌──────────┐
                              [Topic Log]  ───────────────→ │ Consumer │
                                                            │ (Audit)  │
                                                            └──────────┘
  ★ Producer は誰が受信するか知らない (疎結合)
  ★ 後から Consumer 追加可能 (拡張性)
パターン用途代表実装
Publish/Subscribe1対多 / イベント通知Kafka / Pub-Sub / SNS
Event Sourcing状態を全イベントの集積として保持EventStoreDB / Kafka+CQRS
CQRS書き込み/読み取りモデル分離Axon / 自作
Outbox PatternDB更新とイベント発行の整合確保Debezium / 自作

Stream Processingリアルタイム集計・検知Kafka Streams / Flink

📘 OutSystems文脈での対応: BPT（Business Process Technology）はイベントとプロセスの中間。Light BPTは即時起動、通常BPTは永続化トリガで非同期。Service Bus等を組み合わせて社外連携にEDAを適用するパターンが多い。
⚠️ 3大注意点:
① 順序保証: Kafkaは同一パーティション内のみ順序保証。順序必須なら集約IDをキーにする。
② 冪等性: At-least-once配信が標準なので Consumer は同じイベントを2回処理しても大丈夫な実装に。
③ スキーマ進化: イベントは長期保存される。Schema Registry + 後方互換ルールが必須。
現在: After（EDA）
✓ After: EDAで疎結合 [OrderSvc] → 「OrderCreatedイベント発行」 ↓ (Brokerに届けば成功) ↓ Notifyが落ちててもOrderSvcは正常完了 ↓ 後でConsumerが復帰して処理 新機能「在庫予約」を追加: Consumer1個追加するだけ → OrderSvcは無改修
✗ Before: 同期API依存 [OrderSvc] → call NotifySvc API ↓ NotifySvcが応答遅延 → OrderSvcもタイムアウト ↓ NotifySvc障害 → OrderSvcも巻き込まれて落ちる 新機能追加: OrderSvcが3つの新APIを呼ぶよう改修 → 結合・テスト・デプロイで2週間
💡 利用シーン
  • IoTセンサー大量データのリアルタイム集計
  • 金融取引の監査証跡（Event Sourcing）
  • ECの在庫・決済・通知の疎結合連携
  • レガシー基幹と新規SaaSのCDC連携
  • Consumer側の拡張頻度が高いSaaS
📍 こう見えたら出番:
  • 「サービスA障害でサービスB-G全体が連鎖停止」
  • 「新機能追加のたびに既存サービスを改修」
  • 「監査要件で『過去全状態』が再構成可能でなければならない」

# ADR-003: 認証プロトコルに OIDC + 社内 Azure AD を採用

## Status
Accepted (2026-04-15)

## Context
- 全社で Azure AD 利用が標準化
- 既存システムは独自セッションだったが、SSO要件あり
- 監査ログを SAML 中心から OIDC に移行する全社方針

## Decision
本RA配下のWeb業務システムは、全て **OIDC Authorization Code Flow + PKCE**
を Azure AD テナントで利用する。

## Consequences
+ 全社SSO実現、ID管理コスト削減
+ MFA・条件付きアクセスを標準活用
- レガシー連携 (FAX系) は別途ブリッジ必要
- ローカル開発時は dev用テナントで認証フロー検証必須

## Alternatives Considered
- **SAML 2.0**: 既存資産あるが、新規はOIDC方針で却下
- **独自JWT発行**: 監査・回転設計が独自実装になり保守困難で却下
- **Auth0 等外部IDaaS**: コスト・データ越境で却下

評価フレームワーク — ATAM とトレードオフ分析

上級

ATAM (Architecture Tradeoff Analysis Method) は SEI (Software Engineering Institute) が開発したアーキ評価手法。RAやSAの非機能要件達成度とトレードオフを構造的にレビューする。「シナリオ駆動」で具体的に評価するのが特徴。

🔰 ATAM 9ステップの流れ
[Phase 1: 評価準備]
  ① ATAM紹介・契約
  ② ビジネス目標の提示
  ③ アーキ概要の提示

[Phase 2: 構造化分析]
  ④ アーキ手法の特定 (採用パターン)
  ⑤ Quality Attribute (QA) ツリー作成
  ⑥ 重要シナリオの分析

[Phase 3: テスト・検証]
  ⑦ シナリオの優先順位付け (投票)
  ⑧ アーキ再分析・トレードオフ抽出
  ⑨ 結果プレゼン

★ 成果物: 「Risks / Non-Risks / Sensitivity Points / Tradeoff Points」
用語意味例
Risk達成困難・要対策のシナリオ「DR-RTO 1時間が現構成では実現不能」
Non-Risk明らかに達成可能「平均応答 500msは達成」
Sensitivity Point1要素変更が大きく品質に影響「DBインスタンスサイズで応答時間が10倍変動」
Tradeoff Point複数品質に正負の影響「キャッシュ強化で性能↑だが整合性↓」
 
// QA Tree (Quality Attribute Tree) の例
業務RA v3 評価
├── 性能
│   ├── 応答時間 (Top画面 p95 < 1.0s) [優先度: H]
│   │   └─ シナリオS1: ピーク 500並行で1.5秒 → Risk
│   └── スループット (200 req/s) [優先度: M]
│       └─ シナリオS2: 安定 250req/s 達成 → Non-Risk
├── 可用性
│   ├── SLO 99.9% (月43分以内) [優先度: H]
│   │   └─ シナリオS3: AZ単一障害は復旧4分 → Non-Risk
│   └── DR (RTO 4hr) [優先度: H]
│       └─ シナリオS4: DR訓練未実施 → Risk
└── セキュリティ
    └── 監査7年保管 [優先度: H]
        └─ シナリオS5: ストレージライフサイクル設定済 → Non-Risk

  Tradeoff: キャッシュTTL→性能↑ / データ整合性↓ (Sensitivity)
📘 軽量版の代替: 本格ATAMは2-3日のワークショップ。日常運用には軽量版「Mini-ATAM」(半日)、または「Architecture Decision Workshop」(2時間+ADR化)で十分なケースが多い。
⚠️ 評価のタイミング: コード書く前の早期(設計時) と稼働後1年(実績検証) の両方で行うのが理想。設計時のみだと「絵に描いた餅」、稼働後のみだと「手遅れ」。
💡 利用シーン
  • 大型案件キックオフ前のRA妥当性レビュー
  • 本番運用1年後のRA棚卸し
  • 2RA案で迷っている時の比較評価
  • 顧客との非機能要件合意形成
📍 こう見えたら出番:
  • 「非機能要件が合意されないまま設計が進んでいる」
  • 「複数RA案でどれにすべきか決まらない」
  • 「稼働後の問題が設計時に見抜けた可能性が高い」
12

RA導入ロードマップ — 組織で使われるRAにする

上級

RAを作っただけでは誰も使わない。SIerでよく失敗するのは「最初の数案件で適用→更新止まる→陳腐化→誰も見なくなる」サイクル。本ラボでは 4フェーズの導入ロードマップ と 組織的な維持メカニズム を整理する。

🔰 4フェーズのロードマップ
[Phase 0: Seed (1-2ヶ月)]
  ・1-2案件で「先行実装」してフィードバック
  ・最小ドキュメント (構成図 + ADR数本)
  ・推進者(チャンピオン)1-2名で十分

[Phase 1: Standardize (3-6ヶ月)]
  ・章立て統一(Lab02の5+1)
  ・社内Wiki/Gitに公開
  ・3-5案件への適用、適用記録(誰がいつ何を変更)

[Phase 2: Govern (6-12ヶ月)]
  ・適用必須化 + テーラリング指針
  ・新規案件レビュー必須プロセス化
  ・Architecture Review Board (ARB)設立
  ・四半期棚卸し開始

[Phase 3: Evolve (12ヶ月+)]
  ・複数バージョン併存(v1/v2)、バージョン移行ガイド
  ・案件適用率/技術負債KPIを管理
  ・社外公開・コミュニティ展開も視野
役割責務RAでの貢献
Architect (CoE)RAの作成・改訂本体メンテ、ADR承認
Project Architect案件への適用判断テーラリング・違反申請
Champion各事業部での推進勉強会・適用支援
ARB適用レビュー・例外承認逸脱案件の判断
開発リーダー適用結果の報告FB・改善提案
✅ 成功する組織の共通点:
① RA本体に 「適用FB集積ページ」 を設けPRで誰でも追記可能
② 四半期1回の棚卸しを「期日固定」で形骸化を防ぐ
③ 適用実績/違反件数/負債解消をダッシュボード化（OutSystems Architecture Dashboardのような自動計測）
✗ Before（陳腐化パターン）
