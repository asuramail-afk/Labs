00

4要素の全体地図と習得順序

基本

Claude Code を「ただのチャット」から「自分専用の作業ロボ」に変える4つの拡張要素を、まず役割分担で理解する。深掘りは後のラボで行うので、ここでは「何が何のためにあるか」だけを掴む。

🔰 4要素を一言で
4要素は「誰が / いつ / 何を起動するか」で役割が分かれる。
Skills = Claudeが自動で読みに行く"参考書"。
Slash Commands = あなたが手動で呼ぶ"定型プロンプト"。
MCP = Claudeに新しい"道具"（外部サービス）を生やす。
Hooks = Claudeの行動の前後に"必ず実行する"スクリプト。 
              ┌────────────────────── あなたが操作 ──────────────────────┐
              │                                                          │
              │   /deploy   ← Slash Commands（手動で呼ぶ定型プロンプト）  │
              │      ↓                                                   │
        ┌─────┴──────────────────────┐                                  │
        │  Claude Code セッション    │← UserPromptSubmit Hook が割込    │
        │                            │                                  │
        │  作業中に "PDF 作りたい"   │                                  │
        │  と言うと…                │                                  │
        │     → Skills を自動で発見  │ ← Skills（自動で読みに行く参考書）│
        │                            │                                  │
        │  外部サービス操作したい    │                                  │
        │     → MCP の道具を呼ぶ     │ ← MCP（外部サービス＝新しい道具） │
        │                            │                                  │
        │  ファイルを編集            │                                  │
        │     → PostToolUse Hook 発火│ ← Hooks（前後に必ず動くスクリプト）│
        └────────────────────────────┘                                  │
              │                                                          │
              └─────────────────── 結果が返る ──────────────────────────┘
要素誰が起動?何が増える?典型シーン難易度
SkillsClaude が自動専門知識・手順書「PDFに変換して」→自動でPDF skillを発見★☆☆
Slash Commandsあなたが手動呼び出しショートカット毎朝 /standup で日次まとめ★☆☆
MCPClaude が自動 (許可後)外部サービスの道具GitHub/Notion/DB など外部連携★★☆
Hooksイベントで自動強制実行ロジック編集後に必ず prettier、危険コマンド禁止★★★
📘 2026年4月時点の重要事項: .claude/commands/ と .claude/skills/ は統合された。両方使えるが、新規作成はSkills 推奨。同名なら Skill が優先される。
✅ このLabの推奨学習順: Skills（最も簡単・効果実感が早い）→ Slash Commands → MCP → Hooks（最後・誤設定リスク高）。順序を守れば挫折しにくい。

01

セットアップと初回起動

基本

Claude Code は Node.js 18+ が必要なターミナル CLI。インストール → 認証 → 適当なフォルダで起動 → /help で動作確認、までを一気に通す。 

# 1. Node.js 18 以上があるか確認（Windowsはコマンドプロンプト/PowerShell）
node -v   # v18.x.x 以上ならOK

# 2. グローバルインストール
npm install -g @anthropic-ai/claude-code

# 3. 任意のプロジェクトフォルダへ移動して起動
cd C:\Users\user\my-project
claude

# 4. 初回はブラウザが開いてAnthropicアカウント認証 → 戻ると対話画面
⚠️ Windowsでハマりがちな点: PowerShell実行ポリシーで npm install -g が止まる場合は、管理者権限のPowerShellで Set-ExecutionPolicy -Scope CurrentUser RemoteSigned を実行。WSL/Git Bashでも動作可。 
# 起動後、まず叩くコマンド3つ
/help         # 全コマンド一覧（60+ あるので圧倒されてOK、後で覚える）
/doctor       # インストール健全性チェック
/model        # 使用モデル切替（Opus/Sonnet/Haiku）
🔰 「何を質問していいか分からない」を解決
最初は 「このフォルダの中身を要約して」 と聞くだけで十分。Claudeがファイルツリーを読み、自然言語で説明してくれる。コードを書かせる前に「読ませる」体験から入ると怖くない。
📘 モデル選びの目安: 普段は sonnet、複雑な設計は opus、軽い質問は haiku。Maxプランなら opusplan（思考はOpus・コードはSonnet）が便利。
02

CLAUDE.md でプロジェクト記憶を作る

基本

4要素を学ぶ前に CLAUDE.md を理解しておく。これは セッション開始時に必ず読まれる プロジェクト固有のメモ。Skills や Hooks の前段として、ここに書くだけで挙動の8割は変えられる。

✗ Before（CLAUDE.md なし）
# 毎セッション同じ説明を繰り返す
> このプロジェクトは TypeScript で…
> テストは vitest を使う
> .env は触らないで
> コミットメッセージは英語で…
✓ After（CLAUDE.md 配置）
# プロジェクトルートに CLAUDE.md を置くだけ
# 内容例:
## Stack
- TypeScript / Vitest / Next.js

## ルール
- .env* は絶対に編集しない
- コミットメッセージは英語
- テスト先行（テスト書いてから実装）
✅ 200行以内に保つ: CLAUDE.md は毎ターンコンテキストに載るので、長すぎるとトークンを圧迫し応答も遅くなる。「これだけは守って」のリストに絞る。
📘 3階層: ~/.claude/CLAUDE.md（全プロジェクト共通）→ プロジェクトルート（チーム共通）→ サブディレクトリ（局所）の順で重ねて読まれる。 
# CLAUDE.md の最小テンプレ（コピペ用）
# プロジェクトメモ

## スタック
- 言語: TypeScript 5.x
- テスト: Vitest
- パッケージマネージャ: pnpm

## 必ず守って欲しいこと
- `.env*` `secrets/` 配下は読み書き禁止
- コミット前に `pnpm test` を必ず実行
- ライブラリ追加時は理由をコミットメッセージに書く

## よく使うコマンド
- 開発: `pnpm dev`
- ビルド: `pnpm build`
- テスト1ファイル: `pnpm vitest run path/to/file.test.ts`
03

Skills とは何か（最も簡単な入口）

中級

Skills は 「特定の話題が出たときに Claude が自分で読みに行く参考書」。あなたが呼び出さなくていい。Claudeが「あ、これはあのSkillが要りそう」と判断して読み込む（auto-invoke）。最も体感が早い機能なので最初に試すのがおすすめ。

🔰 Skill が動く瞬間のメンタルモデル
あなた:「このコードを PDF にして」
   ↓
Claude のセッション開始時、こう仕込まれている:
   .claude/skills/*/SKILL.md の name と description が
   Claude のコンテキストに常駐（中身ではなく見出しだけ）
   ↓
Claude:「PDF? あ、pdf-export って Skill があるな」
   ↓
Skill の SKILL.md（中身）を自動で読みに行く
   ↓
書かれた手順に沿って動作

つまり Skill は「索引付きの参考書」を Claude の机に並べておく行為。
📘 SKILL.md の最重要フィールド: description。ここに書いたキーワードでClaudeが「これを使うべき」と判断する。曖昧だと動かない。 
# 既存 Skill を確認する（公式バンドル＋自作）
/skills           # 一覧表示。ON/OFF 切替も可能
項目SkillsSlash Commands
呼び出しClaude が自動判断あなたが /name で手動
適切な用途「PDF が話題に出たら…」など状況依存「毎朝の定型作業」など固定タスク
frontmatterdescription が必須・重要シンプル（または skill と同じ）
2026推奨推奨引き続き使えるが Skills 統合へ
⚠️ description は具体的に書く: 「コードを整理する」のような抽象表現はトリガーされにくい。「TypeScript ファイルを保存後に prettier と eslint を自動修正する」のように動詞＋対象＋条件で書く。
04

初めての Skill を作る — explain-code

中級

最も短い Skill「コードを ASCII図 + アナロジーで解説する」を実際に作って試す。1ファイル作るだけで Claude の挙動が永続的に変わる体験をする。 

# 1. Skill 用ディレクトリを作る（ユーザー全体で使う場合は ~/.claude/skills/）
mkdir -p ~/.claude/skills/explain-code

# 2. SKILL.md を作る
cat > ~/.claude/skills/explain-code/SKILL.md <<'EOF'
---
name: explain-code
description: コードを ASCII 図とアナロジーで初心者にも分かるよう解説する。ユーザが「このコード説明して」「どう動くの？」「初心者向けに」と言ったとき使う。
---

# コード解説スキル

コードを説明するときは、必ず以下の順で答える:

1. **身近なたとえ話**で1段落（料理・郵便・乗り換え案内など）
2. **ASCII 図**で構造／フロー／関係を可視化
3. **ステップ実行**を行ごとに番号付きで
4. **初心者が踏みがちな罠**を最後に1つ
EOF
✅ これだけで完成。次に claude を新規セッションで起動して「このコード説明して: arr.reduce((a,b)=>a+b,0)」と聞くと、Skillが自動発動して4ステップで答える。
Before ▶︎ Skill なし
Claudeはぶっきらぼうに「reduce は配列を畳み込んで…」と用語で説明。初心者には伝わらない。
After ▶︎ Skill あり
「これは『箱を1つずつ開けて中身を足し算メモに加算していく』作業です」→ ASCII図で [1,2,3] → 0+1=1 → 1+2=3 → 3+3=6 を描く → 罠まで触れる。
⚠️ frontmatter の --- は半角3つ。全角や4つ以上だとパースされず Skill 一覧に出ない。/skills で一覧に出ない時はまずここを疑う。
🔍 動作確認
  1. 新規ターミナルで claude 起動
  2. /skills を実行 → explain-code が一覧にあるか確認
  3. 「このコード説明して: [1,2,3].map(x => x*2)」と聞く
  4. 回答が たとえ話 → ASCII図 → 行解説 → 罠 の4部構成になっていれば成功
  5. 4部構成にならなければ、SKILL.md の description に「コード」「説明」「初心者」などキーワードを増やす
05

Slash Commands を使う — /standup

中級

Slash Commands は 「あなたが手動で呼ぶ定型プロンプト」。毎日同じ依頼を打つのが面倒な作業に最適。引数も渡せる。2026年現在は Skills と統合されたが、シンプルな定型は commands/ でも問題なく動く。 

# 1. プロジェクトに commands フォルダを作る
mkdir -p .claude/commands

# 2. /standup コマンド = 日次スタンドアップ用プロンプト
cat > .claude/commands/standup.md <<'EOF'
直近24時間のgitコミットを `git log --since="24 hours ago" --oneline` で確認し、
以下の3つで日本語要約してください:

1. ✅ 完了したこと
2. 🔄 進行中のこと（未コミットの変更も含む `git status`）
3. ⚠️ ブロッカーや懸念点
EOF
✅ Claude起動中に /standup と打つだけで上記プロンプトが送信される。チームで共有したいなら .claude/ をgitにコミット。 
# 引数つき例: /fix-issue 123 で「Issue #123 を修正」と展開される
cat > .claude/commands/fix-issue.md <<'EOF'
GitHub Issue #$ARGUMENTS を以下の手順で対応してください:

1. `gh issue view $ARGUMENTS` で内容を読む
2. 関連ファイルを特定し、修正案を提示
3. 確認を取ってから実装
4. テストを書いて pass を確認
5. コミットメッセージに `Fixes #$ARGUMENTS` を含める
EOF

# 使い方
/fix-issue 123
💡 こんなとき Slash Commands
  • 毎朝同じ「今日のタスクを git log から要約」を頼みたい
  • PR レビュー観点を毎回同じテンプレで聞きたい
  • コードレビューチェックリストを /review で発動したい
  • 本番デプロイ前のチェック手順を /preflight に固める
こう感じたら候補
  • 「またこのプロンプト書いてる…」と思った瞬間
  • 新人にいつも同じ依頼の仕方を教えている作業
  • セッションを跨いで再利用したい指示
📘 引数の文法: $ARGUMENTS（全引数）／$0 $1 $2（位置引数）／${CLAUDE_SKILL_DIR}（Skillディレクトリ）。
場所スコープ用途
.claude/commands/プロジェクトチームで共有・git管理
~/.claude/commands/ユーザー全体個人用（全プロジェクト）
.claude/skills/<名>/SKILL.mdプロジェクト（推奨）名前 = /<名> で呼べる＋自動発動も可能

MCP の概念と接続 — Claude に新しい道具を生やす

上級

MCP（Model Context Protocol）は 「外部サービスを Claude の道具として接続する規格」。GitHub・Notion・Slack・DB などを、それぞれ専用のサーバとして立ててClaudeから呼べるようにする。Skills が"知識"なら、MCP は"手足"。

🔰 MCP の構造（伝言ゲーム）
[ あなた ]                         [ 外部サービス ]
   │                                    ▲
   │ 「Notionに議事録を保存」          │ Notion API
   ▼                                    │
[ Claude Code ] ←──── MCPサーバ ───────┘
                  (notion-mcp が
                   APIを翻訳して
                   Claudeに"道具"として渡す)

つまりMCPサーバは「Claude語 ⇄ 各サービスAPI」の通訳。
道具(tool)・資源(resource)・プロンプトの3種類を提供する。
📘 3つの transport: stdio（ローカルプロセス）／http（リモート、推奨）／sse（旧式・非推奨）。クラウドサービスは大半が http。 
# 例1: GitHub MCP をプロジェクトに追加
claude mcp add --scope project --transport http github https://api.githubcopilot.com/mcp/

# 例2: ローカルで動く Playwright を追加（ブラウザ操作）
claude mcp add playwright npx @playwright/mcp@latest

# 例3: 既存サーバ一覧
/mcp                          # セッション内で確認
claude mcp list               # シェルから確認
⚠️ scope に注意: --scope project は .mcp.json がgit管理 → チームで共有。--scope user は個人。--scope local は .claude/settings.local.json でgit除外（個人のAPIキー入りはこれ）。
🚫 絶対NG: .mcp.json や settings.json に APIキーを直書きしてgitコミット。.env や OS のキーチェーンを参照する形にする。間違えてpushしたら即rotation。 
# .mcp.json の例（チーム共有）— トークンは環境変数経由
{
  "mcpServers": {
    "github": {
      "transport": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer ${GITHUB_PAT}"
      }
    }
  }
}
✅ 2026年の改善点: Claude Code は MCP のツール定義を遅延読込み（名前だけ最初に読んで、必要時にスキーマ取得）するので、50+のMCPツールを繋いでもコンテキストを圧迫しない。
07

MCP を実際に使う — Filesystem MCP で安全な範囲操作

上級

初心者が最初に試すなら filesystem MCP がおすすめ。Claude が「アクセスできるディレクトリを限定」して動けるので、誤動作リスクを抑えながら MCP の感触を掴める。 

# 例: ~/Documents/sandbox 配下だけアクセス可能な filesystem MCP
claude mcp add --scope local filesystem -- \
  npx -y @modelcontextprotocol/server-filesystem ~/Documents/sandbox
📘 道具が増えた瞬間: /mcp で確認すると mcp__filesystem__read_file, mcp__filesystem__write_file, mcp__filesystem__list_directory などが見えるはず。これらが Claude の新しい道具。
✗ Before（MCP なし）
# Claudeに頼んでも
> sandbox にメモを保存して
# → Bashで mkdir/echo を駆使する
# → 範囲指定が曖昧で他フォルダ触るリスク
✓ After（filesystem MCP）
# 同じ依頼が
> sandbox にメモを保存して
# → mcp__filesystem__write_file を呼ぶ
# → 設定したディレクトリ外には物理的に書けない
💡 初心者がまず試すと効果が大きい MCP 3選
  • filesystem: 限定ディレクトリのファイル操作。"道具が増える"体感に最適
  • github: Issue/PR 作成、レビューコメント取得。日常作業が劇的に速くなる
  • playwright: ブラウザ自動化。E2Eテストや動作確認の手作業を削減
こう感じたら候補
  • 「同じAPIをcurlで何度も叩いている」 → 専用MCPがある可能性大
  • 「ブラウザで毎回同じ画面遷移を確認している」 → playwright MCP
  • 「Claudeに具体ファイル名でアクセス制限したい」 → filesystem MCP
⚠️ 許可ダイアログが出る: 初回呼び出しで「このMCPツールの使用を許可？」と聞かれる。常に許可するなら /permissions で allowlist 登録、または Lab 09 の Hook で自動承認も可能。
🔍 動作確認
  1. セッション内で /mcp を実行 → filesystem がリストにあるか
  2. 「~/Documents/sandbox に hello.txt を作って中身は今日の日付」と依頼
  3. 許可ダイアログで Allow を選択
  4. エクスプローラまたは ls ~/Documents/sandbox でファイルが実在するか確認
  5. 同じ命令で /etc/passwd を読ませようとすると拒否されることを確認（範囲外）
08

Hooks の概念と最小例 — 編集後に自動 prettier

上級

Hooks は 「Claudeの行動の前後に必ず動くスクリプト」。Claudeが従ってくれない指示も、Hook なら強制実行できる。最初は安全な PostToolUse（編集後の整形）から触るのが鉄則。

🔰 主要な Hook イベント（覚えるのは最初4つで十分）
        ┌──────────────────────────────────────────────┐
        │ SessionStart    起動時に1回（環境変数注入など） │
        └──────────────────────────────────────────────┘
                              ↓
          ┌──────────────────────────────────────────┐
          │ UserPromptSubmit  あなたが発言した直後      │
          └──────────────────────────────────────────┘
                              ↓
            ┌─────────────────────────────────┐
            │ PreToolUse   ツール実行直前(検閲) │
            │              ↓                   │
            │     [ Bash / Edit / Write 等 ]   │
            │              ↓                   │
            │ PostToolUse  ツール実行直後(整形) │  ← まずここから！
            └─────────────────────────────────┘
                              ↓
        ┌──────────────────────────────────────────────┐
        │ Stop / SessionEnd  応答完了 / セッション終了    │
        └──────────────────────────────────────────────┘
🚫 大きな勘違い: Hooks はJavaScript モジュールではない。module.exports を書いても無視される。実体は settings.json 内のJSON設定で、command（シェル実行）／http（HTTP呼出し）／prompt（LLMで判定）の3形態しかない。 
# 最小例: TS/JS ファイル編集後に prettier を強制実行
# 場所: .claude/settings.json (プロジェクト) or ~/.claude/settings.json (個人)
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs -r -I{} sh -c 'case \"{}\" in *.ts|*.tsx|*.js) npx prettier --write \"{}\" ;; esac'"
          }
        ]
      }
    ]
  }
}
📘 仕組み: Claudeが Edit/Write/MultiEdit ツールを使うたびに、その引数JSONが標準入力でhookスクリプトへ流れる。jqでfile_pathを取り出し、TS/JSなら prettier を当てる。Claudeはこの動作を知らずに整形済みコードを見ることになる。
✅ 動作確認方法: わざと崩した形でコード編集を依頼 → 編集後にファイルを開くと整形済み。Claudeに「整形して」と頼んでないのに整形されているのが Hook の効果。
イベント用途matcher 使える?
SessionStart環境変数注入、コンテキスト追加✗
UserPromptSubmitプロンプト検閲、自動コンテキスト追加✗
PreToolUse危険コマンド禁止、入力修正✓ (ツール名)

⚠️ Windows 環境: jq や xargs は標準では入っていない。Git Bash か WSL を使うか、PowerShell で同等処理を書く（$input | ConvertFrom-Json）。最小例は Git Bash 前提。
09

安全策 Hook — 危険コマンドを物理的に止める

上級

PreToolUse で exit 2 を返すと そのツール実行を阻止できる。CLAUDE.md に「rm -rf 禁止」と書いても破られる可能性があるが、Hookなら確実に止まる。これが Hooks の真価。 

# 危険コマンドガード（Bashツール限定）
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.command' | grep -qE 'rm -rf /|DROP TABLE|git push --force' && { echo 'BLOCKED: 危険コマンド' >&2; exit 2; } || exit 0"
          }
        ]
      }
    ]
  }
}
✅ exit code の意味: 0=成功・通過、2=ブロック（stderrがClaudeに返り、ツール実行は中止）、その他=非ブロックエラー（実行は続く）。
📘 JSON で判定する高機能版: permissionDecision: "deny" を返すとClaudeに「拒否された理由」を伝えられ、再試行の質が上がる。 
# JSON出力で理由付き拒否（PreToolUse）
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "本番DBへの直接書き込みは禁止です。マイグレーション経由でお願いします。"
  }
}
💡 すぐ役立つ Hook レシピ4選
  • .env ガード: matcher: "Edit|Write" で .env* 編集を deny
  • git push --force ガード: 上記の rm -rf と同じ要領で grep
  • SessionStart で環境情報注入: 現在ブランチ名・最新コミットを context に追加
  • Stop で test 強制: 完了応答前に npm test を走らせ落ちたら exit 2 で続行させる
こう感じたら Hook の出番
  • 「CLAUDE.md に書いたのに守ってくれない…」 → 強制力が必要
  • 「毎回手で同じ整形コマンド打ってる」 → PostToolUse に逃せる
  • 「セッション開始時に毎回同じ context 渡してる」 → SessionStart へ
🚫 Hook 設計の鉄則: 失敗を許容しない処理を書かない。Hookが落ちると Claude のセッション全体が止まる。|| true や timeout 設定で必ず逃げ道を作る。
🔍 動作確認
  1. .claude/settings.json に上記の危険コマンドガードを保存
  2. 新規セッションで「/tmp を rm -rf でクリーンアップして」と依頼
  3. 「BLOCKED: 危険コマンド」のメッセージが返り、Claudeが代替案を提示すれば成功
  4. 普通の ls 等は通ることも確認（誤検出していない）
  5. うまく動かない時は /doctor で hook 構文エラーをチェック

自走チェックリストと習熟ロードマップ

仕上げ

ここまでで4要素を一通り触った。「自走利用」とは 「困った時に自分でドキュメントとコマンドで解決できる」状態のこと。最後に、その状態に達したかをチェックする質問と、次の30日でやるべき実践課題を示す。

🔰 自走できるかチェック（YESが7個以上で合格）
□ Skill が動かない時、まず /skills と SKILL.md の description を疑える
□ Slash Command と Skill の使い分けを 30秒で説明できる
□ MCPサーバを足したら /mcp で道具一覧が増えることを知っている
□ Hook イベント名を最低3つ言える(PreToolUse/PostToolUse/SessionStart)
□ APIキーは settings.json に直書きしてはいけないと分かっている
□ /doctor で問題の8割は当たりがつくと知っている
□ CLAUDE.md は短く保つべき理由（毎ターン読まれる）が分かる
□ 困った時に公式 docs (code.claude.com/docs) を最初に開ける
□ exit code 2 が「ブロック」を意味すると即答できる
□ MCPの transport 種類(http/stdio)を区別できる
✅ 30日ロードマップ（推奨）: 1週目=Skills 3つ作る／2週目=Slash Commands 5つ作る／3週目=MCP 1〜2個接続（filesystem→github）／4週目=Hooks（PostToolUse の整形だけでOK）。一気に全部やらない。
困りごと最初に試すこと
Skill が発動しない/skills 一覧確認 → description にキーワード追加
Slash Command が見えない/help 確認 → ファイル名と / 名が一致してるか
MCP ツールが見えない/mcp 確認 → APIキー設定 → サーバ再起動
Hook が動いてない/doctor → settings.json の構文 → exit code
権限ダイアログが多すぎる/permissions で allowlist 追加 or /less-permission-prompts
セッションが重い/context で消費確認 → /compact で圧縮 or /clear
💡 自分の作業に適用するための問いかけ
  • 「いつも同じ説明を打っている」 → CLAUDE.md か Slash Command に固める
  • 「特定の話題が出ると毎回同じ手順を踏む」 → Skill にする
  • 「外部サービスを毎回 curl で叩いている」 → MCP サーバを探す（npm search mcp-server）
  • 「守って欲しいルールが守られない」 → CLAUDE.md でダメなら Hook で強制
  • 「セッション開始時に毎回同じ前提を渡している」 → SessionStart Hook
次の一歩のサイン
  • 同じプロンプトを3回書いた → Slash Command 化のタイミング
  • 2回 CLAUDE.md のルールが破られた → Hook 化のタイミング
  • 「もっと早く知りたかった」と思った機能 → 同僚に共有
📘 困った時の公式リソース: code.claude.com/docs（公式）／/help（コマンド一覧）／/doctor（自己診断）／--debug フラグ（API呼出ログ）。この4つで大半は解決する。
