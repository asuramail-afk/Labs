00

AI-DLCとは何か

基本

AI-DLC（AI-Driven Development Lifecycle）は2025年にAWSが提唱した、AIを「中心的な共同作業者」として組み込んだソフトウェア開発手法。従来の「AIアシスト」（補完・テスト生成だけ手伝わせる）でも「AI完全自律」（丸投げ）でもなく、AIが計画と実装を駆動し、人間が判断と検証を担うという第3の道を提示する。

🔰 既存手法との違い（一目で）
┌─────────────────┬──────────────────────────────────┐
│ AI-assisted     │ 人間が主役。AIは補完・テスト生成だけ手伝う      │
│ AI-autonomous   │ AIに丸投げ。品質・意図ズレが多発               │
│ AI-DLC          │ AIが計画→実装、人間が要所で検証・判断          │
│                 │   ↑「Velocity（速度）+ Quality（品質）」両立    │
└─────────────────┴──────────────────────────────────┘
従来 SDLC（Agile/Scrum）AI-DLC
イテレーション = 数週間（Sprint）イテレーション = 数時間〜数日（Bolt）
要件→設計→実装→テストの段階的ハンドオフIntentから連続フローでAIが駆動
人間が会議・ドキュメントに大量の時間AIが叩き台を生成、人間は判断ポイントだけ集中
ドキュメントは後付けになりがち各フェーズが構造化された成果物を残す（監査可能）
📘 提唱元・現状: AWSのDevOpsブログで2025年7月に最初に公開され、Amazon Q DeveloperやKiroが参照実装。GitHubにはTheBushidoCollective/ai-dlcなどClaude Code向けプラグインも登場している。本Labでは Claude Code で個人開発者が一人で実践する方法を扱う（チームのMob Workは概念だけ理解）。
⚠️ 初心者がハマる誤解: AI-DLCは「魔法のプロンプト集」ではない。判断ポイントを構造化して、Markdownでファイルに残すという地味な営みが本質。慣れるまでは「AIに考えさせて、自分で読んで承認する」というリズムを身につけることが目標。
01

5つの中核概念を押さえる

基本

AI-DLCの語彙はやや独特。最初に Intent / Unit / Bolt / Hat / Mob の5つを押さえると、以降のフェーズ説明がスッと入る。「なぜ→何を→どう作る→誰の視点で→どこで合意」の5層と覚える。

🔰 5つの関係を1枚図で
┌─────────────────────────────────────────────────┐
│  Intent   「なぜ作る？」 = 1つの北極星（プロジェクトの目的）│
│    │                                                       │
│    ├─→ Unit A 「何を作る？」 機能の塊（疎結合な単位）       │
│    │     └─→ Bolt 1 「どう作る？」 数時間の実装サイクル    │
│    │     └─→ Bolt 2                                        │
│    ├─→ Unit B                                             │
│    │     └─→ Bolt 1                                        │
│    └─→ Unit C ...                                          │
│                                                           │
│  Hat   「誰の視点？」 = AIが切替える役割（設計者/実装者/レビュアー）│
│  Mob   「どこで合意？」 = 関係者が同席して即決するセッション│
└─────────────────────────────────────────────────┘
用語意味具体例（イベント管理アプリの場合）
Intentビジネス目的・北極星。プロジェクト全体で1つ「主催者が安全にチケット販売・入場管理できるアプリを作る」
Unit独立して価値を生む機能の塊。疎結合・高凝集「Unit A: チケット販売」「Unit B: 入場検証」「Unit C: 残席管理」
Bolt数時間〜数日の最小実行ループ。1つのUnit内で複数回す「Bolt 1: QRコード検証実装」「Bolt 2: オフライン対応」
HatAIが被る役割帽子。Elaborator / Builder / Reviewer など同じClaude Codeセッションが、要件整理→実装→レビューと役割を切替える
Mob関係者が同席して即決する儀式。Mob Elaboration / Mob Construction個人開発では「自分1人 + AI」で疑似Mob。判断ログを必ず残す
✅ 覚え方のコツ: Intent は名詞1文、Unit は3〜7個、Bolt は半日サイズ。これを破ると粒度がブレて判断ログが膨大になる。慣れないうちは「Intent 1個・Unit 3個・各Unit に Bolt 2〜3個」で十分。
02

3フェーズの全体像

基本

AI-DLCは Inception → Construction → Operations の3フェーズで進む。各フェーズで生まれた成果物（Markdown）が次フェーズのContext（文脈）として連鎖し、AIの判断精度を高める。これが「Sequential Knowledge Handoff（順次知識引き渡し）」と呼ばれる仕組み。

🔰 3フェーズと成果物の流れ
┌──────────── Inception（着想） ────────────┐
│ AIが Intent を要件・ストーリー・Unit に展開     │
│ 成果物: intent.md / user-stories/ / units/    │
│ 儀式: Mob Elaboration（要件定義の集中議論）   │
└────────────────────┬────────────────┘
                     │ Context handoff
                     ▼
┌──────────── Construction（建設） ──────────┐
│ Unit ごとに Bolt を回して設計→コード→テスト    │
│ 成果物: domain-design.md / code / tests       │
│ 儀式: Mob Construction（実装中の即時相談）    │
└────────────────────┬────────────────┘
                     │ Context handoff
                     ▼
┌──────────── Operations（運用） ────────────┐
│ デプロイ・監視・振り返り。次のIntentに学びを蓄積 │
│ 成果物: deployment.md / runbook.md /          │
│         reflection.md                         │
└────────────────────────────────────┘
フェーズAI の役割あなたの役割主な成果物
InceptionIntentから要件・Unitを提案／質問曖昧さの解消・優先順位の決定intent.md, units/*.md
Construction設計提案→コード生成→テスト設計判断の承認・コードレビューdesign.md, src/, tests/
Operationsデプロイ手順・監視提案・振り返り環境固有の判断・本番承認runbook.md, reflection.md
📘 Adaptive Workflow（適応的ワークフロー）: 全フェーズを毎回フルでやる必要はない。「タイポ修正」ならInceptionをスキップして直接Boltへ、「インフラ移行」ならドメイン設計をスキップ、というようにタスクの規模・性質で省略可。AWSが2025年11月に公開したオープンソース版（Amazon Q Rules / Kiro Steering Files）はこの判断を自動化する。
⚠️ 初心者は省略しないで: 慣れるまでは小さい題材でフルフェーズを通すこと。省略の判断は数回回した後でないと「何を省いているか」が分からず、結局やり直しになる。
03

Claude Code 環境セットアップ

準備

AI-DLCを実践する最小環境を構築する。Claude Code はターミナルから動くAIエージェントで、ファイル操作・コマンド実行・Git操作までできる。AI-DLCの「成果物をMarkdownで残す→AIに読ませて次のフェーズへ」という流れと相性が良い。

📘 前提: Node.js 18以上、Anthropicアカウント、Git。既存の業務開発環境（Windows/Mac問わず）でOK。本Labではプラグイン無しの素のClaude Codeで進める（プラグインは慣れた後で）。
① Claude Code インストール
# npmでグローバルインストール
npm install -g @anthropic-ai/claude-code

# 動作確認
claude --version

# 初回起動（ブラウザでログイン認証が走る）
claude
② AI-DLC用プロジェクト作成
# 練習用ディレクトリを作る（場所はどこでもOK）
mkdir my-ai-dlc-practice
cd my-ai-dlc-practice

# Git初期化（成果物を版管理）
git init

# AI-DLC用のディレクトリ構造を準備
mkdir -p aidlc-docs/{intent,units,design,reflection}
touch aidlc-docs/intent/intent.md
touch CLAUDE.md

# Claude Codeを起動
claude
✅ CLAUDE.md の役割: プロジェクトルートに置くと、Claude Codeが起動時に自動で読む。ここに「このプロジェクトはAI-DLC方式で進める」と書いておくと、毎回プロンプトで指示しなくて済む。次のラボで中身を書く。
⚠️ 権限に注意: Claude Code は --dangerously-skip-permissions フラグや Shift+Tab の Auto-Accept モードがあるが、AI-DLC初学者は使わないこと。各操作で「これをやってよいか？」とAIが確認してくる動作こそAI-DLCの「人間検証ゲート」を体感する機会になる。
🔍 セットアップ確認
  1. claude --version でバージョンが出るか
  2. プロジェクトディレクトリで claude を起動し、"このプロジェクトの構造を見せて" と聞いて aidlc-docs/ 配下が認識されるか
  3. Ctrl+C か /exit で終了できるか
04

プロジェクト構造を作る

準備

AI-DLCの本質は「Markdownで判断ログを残す」ことなので、最初にディレクトリ構造とCLAUDE.mdを整える。これがAIにとっての「メモリ」になり、Claude Codeのセッションをまたいでも文脈が引き継がれる。

🔰 標準ディレクトリ構造
my-ai-dlc-practice/
├── CLAUDE.md                    ← AI向けのプロジェクト方針（必須）
├── aidlc-docs/                  ← AI-DLCの成果物すべて
│   ├── intent/
│   │   └── intent.md            ← Lab05で書く
│   ├── units/
│   │   ├── unit-01-xxx.md       ← Lab07で生成
│   │   └── unit-02-xxx.md
│   ├── design/
│   │   └── domain-design.md     ← Lab08で生成
│   ├── bolts/
│   │   └── bolt-log.md          ← 各Boltの記録
│   └── reflection/
│       └── reflection.md        ← Lab10で振り返り
├── src/                         ← 実装コード
├── tests/                       ← テスト
└── .gitignore
CLAUDE.md の中身（プロジェクト方針）
# プロジェクト方針

このプロジェクトは AI-DLC（AI-Driven Development Lifecycle）方式で進めます。

## ルール

1. すべての判断は aidlc-docs/ 配下のMarkdownに記録する
2. 実装の前に Intent → Unit → Bolt の順で計画を確定する
3. 各Boltの開始時に「何を作るか／成功条件／触るファイル」を提示し、私の承認を待つ
4. コード生成後は Reviewer の視点で自己レビューし、問題点を列挙する
5. 不明点・曖昧な要件は実装前に必ず質問する（勝手に解釈して実装しない）

## 成果物の置き場所

- Intent定義: aidlc-docs/intent/intent.md
- Unit分解:   aidlc-docs/units/unit-NN-name.md
- 設計:       aidlc-docs/design/
- Bolt記録:   aidlc-docs/bolts/bolt-log.md
- 振り返り:   aidlc-docs/reflection/reflection.md

## 私について

- AI-DLC初心者です。各フェーズで何をしているか短く説明してから進めてください
- 専門用語は初出時に1行で意味を添えてください
📘 なぜCLAUDE.mdが効くか: Claude Codeは起動時にプロジェクト直下のCLAUDE.mdをシステムプロンプトの一部として読み込む。毎回「AI-DLCで進めて」と書く必要がなくなり、AIが勝手にコードを書き始める事故も防げる。React的に言えば、これは「Context Provider」でセッション全体を包むイメージ。
💻 試し方
  1. 上のCLAUDE.mdをコピーしてプロジェクトルートに保存
  2. ターミナルで claude を起動
  3. 「このプロジェクトのルールを3行で要約して」と聞く
  4. AI-DLC・Markdown記録・承認待ちの3点が出てくれば成功
💡 コツ: CLAUDE.mdは育てるもの。Lab10の振り返りで気づいた追加ルールをここに書き足していくとAIの挙動が安定する。
🔍 構造の確認
  1. ルートで ls -la または dir し、CLAUDE.mdとaidlc-docs/が見えるか
  2. Claude Codeで「aidlc-docsの中を見せて」と聞き、空ファイルが認識されるか
  3. 「このプロジェクトはどんな進め方をする？」と聞き、AI-DLCの3フェーズに言及するか
05

Intentを書く（Inception開始）

Inception

Inceptionフェーズの最初の一歩は Intent を書くこと。Intentは「なぜ作るのか」の1文+背景。これがブレるとUnit分解もBoltも全部ブレるので、ここに時間をかける価値がある。

📘 良いIntentの条件: ① 主語（誰のため）② 動詞（何ができるように）③ 価値（なぜ嬉しい）が含まれる。技術用語は出さない（「Reactで」「DBは…」はUnitやDesignの話）。
aidlc-docs/intent/intent.md（テンプレ）
# Intent

## 一文で（北極星）

<誰> が <何> できるように <価値> を提供する。

## 背景

- 現状の課題:
- なぜ今やるか:
- やらないと困ること:

## 成功の定義（Done の判定基準）

- [ ] 計測可能な指標 1
- [ ] 計測可能な指標 2

## スコープ外（やらないこと）

- 〇〇は今回の対象外
- △△は将来検討

## 制約

- 期限:
- 環境:
- 既存システムとの関係:
記入例（Markdownメモアプリ）
# Intent

## 一文で

ひとり開発者が、ブラウザだけでMarkdownメモを書いて即時にローカル保存できる、
ログイン不要の最小限メモアプリを作る。

## 背景

- 現状: 思いついたメモをスマホとPCで同期するのに何個もアプリを使い分けている
- なぜ今やるか: AI-DLC学習の練習題材として、自分が毎日使うものを作るのが一番モチベが続く
- やらないと困ること: 練習が抽象的なまま終わり、業務に活かせない

## 成功の定義

- [ ] ブラウザでURLを開いた瞬間にメモ入力できる
- [ ] リロードしてもメモが消えない
- [ ] 自分が3日連続で使う

## スコープ外

- マルチユーザ・ログイン機能
- クラウド同期
- リッチエディタ（プレーンMarkdownのみ）

## 制約

- 期限: 1週間（夜の自由時間のみ）
- 環境: 静的HTML+JS、サーバなし
- 既存システム: なし（新規）
⚠️ よくある失敗: Intentに「Reactで作る」「IndexedDBで保存する」と書いてしまう。これはUnitや設計のレベル。Intentに技術が混じると、AIが「なぜそれを選ぶか」を考えずにそのまま実装に走る。技術選定はLab07以降で。
💻 一人Mob Elaboration の最初の一歩
  1. テンプレを aidlc-docs/intent/intent.md にコピー
  2. 自分で「一文で」を書いてみる（5〜10分）
  3. Claude Code で「intent.md を読んで、曖昧な点を5つ質問して」と依頼
  4. AIの質問に答えながらintent.mdを書き直していく
  5. 「これでIntentとして十分か、不足があれば指摘して」で確認
💡 コツ: AIの質問に答えるとき、答えはintent.mdに直接書き込むこと。会話だけで合意するとセッションが切れたら消える。「文書に残す」のがAI-DLCの命綱。
🔍 Intent完成の判定
  1. 1ヶ月後の自分が読んで「何のプロジェクトか」が分かるか
  2. 「成功の定義」が計測可能（YES/NOで判定できる）か
  3. 「スコープ外」が3つ以上書けているか（書けないとスコープが膨らむ）
  4. 技術用語が「制約」セクション以外に出ていないか
06

Mob Elaboration を一人で実施

Inception

本来のMob Elaborationは PO・開発者・QA が同席して数時間集中議論する儀式。個人開発では 「自分（あらゆる役割）+ AI」 で疑似Mobをやる。鍵は役割を明示的に切替えること。AIにHat（帽子）を被せる。

🔰 一人Mobの進め方
あなた                    AI（Hat切替）
  │                          │
  ├─「PO目線で要件レビューして」→ Hat: Product Owner
  │       ←質問・抜け漏れ指摘─┤
  │                          │
  ├─「QA目線でテスト観点を出して」→ Hat: QA Engineer
  │       ←テストケース提案 ─┤
  │                          │
  ├─「セキュリティ目線で見て」→ Hat: Security Reviewer
  │       ←リスク指摘    ─┤
  │                          │
  └→ 議事録を intent.md と    ←
     elaboration-log.md に追記
Mob Elaboration プロンプト例
# Claude Code に貼り付ける指示

これから Mob Elaboration をします。あなたに3つの役割を順番に演じてもらいます。

Step 1: Product Owner として
  intent.md を読み、ユーザの実利用シーンを3つ列挙し、
  「これは本当に必要？」「優先度は？」を質問してください。

Step 2: QA Engineer として
  受入基準（Acceptance Criteria）を Given-When-Then 形式で5個書いてください。
  境界値・異常系も含めること。

Step 3: Security Reviewer として
  このIntentに潜むセキュリティ・プライバシーのリスクを3つ挙げ、
  対策の方向性を1行ずつ書いてください。

各Stepの結果を aidlc-docs/intent/elaboration-log.md に追記してください。
私の確認なく次のStepには進まないでください。
Hat（役割）視点主に出すもの
Product Ownerユーザ価値・優先度ユーザストーリー、優先順位、削れる機能
QA Engineer検証可能性受入基準、テストケース、境界値
Security Reviewerリスク脅威モデル、データ保護、認可
Architect非機能要件性能・拡張性・運用要件
Developer実装可能性技術選定の選択肢、見積もり
✅ Hat切替の威力: 同じClaude Codeセッションでも、明示的に役割を変えるとAIの出力が劇的に変わる。POを被ると「ユーザは…」、QAを被ると「もしXが空だったら…」と自然に視点が動く。これは LLMの役割プロンプティングを構造化したもの。
⚠️ 5役全部やる必要はない: 練習の最初は PO + QA の2役だけで十分。役を増やすほど時間がかかり、初心者は判断ログを書ききれず疲弊する。
🔍 Elaboration終了の判定
  1. elaboration-log.md に各Hatの出力が時系列で残っているか
  2. 受入基準が5個以上、Given-When-Then形式で書けているか
  3. Intent修正があれば intent.md に反映済みか
  4. 「次に何を作るか（Unit候補）」が3〜7個書き出せているか
07

Unitに分解する

Inception

Intent から Unit へ分解する。Unitは「独立して価値を生む機能の塊」で、疎結合・高凝集が原則。Unitの粒度を間違えると、Boltで詰まったり並行作業できなかったりする。

📘 良いUnitの3条件: ① 単独でリリースしても何かしらの価値が出る ② 他のUnitに強く依存しない（依存があるなら明示） ③ 1人で1〜3日で終わるサイズ。3日超えるなら2つに割る。
Unit分解 プロンプト例
# Claude Code に貼り付ける指示

intent.md と elaboration-log.md を読み、このプロジェクトを Unit に分解してください。

要件:
1. Unit は 3〜5個（多すぎたら統合、少なすぎたら分割を提案）
2. 各 Unit は疎結合・高凝集を守る
3. Unit 間に依存がある場合は明示（DAG形式で）
4. 各Unitを aidlc-docs/units/unit-NN-name.md として作成

各 Unit ファイルには以下を含めてください:
- 目的（Intentのどこに貢献するか）
- 受入基準（Acceptance Criteria）
- 依存する他のUnit（あれば）
- 推定Bolt数と各Boltの仮タイトル
- 触る予定のファイル/ディレクトリ

最後に aidlc-docs/units/README.md に
全Unitの一覧と依存グラフ（テキストで）を作ってください。

実装はまだ始めないでください。Unit構成案を私が承認してから次に進みます。
🔰 Unit DAG（依存グラフ）の例
Markdownメモアプリの場合:

  unit-01-editor       （Markdownエディタ部品）
       │
       ├─→ unit-02-storage   （LocalStorage保存）
       │        │
       │        └─→ unit-04-export  （JSONエクスポート）
       │
       └─→ unit-03-list-view （メモ一覧UI）
                │
                └─→ unit-04-export

順序: 01 → 02,03 並行 → 04
独立して動かせる: 01単体（保存なしでも編集はできる）
判定このUnit分解は…
✓ 良い「unit-02-storage を作らずに unit-01-editor だけリリースしても、編集体験というデモはできる」
✗ 悪い「unit-01-frontend と unit-02-backend」みたいに技術レイヤーで切る（疎結合に見えて実は密結合）
✗ 悪い「unit-01-全機能MVP」のように大きすぎる（5日以上かかるならもっと割る）
✗ 悪い「unit-01-設定画面の保存ボタン」のように小さすぎる（これはBolt粒度）
💡 なぜUnit分解にこだわるか
  • Boltでの実装中、AIが触るスコープが明確になり余計なファイルを巻き込まない
  • 「ここで詰まったら他のUnitに進める」という退避ルートができる
  • Operations での障害切り分けが楽（このUnitだけロールバックなど）
  • 後で他人に渡すとき、Unit境界が引き継ぎ単位になる
🔍 Unit分解の判定
  1. 各Unitが「何を作るか」を1文で言えるか
  2. 依存グラフに循環依存がないか（A→B→Aは禁止）
  3. 1つのUnitだけ実装した状態で、何かしらの動くデモになるか
  4. Unitの数が3〜7個に収まっているか
08

Boltを回して実装する

Construction

ここからConstructionフェーズ。UnitをBoltに細分化して回す。1Boltは数時間〜半日のサイクルで、「計画→実装→セルフレビュー→人間承認→次へ」という4ステップを毎回踏む。これがAI-DLCの心臓部。

🔰 1 Bolt の流れ（4ステップ）
┌─ Step 1: Plan ────────────────────────┐
│ AI: 「このBoltで何を作る／触るファイル／成功条件」をMD化 │
│ あなた: 内容を読んで承認 or 修正指示                   │
└────────────────┬────────────────┘
                 ▼
┌─ Step 2: Build ───────────────────────┐
│ AI: 計画に従ってコード生成・テスト記述                │
│ あなた: 必要なら横で見守る                            │
└────────────────┬────────────────┘
                 ▼
┌─ Step 3: Self-Review ────────────────┐
│ AI: Reviewer Hatに切替えて自己レビュー、問題点を列挙  │
│ あなた: 指摘の妥当性を確認                            │
└────────────────┬────────────────┘
                 ▼
┌─ Step 4: Human Gate ─────────────────┐
│ あなた: コードを実機で動かして検証、Bolt記録に追記    │
│        OK→コミット、NG→Step 1に戻る                  │
└────────────────────────────────┘
Bolt開始 プロンプト例
# Claude Code に貼り付ける指示

これから unit-01-editor の Bolt 1 を実行します。

Step 1: Plan
unit-01-editor.md を読み、Bolt 1 として「最小のMarkdownエディタ部品を1ファイルで作る」
スコープに絞って、以下を aidlc-docs/bolts/bolt-log.md に追記してください:

- このBoltのゴール（1文）
- 触るファイル（新規 or 既存、フルパス）
- 触らないファイル（明示）
- 成功条件（実機で何が起きればOKか）
- 想定される失敗ケースと対処
- 推定時間

書き終わったら私の承認を待ってください。
私がOKと言うまで実装には入らないでください。
承認後の指示
承認します。Step 2: Build に進んでください。

実装後、Step 3: Self-Review として Reviewer Hat に切替え、
以下の観点で自己レビューし、bolt-log.md に追記してください:

- 計画通りに作れているか
- 触らないと宣言したファイルを触っていないか
- エッジケース・異常系の扱い
- 見落としている点・将来の負債候補

コミットはまだしないでください。私が実機確認した後、コミットメッセージを提案してください。
📘 「触らないファイル」を明示する理由: AIは指示を超えて「ついでに直す」傾向がある。これがUnit境界を崩す原因No.1。Bolt計画に「触らない」と書かせると、誤って手を出したときセルフレビューで気づける。
⚠️ 承認を惰性化しない: 「OK」と言うのは数秒で済むが、計画を読まずに承認すると、AIが間違った方向に全力で走り、戻すコストが大きくなる。計画MDを必ず一読。これがAI-DLCで最も価値のある時間。
🚨 初心者がやりがちな破綻パターン: 「全部いっぺんにやって」と言ってしまうこと。Unit丸ごと、複数Unitを並行、などをBolt無視でやらせると、AIは動くが、出力が大きすぎてレビュー不能になり、結局やり直し。1 Bolt = 1ファイル or 1機能を守る。
💻 はじめてのBoltを回す
  1. 上の「Bolt開始」プロンプトをコピー
  2. Claude Codeに貼り付けて、Plan出力を待つ
  3. bolt-log.mdを開いて計画を読む（30秒）
  4. 違和感があれば「触るファイルが多すぎ。〇〇だけにして」など修正指示
  5. OKなら「承認します。Build に進んで」と返す
  6. 実装完了後、自分でファイルを開いて目視レビュー
  7. ブラウザ等で動作確認、bolt-log.mdに「実機確認OK／NG」を追記
  8. OKならgit commit、NGなら原因をAIに伝えて再Bolt
💡 コツ: Boltが終わるたびにgit commitする。後で「あのBoltに戻したい」が一発でできる。コミットメッセージはAIに「Bolt N: 〇〇」形式で提案させる。
🔍 Bolt完了の判定
  1. 計画MDの「成功条件」が実機で満たされているか
  2. 「触らない」と書いたファイルが本当に変更されていないか（git diffで確認）
  3. セルフレビューで指摘された点に対処済み（または「次Boltで対処」と明示）か
  4. bolt-log.mdに完了時刻と所感が追記されているか
09

レビューと反復ループ

Construction

Boltを回し続けると必ず「想定外」が出る。これをどう吸収するかが品質を分ける。AI-DLCには Reviewer Hat による自己レビューと、失敗をUnit/Intentに反映する仕組みがある。

🔰 失敗を吸収する3つのレベル
レベル1: Bolt内で吸収
  └ 実装ミス・テスト失敗 → 同じBoltで再実装

レベル2: Unitを分割/統合
  └ Bolt 3つ予定だったが5つ必要だと分かった
    → unit-XX-name.md の Bolt一覧を更新、新Boltを追加

レベル3: Intentを修正
  └ そもそも要件が間違っていた／優先度が違った
    → intent.md を修正、影響を受けるUnitを再検討
    → これが「Reflection（振り返り）」の入り口
Reviewer Hatでの厳しめレビュー指示
# 直前のBolt成果物に対して

Reviewer Hatに切替えてください。
甘めではなく、コードレビュー経験10年のシニアエンジニア視点で、以下を確認:

1. 機能的正しさ: 受入基準を満たすか、エッジケースは？
2. コード品質: 命名・関数長・重複・可読性
3. セキュリティ: XSS/インジェクション/権限ミス
4. テスト: 不足しているケース、テストの偽陽性
5. 将来の負債: いま手を打っておくべき設計上の地雷

各観点で「Critical / Major / Minor」のラベル付き指摘を最低5つ出してください。
指摘ゼロは禁止です（必ず何か見つける）。

結果は aidlc-docs/bolts/bolt-log.md の該当Boltセクションに追記。
✅ 「指摘ゼロ禁止」の効果: AIは褒め役になりがち。明示的に「最低5つ」「Critical/Major/Minor」と指定すると、本気でアラを探す。実際にやってみると、自分のコードでも自分のAIが書いたコードでも、必ず何か見つかる。
指摘ラベル対応方針
CriticalこのBolt中に修正。修正前にコミットしない
Major次Boltまでに修正。Unit受入基準に追加
Minorreflection.md に「技術負債リスト」として記録、後で扱う
⚠️ 反復の罠: 「あと少し」でAIに直させ続けると無限ループに陥る。2回直して直らないなら、そのBoltは一度コミットして次に進む。技術負債としてreflection.mdに記録すれば、後で別Boltとして対処できる。完璧を狙うとAI-DLCの速度メリットが死ぬ。
🔍 反復ループの健全性
  1. Bolt再実行が3回を超えたUnitがないか（あれば設計を疑う）
  2. Critical指摘が放置されていないか
  3. Unit境界を崩す変更（他Unitのファイルを触る）が混入していないか
  4. bolt-log.md が時系列で読める形になっているか（後の振り返りで使う）
10

Operations と Reflection

Operations

全Unitが完成したらOperationsフェーズへ。デプロイ・運用の観点と、最も重要なReflection（振り返り）を行う。Reflectionは次のIntentを賢くするための燃料で、AI-DLCを継続的に効くものにする鍵。

🔰 Operations で押さえる4点
1. Deploy:    どこで動かす？手順は？ロールバックは？
2. Observe:   何を見れば壊れたと分かる？ログ・指標
3. Maintain:  誰が直す？どこに依頼が来る？
4. Reflect:   今回の学びを次に活かすため何を残す？
              ↑ これがAI-DLCの差別化ポイント
Operations プロンプト例（小規模個人プロジェクト）
# Claude Code に貼り付ける指示

Operationsフェーズに入ります。intent.md と全Unitを踏まえ、以下を作成:

1. aidlc-docs/operations/runbook.md
   - デプロイ手順（コマンド単位）
   - ロールバック手順
   - 動作確認チェックリスト

2. aidlc-docs/operations/observability.md
   - 「壊れた」を判定する観点（エラーログ・UI崩れ・データ消失）
   - 自分が手動で確認するチェック頻度

個人開発・サーバなしのプロジェクトなので、過剰なツール導入はしない。
シンプルで継続できる運用にすること。
Reflection プロンプト例（最重要）
# Claude Code に貼り付ける指示

このプロジェクトの Reflection を行います。
全 bolt-log.md と elaboration-log.md を読み、以下を aidlc-docs/reflection/reflection.md に書いてください:

## 1. 数値で振り返る
- 総Bolt数、再実行が必要だったBolt
- Intent修正の回数とタイミング
- Unit分割/統合があったか

## 2. 良かったこと（次も続ける）
- 効果が高かったプロンプトパターン
- スムーズに進んだフェーズ

## 3. ハマったこと（次は避ける）
- 想定外だった点
- 計画と実装のズレが出た原因

## 4. CLAUDE.md に追加すべきルール
- 今回の経験から、次プロジェクトの CLAUDE.md に書くべき新ルールを3つ提案

## 5. 技術負債リスト
- 今回意図的に先送りにした項目
- 次プロジェクトの最初の Bolt 候補
✅ Reflectionが本当に効くタイミング: 次プロジェクトを始める時、新しい CLAUDE.md を作る前に前プロジェクトのreflection.mdを読み返す。「ハマったこと」と「追加すべきルール」が次の防御策になる。これを3〜5プロジェクト続けると、自分専用のAI-DLCスタイルが固まる。
💡 Reflectionで気づきやすいパターン
  • 「Bolt粒度が大きすぎた」→ 次は半分のサイズで切る
  • 「IntentとUnitの間にギャップ」→ Mob Elaborationの時間を増やす
  • 「特定のHat（例: Security）を呼び忘れた」→ CLAUDE.mdに必須Hatリストを追加
  • 「同じ質問を何度もAIにした」→ FAQをCLAUDE.mdに転記
🔍 Operations完了の判定
  1. runbook.mdを読んで1ヶ月後の自分がデプロイできるか
  2. reflection.md の「次プロジェクトのCLAUDE.md追加ルール」が3つ書けたか
  3. 技術負債リストが「Lab07のUnit分解」のようなBolt候補にできる粒度か
  4. Intent.mdの「成功の定義」が実際に達成されたか確認したか
