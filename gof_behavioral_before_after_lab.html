Chain of Responsibility — 巨大if文をハンドラの数珠つなぎに

フロー制御

HTTPリクエストの認証→ログ→レート制限→本処理のような多段処理が 1つの巨大関数に詰め込まれていると、項目追加・順序変更・テストのたびに本体が壊れる。 各処理を独立ハンドラにして連鎖させると、追加は新クラス1個、順序変更はリストの並び替えで済む。

✗ Before — 巨大関数で全部書く
// 認証/ログ/レート制限が1関数に同居
function handle(req) {
  // 1) 認証
  if (!req.token) return "401";
  if (!verify(req.token)) return "401";

  // 2) レート制限
  if (counter[req.ip] > 100) return "429";
  counter[req.ip]++;

  // 3) ログ出力
  console.log("[req]", req.path);

  // 4) 本処理
  return process(req);
}
// → 「ログだけ外したい」「順序を変えたい」
//   のたびに本体を切り貼り。テスト分離も困難。
✓ After — ハンドラの連鎖
abstract class Handler {
  protected next?: Handler;
  setNext(h: Handler) { this.next = h; return h; }
  handle(req): string | null {
    return this.next?.handle(req) ?? null;
  }
}
class Auth extends Handler {
  handle(req) {
    if (!req.token) return "401";
    return super.handle(req);
  }
}
class RateLimit extends Handler { /* 同様 */ }
class Log       extends Handler { /* 同様 */ }

// 組み立てだけで順序自由
const chain = new Auth();
chain.setNext(new RateLimit())
     .setNext(new Log());
▶ 何が変わったか（効果）
  • 追加コスト: 新ステップ＝新クラス1つだけ。本体ゼロ修正
  • 順序変更: setNext()のつなぎ替えのみ。コード本体は無傷
  • 単体テスト容易: 各ハンドラを単独でhandle()できる
  • 条件分岐の所在: 「自分で処理 vs 次へ流す」が各クラスに自閉。横の知識不要
🔰 図で見る連鎖
  リクエスト
     │
     ▼
  ┌──────┐ token無? ┌──────────┐ 100超? ┌──────┐
  │ Auth │─────────▶│RateLimit │───────▶│ Log  │──▶ 本処理
  └──────┘ 401で終了 └──────────┘ 429終了 └──────┘
     ↑ どこか1つでも止めればチェーン終了
     ↑ 各クラスは自分の責務だけ知っていればよい
📘 典型例: Express/Koa/ASP.NET Core のミドルウェアはこの形そのもの。 app.use(auth).use(rateLimit).use(log) と並べる発想は Chain of Responsibility の応用。

Command — 操作を「データ」にしてUndo・キュー・ログを後付け

フロー制御

関数呼び出しはその場で消費される。Undoしたい・キューに溜めたい・別マシンに送りたいときに困る。 操作を execute()＋undo() のオブジェクトに変換すると、操作自体を配列に積む・直列化する・逆順に走らせることが可能になる。

✗ Before — 直接呼び出し
class Editor {
  text = "";
  type(s) { this.text += s; }
  delete(n) { this.text =
    this.text.slice(0, -n); }
}

const ed = new Editor();
ed.type("Hi");
ed.type(" Tom");
ed.delete(4);

// Undoしたい？ → 履歴をどう持つ？
// type/delete を文字列で覚える？
// 引数も覚える？ 逆操作は誰が知る？
// → 自前で全部設計する羽目に
✓ After — 操作をオブジェクト化
interface Command {
  execute(): void;
  undo():    void;
}
class TypeCmd implements Command {
  constructor(private ed, private s) {}
  execute() { this.ed.type(this.s); }
  undo()    { this.ed.delete(this.s.length); }
}

const history: Command[] = [];
function run(cmd) {
  cmd.execute(); history.push(cmd);
}
run(new TypeCmd(ed, "Hi"));
run(new TypeCmd(ed, " Tom"));
history.pop().undo(); // 巻き戻し
▶ 何が変わったか（効果）
  • Undo/Redo: 履歴スタックにpush/popするだけで実現
  • 遅延実行: queue.push(cmd)で後回し・別プロセス送信が可能
  • JSON化: コマンド名と引数だけ持つので直列化できる→DB保存・ジョブキュー
  • マクロ: コマンド配列をまとめてexecute()すれば一括操作
📘 典型例: BullMQ/Sidekiq/Celery のジョブはまさにCommand。 テキストエディタのUndo、OutSystemsのBPTアクティビティ、トランザクションの補償処理も同じ発想。

Template Method — 流れは親、可変部分だけ子で穴埋め

フロー制御

CSV/JSON/XMLそれぞれの処理クラスが同じフロー（読込→変換→保存）を毎回コピペしていると、 バグ修正の漏れ・流れの微妙なズレが必ず発生する。 流れを親で1度だけ書き、可変部分のメソッドを抽象化して子に埋めさせる。

✗ Before — 各クラスが流れもコピペ
class CSVProcessor {
  process() {
    const data = this.read();
    const result = this.transform(data);
    this.save(result);
  }
  read() { return "a,b,c"; }
  transform(d) { return d.toUpperCase(); }
  save(d) { console.log("保存:", d); }
}

class JSONProcessor {
  process() {
    const data = this.read();   // ← 同じ
    const result = this.transform(data);
    this.save(result);          // ← 同じ
  }
  // → 流れにバグがあると2箇所直す
}
✓ After — 流れは親で1回だけ
abstract class DataProcessor {
  process() { // テンプレ — 流れを固定
    const data = this.read();
    const result = this.transform(data);
    this.save(result);
  }
  protected abstract read(): string;
  protected abstract transform(d): string;
  protected save(d) { // 共通実装
    console.log("保存:", d);
  }
}
class CSV extends DataProcessor {
  read() { return "a,b,c"; }
  transform(d) { return d.toUpperCase(); }
}
// 流れの修正は親1箇所だけで全派生に反映
▶ 何が変わったか（効果）
  • 共通フローのバグ修正: 親1箇所→全派生に自動反映
  • 流れの一貫性: 派生クラスが順番を勝手に変えられない（フレームワーク的強制）
  • 新形式の追加: 抽象メソッドを実装するだけ。流れの記述不要
  • 共通処理の集約: save()のような不変部分は親に置き、再利用
⚠️ Strategyとの違い: 同じ「処理を差し替える」だが、 Template Methodは継承（コンパイル時固定）、 Strategyはコンポジション（実行時切替）。 実行時に何度も切り替えたいなら Strategy、流れ自体を派生先に強制したいなら Template Method。

Strategy — if-else 地獄をクラスに分解して実行時に差し替え

アルゴリズム選択

税額計算・決済・ソート・配送料——「同じ目的の複数アルゴリズム」を if (type === ...) で切り替えると、 新方式の追加でメソッド本体に手が入り続け、テストもしにくい。 各アルゴリズムを同じIFを持つクラスにして、利用側に差し込む形に変える。

✗ Before — switch文に固定化
class PriceCalculator {
  calc(price, type) {
    switch (type) {
      case "normal":
        return price;
      case "vip":
        return price * 0.8;
      case "student":
        return price * 0.7;
      case "coupon":
        return price - 500;
      // 新区分追加 → switch を毎回触る
    }
  }
}
calc.calc(1000, "vip"); // 800
✓ After — 各方式を独立クラスに
interface PriceStrategy {
  calc(price: number): number;
}
class Normal  implements PriceStrategy {
  calc(p) { return p; }
}
class Vip     implements PriceStrategy {
  calc(p) { return p * 0.8; }
}
class Student implements PriceStrategy {
  calc(p) { return p * 0.7; }
}

class Calculator {
  constructor(private s: PriceStrategy) {}
  setStrategy(s) { this.s = s; }
  calc(p) { return this.s.calc(p); }
}
const c = new Calculator(new Vip());
c.setStrategy(new Student()); // 実行時切替
▶ 何が変わったか（効果）
  • Open-Closed原則: 新区分追加で既存コード変更なし。新クラス追加のみ
  • テスト独立: 各Strategyを単独でユニットテスト可能
  • 実行時切替: ユーザー操作・ABテスト・設定で動的に変更可能
  • 関心の分離: 「いつ使うか」と「どう計算するか」が別クラス
✅ Tomさんの実務で効く場面: Wijmo FlexGridのソート/フィルタ/集計。 OutSystemsで決済プロバイダ切替（クレカ/PayPay/銀行振込）、 料金計算のテーブル別ロジックなど、「switchがアプリ各所に散らばっている」現象は Strategy の出番。

State — ステータス別ifを「状態オブジェクト」に変換

アルゴリズム選択

注文ステータス（下書き/承認待ち/配送中/完了/キャンセル）で操作の可否が変わるとき、 全メソッドの先頭に if (status === ...) が並ぶ典型的な悪臭が発生する。 状態をクラス化すると、状態追加で既存メソッドを触る必要がなくなり、状態遷移図がそのままコード構造になる。

✗ Before — 全メソッドにステータス分岐
class Order {
  status = "draft";

  submit() {
    if (this.status === "draft") {
      this.status = "pending";
    } else throw new Error("NG");
  }
  approve() {
    if (this.status === "pending") {
      this.status = "shipping";
    } else throw new Error("NG");
  }
  cancel() {
    if (this.status === "draft" ||
        this.status === "pending") {
      this.status = "cancelled";
    } else throw new Error("NG");
  }
  // 状態追加で全メソッド要修正
}
✓ After — 状態がオブジェクト
interface OrderState {
  submit(o: Order):  void;
  approve(o: Order): void;
  cancel(o: Order):  void;
}
class Draft implements OrderState {
  submit(o)  { o.setState(new Pending()); }
  approve(o) { throw new Error("NG"); }
  cancel(o)  { o.setState(new Cancel()); }
}
class Pending implements OrderState {
  submit(o)  { throw new Error("NG"); }
  approve(o) { o.setState(new Shipping()); }
  cancel(o)  { o.setState(new Cancel()); }
}
class Order {
  private state: OrderState = new Draft();
  setState(s) { this.state = s; }
  submit()  { this.state.submit(this); }
  approve() { this.state.approve(this); }
}
▶ 何が変わったか（効果）
  • 状態追加: 新クラス1個追加のみ。既存メソッドゼロ修正
  • 状態遷移の局所化: 「Draftから何になれるか」がDraftクラスに集約
  • 不正遷移の検出: 「Pendingでsubmit()すると例外」がクラス境界で表現
  • 状態遷移図と1:1対応: ドキュメントの状態図がそのままクラス図になる
🔰 Strategy との違い（よく混同される）
Strategy: 利用側が能動的にアルゴリズムを選ぶ
   ┌─────┐ setStrategy(B)  ┌─────┐
   │利用 │────────────────▶│ B   │   外部から制御
   └─────┘                 └─────┘

State:    状態オブジェクトが「次の自分」を決めて自律遷移
   ┌──────┐ submit()  ┌────────┐
   │Draft │──────────▶│Pending │   内部で遷移
   └──────┘ 自己解任   └────────┘
   ↑ 利用側はsubmit()と呼ぶだけ。次がPendingか
     何かを意識しない

Observer — データ側がUI/ログ/通知を直接知る依存関係を断ち切る

通信・通知

「データが更新されたら、関連UI3箇所と通知バーとログを更新」を直書きすると、 データ側が下流の全クラスを知ることになり、依存方向が逆転して結合が密になる。 Observerでは「変化があった」と通知するだけ。誰が何をするかは購読者が自分で決める。

✗ Before — データ側が下流を直接呼ぶ
class Cart {
  items = [];
  constructor(
    private ui: UIRenderer,
    private log: Logger,
    private noti: Notifier
  ) {}

  add(item) {
    this.items.push(item);
    // データ側が全員を知っている
    this.ui.render(this.items);
    this.log.write("add", item);
    this.noti.show("追加");
  }
  // 集計クラスを追加 → Cart修正
  // 通知を1つ削減 → Cart修正
  // → Cart が下流の事情で揺れる
}
✓ After — 購読者が自分で登録
type Listener = (items) => void;

class Cart {
  private listeners: Listener[] = [];
  items = [];
  subscribe(l) { this.listeners.push(l); }
  add(item) {
    this.items.push(item);
    // 誰が聞いてるか知らない
    this.listeners.forEach(
      l => l(this.items)
    );
  }
}

const cart = new Cart();
cart.subscribe(items => ui.render(items));
cart.subscribe(items => log.write(items));
cart.subscribe(items => noti.show("追加"));
// 集計クラス追加 → subscribe追加だけ
// Cart は無傷
▶ 何が変わったか（効果）
  • 依存方向の逆転: データ側→下流 ではなく 下流→データ側 への単方向に
  • 追加の容易さ: 新しい監視対象はsubscribe()するだけ。データ側ゼロ修正
  • テスト容易: subscribeに検証用の関数を渡すだけで通知をテストできる
  • 疎結合: データクラスがUIライブラリやロガーに依存しなくなる
✅ Tomさんの実務で効く場面: ReactのuseState/setStateはObserverそのもの。 OutSystemsのデータバインディング、Vue/MobX/RxJSのリアクティブ系、 DOMのaddEventListener、Pub/Sub（Redis/Kafka）の根本概念。

Mediator — N対Nの網の目をハブ集約に変える

通信・通知

ダイアログ内のテキスト入力・チェックボックス・ボタン・リストが互いを直接参照すると、 参照関係が網の目になり1つの変更が全体に波及する。 仲介役（Mediator）を間に置き、各部品はMediatorだけを知るようにすると N×N が N×1 に下がる。

✗ Before — 部品同士が直接参照
class NameInput {
  constructor(
    private btn: SubmitBtn,
    private label: ErrorLabel
  ) {}
  onChange(v) {
    if (v.length < 3) {
      this.label.show("短い");
      this.btn.disable();
    } else {
      this.label.hide();
      this.btn.enable();
    }
  }
}
// SubmitBtn も EmailInput も
// 互いを参照... 関係が網の目に
// 部品Aの変更が部品B,C,Dに波及
✓ After — 仲介役に集約
class FormMediator {
  name: NameInput;
  email: EmailInput;
  btn: SubmitBtn;
  label: ErrorLabel;

  notify(sender, event) {
    if (sender === "name" &&
        event === "changed") {
      const ok = this.name.value.length >= 3;
      this.label.toggle(!ok);
      this.btn.setEnabled(ok);
    }
  }
}
class NameInput {
  constructor(private m: FormMediator) {}
  onChange() {
    this.m.notify("name", "changed");
  }
}
// 部品は Mediator だけ知る
▶ 何が変わったか（効果）
  • N×N → N×1: 部品10個でも依存先はMediator1つのみ
  • 協調ロジック集約: 「誰が何に反応するか」が1箇所で見渡せる
  • 部品の再利用性: 部品自体は他の画面でも使える（直接参照なし）
  • 変更影響の局所化: ルール変更はMediatorのみ修正
🔰 図で見る依存関係の変化
【Before】 N×N の結合（4部品で6本の線）
   A ───── B
    \  ✕  /
     \   /
      ╳    ← 1本の変更が全体に波及
     /   \
    /  ✕  \
   C ───── D

【After】 ハブ集約（4部品で4本の線、Mediator1点に集中）
       A   B
        \ /
         M     ← 全ての協調ロジックがここに
        / \
       C   D
📘 Observerとの違い: Observerは「1対多の通知（誰が反応するかは購読者の自由）」。 Mediatorは「多対多の協調ロジックを集約」。 Mediator内では「Aが変わったらBとCを更新」のような具体的なルールを持つ点が違う。

Iterator — 内部構造を隠蔽してforループを統一

構造走査・記録

コレクションが配列か連結リストか木構造かを利用側が直接知っていると、 内部構造を変えただけで全利用箇所を書き換える羽目になる。 next()を返すIteratorに統一すれば、内部実装は後から差し替え自由になる。

✗ Before — 内部構造に直接アクセス
class UserList {
  public items: User[] = []; // public!
  add(u) { this.items.push(u); }
}

const list = new UserList();

// 利用側は配列であることを前提に書く
for (let i = 0; i < list.items.length; i++) {
  console.log(list.items[i].name);
}

// 後日「DB遅延ロードに変えたい」「木構造
// に変えたい」となったら、
// 全利用箇所の for ループを修正する羽目に
✓ After — Iterator経由でアクセス
class UserList {
  private items: User[] = []; // private
  add(u) { this.items.push(u); }

  [Symbol.iterator]() {
    let i = 0;
    const arr = this.items;
    return {
      next() {
        return i < arr.length
          ? { value: arr[i++], done: false }
          : { value: undefined, done: true };
      }
    };
  }
}

const list = new UserList();
// 内部構造を意識しない
for (const u of list) console.log(u.name);
// → 配列→木→DBカーソル に変えても
//   この for...of は無傷
▶ 何が変わったか（効果）
  • カプセル化: itemsがprivate化され、外部から構造を触れない
  • 実装差替の自由: 配列→Map→木→DB遅延ロード、利用側のforは無傷
  • 遅延評価対応: next()呼ばれた時に1件取る形でストリーム化可能
  • 言語標準との統合: for...of、spread、Array.from等が使える
📘 身近な例: JSのfor...of、JavaのIterator、C#のIEnumerable、 DBカーソル、RxJS/LINQ/Java Stream。Iteratorは23パターン中最も内部に組み込まれているパターン。 自前で書くことは少ないが、毎日使っている。

Memento — カプセル化を壊さずに状態を保存・復元

構造走査・記録

Undoのために内部変数を全部 public にすると誰でも書き換え可能になり、カプセル化が壊れる。 Memento は「本人が save()/restore() する」ことで、外部から内部状態を直接触らせずに復元を可能にする。

✗ Before — public化で破綻
class Game {
  // Undo のために全部 public
  public hp = 100;
  public level = 1;
  public inventory = [];
  public position = { x:0, y:0 };
}

const g = new Game();

// セーブ: 自前でコピー
const snap = {
  hp: g.hp, level: g.level,
  inventory: [...g.inventory],
  position: {...g.position}
};

// 問題:
// - 利用側がhpを直接書き換え可能
// - フィールド追加 → セーブ漏れ
// - ディープコピー漏れでバグ
✓ After — 本人がスナップ管理
class Game {
  private hp = 100;
  private level = 1;
  private inventory: string[] = [];

  attack() { this.hp -= 10; }
  levelUp() { this.level++; }

  // Memento を返す（不変）
  save(): GameMemento {
    return {
      hp: this.hp,
      level: this.level,
      inventory: [...this.inventory]
    };
  }
  restore(m: GameMemento) {
    this.hp = m.hp;
    this.level = m.level;
    this.inventory = [...m.inventory];
  }
}

const g = new Game();
const snap = g.save(); // 内部は隠蔽
g.attack();
g.restore(snap);     // 巻き戻し
▶ 何が変わったか（効果）
  • カプセル化保持: フィールドはprivateのまま。外部から書き換え不可
  • ディープコピー責務の集約: 本人だけが正しいコピー方法を知る
  • フィールド追加に強い: save/restoreの両方を1箇所で更新
  • Commandと組み合わせて強力: 各CommandがMementoを持てば完璧なUndo
📘 典型例: ゲームのセーブ/ロード、エディタのUndo、フォームの自動保存、 DBトランザクションの「変更前の状態」。Commandと組み合わせると履歴スタックが極めて強力になる。

Visitor — クラス階層を凍結したまま機能を増やす

構造走査・記録

Shape階層に「面積」「描画」「JSON出力」「コピー」と機能を増やすたびに Circle/Square/Triangle 全クラスを修正するのは Open-Closed原則違反。 Visitorでは新機能＝新クラスとして外部に追加し、Shape側は不変のまま操作だけ増やせる。

✗ Before — 機能追加で全クラス修正
class Circle {
  constructor(public r: number) {}
  area()       { return Math.PI * this.r ** 2; }
  draw()       { /* 描画 */ }
  toJson()     { /* JSON化 */ }
  perimeter()  { return 2*Math.PI*this.r; }
  // 機能追加 → ここに足す
}
class Square {
  constructor(public side: number) {}
  area()       { /* ... */ }
  draw()       { /* ... */ }
  toJson()     { /* ... */ }
  perimeter()  { /* ... */ }
  // 機能追加 → ここにも足す
}
// 「シリアライズ」機能追加
// → Circle, Square, Triangle 全て修正
✓ After — 機能を外部Visitorに分離
interface Shape {
  accept(v: Visitor): void;
}
class Circle implements Shape {
  constructor(public r: number) {}
  accept(v) { v.visitCircle(this); }
}
class Square implements Shape {
  constructor(public side: number) {}
  accept(v) { v.visitSquare(this); }
}
// Shape側はもう触らない

interface Visitor {
  visitCircle(c: Circle): void;
  visitSquare(s: Square): void;
}
// 新機能 = 新Visitor
class AreaVisitor implements Visitor {
  visitCircle(c) { console.log(Math.PI*c.r**2); }
  visitSquare(s) { console.log(s.side**2); }
}
class JsonVisitor implements Visitor { /* */ }
▶ 何が変わったか（効果）
  • Open-Closed原則の貫徹: Shape階層は完全凍結、新機能は外で増殖
  • 機能ごとにファイル分離: AreaVisitor.ts / JsonVisitor.ts と分けられる
  • 1階層の操作を一覧: 「面積計算」のロジックが1ファイルにまとまる
  • テスト容易: Visitor単体でモックShape相手にテストできる
⚠️ 適用注意: Visitorは「クラス階層が固定で、操作が増える」場面に限る。 逆に Shape階層が頻繁に増える場合は全Visitorを修正する羽目になり逆効果。 コンパイラ/トランスパイラのASTのように「文法ノードは決まっているが、解析パスは増え続ける」場面が王道。

Interpreter — 危険な eval を文法ツリーに置き換える

構文解釈

ユーザーや業務担当に「price > 1000 AND category = '本'」のような式を書かせたい。 evalは危険、独自ifはメンテ不能、JS関数化もスコープ汚染リスク。 文法をノードクラスに分解して木として評価すれば、安全に・拡張容易に・テスト可能になる。

✗ Before — eval / 巨大if
// 案1: eval — 危険すぎる
function evalRule(rule, ctx) {
  return eval(rule); // 任意コード実行可能！
}
evalRule("price > 1000", { price:1500 });
evalRule("alert(1); 1", {}); // XSS

// 案2: 巨大if
function evalRule2(rule, ctx) {
  if (rule === "price>1000")
    return ctx.price > 1000;
  if (rule === "vip")
    return ctx.user.vip;
  // ルール追加のたびにコード追加・デプロイ
}
✓ After — 式木で評価
interface Expr {
  interpret(ctx): boolean;
}
class Gt implements Expr {
  constructor(private field, private v) {}
  interpret(ctx) {
    return ctx[this.field] > this.v;
  }
}
class And implements Expr {
  constructor(private l: Expr, private r: Expr) {}
  interpret(ctx) {
    return this.l.interpret(ctx)
        && this.r.interpret(ctx);
  }
}

// price > 1000 AND vip
const rule = new And(
  new Gt("price", 1000),
  new Eq("vip", true)
);
rule.interpret({ price:1500, vip:true }); // true
▶ 何が変わったか（効果）
  • 安全性: 任意コード実行不可。許可された演算子しか動かない
  • 拡張容易: 新演算子＝新クラス。Or、Not、Inを順次追加
  • テスト可能: 各ノードを単体でユニットテストできる
  • 業務担当が編集可: JSONで式木を表現すれば管理画面でルール編集→DB保存
⚠️ 適用頻度は低め: 23パターン中、最も実装機会が少ない。 本格的な言語処理はANTLRやPEG.jsなどパーサジェネレータが現実解。 Interpreterパターンは「小さなDSL・ビジネスルール式」に限定するのが鉄則。
