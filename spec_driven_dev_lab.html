仕様駆動開発（SDD）とは何か

基本

仕様駆動開発（Spec-Driven Development） は、コードを書く前に「何を作るか」「なぜ作るか」「どう動くべきか」を文書化し、その仕様を中心に開発・テスト・レビューを進めるやり方。「コード優先」で書き始めて後から仕様を埋める従来手法と真逆のアプローチ。

🔰 SDDのイメージ
仕様書は「設計図」。家を建てる時、図面なしでいきなり木材を切り始めない。ソフトウェアも同じ。
AI支援開発（Claude Code等）が普及した今、仕様書 = AIへの最良の指示書でもある。曖昧な口頭指示より、整った仕様書を渡す方が結果が安定する。 
┌────────────┐    ┌────────────┐    ┌────────────┐
│  WHY       │───▶│  WHAT       │───▶│  HOW        │
│ 要求仕様    │    │ 機能仕様    │    │ 実装        │
│ (なぜ)     │    │ (なにを)    │    │ (どう作る)  │
└────────────┘    └────────────┘    └────────────┘
       ▲                                      │
       └──── 振返り・変更管理 ─────────────────┘
観点コード優先仕様駆動（SDD）
始めることいきなりコード仕様の文書化
議論の対象動くコード仕様書とサンプル
変更時の追跡困難仕様 ⇄ コード対応
AI/LLM 活用場当たり的仕様書をプロンプト化
初心者の学習動かして覚える考えて整理して書く
現在: After（仕様駆動）
✓ 仕様駆動の朝 1. specs/todo.md を開く 2. 「タスク完了の定義」を1段落書く 3. 受入基準を3つ書く 4. その3つが満たされる最小コードを書く → 何ができたら終わりか、最初から明確
✗ コード優先の朝 1. main.py を開く 2. とりあえず addTask() を書く 3. 「あれ完了状態どう持つ?」と悩む 4. 1時間後、仕様も曖昧、テストもない → 気付くと迷子、終わる基準が無い
01

題材プロジェクト：MyTodo の紹介

基本

この手順書で作る仮想プロジェクトは MyTodo。「1人用・コマンドライン版・データはJSONファイルに保存」というシンプルなTODO管理アプリ。Webサーバ不要、DB不要。Python（または好きな言語）が動けばOK。

🔰 なぜCLI＋JSONなのか
・UI/サーバ/DBがあると 仕様書を書く前に環境構築で疲れる。
・CLI+JSONなら20行のコードで動く → 仕様の議論に集中できる。
・SDDの本質（書く順序・粒度・追跡）はプロジェクト規模に関係なく同じ。 
# 完成イメージ（CLI操作の例）
$ python mytodo.py add "牛乳を買う"
✓ 追加: #1 牛乳を買う

$ python mytodo.py add "資料レビュー"
✓ 追加: #2 資料レビュー

$ python mytodo.py list
[ ] #1 牛乳を買う
[ ] #2 資料レビュー

$ python mytodo.py done 1
✓ 完了にしました: #1

$ python mytodo.py list
[x] #1 牛乳を買う
[ ] #2 資料レビュー
項目内容
言語Python 3 推奨（無くてもOK、JS等でも置換可）
機能add / list / done / delete の4コマンド
保存先tasks.json（同フォルダ）
外部依存なし（標準ライブラリのみ）
所要時間仕様書 60〜90分 / 実装 30〜60分

STEP1：要求仕様を書く（WHY）

実践

まず 「誰が」「何のために」「これを使うのか」 を書く。機能を書きたくなるのを我慢して、背景・目的・制約・対象外 の4点だけ。所要時間 15分。

🔰 「対象外」を書く意味
初心者がやりがちな失敗：「あれもこれも」と機能が膨らむ。
「やらないこと」を明示すれば、後で「これは仕様外なのでやりません」と堂々と言える。これが範囲（スコープ）管理の出発点。 
# specs/01_requirements.md にこれを書く

# MyTodo 要求仕様

## 1. 背景
個人用のタスク管理を、軽量に・依存なく・どのPCでも動く形で実現したい。
既存のWebサービスは起動が遅く、オフラインで動かないのが不満。

## 2. 目的
1日5件程度の個人タスクを、ターミナルから30秒以内で追加・確認・完了できる。

## 3. 利用者
作者本人1名のみ。他ユーザーやログイン機能は対象外。

## 4. 制約
- Python 3.9以上が動くPCで動作
- 外部ライブラリのインストール不要（標準ライブラリのみ）
- データは1ファイル（tasks.json）で完結

## 5. 対象外（やらないこと）
- 期日・優先度・カテゴリ機能
- 複数ユーザー対応
- GUI/Web UI
- スマホアプリ連携
📘 「目的」は測れる形で書く。「便利にする」はNG（測れない）。「30秒以内で追加できる」はOK（時計で計れる）。これが後の受入基準につながる。
✗ Before（曖昧で測れない）
# 目的
タスクを便利に管理したい。
使いやすくて速いものが欲しい。

# → 「便利」「使いやすい」の判定不能
✓ After（具体的・測れる）
# 目的
1日5件程度の個人タスクを、
ターミナルから30秒以内で追加・確認できる。

# → 「30秒」で達成判定が明確

STEP2：機能仕様を書く（WHAT）

実践

要求仕様を満たす機能を箇条書きでリスト化する。各機能にはID（FN-001 等）を振る。これが後で「コードのこの部分はFN-003を実現している」と紐づける鍵になる。 

# specs/02_features.md

# MyTodo 機能仕様

## 機能一覧

| ID     | 機能名      | 概要                               |
|--------|-------------|------------------------------------|
| FN-001 | タスク追加  | 文字列を渡すと新規タスクを登録     |
| FN-002 | 一覧表示    | 全タスクをID順に表示               |
| FN-003 | 完了マーク  | IDを指定して完了状態に変更         |
| FN-004 | タスク削除  | IDを指定してタスクを削除           |

## FN-001 タスク追加 詳細
- 入力: タスクのタイトル文字列（1〜100文字）
- 動作: 新しいIDを採番して tasks.json に追記
- 出力: 「✓ 追加: #<ID> <タイトル>」を表示

## FN-002 一覧表示 詳細
- 入力: なし
- 動作: tasks.json を読み、ID昇順で全件表示
- 出力形式: 「[x] #1 牛乳を買う」未完了は「[ ]」、完了は「[x]」

# （FN-003, FN-004 も同様に書く）
💡 機能IDを振る効果
  • テスト関数名に使える: def test_FN001_add_task():
  • コミットメッセージで参照できる: feat: FN-003 完了マーク実装
  • レビュー指摘が明確に: 「FN-002の出力形式と実装が不一致」
  • Claude Code等への指示で具体的に: 「FN-001を実装して」
こう見えたら機能IDの出番:
  • 「あの機能のことなんだけど…」と毎回説明している
  • テストとコードの対応関係が分からなくなっている
⚠️ ここでHOW（どう実装するか）は書かない。「ファイルをロックして…」「dictをsortedで…」は禁物。WHATだけ。実装の自由度を残しておく。

STEP3：受入基準と具体例

実践

機能ごとに「これが満たされたら完成と認める」基準を書く。Given / When / Then 形式で書くと後でテストにそのまま落とせる。

🔰 Given / When / Then とは
・Given（前提）: テスト開始前の状態
・When（操作）: 利用者が何をするか
・Then（期待）: 何が起きるべきか
この3点が揃っていれば、誰がレビューしても解釈が同じになる。 
# specs/03_acceptance.md

# 受入基準

## AC-001-1: 空のリストにタスクを追加
- **Given** tasks.json が空（[]）の状態
- **When**  `python mytodo.py add "牛乳を買う"` を実行
- **Then** 標準出力に「✓ 追加: #1 牛乳を買う」と表示
- **Then** tasks.json に id=1, title="牛乳を買う", done=false のタスクが1件存在

## AC-001-2: 既存タスクがある状態で追加
- **Given** tasks.json に id=1 のタスクが1件
- **When**  `python mytodo.py add "資料レビュー"` を実行
- **Then** 標準出力に「✓ 追加: #2 資料レビュー」と表示
- **Then** tasks.json に2件存在し、新規IDは2

## AC-001-3: 空文字でエラー
- **Given** どんな状態でも
- **When**  `python mytodo.py add ""` を実行
- **Then** 標準エラーに「Error: タイトルが空です」と表示
- **Then** 終了コード 1 で終了
- **Then** tasks.json は変更されない

## AC-003-1: 完了マーク
- **Given** id=1 のタスクが done=false
- **When**  `python mytodo.py done 1` を実行
- **Then** 標準出力に「✓ 完了にしました: #1」と表示
- **Then** tasks.json で id=1 の done が true になる

## AC-003-2: 存在しないIDで完了
- **Given** id=99 のタスクが存在しない
- **When**  `python mytodo.py done 99` を実行
- **Then** 標準エラーに「Error: ID 99 のタスクは見つかりません」と表示
- **Then** 終了コード 1 で終了
✅ 異常系を必ず1つ以上書く。空文字、存在しないID、ファイル破損など。「うまくいくケース」だけ書くとバグだらけになる。AC-001-3 や AC-003-2 のような「失敗してほしいケース」が品質を支える。
✗ Before（曖昧で複数解釈可能）
タスクを追加できる。
追加されたら表示する。
エラー時は適切に処理する。

# → 「適切に」って何?
# → 何を表示する? どこに?
✓ After（一意に解釈できる）
Given: tasks.json が空
When:  add "牛乳を買う"
Then:  stdout に
       "✓ 追加: #1 牛乳を買う"
Then:  tasks.json に
       {id:1,title:"牛乳を買う",done:false}

STEP4：データモデルを定義

実践

保存されるデータの形（スキーマ）を確定させる。型・必須/任意・値の範囲を明記。これが決まらないとテストも書けない。 

# specs/04_data_model.md

# データモデル

## ストレージ
- 形式: JSON
- ファイル名: tasks.json（実行ディレクトリ直下）
- 文字コード: UTF-8（BOMなし）

## ルートスキーマ
ルートは Task オブジェクトの配列。

```json
[
  {"id": 1, "title": "牛乳を買う", "done": false, "created_at": "2026-04-28T09:00:00"},
  {"id": 2, "title": "資料レビュー", "done": true,  "created_at": "2026-04-28T09:05:00"}
]
```

## Task フィールド定義

| フィールド   | 型      | 必須 | 説明                                       |
|--------------|---------|------|--------------------------------------------|
| id           | int     | ○    | 1以上の整数。一意。新規追加時は max(id)+1  |
| title        | string  | ○    | 1〜100文字。前後の空白は除去               |
| done         | boolean | ○    | 完了状態。新規追加時は false               |
| created_at   | string  | ○    | ISO 8601形式（YYYY-MM-DDTHH:MM:SS）        |

## ファイルが存在しない場合
- 起動時に tasks.json が無ければ、空配列 `[]` の新規ファイルを作成して続行する。
🔰 データモデルが先で良い理由
      [仕様]
        │
        ▼
   [データモデル] ─────┐
        │              │ 全テストの土台
        ▼              │ になる
   [テストコード] ◀────┘
        │
        ▼
   [実装コード]
データモデルが揺れると、テストもコードも全部書き直し。最初に固めるのが結局速い。
📘 "前後の空白は除去" のような小さなルールも書いておく。書かないと実装者ごとにブレる。

STEP5：API/インターフェース設計

実践

利用者から見た入口（CLIサブコマンド）と、内部関数のシグネチャ（引数と戻り値）を定義。これが「実装の契約」になる。 

# specs/05_interface.md

# インターフェース設計

## 5.1 CLIサブコマンド

| コマンド               | 機能ID  | 説明                       |
|------------------------|---------|----------------------------|
| `mytodo add <title>`   | FN-001  | タスク追加                 |
| `mytodo list`          | FN-002  | 一覧表示                   |
| `mytodo done <id>`     | FN-003  | 完了マーク                 |
| `mytodo delete <id>`   | FN-004  | タスク削除                 |

## 5.2 終了コード（Exit Code）

| コード | 意味                       |
|--------|----------------------------|
| 0      | 正常終了                   |
| 1      | 入力エラー（空文字、ID未指定など） |
| 2      | データファイルエラー       |

## 5.3 内部関数シグネチャ（実装の契約）

```python
def load_tasks(path: str) -> list[dict]:
    """tasks.jsonを読む。無ければ空配列を返す。破損時はSystemExit(2)"""

def save_tasks(path: str, tasks: list[dict]) -> None:
    """tasks.jsonへ書き戻す。UTF-8、indent=2で整形"""

def add_task(tasks: list[dict], title: str) -> dict:
    """新規タスクを生成しリスト末尾に追加。生成したdictを返す"""

def mark_done(tasks: list[dict], task_id: int) -> dict:
    """指定IDのタスクのdoneをTrueにして返す。存在しなければValueError"""
```
💡 関数シグネチャを先に書く効果
  • テストが先に書ける（中身がなくてもimport可能なスケルトンを置けば良い）
  • 引数の型が決まる → 不正な使い方の議論が早期にできる
  • Claude Code等に「このシグネチャで実装して」と頼める
  • 関数の責務（やること）が一文で言えなければ、設計が悪いサイン
こう見えたらシグネチャ見直し:
  • 引数が5個以上ある → 責務が多すぎる、分割を検討
  • 戻り値の説明が「色々」「状況による」 → 仕様が固まっていない

STEP6：テストを書いて実装する

応用

ここでようやくコード。受入基準（AC-xxx）をそのままテストに変換し、テストが赤い状態（失敗）から始める。1個ずつ緑に変えていく流れ。 

# tests/test_mytodo.py — AC-001-1 をそのまま書く
import json, subprocess, tempfile, os
from pathlib import Path

def test_AC_001_1_add_to_empty_list(tmp_path):
    """AC-001-1: 空のリストにタスクを追加"""
    # Given: tasks.json が空
    db = tmp_path / "tasks.json"
    db.write_text("[]", encoding="utf-8")

    # When: add コマンド実行
    result = subprocess.run(
        ["python", "src/mytodo.py", "add", "牛乳を買う"],
        capture_output=True, text=True, cwd=tmp_path
    )

    # Then: 出力チェック
    assert "✓ 追加: #1 牛乳を買う" in result.stdout
    assert result.returncode == 0

    # Then: ファイル状態チェック
    tasks = json.loads(db.read_text(encoding="utf-8"))
    assert len(tasks) == 1
    assert tasks[0]["id"] == 1
    assert tasks[0]["title"] == "牛乳を買う"
    assert tasks[0]["done"] is False
# src/mytodo.py — 最小実装（FN-001 のみ）
import sys, json
from datetime import datetime
from pathlib import Path

DB = Path("tasks.json")

def load_tasks(path):
    if not path.exists():
        return []
    return json.loads(path.read_text(encoding="utf-8"))

def save_tasks(path, tasks):
    path.write_text(json.dumps(tasks, ensure_ascii=False, indent=2), encoding="utf-8")

def add_task(tasks, title):
    title = title.strip()
    if not title:
        print("Error: タイトルが空です", file=sys.stderr)
        sys.exit(1)
    new_id = max([t["id"] for t in tasks], default=0) + 1
    task = {
        "id": new_id,
        "title": title,
        "done": False,
        "created_at": datetime.now().isoformat(timespec="seconds")
    }
    tasks.append(task)
    return task

if __name__ == "__main__":
    cmd = sys.argv[1] if len(sys.argv) > 1 else ""
    tasks = load_tasks(DB)

    if cmd == "add":
        title = sys.argv[2] if len(sys.argv) > 2 else ""
        task = add_task(tasks, title)
        save_tasks(DB, tasks)
        print(f"✓ 追加: #{task['id']} {task['title']}")
現在: After（テスト先行）
✓ AC → テスト → 実装 の順 1. AC-001-1 を読む 2. test_AC_001_1_... を書く 3. 実行 → RED（失敗） 4. add_task() を実装 5. 実行 → GREEN（成功） 6. 次のACへ → 受入基準が常に検証される
✗ 実装 → 後付けテスト 1. なんとなく add_task() を書く 2. 動かしてみる、なんか動く 3. テスト書こうかな…めんどい 4. 後で書く（書かない） 5. 仕様変更で気付かず壊れる → 受入基準と無関係なコード
📘 1ACずつ赤→緑にする。全機能を一気に実装するとデバッグ地獄。AC-001-1 → AC-001-2 → AC-001-3 → AC-002-1 ... と1個ずつテストを通す。

STEP7：仕様とコードを紐づける

応用

仕様とコードが分離していると、すぐに片方が古くなる。機能ID（FN-xxx / AC-xxx）をコードのコメント・テスト名・コミットメッセージに埋め込むことで、両者を機械的にひも付ける。

def add_task(tasks, title):
    # 仕様: FN-001 / AC-001-1, AC-001-3
    # 参照: specs/02_features.md, specs/03_acceptance.md
    title = title.strip()

# decisions/ADR_001_storage.md (Architecture Decision Record)

# ADR-001: ストレージにJSONファイルを採用

## 状況（Context）
個人用TODOアプリで、データ保存方式を選ぶ必要があった。
候補: SQLite / JSONファイル / CSVファイル / メモリのみ

## 決定（Decision）
**JSONファイル（tasks.json）** を採用する。

## 理由（Reasoning）
- 1人利用で同時書き込みが起きない → DB不要
- 標準ライブラリのみで読み書き可能 → 依存ゼロ
- ユーザーがエディタで直接見られる → デバッグ容易
- 件数想定が数百件以下 → 性能問題なし

## 結果（Consequences）
+ 軽量で起動が速い
+ Gitで差分が見える
- 数千件を超えるとパフォーマンス低下（その時に再評価）
- 並行書き込みは未対応（要求外）
