Web Animations API — element.animate() で CSS animation を JS から制御

✓ iOS ✓ Android

Why exists: CSS の @keyframes + animation は静的に書く前提で作られた。「行を1秒ハイライトしてから消す」のような JSの状態に応じて1度だけ走らせる 用途では、クラス付与 → 完了を待つ → クラス除去という回りくどい構造になりがちだった。Web Animations API は同じキーフレームを element.animate(keyframes, options) という1行で記述でき、戻り値の Animation オブジェクトに finished Promise が生える。CSS の世界と JS の制御を 橋渡し するために生まれた。

💡 利用シーン
  1. Wijmo FlexGrid で「保存成功した行」を一瞬だけ緑にハイライトして自然に戻す
  2. 通知バナーを上からスライドイン → 3秒後にフェードアウト
  3. 長押し中だけ要素を波打たせ、離した瞬間に止める (cancel/finish の制御)
  従来の CSS animation:
  ─────────────────────
  ① CSS で @keyframes 定義
  ② JS で classList.add('flash')
  ③ animationend を待つ
  ④ classList.remove('flash')
       ↑ 4ステップ + イベント漏れリスク

  Web Animations API:
  ─────────────────────
  el.animate(
    [{bg:'#fff'},{bg:'#dfd'},{bg:'#fff'}],
    {duration:1000}
  ).finished.then(() => done())
       ↑ 1ステップ + Promise で完了を待てる
📌 OutSystems文脈での旨味: Wijmo FlexGrid で itemsSourceChanged 後に「変わった行だけ」を識別しても、CSS animation だと「終わったらクラスを消す」処理を animationend で書く必要がある。Web Animations API なら cellElement.animate(keyframes, {duration:800}).finished.then(() => cellElement.style.background = '') と1行で「ハイライト→自然に戻す」が書ける。OutSystems の Action から呼ぶ OnCellEditEnded Client Action でも、Promise ベースなので BPT/Server Action との連携と相性がよい。FlexGrid の refresh() 後の DOM 入れ替わりにも、再度 animate を呼び直すだけで対応できる。

const lab1Run = () => {
  clearLog('lab1-log');
  const el = document.getElementById('lab1-target');
  // ① keyframes (配列で渡す)
  const keyframes = [
    { background: 'linear-gradient(135deg,#22863a,#79c0ff)', transform: 'scale(1.15)' },
    { background: 'linear-gradient(135deg,#005cc5,#6f42c1)', transform: 'scale(1.0)' }
  ];
  // ② options (duration, easing, fill 等)
  const opts = { duration: 1000, easing: 'ease-out', fill: 'forwards' };
  // ③ animate() の戻り値は Animation オブジェクト
  const anim = el.animate(keyframes, opts);

  console.log('animate() 開始 / playState:', anim.playState);

  // ④ Promise で完了を待てる
  anim.finished.then(() => {
    console.log('finished / playState:', anim.playState);
    setBA('lab1', 'classList.add/remove で2回触る', 'animate() + finished で1回完結');
  }).catch(() => console.log('cancelled'));
};

View Transitions API — DOM 切替の前後を自動補間

✓ Chrome ⚠ iOS 18+ ✓ Android Chrome

Why this design: 従来「画面Aから画面Bへの遷移をアニメーション」は、CSSのトランジションでは 共存する両画面 を一度DOMに同居させ、片方を非表示にしながら、もう片方を表示する……という二重管理が必要だった。View Transitions は「document.startViewTransition(callback) の中で DOM を書き換えるだけ」で、変更前と変更後のスナップショットをブラウザが自動でクロスフェードしてくれる。設計の核は「JSは結果の状態だけ書け、見た目の補間はブラウザに任せろ」。

💡 利用シーン
  1. SPA の画面切替で Before/After を自動でフェード
  2. リスト並び替え時に各カードがスムーズに移動
  3. 詳細表示 → 一覧戻りで「逆向き」の遷移を自然に見せる
  従来:
  ──────
  [Aを見せる] → [Aを fade-out] → [Bを fade-in]
  (両方を同時に DOM に存在させる必要)

  View Transitions:
  ──────────────────
  document.startViewTransition(() => {
    container.innerHTML = newHTML;  // ← 単に書き換え
  });
  └─ ブラウザが内部で:
     1. 変更前の画面をスナップショット
     2. callback 実行 (= DOM変更)
     3. 変更後をスナップショット
     4. ::view-transition-old/new で補間
📌 OutSystems文脈での旨味: OutSystems の Block 切替や Conditional Container の表示・非表示で、純粋にHTMLを差し替えても自然なフェードが付くため、React 的な「key プロパティで再マウント時にアニメーション付与」を自前で書く必要がなくなる。ただし iOS Safari は 18 から段階対応。if (document.startViewTransition) でフォールバック必須。
⚠ iOS制限: 16/17 では未対応 (即座に callback を実行 → アニメなし)。ブラウザ側が「使えない場合は普通にDOMを書き換える」フォールバックを内蔵しているわけではないので、自前で if-else を書く必要あり。

requestAnimationFrame — ブラウザの描画リズムに同期する

✓ iOS ✓ Android

Why this design: setInterval(fn, 16) でアニメを書くと、画面が非表示のときも回り続けてバッテリーを食う/タブ切替後に たまったコールバックがバースト する/タイマー精度が16msぴったりではない、など問題が多い。requestAnimationFrame は「ブラウザが次に描画するタイミングで1回だけ呼ぶ」契約。Refresh Rate (60Hz/120Hz) に自動追従、非表示タブでは止まる、誤差の少ない高精度タイムスタンプを引数で受け取る、と 「描画にロックステップ」 な設計。

💡 利用シーン
  1. JS制御のスムーズスクロール・パララックス
  2. FPSメーター(直近Nフレームの平均)
  3. 長時間処理を分割して描画ブロックを避ける(`requestIdleCallback` 代替)
  setInterval(fn, 16):
  ────────────────────
  fixed 16ms ─┬─ 16ms ─┬─ 16ms ─ ...
              ↓        ↓
            描画と    描画と
            ズレる   ズレる
  (タブ非表示でも継続 → 電池ドレイン)

  requestAnimationFrame(fn):
  ──────────────────────────
  ┌─ 描画 ─┬─ 描画 ─┬─ 描画 ─ ...
  fn(t)    fn(t)    fn(t)
   ↑ 描画直前にロックステップで呼ばれる
   ↑ tはhigh-resolution時刻 (DOMHighResTimeStamp)
   ↑ タブ非表示では 1Hz に落ちる(ブラウザ判断)
📌 OutSystems文脈: 大量データの可視化(Wijmo Chart, FlexGrid のスクロール監視)で setInterval を使うと scroll 中にカクつく原因になる。rAF + 直近 16ms 内の差分のみ描画すれば、ブラウザの描画リズムに自然に合う。

matchMedia + listener — メディアクエリを JS から監視

✓ iOS ✓ Android

Why care: 「画面サイズで条件分岐」は CSS の @media で十分だが、JS のロジック自体を切り替えたい(チャートの描画密度、ロード戦略、データ取得粒度) ケースでは CSSは無力。window.matchMedia(query) は matches 真偽値と change イベントを返し、画面サイズだけでなく ユーザの環境設定(prefers-reduced-motion, prefers-color-scheme) にも反応する。「配慮」の足場として重要。

💡 利用シーン
  1. ダークモード切替時にChart.js の配色を再描画
  2. 「アニメ控えめ設定」のユーザに対して animate() を skip
  3. 狭画面ではテーブルからカードレイアウトに DOM を組み替え
  matchMedia の構造:
  ──────────────────
  const mql = window.matchMedia('(prefers-reduced-motion: reduce)');
  ↓
  mql.matches              ← 現在の状態 (boolean)
  mql.addEventListener('change', e => { ... e.matches });
  ↓ 変化を監視 (ユーザがOS設定を変えた瞬間に発火)

  一覧:
   prefers-color-scheme   ライト/ダーク
   prefers-reduced-motion  アニメ控えめ
   prefers-contrast       ハイコントラスト
   (max-width: 768px)     画面幅
   (orientation: portrait) 縦/横
📌 OutSystems文脈: テーマ切替やレスポンシブ Block で 「ダークモード時だけ Wijmo に FlexGrid.theme を当てる」 のような JS制御は matchMedia でクリーンに書ける。

Popover API / <dialog> — モーダルを標準で書く

✓ iOS 17+ ✓ Android Chrome

Why exists: 「押すと開く・他をクリックすると閉じる・Escで閉じる・z-index で上に積む・スクロールロック」を全て自前で書くのは bug magnet。<dialog> はモーダル専用、Popover API は「ホバー/クリックで開くカード型UI」専用と用途が分かれており、ブラウザがフォーカストラップ・トップレイヤー・dismiss を担保する。z-index 戦争から解放されるための機能。

💡 利用シーン

  2. セルクリックでツールチップ的な詳細パネル
  3. フォーム入力エラーの説明ポップオーバー
  従来の自前モーダル:
  ───────────────────
  <div class="overlay">       ← position:fixed; z-index:9999
    <div class="modal">       ← フォーカストラップ自前
      ...
    </div>
  </div>
  + JSで Esc/外側click のリスナー
  + body にスクロールロック class
  + Tab キーでフォーカス循環

  <dialog> / Popover:
  ────────────────────
  <dialog id="d">...</dialog>
  d.showModal();   ← これだけ
  ↓
  ・トップレイヤーに昇格 (z-index 不要)
  ・::backdrop で背景暗転
  ・Esc キーで自動 close
  ・フォーカストラップ自動

  Popover (新顔):
  <button popovertarget="p">...
  <div id="p" popover>...</div>
  ↓ click = toggle / outside click = auto close

performance.now() — 高精度・単調増加なタイマー

✓ iOS ✓ Android

Why this design: Date.now() は (1) ms 単位までしか精度がない、(2) システム時計に依存 するので NTP 同期や手動変更で値が逆戻りする ことがある。「処理が速くなった」ことを計測してマイナス値が出たら本末転倒。performance.now() はページロードを起点とする 単調増加 な高精度時刻 (μs〜ns 級、ただしSpectre対策で粗くされている)。差分を取って所要時間を測る用途に最適化されている。

💡 利用シーン
  1. 関数の実行時間を計測 (`now() - start`)
  2. FPS 計測 / フレーム間隔の正確な測定
  3. ベンチマーク・A/B テストの実行時間比較
  Date.now():
  ───────────
  単位:    ms (整数)
  起点:    1970-01-01 (UTC)
  単調性:  ✗ NTPで時計が戻ると逆行する
  例:      1715000000000

  performance.now():
  ──────────────────
  単位:    ms (小数, μs精度)
  起点:    timeOrigin (= ページロード開始)
  単調性:  ✓ 必ず増加 (Spectre緩和で粒度はやや粗い)
  例:      12345.678

  ┌─ 計測ルール ─┐
   const t0 = performance.now();
   doWork();
   const t1 = performance.now();
   console.log(`${(t1-t0).toFixed(3)}ms`);
📌 OutSystems文脈: BPT や Server Action の処理時間は OutSystems サーバー側のログで取れるが、クライアント側の体感(REST レスポンス受信〜画面更新完了) は performance.now() でしか計れない。Wijmo FlexGrid の itemsSourceChanged から描画完了までの実時間を取りたいときに必須。

performance.mark / measure — 名前付き計測ポイント

✓ iOS ✓ Android

Why exists: console.time('label') は便利だが、結果が DevTools の console にしか残らない。本番環境で計測値を集めたい/区間と区間の差を可視化したい/DevTools の Performance パネルに線を引きたい、という要求に応えるのが Performance Timeline。mark() で「点」を打ち、measure(name, startMark, endMark) で「区間」を作ると、performance.getEntriesByType('measure') で取り出せる + DevTools にも描画される。

💡 利用シーン
  1. 「データ取得 → 描画完了」の各フェーズ時間をトラッキング
  2. 本番環境で集めた measure を Beacon で送信 (Real User Monitoring)
  3. DevTools の Performance パネルで自前のフェーズを線として確認
  時間軸:
  ─────────
   mark('A')               mark('B')              mark('C')
        │                       │                      │
        ▼                       ▼                      ▼
  ──────●──── fetch ──────────●──── render ─────────●───→
        ↑─────────────────────↑                     ↑
            measure('fetch',                        │
                   'A','B')                         │
                                ↑─────────────────  │
                                  measure('render',
                                         'B','C')

  取得:
   performance.getEntriesByType('measure')
   → [{ name:'fetch', duration:230 },

📌 OutSystems文脈: Reactive Web App の OnReady → REST取得 → CollectionView 適用 → FlexGrid 描画完了 までを各フェーズで mark() を打つと、「どこで遅いか」が DevTools で線で見える。OutSystems 標準の LifecycleEvents だけでは粒度不足な部分を補える。

  setBA('lab7', '雑にconsole.time', `${measures.length}フェーズを構造化計測`);
};

PerformanceObserver — push 型で計測値を取りこぼさない

✓ iOS ✓ Android

Why this design: performance.getEntriesByType('measure') は「その瞬間にバッファに溜まっているもの」を pull 型で取得する。だから「リスナーを登録する前に発火した entry」は取りこぼす。PerformanceObserver は逆に push 型 で、observe を登録した時点以降に発生する PerformanceEntry を すべてコールバックで受け取れる。{ buffered: true } を付ければ過去分も初回コールバックで届く。Real User Monitoring (RUM) の標準パターン。

💡 利用シーン
  1. 本番環境で Long Task (>50ms) を全部拾って原因特定
  2. LCP / FID / CLS の値を取って分析サーバへ送信 (Web Vitals)
  3. resource タイプを observe して「遅いリソース」を自動検知
  Pull型 (getEntries):
  ─────────────────────
   ┌──────┐  poll   ┌────────────┐
   │ JS   │ ──────→ │ Performance │
   │      │ ←────── │  Buffer    │
   └──────┘ result  └────────────┘

crypto.getRandomValues() — 暗号学的に安全な乱数

✓ iOS ✓ Android

Why this fails: Math.random() は擬似乱数生成器 (PRNG) で、シードが分かれば 未来の値が完全に予測できる。さらに各ブラウザの内部状態は数百ビット程度で、十分なサンプルから状態復元が可能。セッショントークン・CSRF トークン・パスワードリセットURL の生成に使うと セキュリティ穴。crypto.getRandomValues() はOS/ハードウェアのエントロピープールから「予測不能な」乱数を取る。これが暗号用途の正解。

💡 利用シーン
  1. CSRF トークン・nonce・session ID の生成
  2. 暗号鍵の生成 (Lab 13 で使用)
  3. UUID v4 の生成 (`crypto.randomUUID()` の足回り)
  Math.random():
  ──────────────
  PRNG (Mersenne Twister など)
   ┌─────────┐
   │ シード値  │ → 計算 → 0.0〜1.0 の数値
   └─────────┘
        ↑ シード+回数が同じなら結果も同じ
        ↑ 過去の出力数値からシード復元可能

   暗号用途 → ✗ NG (予測される)

  crypto.getRandomValues(buf):
  ──────────────────────────
   ┌──────────────────┐
   │ OS Entropy Pool   │ ← マウス動作・ディスク
   │  (ハードウェア乱数 │   I/O・ネットワーク
   │   + キャプチャ)   │   ジッター等
   └──────────────────┘
        ↓
   buf を予測不能な値で埋める

   暗号用途 → ✓ OK
⚠ 絶対に Math.random() を使ってはいけない場面: パスワード/トークン生成、暗号鍵、ID 生成 (UUID v4 含む)、A/B テストのユーザー振り分け (これは漏洩の問題ではないが「再現可能性」が必要なら別の決定論的シードが必要)、ゲームの抽選 (チート対策)。
📌 OutSystems文脈: OutSystems の GenerateGuid はサーバー側 (.NET の Guid.NewGuid()) なので暗号学的に安全だが、クライアント側で前段でセッションIDなどを発行する ケースでは Math.random() を絶対に使わず、必ず crypto.getRandomValues() か crypto.randomUUID() を使う。

crypto.subtle.digest — SHA-256 ハッシュをブラウザネイティブで

✓ iOS ✓ Android ⚠ HTTPS必須

Why exists: SHA-256 ハッシュを純 JavaScript で実装すると、(1) 1MB のファイルで数秒かかる、(2) サイドチャネル攻撃に脆弱なコードになりがち、(3) 同じ実装を全員が書く非効率、と問題が多かった。crypto.subtle.digest はブラウザのネイティブ暗号ライブラリ (Mac は CommonCrypto / Win は CNG / Linux は OpenSSL系) を呼び、数十倍速く・安全に ハッシュ計算する。Promise ベースなので大きなファイルでも UI を止めない。

💡 利用シーン
  1. ファイルアップロード前にクライアント側でハッシュを取り、サーバ送信後と整合性確認
  2. パスワード以外の機密値の固定長指紋を作る (=ID 生成)
  3. ETag 自前計算 (キャッシュ判定)
  純JS実装:
  ──────────
  for (i = 0; i < bytes.length; i++) {
    // SHA-256 のラウンド計算 (64 ラウンド)
    // ... 数百行 ...
  }
  → 1MB で 3〜5秒、UIブロック

  crypto.subtle.digest:
  ────────────────────
  const hash = await crypto.subtle.digest(
    'SHA-256', uint8Array);
  → 1MB で 10〜30ms、非同期で UI を止めない
  → ハードウェアアクセラレーション (AES-NI 等)

  対応アルゴリズム:
   SHA-1 (※非推奨)、SHA-256、SHA-384、SHA-512
   (MD5 は非搭載 — 既知の脆弱性のため)
⚠ HTTPS 必須: crypto.subtle は Secure Context 限定。http:// では undefined。localhost と file:// のうち localhost は OK だが file:// は NG。
📌 OutSystems文脈での旨味: 大容量ファイル (動画・PDF) のチャンク化アップロードで、各チャンクの SHA-256 をブラウザで計算してサーバ側 (VB.NET 拡張) で照合 → 転送中の改ざん・破損を即検知できる。OutSystems 標準 BinaryData 型は SHA を取る Server Action がないので、System.Security.Cryptography.SHA256.Create() を Integration Studio Extension で公開し、クライアント側 (subtle.digest) と組み合わせて E2E ハッシュ整合チェックの仕組みを作るのが鉄板。Wijmo FlexGrid に「アップロード済み行の改ざん検知列」を追加する用途にも使える。

subtle.encrypt / decrypt — AES-GCM で機微データを暗号化

✓ iOS ✓ Android ⚠ HTTPS必須

Why care: クライアント側で「サーバに送る前に暗号化する」「IndexedDB に機微情報を保存する前に暗号化する」需要は地味に多い。AES-GCM は (1) 認証付き暗号 (改ざん検知込み)、(2) 共通鍵で対称、(3) IV (Initialization Vector) を毎回新しくすれば同じデータでも違う暗号文になる、という性質を持つ 業界標準。E2E 暗号化を自前で組むなら最初に触る対称暗号がこれ。

💡 利用シーン
  1. 下書き機能で IndexedDB に保存する前に暗号化
  2. サーバに送る前にクライアント側で暗号化(エンドツーエンド)
  3. 外部共有用のリンクに暗号化済みデータを埋め込む
  AES-GCM 暗号化フロー:
  ────────────────────
  ① 鍵を生成 or インポート (256bit)
       crypto.subtle.generateKey({name:'AES-GCM',length:256},...)

  ② IV (96bit) を毎回ランダム生成
       crypto.getRandomValues(new Uint8Array(12))

  ③ 暗号化
       subtle.encrypt({name:'AES-GCM', iv}, key, plaintext)
                ↓
       ┌────────────────────────────┐
       │ ciphertext + 認証タグ(16B)   │
       └────────────────────────────┘
       (IV と一緒に保管 / 送信する)

  ④ 復号
       subtle.decrypt({name:'AES-GCM', iv}, key, ciphertext)
       → 改ざんがあれば例外

  注意: IV は毎回違う値にする (鍵+IVの組み合わせ重複は致命的)
⚠ 絶対NGパターン: (1) 同じ鍵+同じ IV を再利用 → 過去の暗号文と XOR して平文が漏れる。(2) 鍵を平文で localStorage に保存 → 暗号化の意味がない。鍵管理は別の話 (PBKDF2 でパスワードから派生、HSM、サーバ管理 等)。
📌 OutSystems文脈での旨味: 「下書き保存」「オフライン対応」で IndexedDB に機微情報を入れたいとき、(1) ユーザのパスワードから PBKDF2 で鍵を派生 → (2) 各レコードを subtle.encrypt → (3) 暗号文と IV のみ保存、という流れが組める。OutSystems 標準では IndexedDB を直接触る LocalStorage Plugin はあるが、暗号化はサポート外。subtle.encrypt を Client Action から呼ぶ Block を1個用意すれば、全アプリで使い回せる「暗号化 LocalStorage」基盤になる。VB.NET サーバ側 (System.Security.Cryptography.AesGcm) と鍵を共有すれば真の E2E 暗号化に。

Content Security Policy — XSS への深層防御

✓ iOS ✓ Android ⚠ HTTP Header 設定

Why this design: XSS の根本原因は「ブラウザがスクリプトをどこから読むかを問わず実行してしまう」こと。CSP は HTTP レスポンスヘッダで 「読んでよい場所のホワイトリスト」 を宣言し、それ以外のスクリプト・スタイル・画像読み込みを ブラウザに拒否させる。アプリがバグで XSS を仕込んでしまっても、外部ドメインからのスクリプト読み込みが止まれば被害は最小化される — 多層防御の典型。

💡 利用シーン
  1. SaaS の本番環境で XSS の影響範囲を限定する
  2. サードパーティ widget の読み込み元を厳格に管理
  3. 違反が起きたら report-uri で集約してアラート
  CSP がない場合 (XSS 発生時):
  ─────────────────────────────
   攻撃者投稿: <script src="evil.com/x.js">
        ↓ そのままレンダリング
   ブラウザ: evil.com から取得 → 実行 ✗

  CSP あり:
  ──────────
   Response Header:
     Content-Security-Policy:
       default-src 'self';
       script-src 'self' https://cdn.allowed.com;
       style-src  'self' 'unsafe-inline';
       img-src    'self' data: https:;
       report-uri /csp-report

   攻撃者投稿: <script src="evil.com/x.js">
        ↓ ブラウザがチェック
   evil.com は script-src に無い → 読込ブロック
   違反は /csp-report にPOSTで通知される
📌 OutSystems文脈: OutSystems Cloud では Service Studio から CSP ヘッダを設定可能(Network/Settings)。Forge コンポーネントが CDN を使う場合は、その CDN ドメインを script-src に追加する必要がある。実装後は report-only モードで一定期間運用 → 違反が出なければ enforce 化するのが安全。
⚠ このラボはコード例中心: CSP は HTTP レスポンスヘッダで効くため、単一HTML内でリアル違反を再現するのは難しい。実例 HTML サンプルと違反時のブラウザコンソール表示を見ます。

Subresource Integrity (SRI) — CDN 改ざん検知

✓ iOS ✓ Android

Why care: <script src="https://cdn.example.com/lib.js"> と書いた瞬間、CDN 側に侵入した攻撃者は あなたのサイト全員に任意のJSを実行 させられる。SRI は integrity="sha384-XXX..." 属性で「この内容のスクリプトしか実行しない」と 事前にハッシュをハードコード する仕組み。CDN が改ざんされてもブラウザが実行を拒否する。crossorigin="anonymous" とセットで使うのが標準。

💡 利用シーン
  1. jQuery, Vue 等の CDN 配信ライブラリを使うとき
  2. サードパーティ JS の固定バージョン参照
  3. サプライチェーン攻撃への防御線
  SRI のチェックフロー:
  ────────────────────
  <script src="https://cdn.example.com/lib.js"
          integrity="sha384-OLBgp1G..."
          crossorigin="anonymous"></script>

   1. ブラウザ: lib.js を取得
   2. ブラウザ: 取得した内容の SHA-384 を計算
   3. integrity 属性の値と比較
        一致      → 実行 OK
        不一致    → 実行拒否 + console エラー
                    (CDN 改ざんを検知)

  ハッシュ取得:
   $ openssl dgst -sha384 -binary lib.js | openssl base64 -A
   $ # または cdn の配信ページに通常記載されている
📌 OutSystems文脈: Forge コンポーネントが内部で外部CDN参照している場合、SRI 属性が付いていないと サプライチェーン攻撃の入り口 になる。導入時の Forge コードレビューで「integrity 属性が付いているか?」を確認するのが望ましい。Service Studio で生成される `<Resources>` ブロック内の外部参照も SRI 対応すると堅い。
⚠ 注意点: integrity は 固定バージョン 前提。CDN URL に ?v=latest のような可変パラメータを使うと、CDN がバージョン更新するたびに integrity を更新しないと壊れる。「version pinning + SRI」のセットで運用する。

const lab15ToB64 = (buf) => {
  let bin = '';
  new Uint8Array(buf).forEach(b => bin += String.fromCharCode(b));
  return btoa(bin);
};

const lab15Run = async () => {
  clearLog('lab15-log');
  const code = document.getElementById('lab15-input').value;
  const bytes = new TextEncoder().encode(code);

  // SRI 仕様: sha256 / sha384 / sha512 が許可
  const hashBuf = await crypto.subtle.digest('SHA-384', bytes);
  const b64 = lab15ToB64(hashBuf);
  const integrity = `sha384-${b64}`;
  console.log(`integrity = "${integrity}"`);

  const tagHTML =
    '<script src="https://cdn.example.com/lib.js"\n' +
    `        integrity="${integrity}"\n` +
    '        crossorigin="anonymous"></script>';

  document.getElementById('lab15-tag').textContent = tagHTML;
  setBA('lab15', 'CDN改ざんで任意JS実行', `${integrity.slice(0,30)}... で固定`);
};
