00

なぜSAMLが必要か — 課題の提示

基本

SAMLの仕組みを理解する前に、まず「SAMLがなかったら何が困るのか」を明確にする。 課題が見えなければ、解決策の設計意図は理解できない。

なぜ「各アプリに個別ログイン」ではダメなのか
課題1: パスワードの増殖 — 社内にアプリが10個あれば、ユーザーは10個のID/パスワードを管理。 使い回し→漏洩リスク、個別管理→忘却コスト。
課題2: 退職者のアカウント停止 — 10個のアプリそれぞれで手動無効化。1つ漏れれば情報漏洩。
課題3: ログイン体験 — アプリ切替のたびにログイン画面。生産性低下。
SAML が解決すること
「認証（この人は誰か？）」を1箇所（IdP）に集約する。 各アプリ（SP）はIdPの「この人は認証済みです」という証明書を受け取るだけ。 
  【SAMLなし】                       【SAMLあり】
  ┌──────┐  ID/PW  ┌─────┐        ┌──────┐        ┌─────┐
  │ユーザー├───────→│App A│        │ユーザー├──┐     │App A│←─証明書─┐
  │      ├───────→│App B│        │      │  │     │App B│←─証明書─┤
  │      ├───────→│App C│        │      │  ▼     │App C│←─証明書─┤
  └──────┘ 3つのPW └─────┘        └──────┘ 1回   └─────┘        │
                                         のログイン          ┌──┴──┐
                                              └──────→│ IdP │
                                                       └─────┘
用語整理
IdP（Identity Provider）= 認証を担当するサーバー。今回は localhost:7000（saml-idp）。
SP（Service Provider）= サービスを提供するアプリ。今回は localhost:3000（Express）。
Assertion = IdPが発行する「この人は認証済み」という証明データ（XML）。
SAML が使われる現場
  • 社内ポータルから Salesforce / Google Workspace / AWS Console へのSSO
  • Azure AD (Entra ID) をIdPとして、社内Webアプリ群にシングルサインオン
  • 大学のLMSから外部教材サービスへの認証連携
  • B2Bサービスが顧客企業のIdPと連携して「自社ログイン画面なし」を実現
確認ポイント
  1. SAMLがない世界の課題を3つ挙げられるか（パスワード増殖、退職者管理、ログイン体験）
  2. IdP・SP・Assertionの3用語を自分の言葉で説明できるか
  3. 「認証を集約する」とはどういう意味か — IdPが認証、SPは証明書を受け取るだけ
01

全体フロー俯瞰図 — SP-Initiated SSO

基本

Lab 04以降で各ステップを深掘りする前に、全体の流れを先に頭に入れる。 今回のテスト環境で実際に起きた通信を、時系列で1枚の図にまとめた。

SP-Initiated SSO フロー（実データ付き）
  ブラウザ              SP (:3000)                    IdP (:7000)
    │                     │                              │
    │── GET /login ──────→│                              │
    │                     │ AuthnRequest 生成             │
    │                     │  id: _4d7b3f3d...            │
    │                     │  issuer: localhost:3000       │
    │←── 302 Redirect ────│                              │
    │        Location: localhost:7000/saml/sso            │
    │        ?SAMLRequest=nVPBjtow... (Base64+Deflate)    │
    │                     │                              │
    │── GET /saml/sso?SAMLRequest=... ──────────────────→│
    │                     │                              │ AuthnRequest 解析
    │←──────────────── ログイン画面 HTML ─────────────────│
    │                     │                              │
    │── POST (Sign in) ─────────────────────────────────→│
    │                     │                              │ ユーザー認証OK
    │                     │                              │ SAMLResponse 生成
    │                     │                              │  ID: _3d7d3106...
    │                     │                              │  署名: RSA-SHA256
    │←──── 自動POST用 HTML (SAMLResponse埋込) ───────────│
    │                     │                              │
    │── POST /login/callback ─→│                         │
    │   Body: SAMLResponse=... │                         │
    │                     │ Base64デコード                │
    │                     │ XML署名検証                   │
    │                     │ 5項目チェック                  │
    │                     │ Profile抽出                   │
    │                     │ セッション確立                 │
    │←── 302 /profile ────│                              │
    │                     │                              │
    │── GET /profile ────→│                              │
    │←── 認証済みページ ──│                              │
なぜ「SP-Initiated」と呼ぶのか
ユーザーが最初にアクセスするのがSP（localhost:3000/login）だから。 SPが「この人を認証してください」とIdPにリクエストを開始（Initiate）する。
逆に「IdP-Initiated」はIdP側のポータル画面からSPを選んでアクセスするパターン。
重要な設計特徴: SPとIdPは直接通信しない。 全てのデータはブラウザを経由する（リダイレクト or 自動POST）。 だからこそ「途中で改ざんされない」保証 = XML署名が必須になる（Lab 09で深掘り）。
確認ポイント
  1. 全体で何回のHTTPリクエストが発生するか数えてみる（6回: GET /login → 302 → GET /saml/sso → POST Sign in → POST /login/callback → GET /profile）
  2. SPとIdPが直接通信する矢印が1本もないことを図で確認する
  3. データの形式変換を追う: AuthnRequest(XML) → Base64+Deflate → URLパラメータ → IdPがデコード

generate-certs.js 自己署名証明書の生成 IdPがSAMLResponseに署名するための秘密鍵と、SPが署名を検証するための公開鍵証明書を生成。SAML認証は署名がなければ成立しないため必須。 手動作成 → npm run generate-certs で1回実行

app.js SP（Service Provider）本体 Express Webサーバー + passport-saml によるSAML認証。ルーティング、セッション管理、SAML設定の全てを含む。Lab 04〜12で詳述。 手動作成

なぜ証明書を「自分で生成」するのか
本番環境では認証局（CA）が発行した正式な証明書を使う。 しかしこのテスト環境は全てlocalhostで完結するため、正式な証明書は不要（取得もできない）。 selfsigned パッケージで自己署名証明書を生成し、IdPとSPが同じ証明書を参照することで「信頼関係」を構築している。
generate-certs.js — 証明書生成スクリプト全文
// IdP用の自己署名証明書を生成するスクリプト
const selfsigned = require("selfsigned");
const fs = require("fs");

const attrs = [{ name: "commonName", value: "localhost-idp" }];
const pems = selfsigned.generate(attrs, {
  days: 365,      // 有効期限: 1年間
  keySize: 2048,  // RSA鍵長: 2048ビット（現在の推奨最低値）
});

fs.writeFileSync("idp-cert.pem", pems.cert);     // 公開鍵証明書 → SP が読み込む
fs.writeFileSync("idp-key.pem", pems.private);    // 秘密鍵 → IdP が署名に使う

console.log("証明書を生成しました: idp-cert.pem, idp-key.pem");
秘密鍵 (idp-key.pem) の扱いに注意
idp-key.pem はIdPの秘密鍵。この鍵があれば誰でもSAMLResponseに正当な署名ができる = IdPになりすませる。 本番環境では厳重に保管し、Git にコミットしない（.gitignore に追加すべき）。 今回はテスト用なのでディレクトリに平文で置いているが、実運用では絶対にやらない。

03

package.json — 依存とスクリプト全解説

構成

package.json はNode.jsプロジェクトの設計図。 どのパッケージを使い、どのコマンドでアプリを起動するかを定義している。 各行がなぜ存在するかを1つずつ解説する。

package.json — 全文（注釈付き）
{
  "name": "saml-local-test",       // プロジェクト名（npm 内部管理用）
  "version": "1.0.0",              // バージョン番号
  "private": true,                  // ← ①

  "scripts": {                        // ← ② npm run で実行するコマンド
    "generate-certs": "node generate-certs.js",           // ← ②-A
    "idp": "saml-idp --acsUrl http://localhost:3000/login/callback --audience http://localhost:3000 --cert idp-cert.pem --key idp-key.pem --port 7000",  // ← ②-B
    "sp": "node app.js",                                    // ← ②-C
    "start": "echo \"Terminal 1: npm run idp\" && echo \"Terminal 2: npm run sp\""  // ← ②-D
  },

  "dependencies": {                   // ← ③ npm install で取得するパッケージ
    "@node-saml/passport-saml": "^5.0.0",  // ← ③-A
    "express": "^4.21.0",                 // ← ③-B
    "express-session": "^1.18.0",         // ← ③-C
    "passport": "^0.7.0",                // ← ③-D
    "saml-idp": "^1.2.1",                // ← ③-E
    "selfsigned": "^2.4.1"               // ← ③-F
  }
}

① private: true

"private": true は「このパッケージをnpmレジストリに公開しない」宣言。 テスト用プロジェクトを誤って npm publish してしまう事故を防ぐ安全装置。

② scripts — 起動コマンド

スクリプト名 実行コマンド なぜ必要か 実行タイミング
②-A generate-certs node generate-certs.js IdP用の自己署名証明書ペア（公開鍵+秘密鍵）を生成。SAML認証の署名・検証に必須。最初の1回だけ実行すればよい。 セットアップ時に1回
②-B idp saml-idp --acsUrl ... --port 7000 テスト用IdPサーバーを起動。4つのオプションでSPとの信頼関係を設定する（下記で深掘り）。 テスト時にターミナル1で常駐
②-C sp node app.js SP（Express アプリ）をポート3000で起動。 テスト時にターミナル2で常駐
②-D start echo ... 起動手順のヘルプ表示。IdPとSPは別プロセスで起動する必要があるため、案内だけ出力。 参考用
なぜ idp スクリプトに4つのオプションがあるのか
saml-idp コマンドの各オプションは、IdPとSPの信頼関係を定義している:
npm run idp のコマンド分解
saml-idp \
  --acsUrl  http://localhost:3000/login/callback \  ← SPのコールバックURL（認証結果の送信先）
  --audience http://localhost:3000 \                ← SPの識別子（Assertion の Audience に埋め込む）
  --cert    idp-cert.pem \                          ← 署名に使う公開鍵証明書
  --key     idp-key.pem \                           ← 署名に使う秘密鍵
  --port    7000                                    ← IdPの待ち受けポート
app.js の設定との対応関係
--acsUrl ↔ callbackUrl — 必ず一致すること
--audience ↔ issuer — 必ず一致すること
--cert ↔ idpCert — 同じファイルを参照すること
→ この3つの対応が崩れると SAML認証は失敗する（Lab 04 で詳述）

③ dependencies — 6つのパッケージ

パッケージ 役割 なぜ必要か 使われるファイル
③-A @node-saml/passport-saml SAML認証のPassport戦略 SAMLプロトコルの全処理を担当: AuthnRequest生成、SAMLResponseのBase64デコード・XML解析・署名検証・Profile抽出。このパッケージが SAML の核心。 app.js
③-B express Webフレームワーク HTTPリクエストのルーティング（GET /login、POST /login/callback など）とレスポンス生成。Node.js標準の http モジュールだけでは煩雑すぎるため。 app.js
③-C express-session セッション管理 SAML認証成功後、ユーザー情報をサーバー側セッションに保存。2回目以降のリクエストでは SAML認証なしでセッションCookieだけで認証状態を維持。 app.js

③-E saml-idp テスト用IdPシミュレータ ローカルで動くIdPサーバー。CLIコマンド1つでSAML IdPを起動でき、ログイン画面・SAMLResponse生成・署名を全て行う。本番環境では不要（Azure AD、Okta等を使う）。 npm run idp（CLI）
③-F selfsigned 自己署名証明書生成 X.509証明書と秘密鍵のペアをプログラムから生成。OpenSSLコマンドを手動で実行する代わりに、Node.jsスクリプト1つで完結。 generate-certs.js

なぜ passport と passport-saml が分離しているのか
passport = 認証の「枠組み」（serialize/deserialize、セッション連携）。
passport-saml = SAMLという「方式」の具体的な実装。
分離する理由: 将来、同じアプリにGoogle OAuth (passport-google-oauth20) を追加する場合、 passport 部分はそのまま使い回し、Strategy だけ追加すればよい。認証方式に依存しない設計。
バージョン指定の ^ の意味
"express": "^4.21.0" の ^ は「メジャーバージョン4の範囲で最新を許容」。 4.21.0 以上 5.0.0 未満を自動取得する。 厳密な再現性が必要な場合は package-lock.json がバージョンを固定する。
セットアップ手順の全体フロー
  • Step 1: npm install — package.json の dependencies を全て取得 → node_modules/ 生成
  • Step 2: npm run generate-certs — 証明書ペア生成 → idp-cert.pem, idp-key.pem 生成
  • Step 3: ターミナル1で npm run idp — IdPサーバー起動 (localhost:7000)
  • Step 4: ターミナル2で npm run sp — SPサーバー起動 (localhost:3000)
  • Step 5: ブラウザで http://localhost:3000 → 「SAMLログイン」クリック
確認ポイント
  1. 6つの依存パッケージそれぞれの役割を一言で説明できるか
  2. npm run idp のオプションと app.js の設定が対応していることを確認できるか
  3. passport と passport-saml が分離されている理由を説明できるか
  4. "private": true がなかったら何が起きるか想像できるか（誤って npm publish してしまうリスク）
  5. セットアップ手順を1〜5の順で正しく説明できるか（順番が重要 — 証明書生成はインストール後・起動前）
04

SP起動時の設定 — なぜこの設定が必要か

設定

SPが起動する時点で、IdPとの「信頼関係」を事前設定している。 各設定項目がなぜ必要なのかを1つずつ紐解く。

app.js — SamlStrategy 設定
const samlStrategy = new SamlStrategy({
  callbackUrl: "http://localhost:3000/login/callback",  // ← ①
  issuer:      "http://localhost:3000",               // ← ②
  entryPoint:  "http://localhost:7000/saml/sso",       // ← ③
  idpCert:     idpCert,                                // ← ④
  wantAuthnResponseSigned: false,                     // ← ⑤
  wantAssertionsSigned:    false,                     // ← ⑤
}, ...)
設定項目 値（実データ） なぜ必要か
① callbackUrl http://localhost:3000/login/callback IdPが認証結果をどこにPOSTするかをSPが宣言。IdPはこのURLを Recipient / Destination に埋め込み、SP側で一致確認する。不一致なら「別のSP宛の応答が横取りされた」と判断して拒否。
② issuer http://localhost:3000 SPの識別子。AuthnRequestに含まれ、IdPは「このSPからのリクエストか」を確認。複数SPがある環境で、どのSP向けの応答かを区別するために必須。
③ entryPoint http://localhost:7000/saml/sso IdPのSSOエンドポイントURL。SPは「ここにリダイレクトすれば認証してもらえる」と知っている必要がある。これがないとSPはIdPの場所がわからない。
④ idpCert idp-cert.pem の中身 IdPの公開鍵証明書。SAMLResponseの署名を検証するために使う。これがないと「本当にそのIdPが発行したか」を確認できず、偽の応答を受け入れてしまう。
⑤ wantSigned false テスト用の緩和設定。本番では true にして署名必須にする。
なぜ「事前に」設定が必要なのか
SAMLはSPとIdPが直接通信しないプロトコル。だからこそ、お互いの情報（URL、証明書、識別子）を事前に交換しておく必要がある。 これをメタデータ交換と呼ぶ。実運用では /metadata エンドポイントのXMLを互いに読み込んで自動設定する。
IdP側の対応する設定（起動コマンド）
--acsUrl http://localhost:3000/login/callback ← SPの①と一致
--audience http://localhost:3000 ← SPの②と一致
--cert idp-cert.pem --key idp-key.pem ← SPの④と同じ証明書
→ SP側の設定とIdP側の設定が対になっていることが信頼関係の本質。
確認ポイント
  1. callbackUrl と IdP起動時の --acsUrl が完全一致していることを確認する
  2. issuer と --audience が一致していることを確認する
  3. idpCert の読み込みで使っている idp-cert.pem が、IdP起動の --cert と同じファイルか確認する
  4. もし callbackUrl を間違えたら何が起きるか想像する（IdPが別のURLにPOST → SPで受信できないか、Recipient不一致で拒否）
05

GET /login — なぜリダイレクトするのか

フロー

ユーザーがブラウザで http://localhost:3000/login にアクセスした瞬間、 SPは何をして、なぜブラウザをIdPへリダイレクトするのか。

app.js — ログインルート
// ユーザーがこのURLにアクセスすると...
app.get("/login", passport.authenticate("saml"));
// passport-saml が内部で以下を実行:
// 1. AuthnRequest XML を生成
// 2. Deflate 圧縮 → Base64 エンコード
// 3. res.redirect(entryPoint + "?SAMLRequest=" + encoded)
なぜSPが自分で認証しないのか
SPは「サービス提供」が仕事であり、ユーザーのID/パスワードを持っていない。 パスワードを管理するのはIdPの責務。だからSPは「認証してください」とIdPにお願いするしかない。 その「お願い」がリダイレクトによるAuthnRequestの送信。
なぜ「リダイレクト」なのか（SPがIdPにAPIコールしない理由）
ユーザーがIdPのログイン画面で自分のパスワードを入力する必要があるから。 SPがバックエンドでIdPにAPI呼び出しすると、ユーザーはIdPの画面を見られない。 ブラウザのアドレスバーが localhost:7000 になることで、 ユーザーは「自分が信頼するIdPにパスワードを渡している」と視覚的に確認できる。
1
passport-saml が AuthnRequest XML を生成
Lab 06 で詳しく見る XML 文書を内部生成する
↓
2
Deflate 圧縮 → Base64 エンコード → URL エンコード
XMLはそのままURLに入れるには大きいので、圧縮してからBase64でテキスト化し、URLパラメータとして安全に送れる形にする
↓
3
HTTP 302 レスポンス
ブラウザに「このURLへ移動しなさい」と指示する
実際の 302 レスポンス（ブラウザのネットワークタブで見える）
HTTP/1.1 302 Found
Location: http://localhost:7000/saml/sso
  ?SAMLRequest=nVPBjtowEP2VyHcSEyBpLcIqBVVF2rYRpHvYS%2BXYk8Wq...
           ↑ Deflate+Base64+URLエンコードされたAuthnRequest XML
HTTP-Redirect Binding: SAMLRequestをURLのクエリパラメータに乗せて302リダイレクトで送る方式。 GETリクエストなのでURLの長さ制限（約2000文字）に注意。AuthnRequestは小さいので問題ないが、 SAMLResponse（大きい）はこの方式では送れない → だからSAMLResponseはPOSTで送る（Lab 10）。
確認ポイント
  1. ブラウザで http://localhost:3000/login にアクセスし、アドレスバーが localhost:7000 に変わることを確認
  2. 「なぜリダイレクトか」を2つの理由で説明できるか（SPにパスワードがない / ユーザーがIdPの画面を見る必要がある）
  3. データの変換を追える: XML → Deflate圧縮 → Base64 → URLエンコード
06

AuthnRequest — なぜこのデータ構造か

データ

IdPが受信したAuthnRequestの実データを見ながら、各フィールドがなぜ存在するのかを1つずつ確認する。

IdPログ — 受信した AuthnRequest（デコード後）
Received AuthnRequest =>
  id:          '_4d7b3f3d3ca7701577c8fabb0df2f227606bdfe5'
  issuer:      'http://localhost:3000'
  destination: 'http://localhost:7000/saml/sso'
  acsUrl:      'http://localhost:3000/login/callback'
  forceAuthn:  false
フィールド 実データ なぜ必要か（もしなかったら何が起きるか）
id _4d7b3f3d...606bdfe5 このリクエスト固有のID。IdPが応答する際に InResponseTo にこのIDをコピーする。SPは「自分が送ったリクエストへの応答か」を照合できる。もしなかったら: 攻撃者が別の正当な応答を横流しする「リプレイ攻撃」を防げない。
issuer http://localhost:3000 「私はこのSPです」という自己申告。IdPは登録済みSPか確認する。もしなかったら: 未登録の不正SPからのリクエストを受け付けてしまう。
destination http://localhost:7000/saml/sso 「このIdPに送っています」という宛先宣言。別のIdPに誤送信されても、宛先不一致で拒否できる。
acsUrl localhost:3000/login/callback Assertion Consumer Service URL。「認証結果はここに返してください」というSPの指定。IdPはここにSAMLResponseをPOSTする。
forceAuthn false IdPに既存セッションがあれば再ログイン不要。trueにすると毎回パスワード入力を強制（金融系など高セキュリティ用途）。
セキュリティ視点: id フィールドの重要性
id: _4d7b3f3d...606bdfe5 はランダム生成された一意な値。
IdPの応答 InResponseTo: _4d7b3f3d...606bdfe5 がこれと一致することで、SPは以下を保証する:
(1) この応答は自分が出したリクエストに対するものである（他SPの応答を流用されていない）
(2) 過去の応答が再利用されていない（リプレイ攻撃防止）
データ変換の全体像
AuthnRequest は以下の変換を経てIdPに届く: 
  passport-saml 内部         ブラウザ              IdP
  ┌─────────────────┐
  │ AuthnRequest XML │
  │ <samlp:AuthnReq  │
  │   ID="_4d7b..."   │
  │   Issuer="..."    │
  │   ...>            │
  └───────┬─────────┘
          ▼ Deflate圧縮
  ┌─────────────────┐
  │ バイナリデータ     │  (XMLより小さくなる)
  └───────┬─────────┘
          ▼ Base64エンコード
  ┌─────────────────┐
  │ nVPBjtowEP2V... │  (テキスト文字列になる)
  └───────┬─────────┘
          ▼ URLエンコード
  ┌─────────────────┐
  │ nVPBjtowEP2V    │  302 Location ヘッダに付与
  │ %2BXYk8Wq...    │ ──────────────→ GET で受信
  └─────────────────┘              ──→ 逆変換でXML復元
確認ポイント
  1. 5つのフィールドそれぞれについて「もしなかったら何が困るか」を説明できるか
  2. id がランダムであることの意味 — 予測可能だったらどうなるか考える
  3. IdPログの acsUrl と、SPの設定 callbackUrl が一致していることを確認
07

IdPでの認証 — なぜIdPが判断するのか

フロー

IdPがAuthnRequestを受信してからSAMLResponseを返すまでに何が起きるか。 テスト用IdP（saml-idp）のログイン画面で「Sign in」を押した瞬間に何が決まるか。

IdP 内部の処理フロー
  ブラウザ                          IdP (:7000)
    │                                 │
    │── GET /saml/sso?SAMLRequest ───→│
    │                                 │ ① AuthnRequestをデコード
    │                                 │    - issuer確認 (登録済みSP?)
    │                                 │    - acsUrl確認 (登録済みURL?)
    │                                 │
    │←──── ログインフォーム HTML ──────│ ② ユーザーにログイン画面を表示
    │                                 │
    │── POST /signin ────────────────→│ ③ ユーザーの認証情報を受信
    │   (username, password)          │    - ID/パスワード検証
    │                                 │    - 認証成功を確認
    │                                 │
    │                                 │ ④ SAMLResponse XML 生成
    │                                 │    - Assertion (証明書) 作成
    │                                 │    - 秘密鍵で署名
    │                                 │    - ユーザー属性を埋め込み
    │                                 │
    │←── 自動送信HTMLフォーム ─────────│ ⑤ ブラウザ経由でSPへ返送
    │   <form action="SP/callback">   │
    │     <input name="SAMLResponse"  │
    │            value="Base64...">   │
    │   自動 submit                   │
なぜIdPだけが認証を判断できるのか
IdPはユーザーの認証情報（ID/パスワード、証明書、生体認証など）を保管している唯一の存在だから。 SPはパスワードを持っていない。持つべきでもない（漏洩リスクの分散を避ける）。
IdPが認証した結果を秘密鍵で署名してSPに渡す。SPはIdPの公開鍵で署名を検証するだけ。
IdPログ — 認証後のユーザー情報
User =>
  userName:      saml.jackson@example.com
  nameIdFormat:  urn:oasis:names:tc:SAML:1.1:nameid-format:emailAddress
  firstName:     Saml
  lastName:      Jackson
  email:         saml.jackson@example.com
  groups:        Simple IdP Users, West Coast Users, Cloud Users
  userType:      Admin
テスト用IdP (saml-idp) の仕組み
saml-idpはログイン画面で入力された値をそのまま使う（パスワード検証なし）。 デフォルトのダミーユーザー saml.jackson@example.com が事前設定されている。 実際のIdP（Azure AD、Okta等）ではここでLDAPやDBへのパスワード照合が行われる。
IdPログ — SAMLP Options（SAMLResponse生成パラメータ）
SAMLP Options =>
  issuer:              urn:example:idp           ← IdP自身の識別子
  audience:             http://localhost:3000      ← このSP向けですよ
  recipient:            http://localhost:3000/login/callback ← ここにPOST
  destination:          http://localhost:3000/login/callback ← 同上
  signatureAlgorithm:   rsa-sha256                ← 署名アルゴリズム
  signResponse:         true                      ← レスポンスに署名する
  lifetimeInSeconds:    3600                      ← 有効期限: 1時間
  inResponseTo:         _4d7b3f3d...606bdfe5      ← SPのリクエストIDをコピー
inResponseTo の照合
IdPは受信した AuthnRequest の id: _4d7b3f3d...606bdfe5 を、 SAMLResponseの inResponseTo にそのままコピーしている。 SPはこの値が自分が発行したIDと一致するか確認する。一致しなければ拒否。
確認ポイント
  1. IdPログの inResponseTo と Lab 06 の id が同じ値 _4d7b3f3d...606bdfe5 であることを確認
  2. audience: http://localhost:3000 が SPの issuer と一致していることを確認
  3. lifetimeInSeconds: 3600 が意味するもの — 1時間後にこのAssertionは無効になる理由を考える
  4. IdPのログイン画面でアドレスバーが localhost:7000 であることの安全上の意味を説明できるか
08

SAMLResponse — なぜ各フィールドがあるか

データ

IdPが生成したSAMLResponse XMLの全構造を展開し、各要素がなぜ存在するかを解説する。 これはSAMLの核心部分。

SAMLResponse XML — 全構造（実データ）
<!-- 最外殻: Response -->
<samlp:Response
  ID="_3d7d310638bcabbbba53"                     <!-- A: Response自体のID -->
  InResponseTo="_4d7b3f3d...606bdfe5"             <!-- B: SPのリクエストIDの転記 -->
  Destination="http://localhost:3000/login/callback" <!-- C: 宛先SP -->>

  <saml:Issuer>urn:example:idp</saml:Issuer>     <!-- D: 発行者 -->

  <Signature>...</Signature>                       <!-- E: Response全体の署名 -->

  <samlp:Status>
    <samlp:StatusCode Value="Success"/>           <!-- F: 認証結果 -->
  </samlp:Status>

  <!-- ★ 核心: Assertion（認証証明書） -->
  <saml:Assertion ID="_wWAYVr0CJMi8...">

    <saml:Issuer>urn:example:idp</saml:Issuer>   <!-- G: Assertionの発行者 -->
    <Signature>...</Signature>                     <!-- H: Assertion単体の署名 -->

    <!-- 誰について言っているか -->
    <saml:Subject>
      <saml:NameID Format="emailAddress">
        saml.jackson@example.com                    <!-- I: ユーザー識別子 -->
      </saml:NameID>
      <saml:SubjectConfirmation Method="bearer">
        <saml:SubjectConfirmationData
          NotOnOrAfter="2026-05-24T06:08:09"         <!-- J: 有効期限 -->
          Recipient="http://localhost:3000/login/callback" <!-- K -->
          InResponseTo="_4d7b3f3d...606bdfe5"/>     <!-- L: 再びリクエストID -->
      </saml:SubjectConfirmation>
    </saml:Subject>

    <!-- いつまで・誰向けに有効か -->
    <saml:Conditions
      NotBefore="2026-05-24T05:08:09"
      NotOnOrAfter="2026-05-24T06:08:09">           <!-- M: 有効期間 -->
      <saml:AudienceRestriction>
        <saml:Audience>http://localhost:3000</saml:Audience> <!-- N -->
      </saml:AudienceRestriction>
    </saml:Conditions>

    <!-- どうやって認証したか -->
    <saml:AuthnStatement SessionIndex="1578761197">  <!-- O -->
      <saml:AuthnContextClassRef>
        PasswordProtectedTransport                  <!-- P: 認証方法 -->
      </saml:AuthnContextClassRef>
    </saml:AuthnStatement>

    <!-- ユーザーの属性情報 -->
    <saml:AttributeStatement>
      <saml:Attribute Name="email">
        <saml:AttributeValue>saml.jackson@example.com</...>
      </saml:Attribute>
      <saml:Attribute Name="groups">               <!-- Q: 権限情報 -->
        <saml:AttributeValue>Simple IdP Users</...>
        <saml:AttributeValue>West Coast Users</...>
        <saml:AttributeValue>Cloud Users</...>
      </saml:Attribute>
      <saml:Attribute Name="userType">
        <saml:AttributeValue>Admin</...>
      </saml:Attribute>
    </saml:AttributeStatement>

  </saml:Assertion>
</samlp:Response>
記号要素なぜ必要か
B, LInResponseToSPが送った AuthnRequest の ID と照合。「自分が頼んだ認証の返事か？」を確認。なければリプレイ攻撃が可能。
C, KDestination / Recipient「このSPのこのURLに届けるべき」という指定。別のURLで受け取った場合は偽装の疑い → 拒否。
D, GIssuerResponse にも Assertion にも入る。SP は「信頼する IdP が発行したか」を確認。
E, HSignature（2箇所）Response全体と Assertion個別の二重署名。片方だけだと部分改ざんのリスク（Lab 09で深掘り）。
INameIDユーザーの一意識別子。SPがDBと紐付けるキー。メールアドレス形式が一般的。
J, MNotOnOrAfter有効期限。古いAssertionの再利用を防ぐ。今回は1時間（3600秒）。
NAudience「このSPだけが使っていい」という制限。他のSPがこのAssertionを流用することを防ぐ。
OSessionIndexIdP側のセッション識別子。シングルログアウト（SLO）で「どのセッションを切るか」を指定するのに使う。
PAuthnContextClassRef認証方法の申告。「パスワード認証でした」「MFAでした」等。SPはこれを見て信頼度を判断できる。
Qgroups / userType権限判断用の属性。SPはこれを見て「管理者画面を見せるか」等を決定。
なぜ Response と Assertion の2層構造なのか
Response = 配送用の封筒。宛先（Destination）、配送状況（Status）を持つ。
Assertion = 封筒の中身の証明書。ユーザー情報、有効期限、署名を持つ。
分離する理由: Assertion は IdP-Initiated フローなど別のコンテキストでも再利用可能な独立した証明書として設計されている。 また、Assertionだけを暗号化して Response は平文にする、といった柔軟な運用ができる。
確認ポイント
  1. XML内に InResponseTo が2箇所（Response属性と SubjectConfirmationData）あることを確認
  2. 両方とも同じ値 _4d7b3f3d...606bdfe5 で、Lab 06 の AuthnRequest id と一致するか
  3. Audience の値がSPの issuer と一致するか確認
  4. Response と Assertion に分離されている理由を「封筒と証明書」のアナロジーで説明できるか
09

XML署名 — なぜ署名するのか

セキュリティ

SAMLの全データはブラウザを経由する。ブラウザはユーザーが操作できる環境。 ということは、データを改ざんできる。これを防ぐのがXML署名。

なぜ署名が必要か — 攻撃シナリオで考える
もし署名がなかったら:
① 攻撃者がブラウザの開発者ツールでSAMLResponse（Base64）をデコード
② XML内の <saml:NameID> を admin@company.com に書き換え
③ 再度Base64エンコードしてPOST
→ SPは「IdPが admin を認証した」と信じてしまう = なりすまし成功

署名があれば: XMLを1文字でも変更すると署名検証が失敗 → SPが拒否
SAMLResponse 内の Signature 要素（実データ抜粋）
<Signature>
  <SignedInfo>
    <CanonicalizationMethod Algorithm="xml-exc-c14n#"/>
    <SignatureMethod Algorithm="rsa-sha256"/>        <!-- ① 署名アルゴリズム -->
    <Reference URI="#_3d7d310638bcabbbba53">         <!-- ② どの要素を署名対象にしたか -->
      <DigestMethod Algorithm="sha256"/>              <!-- ③ ダイジェスト計算法 -->
      <DigestValue>GiqqZKKWee...</DigestValue>      <!-- ④ XML本体のハッシュ値 -->
    </Reference>
  </SignedInfo>
  <SignatureValue>Eh5FcOI8z3UIEe7y...</SignatureValue> <!-- ⑤ 秘密鍵で暗号化した署名 -->
  <KeyInfo>
    <X509Certificate>MIIC+DCCAeC...</X509Certificate> <!-- ⑥ 検証用の公開鍵証明書 -->
  </KeyInfo>
</Signature>
署名検証の仕組み（簡略版）
  【IdP（署名する側）】
  ┌───────────────┐     ┌──────────────┐
  │ XML本体       │ ──→ │ SHA-256 Hash │ ──→ DigestValue
  └───────────────┘     └──────────────┘
                                │
                          ┌─────▼──────┐
                          │ RSA暗号化   │ ← IdPの秘密鍵
                          └─────┬──────┘
                                ▼
                          SignatureValue

  【SP（検証する側）】
  ┌───────────────┐     ┌──────────────┐
  │ XML本体       │ ──→ │ SHA-256 Hash │ ──→ 計算した DigestValue
  └───────────────┘     └──────────────┘          │
                                                   │ 一致?
  ┌────────────────┐     ┌──────────────┐          │
  │ SignatureValue │ ──→ │ RSA復号      │ ← idp-cert.pem (公開鍵)
  └────────────────┘     └──────┬───────┘          │
                                ▼                  │
                          復号した DigestValue ─── 比較 ─→ OK or NG
なぜ Response と Assertion の両方に署名があるのか
Response署名のみの場合: 攻撃者がResponse内のAssertionを別の正当なAssertionに差し替える攻撃が理論上可能。
Assertion署名のみの場合: ResponseのStatus(Success)を改ざんされるリスク、Destination書き換えリスク。
両方署名: Responseの封筒もAssertionの中身も、どちらも改ざん検知可能。二重の防御。
テスト環境での緩和設定に注意
今回の app.js では wantAuthnResponseSigned: false にしている。 これはテスト用の緩和設定。本番環境では必ず true にすること。 false のまま本番運用すると、上記の攻撃シナリオが現実のリスクになる。
確認ポイント
  1. 「署名がなかったら何ができてしまうか」を攻撃者の視点で説明できるか
  2. DigestValue が「XML本体のハッシュ」であることを理解 — 1文字でも変えるとハッシュが変わる
  3. SignatureValue が「DigestValueを秘密鍵で暗号化したもの」であることを理解
  4. SP側は idp-cert.pem（公開鍵）だけで検証できる理由を説明できるか

POST /login/callback — なぜPOST・なぜブラウザ経由

フロー

IdPがSAMLResponseをSPに届ける方法として「HTTP-POST Binding」が使われる。 なぜGETではなくPOSTなのか、なぜIdPがSPに直接送らないのか。

なぜ GET ではなく POST なのか
SAMLResponseのXMLは数KB〜数十KBの大きさになる（署名、証明書、属性情報が含まれるため）。 GETのURLパラメータには約2000文字の制限がある（ブラウザ依存）。 AuthnRequest（小さい）はGETで送れたが、SAMLResponse（大きい）はPOSTでしか送れない。
なぜ IdP → SP に直接 POST しないのか
理由1: SAMLの設計原則「IdPとSPは直接通信しない」。イントラネット内のSPにインターネット上のIdPから直接到達できないケースが多い。
理由2: ブラウザのセッションCookieを活用するため。SPはブラウザのCookieでセッションを管理する。サーバー間通信ではCookieが使えない。
理由3: ブラウザがSPにPOSTすることで、SPから見ると「ユーザーのブラウザからのリクエスト」になり、通常のWebアプリのセッション管理と自然に統合できる。
IdP が返す自動送信 HTML フォーム（概念）
<!-- IdP がブラウザに返す HTML -->
<html>
<body onload="document.forms[0].submit()">   <!-- ページ読込と同時に自動送信 -->
  <form method="POST"
        action="http://localhost:3000/login/callback">
    <input type="hidden"
           name="SAMLResponse"
           value="PHNhbWxwOlJlc3BvbnNlIHhtbG5z..."/>  <!-- Base64エンコードされたXML -->
  </form>
</body>
</html>
自動送信の仕組み: IdPはHTMLフォームを返し、onload イベントで自動 submit() する。 ユーザーから見ると「一瞬白い画面が表示された後、SPのページに戻る」ように見える。 この瞬間にSAMLResponse（Base64）がPOSTのBody部として送信される。
app.js — コールバックルート

app.post(
  "/login/callback",
  passport.authenticate("saml", {
    failureRedirect: "/login-failed",   // 検証失敗時のリダイレクト先
  }),
  (req, res) => {
    res.redirect("/profile");              // 検証成功 → プロフィールページへ
  }
);

  1. SAMLResponseがGETではなくPOSTで送られる理由を「データサイズ」で説明できるか
  2. IdPがSPに直接通信しない理由を3つ挙げられるか（到達性、Cookie、セッション管理）

検証5項目 — なぜ各検証が必要か

セキュリティ

SPが SAMLResponse を受信した後、passport-saml は内部で5つの検証を行う。 各検証がどの攻撃を防いでいるかをセットで理解する。

検証項目 実データの照合 防ぐ攻撃 もし検証しなかったら
① 署名検証 SignatureValue を idp-cert.pem で復号 → DigestValue と照合 改ざん 攻撃者が NameID を書き換えて別ユーザーになりすまし
② InResponseTo _4d7b3f3d...606bdfe5 がSPの送ったIDと一致するか リプレイ攻撃 過去の正当なSAMLResponseを再送信して認証を突破
③ 有効期限 現在時刻が NotBefore〜NotOnOrAfter の範囲内か 期限切れの流用 1年前のSAMLResponseを保存しておいて再利用
④ Audience http://localhost:3000 が自分（SP）の issuer と一致するか 横流し 別のSP向けAssertionを横取りして自分のSPで使用
⑤ Recipient http://localhost:3000/login/callback が自分のcallbackUrlと一致するか URL偽装 攻撃者のサーバーに送られたAssertionが正当なSPで受理される
5検証の関係図 — なぜ全部必要か
   攻撃パターン        どの検証が防ぐか
  ┌─────────────────┐
  │ XML内容を改ざん   │ ──→ ① 署名検証
  │ (NameID書換等)    │
  ├─────────────────┤
  │ 過去の応答を再送   │ ──→ ② InResponseTo + ③ 有効期限
  │ (リプレイ攻撃)    │
  ├─────────────────┤
  │ 別SP向け応答を流用 │ ──→ ④ Audience
  ├─────────────────┤
  │ 別URL向け応答を流用│ ──→ ⑤ Recipient
  └─────────────────┘

  → どれか1つでも欠けると、対応する攻撃が成立する
  → だから5つ全てが必要
検証②と③の組み合わせが重要な理由
InResponseTo だけの場合: SPがリクエストIDを永久保存しなければ、古いIDの再利用を検知できない。
有効期限だけの場合: 有効期限内であれば何度でも再送可能。
両方: InResponseToで「自分のリクエストへの応答か」を確認 + 有効期限で「古すぎないか」を確認 = 二重の防御。 SPは通常、InResponseToのIDをメモリに一定時間だけ保持し、有効期限切れで自動破棄する。
passport-saml 内部の検証フロー
  POST /login/callback でSAMLResponse受信
          │
          ▼
  ┌── Base64 デコード → XML 取得 ──┐
  │                                 │

確認ポイント

  2. InResponseTo と有効期限がなぜセットで必要かを説明できるか

  4. 全ての検証が1つでもNGなら401で拒否されることを理解しているか

セッション確立 — XML → Profile の変換

データ

全検証をパスした後、passport-saml は XML の Assertion からユーザー情報を抽出し、 JavaScript オブジェクト（Profile）に変換する。この Profile がアプリで使えるユーザー情報になる。

Before: SAMLResponse XML（IdPから受信）
<saml:NameID>saml.jackson@example.com</saml:NameID>
<saml:Attribute Name="firstName"><saml:AttributeValue>Saml</...></...>
<saml:Attribute Name="groups">
  <saml:AttributeValue>Simple IdP Users</...>
  <saml:AttributeValue>West Coast Users</...>
  <saml:AttributeValue>Cloud Users</...>
→ XML要素として散在
After: Profile オブジェクト（SPで利用可能）

  firstName: "Saml",
  groups: ["Simple IdP Users",
    "West Coast Users",
    "Cloud Users"],
  userType: "Admin" }
→ フラットなJSオブジェクトに正規化

app.js — 検証コールバック → セッション保存 → リダイレクト
// ① 検証成功後、passport-saml がこのコールバックを呼ぶ
(profile, done) => {
  console.log("--- SAML認証成功 ---");
  console.log("Profile:", JSON.stringify(profile, null, 2));
  return done(null, profile);  // ← done(null, user) でPassportにユーザー情報を渡す
}

// ② passport.serializeUser がセッションに保存
passport.serializeUser((user, done) => done(null, user));
// → req.session.passport.user に profile 全体が格納される

// ③ 以降のリクエストで passport.deserializeUser がセッションから復元
passport.deserializeUser((user, done) => done(null, user));
// → req.user に profile が復元される

// ④ 認証済みページで利用
app.get("/profile", (req, res) => {
  if (!req.isAuthenticated()) return res.redirect("/");
  // req.user.nameID → "saml.jackson@example.com"
  // req.user.groups → ["Simple IdP Users", ...]
  // req.user.userType → "Admin"
});
