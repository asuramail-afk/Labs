3行で違いを掴む

前提

両者ともSDD（仕様駆動開発）の代表的実装だが、「どこで動くか」「誰が使うか」「どこまで囲うか」が違う。Spec Kit は素のエージェントに薄く乗せるレイヤー、KiroはSDD専用の独立IDE製品。

🔵 GitHub Spec Kit

  • 形態: CLI + Markdownテンプレ群
  • 動く場所: 既存のClaude Code/Copilot/Geminiなど
  • コスト: ツール無料（裏のエージェント側課金）
  • 強み: ツール自由・カスタマイズ性高

🟢 AWS Kiro Spec モード

  • 形態: 独立IDE（Code OSSベース）+ CLI
  • 動く場所: Kiroアプリ内（VS Codeとは別アプリ）
  • コスト: Free 50credits → Pro $20/月〜
  • 強み: GUI完備・SDDに最適化された体験
📘 一言で覚えるなら: Spec Kit = SDDのレシピ集（既存キッチンで自分で料理する）/ Kiro = SDD専用レストラン（メニューに沿って体験する）。Tomさんの状況では、既にClaude Codeに慣れているならSpec Kit、SDD体験を最短で味わいたいならKiro。
🔰 視覚的に並べる
─── Spec Kit（薄い層） ────────────────────
    [既存のAIエージェント (Claude Code等)]
              ↑ /speckit.* スラッシュコマンドを足す
        [Spec Kit テンプレ群]
              ↑ specify init で配置
        [あなたのプロジェクト]

─── Kiro（厚い層・統合体験） ───────────────
    [Kiro IDE = Code OSS ベース 独立アプリ]
        ├ Specs ペイン（GUI）
        ├ Steering ペイン（GUI）
        ├ Hooks ペイン（GUI）
        ├ Auto エージェント（Sonnet/Opus等）
        └ あなたのプロジェクト
01

提供形態の違い（CLI vs IDE）

前提

最も実感しやすい違いは「どこで動くか」。Spec Kit は普段使っているコーディングエージェントに乗せる薄いレイヤー、Kiro はそれ自体が完結したIDE。インストールから初回起動までの体験が根本的に違う。

項目Spec KitKiro
本体Pythonツール（specify-cli）独立IDE（Code OSSフォーク）+ CLI
インストールuv tool install でCLIだけOSごとのインストーラをダウンロード
VSCode拡張との関係不要（CLIから配置）Open VSX互換プラグインのみ対応（Microsoft専有拡張は不可）
サポートエージェントClaude Code, Copilot, Gemini, Cursor, Codex, Codebuddy, Pi など多数Kiro内蔵のAuto（複数モデル混合）or 単一モデル指定
UIの作りMarkdownファイル+スラッシュコマンドのみSpecs/Steering/Hooksの専用ペインGUI
タスク実行UItasks.mdをエージェントが読む（テキスト）tasks.mdに「Run/Run all」ボタン、進捗表示
ログイン裏のエージェントの認証（例: Claude Codeの認証）GitHub / Google / AWS Builder ID / IAM Identity Center
OS対応Win/Mac/Linux（Pythonが動けば）Win/Mac/Linux のインストーラあり
📘 「Code OSSベース」の意味: KiroはVS Codeのオープンソース部分（Code OSS）をフォークして作られた独立IDE。VS Codeの設定・テーマは引き継げるが、Microsoft専有の拡張機能（Pylance、Remote Development、GitHub Copilot拡張など）は動かない。Open VSXマーケットプレイスにあるものだけ。これは規制業界での採用判断ポイント。
⚠️ Tomさんが業務で使う場合の注意: 業務PCに新しいIDEを入れるのはハードルが高い場合がある。Spec Kit なら既存環境を触らずに導入できる。Kiro は別アプリのインストール承認が必要。個人学習・自宅PCで試すならKiroが手早い、業務環境ならSpec Kitが導入しやすい。

🔵 Spec Kit が合う人

  • 既にClaude Code等の使用経験がある
  • ターミナル中心で作業している
  • 複数のエージェントを使い分けたい
  • MarkdownとGitだけで完結させたい
  • 既存IDE（VS Code等）を変えたくない

🟢 Kiro が合う人

  • GUIでSDD体験をしたい
  • 初めてSDDに触れる初学者
  • 仕様→設計→タスクの進捗を可視化したい
  • 1ツールで完結する方が好み
  • AWSエコシステム志向
02

料金とモデル選択

前提

ここが見落とされがちだが、実用上もっとも違う点。Spec Kit はツール自体が無料で裏のエージェント側で課金。Kiroは独自のクレジット制。同じ仕様作成でも累積コストが変わる。

プランSpec KitKiro（2026年4月時点）
ツール本体無料（OSS）Free / Pro $20/月 / Pro+ $40/月 / Power $200/月
無料枠—（裏のエージェント次第）50 credits/月（永続）+ 初回30日間500 bonus credits
料金体系Claude Code: 通常のClaude課金。Copilot: GitHubサブスク。等月額固定 + クレジット超過 $0.04/credit
モデル選択裏のエージェント次第（Claude Codeなら Anthropicのモデル群）Auto（混合）/ Sonnet 4.5 / Haiku 4.5 / Opus 4.5/4.6/4.7 / Sonnet 4 を指定可
AWS GovCloud対応—あり（料金20%増、Freeなし、IAM Identity Center必須）
📘 Kiroのクレジット消費感: 簡単な質問は1credit未満、Spec実行（要件→設計→タスク→実装）は1回でクレジットを多く消費する。Free 50credits は1〜2機能の練習で使い切る感覚。本格運用なら Pro$20/月以上が現実的。
⚠️ 日本円換算と消費税: Kiroの公式FAQは「日本の請求先住所には日本の消費税が適用される」と明記。Pro $20/月+消費税 ≒ 月額3,200円前後。Claude.ai有料プラン（既に持っている場合）と二重支払いになる点に注意。
✅ 料金で迷ったらまずFree+Trial: Kiroは初回30日間500 bonusクレジットがある。これでSpec Kitと同じ題材を1〜2本通せる。比較してから有料化判断するのが安全。

    busty usage（月初に集中）するとProでも超過しやすい
03

フェーズ対応表

フェーズ比較

両者のフェーズを並べると、似ているようで段数と名前が違う。Spec Kitは6段、Kiroは3段（+ Bugfixは別系統）。同じ内容を異なる粒度で扱っている。

🔰 フェーズ対応図
─── Spec Kit ───────────────────────────────────
  /speckit.constitution → /speckit.specify → /speckit.clarify
                       → /speckit.plan     → /speckit.tasks
                       → /speckit.implement
  （6段。Constitution はプロジェクト1回、以降は機能ごと）

─── Kiro Spec モード ───────────────────────────
  Steering(任意で先に) →  Requirements → Design → Tasks → Implement
  または                  Design → Requirements → Tasks → Implement
  （3段+任意のSteering。Requirements-First / Design-First の2変種）

  Bugfix Spec は別系統:
  Bug Analysis(bugfix.md) → Design → Tasks → Implement
役割Spec KitKiro
原則・ルールconstitution.md（明示的に書く）.kiro/steering/*.md（複数ファイル：product.md / tech.md / structure.md）
What/Whyspec.md（汎用Markdown）requirements.md（EARS記法強制）
曖昧解消/speckit.clarify として独立フェーズRequirements中の対話で吸収
How / 設計plan.md / data-model.md / contracts/ / research.md / quickstart.md（多ファイル）design.md（1ファイル、シーケンス図含む）
分解tasks.md（依存DAG・[P]マーク）tasks.md（GUIで Run/Run all ボタン）
実装/speckit.implement各タスク横の「Start Task」or「Run all tasks」
バグ修正特化—（Spec全体を通すか、軽量プロンプトで対応）Bugfix Spec（bugfix.md でcurrent/expected/unchanged 構造）
📘 Kiroのフェーズが少ない理由: Spec Kit が独立フェーズにしている clarify や plan 内の補助文書（research.md / data-model.md / contracts/）を、KiroはRequirements ↔ Design の対話に吸収している。GUIが対話を補助するのでフェーズを増やす必要が少ない、という思想。
⚠️ 「設計→要件」の逆順がKiroの独自性: Spec Kit は基本的に Requirements → Plan の順。Kiroは2026年2月のv0.10で Design-First ワークフローを追加し、技術設計から要件を導出することを正式サポート。これはbrownfield（既存資産活用）や非機能要件が厳しい場面で効く。
04

Kiroの2ワークフロー（Requirements-First / Design-First）

フェーズ比較

Kiroが2026年2月v0.10で追加した「2ワークフロー選択」は、Spec Kitには無い独自機能。「ユーザ視点の要件から始めるか、技術アーキから始めるか」を最初に選ぶ。

🔰 2ワークフローの違い
─── Requirements-First（標準） ─────────────────
  「ユーザが何をできるか」から始める
  
  あなたのプロンプト
       ↓
  requirements.md（EARS記法）
       ↓ 人間レビュー
  design.md（要件を満たす設計を生成）
       ↓ 人間レビュー
  tasks.md
       ↓
  Implement

─── Design-First（v0.10新機能） ───────────────
  「どう作るか」から始める。要件は設計から導出
  
  あなたのプロンプト + 詳細レベル選択（高/低）
       ↓
  design.md（先に作る）
       ↓ 人間レビュー
  requirements.md（設計から実現可能な要件を導出）
       ↓ 人間レビュー
  tasks.md
       ↓
  Implement
シナリオRequirements-FirstDesign-First
新機能を考えるとき○ 標準的×
非機能要件が厳しい（性能・コンプラ）△ 後で実現性NG発見○ 設計の実現性が保証される
技術スタックが既に決まっている△ 重複作業○ 設計を素直に書ける
brownfield（既存コードベースに追加）△○ 既存設計に整合させやすい
プロトタイプ・実現可能性検証×○ アーキ案を素早く試せる
初学者の最初の一歩○ 直感的×（設計知識が必要）
📘 Kiro公式の説明: 「Design-First は、技術的アプローチが 出発点 であって 到達点 ではないときに最適」。性能・コンプラ・既存アーキへの統合などの制約から設計をスタートさせる場合に効く。Spec Kitだと plan.md フェーズで類似のことをするが、Kiroはworkflow選択として明示的にサポートしている点が違う。
⚠️ workflowは途中で切り替え不可: Kiroの公式FAQで明言されている。Requirements-First で始めたSpecをDesign-Firstに変えるには、新しいSpecを作って必要な内容をコピーする必要がある。最初の選択は慎重に。
✅ Spec KitでDesign-First相当をやるには: /speckit.constitution で技術スタックを書く → /speckit.plan 相当の内容を先に書く → spec.md を後で作る、という順で運用すれば近いことはできる。ただしテンプレが Requirements-First を前提にしているので、AIへの追加指示が必要。
05

EARS記法（Kiro固有）

フェーズ比較

Kiroの requirements.md は EARS（Easy Approach to Requirements Syntax）という構造化記法を使う。Spec Kit の Given/When/Then よりさらに厳密で、安全クリティカル領域（航空エンジン制御等）由来の記法。

📘 EARSの起源: Rolls-Royceが航空機エンジン制御ソフトウェアの安全要件記述のために開発。曖昧さの排除・テスト可能性・要件→実装のトレーサビリティを目的とする。Kiroが採用した理由は「AIが要件を機械的に解釈しやすい」から。
EARSの基本パターン（Kiro requirements.md）
## User Authentication

### User Registration
WHEN a user submits valid registration data
THE SYSTEM SHALL create a new user account

WHEN a user submits an email that already exists
THE SYSTEM SHALL display "Email already registered" error

WHEN a user submits invalid email format
THE SYSTEM SHALL display email validation error

## EARS の5つの基本パターン
# 1. Ubiquitous（常時）       : THE SYSTEM SHALL ...
# 2. Event-driven（条件発生時）: WHEN ... THE SYSTEM SHALL ...
# 3. State-driven（状態時）   : WHILE ... THE SYSTEM SHALL ...
# 4. Optional（条件付き）     : WHERE ... THE SYSTEM SHALL ...
# 5. Unwanted（異常時）       : IF ... THEN THE SYSTEM SHALL ...
観点Spec Kit (Given/When/Then)Kiro (EARS)
由来BDD（Cucumber等）形式手法・安全クリティカル系
主語の扱い暗黙（テスト視点）明示（"THE SYSTEM SHALL"が必須）
記述の自由度高め（自然言語寄り）低め（パターン縛り）
AIの解釈テストコードへ落としやすいシステム振る舞いとして解釈・検証しやすい
テスタビリティ○◎（Property-Based Testに乗せやすい）
習得コスト低い（広く知られている）中（最初は窮屈に感じる）
✅ EARSが強い場面: ① 要件の曖昧さを最小化したいとき（規制業界・医療・金融） ② AIに「これを必ず満たして」と強い制約を与えたいとき ③ レビュアーが多人数で「この要件はどう解釈する？」を減らしたいとき。普段の自由記述に慣れた人ほど、最初は窮屈に感じるが、慣れると曖昧さが激減する効果が出る。
⚠️ EARSは万能ではない: 探索的なUI/UXや「ここはユーザに任せる」のような曖昧さを残したい要件には不向き。すべてEARSで書こうとすると窮屈で、結果的に網羅できないことがある。Kiroも実運用では EARSベース + 自然言語の補足 が一般的。
06

Bugfix Spec（Kiro固有）

フェーズ比較

Kiroがv0.10で追加した Bugfix Spec は、SDDの「Sledgehammer問題（小修正に重い）」を解決する仕組み。バグ修正専用の軽量フローで、「変える挙動 / 変えない挙動」を構造化して扱う。Spec Kitには対応する仕組みがない。

🔰 Bugfix Spec の構造（bugfix.md）
┌── bugfix.md ──────────────────────┐
│  ## Current Behavior（今の挙動）        │
│  ─ バグの再現条件と現状の動作            │
│                                          │
│  ## Expected Behavior（期待する挙動）  │
│  ─ 修正後の正しい動作                    │
│                                          │
│  ## Unchanged Behavior（変えない挙動） │
│  ─ 触ってはいけない既存機能              │
│  ─ ここが Bugfix Spec の核心             │
└────────────────────────────────┘
            ↓
    design.md（修正設計）
            ↓
    tasks.md（surgical fix のステップ）
            ↓
    Property-Based Testing（PBT）で検証
      - 現状にバグがあることを検証する PBT
      - 修正後にバグが解消することを検証する PBT
      - 変わらない挙動が変わらないことを検証する PBT
📘 「Unchanged Behavior」がブレイクスルー: AIが「ついでに直す」傾向（前回手順書でも警告した暴走パターン）を、仕様レベルで明示的にブロックする。「ここは触らない」を明記し、PBTで検証することで、サージカルな修正を保証する。これは Spec Kit にはない独特のアプローチ。
✅ Property-Based Testing（PBT）の役割: ランダムな入力を大量に生成して、与えた性質（property）が常に成り立つかを検証する手法。Bugfix Specでは「変わらない挙動が本当に変わらないか」を網羅的に検証する。具体的なテストケースだけだと見落とす副作用を捕まえる。
シナリオSpec KitKiro Bugfix Spec
typo 修正軽量プロンプト or Spec全部通す（重い）Bugfix Spec で軽量に
1関数のロジックバグ同上Bugfix Spec が最適
影響範囲が広い修正Spec を通すBugfix Specで影響範囲を明示
regression防止が重要テスト追加を手動指示PBTが組み込みで生成される
レガシーコードの修正brownfield的に進めるBugfix Spec＋既存挙動の保護
⚠️ Spec Kitで類似のことをやるには: /speckit.specify 内に「Constraints: 既存の○○機能は変更しない」と明記し、/speckit.tasks 生成時に「touchable / untouchable」セクションを書かせる工夫が必要。Kiroのように構造化されたテンプレが提供されないので、運用で補う必要がある。
07

Steering Files vs Constitution

運用

プロジェクト全体に常に適用するルール群。Spec Kitは1ファイルに集約（constitution.md）、Kiroは用途別に複数ファイル（steering files）。同じ目的でも構造が違う。

🔵 Spec Kit: constitution.md

場所: .specify/memory/constitution.md

  • 1ファイルに全原則を集約
  • 条文形式（Section X.Y）
  • 明示的に /speckit.constitution で生成・更新
  • すべてのフェーズで自動参照

🟢 Kiro: Steering Files

場所: .kiro/steering/*.md

  • 用途別に複数ファイル
  • 標準: product.md / tech.md / structure.md
  • 追加可（specs.md でSpec生成挙動を変更等）
  • すべての対話で自動的に文脈に含まれる
🔰 Kiro Steering Files の典型構成
.kiro/steering/
├── product.md      ← 何を作っているプロダクトか
│                     対象ユーザ・主要機能・差別化要素
├── tech.md         ← 技術スタック・コーディング規約・依存
│                     使うフレームワーク・禁止事項
├── structure.md    ← ディレクトリ構造・モジュール境界
│                     ファイル命名・配置ルール
└── specs.md        ← (任意) Spec生成挙動のカスタム
                      「テストファースト」等の追加ルール
観点Spec Kit constitutionKiro Steering
ファイル数1個（constitution.md）3〜N個（用途別）
初期生成/speckit.constitution 必須任意（ない状態でも動く）
更新方法同コマンド再実行 or 直接編集直接編集 or チャットで指示
適用範囲全フェーズで参照全対話で自動文脈に
個別Specへの上書きspec.md に明記すれば可能specs.md で挙動カスタム可
チームで共有Gitで.specify/全体を共有Gitで.kiro/全体を共有
📘 Kiroの「Hooks」も合わせて理解: Steeringとは別に .kiro/hooks/ でファイル変更イベントに反応する自動化を仕掛けられる。「テストファイル保存時にカバレッジ計算」「コミット直前にSpec同期チェック」など。Spec Kitには対応する組み込み機構はなく、Git Hooksで自前実装する必要がある。
✅ どちらが優れているわけではない: 1ファイル集約はシンプルで読みやすい、複数ファイルは関心ごとに分離されメンテしやすい。Tomさんが慣れたOutSystems的に言えば、Spec Kit constitution は「1つのSettings Module」、Kiro Steering は「用途別の複数Settings」のような違い。
08

テスト戦略の違い

運用

両者ともテスト統合を重視するが、「何をテストとして組み込むか」が違う。Spec Kitは伝統的なTDD志向、KiroはProperty-Based Testing（PBT）を組み込んでいる。

観点Spec KitKiro
テスト戦略TDD（constitution で「テストファースト必須」を明文化）機能Spec: 通常テスト + Bugfix: PBT必須
強制度constitution に書けば強制（緩い）BugfixではPBTが組み込み（強い）
テストの順序tasks.md でテスト→実装の順を明示同上（steering でカスタム可）
網羅性検証カバレッジツールを自前で組み込むPBTがランダム入力で網羅
テスト実行UIターミナルで pytest 等IDE内タスク実行UI、結果可視化
📘 Property-Based Testing（PBT）とは: 「すべての入力xに対してf(x)>0」のような性質（property）を宣言し、ランダムな入力を大量生成して反例を探す手法。Pythonのhypothesis、JSの fast-check 等が代表的。具体的なテストケースを書くより仕様の不変条件を表現できる。

🔵 Spec Kit のテスト

def test_add_task():
  todo = Todo()
  todo.add("buy milk")
  assert len(todo.tasks) == 1

def test_add_empty_raises():
  todo = Todo()
  with pytest.raises(ValueError):
    todo.add("")

✅ Kiro が PBT を採用した理由: 公式ブログ曰く「PBT がないと、エージェントが本当にバグを修正したかと、変更が本当にサージカルだったかを確認するのが難しい」。AIが書いたコードを機械的に検証する手段として、PBT が最適だと判断したと考えられる。
⚠️ PBTは万能ではない: ① UI・IO 重視のテストには向かない ② 性質を見つける思考が必要で初心者には難しい ③ 実行時間が長くなりがち。通常のテスト+ピンポイントでPBTのハイブリッドが現実的。Kiroもこのバランスで運用される想定。

# 3. Claude Code起動して、変換指示
claude
変換プロンプト
specs/001-feature-from-kiro/ 配下に Kiro形式のファイル
（requirements.md / design.md / tasks.md）があります。

これを Spec Kit形式に整えてください:

1. requirements.md（EARS記法）を spec.md に変換
   - User Story（As a/I want/So that）形式を併記
   - Acceptance Criteria は EARS の表現を残しつつ Given/When/Then を追加

2. design.md を plan.md として再構成
   - データモデル部分は data-model.md に分離
   - API契約があれば contracts/ 配下に切り出し

3. tasks.md は構造を保持しつつ、Spec Kit の[P]マーカーと依存関係表記に揃える

4. constitution.md がない場合、Kiroのsteering（あれば渡す）から原則を抽出して生成

各変換結果は元ファイルを残したまま、新しいファイルとして作成してください。
