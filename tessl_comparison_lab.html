3行で違いを掴む

前提

Spec Kit / Kiro が「仕様を書いてからコードを生成する」のに対し、Tesslは「仕様だけ保守し、コードは仕様の派生物として再生成可能にする」を目指す。SDDの中で最も野心的かつ最も実験的。

🔵 Spec Kit

レベル: Spec-First

仕様→計画→タスク→実装。仕様は実装の出発点。実装後はコードを直接編集することも普通。

🟢 Kiro

レベル: Spec-First / Anchored

requirements/design/tasks を継続的に保守。コードと仕様の両方をメンテする。

🔴 Tessl

レベル: Spec-as-Source

仕様のみ保守。コードは // GENERATED FROM SPEC - DO NOT EDIT。仕様→コードの1:1マッピング。

📘 一言で覚えるなら: Spec Kit/Kiro = 仕様＋コードを保守 / Tessl = 仕様のみ保守。Tomさんが過去に触れた可能性があるMDD（Model-Driven Development）の考え方を、LLM時代に蘇らせた取り組み。MDDの「UML/DSLで書いて、コードジェネレータで生成」を、「自然言語で書いて、LLMで生成」に置き換えたもの。
🔰 視覚的に並べる
─── Spec Kit / Kiro ──────────────────
  仕様 → コード生成 → 以後、コードと仕様の両方を保守
       ↓                ↓
       人が編集          人が編集

─── Tessl（理想形） ──────────────────
  仕様 ──→ コード（自動生成・編集禁止）
   ↑              ↓
   人が編集       // GENERATED FROM SPEC - DO NOT EDIT
                  仕様を変えるとコードが再生成される
⚠️ 重要な現実: 2026年4月時点で、Tesslの「Framework（フル機能版）」はv0.28系で開発停止、現在の主力は v0.50系の「Registry中心 + 軽量MCP」へ大転換した。「Spec-as-Sourceは未来形、現在は仕様駆動方法論の配布プラットフォーム」というのが正確な現状認識。
01

SDDの3レベル理解

前提

Tesslを理解するには、まずSDDが3つの厳格度レベルに分けられることを押さえる。Martin Fowlerチームの分析（thoughtworks）が定義したフレーム。これがTesslの位置を理解する地図になる。

🔰 SDDの3レベル
┌────────────────────────────────────────┐
│ Level 1: Spec-First                              │
│   仕様を先に書く。実装後は仕様が放置されることも     │
│   代表: 旧来のwaterfall、初期の Spec Kit         │
├────────────────────────────────────────┤
│ Level 2: Spec-Anchored                           │
│   仕様を完了後も保守。仕様↔コードの整合性を維持      │
│   代表: 現在の Spec Kit、Kiro                    │
├────────────────────────────────────────┤
│ Level 3: Spec-as-Source                          │
│   仕様だけが「正」。人間はコードを編集しない         │
│   代表: Tessl（理想形・実験中）                   │
└────────────────────────────────────────┘
    上に行くほど、仕様の厳密さ要求が高い
    上に行くほど、コードを「捨てて再生成」できる
レベル仕様の役割コードとの関係典型ツール
Spec-First実装の出発点実装後は仕様と独立に編集BDD・初期 Spec Kit
Spec-Anchored持続する真実源両方を保守、乖離検知現Spec Kit / Kiro
Spec-as-Source唯一の真実源コードは派生物・編集禁止Tessl（実験中）
📘 Tessl CEOのビジョン: 創業者 Guy Podjarny（元Snyk創業者）は「2027年末までに、エージェントと協業する開発者はほとんどコードを見なくなる」と予測。2026年中に「ほとんどの開発が少なくともspec-assistedになる」とも。これはSpec-as-Sourceが当たり前になる世界を見据えた発言。
⚠️ Spec-as-Source の難しさ: 仕様だけで実装を決められるレベルの記述精度が必要。現状のLLMには非決定性（同じ仕様でも違うコードを生成しうる）があり、完全自動化は理論的にも実装上も難しい。Tessl自身も「現在は1ファイル＝1仕様の小さな単位」に絞っている。
02

Tessl の正体と思想

前提

Tesslは2024年に Series A を調達したスタートアップ。CEO Guy Podjarny はSnyk（時価総額数十億ドルのセキュリティ会社）の創業者。2025年9月に最初の製品（Spec Registry + Framework）を公開、2026年に大きく方向転換した。

📘 Tessl の解こうとする問題: 「エージェントは強力だが信頼できない」。短いプロンプトで自信満々にコードを書き、APIをハルシネーションし、既存機能を壊しながら「成功した」と主張する。コード中心の世界では、AIが意図を間違えてもそれを検知する手段がない。仕様を中心に据えれば、人間↔AI、AI↔AI のアラインメントが取れる。
🔰 Tessl が指摘する3つのエージェント問題
問題1: API のハルシネーション
       LLMは古いライブラリ知識を持ち、存在しないAPIを使う
       → Spec Registry で解決（10,000+ specs で正しい使い方を提供）

問題2: 既存機能を壊す
       新機能追加時、関連する既存コードを意図せず変更
       → Framework のテストガードレールで解決

問題3: 意図と実装のズレ
       短いプロンプトでは要件が捉えられない
       → Spec を first-class にすることで解決
✅ Tesslの哲学的立場: 「コードは情報を欠落している」。コードを見ても「なぜそう書かれたか」「変えていい部分とダメな部分」「どんな制約のもとで設計されたか」は分からない。仕様にはこれらが書かれている。AIに正しく仕事させるには、仕様を主役にする必要がある、という主張。
⚠️ 批判される点: ① まだプロダクトが頻繁に大変更される（v0.28→v0.50）② Spec-as-Source は理論先行で実用例が少ない ③ MDD（Model-Driven Development）が業務系で失敗した歴史を繰り返さないか懸念 ④ 1:1 spec-to-code mapping は粒度が小さすぎて全体俯瞰しづらい。
03

2つの製品（Registry + Framework）

構造

Tessl は2つの製品で構成される。Spec Registry（公開・無料）とFramework（クローズドベータ）。実は2026年に Framework の重みは大きく下がり、Registry中心 + 軽量MCP統合へシフトしている。

📘 Spec Registry とは: オープンソースライブラリの「正しい使い方」を仕様化したもの。10,000以上のpre-built specsが集まり、AIが古い知識でAPIを誤用するのを防ぐ。tessl install tessl/npm-express のようにインストール可能で、Claude Code 等のMCP対応エージェントが自動的に文脈に含めて読む。
Tessl Registry の使い方（基本）
# プロジェクト初期化（既存プロジェクトでもOK）
tessl init

# 使うライブラリの spec をインストール
tessl install tessl/npm-express
tessl install tessl/npm-langchain

# 方法論 tile（Spec-driven development）もインストール可能
tessl install tessl-labs/spec-driven-development

# 何が入っているか確認
tessl list

# MCPサーバを起動（Claude Code等から使える状態に）
tessl mcp start
🔰 Tessl Registry の中身
.tessl/
├── tiles/              ← インストールしたtileの実体
│   ├── tessl/
│   │   └── npm-express/
│   │       ├── docs/         ← APIの正しい使い方ドキュメント
│   │       ├── rules/        ← AIに守らせるルール
│   │       └── skills/       ← 再利用可能なスキル
│   └── tessl-labs/
│       └── spec-driven-development/
│           └── ...    ← 方法論tile
├── RULES.md            ← AIエージェントへの統合ルール
└── (project)
    └── tessl.json      ← マニフェスト（package.jsonに相当）
製品状態（2026年4月）役割
Spec Registry✅ 公開・無料OSSライブラリの正しい使い方をAIに教える
SDD Tile✅ 公開・無料SDD方法論をAIに教える（Tile経由）
Framework（v0.28系）⚠️ 開発停止・継続利用可Spec-as-Source（@generate/@describe）の実装
新CLI（v0.50系）✅ アクティブ開発軽量化：tile管理 + MCP配布が中心
⚠️ 製品方針の急変: 2025年9月の最初の発表ではFrameworkがメイン製品だったが、2026年に入って 「フル機能のフレームワークより、軽量なMCP配布のほうが市場ニーズに合う」と判断したとみられる。Spec-as-Source は今のところ "野心的目標" であり、実用には至っていないのが正直な現状。
04

.spec.md 構造を読む

構造

Tessl Framework（v0.28系）の Spec ファイルは .spec.md 拡張子で、YAMLフロントマター + Markdown本体の構造。「何を作るか」と「どう使えるか」を1ファイルに収めるのが特徴。

典型的な .spec.md（math library の例）
---
name: Math Library
description: Simple arithmetic operations
targets:
  - ../src/index.ts
---

# Math Library

[@generate](./src/index.ts): This tells Tessl to generate code
from this spec, specifically the /src/index.ts file.

## Capabilities

- It adds two numbers together [@test](../tests/add.test.ts)
- It subtracts two numbers [@test](../tests/sub.test.ts)
- It multiplies two numbers [@test](../tests/mul.test.ts)

## API

```ts { .api }
export function add(a: number, b: number): number;
export function subtract(a: number, b: number): number;
export function multiply(a: number, b: number): number;
```
🔰 .spec.md の3要素
┌── 1. メタデータ（YAMLフロントマター） ────────┐
│   name / description / targets（生成対象ファイル）  │
└──────────────────────────────────────┘

┌── 2. Capabilities（機能の説明） ─────────────┐
│   自然言語で書いた機能リスト                       │
│   各機能に [@test](path) でテストへのリンク         │
└──────────────────────────────────────┘

┌── 3. API（公開インターフェース） ────────────┐
│   コードブロック（言語指定）+ { .api } マーカー    │
│   ここがコード生成の制約になる                     │
└──────────────────────────────────────┘
✅ spec ファイル単位の粒度: 1つの .spec.md = 1つのコードファイル（src/index.ts 等）に対応。これは MDD の細かい粒度と同じ思想。大きな機能は複数の specファイルで構成される。Spec Kitやkiroが「機能単位の大きな仕様」なのに対し、Tesslはファイル単位の小さな仕様。
📘 Spec Kit/Kiro との粒度差: Spec Kit の spec.md は機能全体（ユーザストーリー含む）を扱う1ファイル。Tesslの .spec.md は1コードファイル分の仕様しか持たない。前者は「ビジネス仕様書」、後者は「コードファイルの設計図」と性格が違う。
05

@generate / @describe アノテーション

構造

Tessl の核心アノテーションが @generate と @describe。仕様とコードの方向を制御する。これが Spec-as-Source を可能にする最重要の仕組み。

アノテーション意味使い所
@generate仕様 → コード方向。
仕様を変えるとコードが再生成される		Greenfield、新規開発
@describeコード → 仕様方向。
既存コードから仕様を抽出する（リバース）		Brownfield、レガシー文書化
@test機能とテストの紐付けCapabilityごとに必須
@generate vs @describe の使い分け
# 新規ファイルを仕様から作る場合
[@generate](./src/calculator.ts)
# → tessl build で src/calculator.ts が生成される
# → src/calculator.ts の先頭に // GENERATED FROM SPEC - DO NOT EDIT

# 既存コードに後から仕様を付ける場合
[@describe](./src/legacy_module.js)
# → 既存コードはそのまま、仕様がドキュメントとして付く
# → tessl document コマンドで自動的に仕様を逆生成できる
既存コードから仕様をリバースする例
# 既存の JavaScript ファイルから .spec.md を生成
tessl document --code src/auth.js

# 生成される spec の例:
# ---
# name: Authentication
# targets:
#   - ../src/auth.js
# ---
# 
# [@describe](./src/auth.js)
# 
# ## Capabilities
# - validates user credentials
# - issues JWT tokens
# - handles token refresh
# 
# ## API
# ```js { .api }
# export function login(email, password) { ... }
# export function refresh(token) { ... }
# ```
✅ @describe が brownfield に強い理由: 既存コードベースに対して、いきなり Spec-as-Source は適用できない（コードを全部再生成するリスク）。まず @describe でドキュメント化して仕様↔コードの紐付けを作り、慣れてきたら徐々に @generate へ移行できる。レガシー資産（OutSystems等）に SDD を導入する場合の現実解。
⚠️ // GENERATED FROM SPEC - DO NOT EDIT の重さ: @generate したファイルにはこのコメントが先頭に入る。チーム開発で「ちょっとここだけ直したい」がやりづらい。緊急パッチで仕様を経由できないときのフローが必要になる。これも Tessl が広く採用されにくい理由の1つ。
📘 v0.28系での話: ここで紹介した @generate / @describe / tessl build / tessl document はFrameworkのv0.28系（開発停止）の機能。新v0.50系ではこのSpec-as-Source機能は含まれていない。試したい場合は v0.28 を明示インストールする必要がある。
06

v0.50 への大転換

構造

2026年に Tessl は大きな路線変更を行った。Frameworkの巨大機能を切り離し、軽量なtile配布 + MCPサーバ + Spec Registry にフォーカス。これが現在のTesslの実態。

🔰 v0.28 → v0.50 の比較
─── v0.28系（〜2025年末まで） ──────────────
  巨大Framework：
   - .spec.md ファイル形式
   - @generate / @describe アノテーション
   - tessl build でコード生成
   - tessl document でリバースエンジニアリング
   - KNOWLEDGE.md で文脈管理
   - Spec Registry 統合
  → 「Spec-as-Source の野心的実装」

─── v0.50系（2026年〜） ──────────────────
  軽量化：
   - tile（docs / rules / skills）の配布が主役
   - MCPサーバとして AIエージェントに統合
   - Spec Registry が中心
   - フル Framework 機能は別離（v0.28に残る）
   - KNOWLEDGE.md 廃止（オンデマンド取得に）
  → 「SDD方法論を配布するプラットフォーム」
機能v0.28v0.50（現行）
.spec.md ファイル✅ コア機能❌ 削除（別離）
@generate / @describe✅ あり❌ なし
tessl build / document✅ あり❌ なし
Spec Registry（tile install）✅ あり✅ 強化された
MCP server統合△ 部分的✅ 中核機能
SDD Tile（方法論配布）—✅ 新登場（tessl-labs/spec-driven-development）
対応エージェント多数Claude Code, Cursor を自動設定（他は手動）
⚠️ 公式の説明: Tesslの changelog より「The Framework functionality is no longer included. If you need the full framework features, v0.28.0 remains available (though development is paused)」（2026年初めのリリースノート）。Spec-as-Source は実験段階の機能として「凍結」されている。
v0.28（フル Framework）を試したいとき
# バージョン固定でインストール
npm install -g @tessl/cli@0.28.0

# または npx で単発実行
npx @tessl/[email protected] init

# フル機能を使うには
tessl init --framework
# これで .spec.md / @generate などが使える
📘 現状の Tessl の立ち位置: 「SDD方法論をAIエージェントに教えるためのMCPベース配布プラットフォーム」。Spec Kit や Kiro が「ツール」なのに対し、Tessl は「ツールに乗せるレイヤー」になった。Claude Code に Tessl Registry をインストールすれば、Spec Kit の代わりにも使える、という関係。
✅ Spec-as-Source は捨てたわけではない: Tessl CEO の長期ビジョン（2027年末までに開発者がコードを見なくなる）は変わっていない。だが「今すぐ普及できるもの」と「未来形」を分け、まずは普及しやすい配布プラットフォームから市場を取りに行く戦略に見える。Spec-as-Source は v0.28 で検証中、いずれ復活する可能性が高い。

🚨 Tesslの推奨レベル（2026年4月時点）: メイン開発手法として採用するのは時期尚早。だが tessl install tessl/npm-XXX でOSSライブラリ統合の MCPレイヤーとして補助的に使うのは即効性がある。Spec Kit/Kiro と競合ではなく補完と位置づけるのが現実的。

MDD との歴史的関係

3軸比較

Tessl の Spec-as-Source は、実は2000年代の MDD（Model-Driven Development）の現代版。Tomさんが業務で OutSystems（ローコードプラットフォーム）に長く関わってきた経験がここで効く。

🔰 MDD の歴史と Tessl の位置
2000年代: MDD（Model-Driven Development）
   - UML や 独自DSL でモデル（仕様）を書く
   - カスタムコードジェネレータでコード生成
   - 例: Eclipse Modeling Framework、Rational Rose
   - 結果: 業務系では普及せず（オーバーヘッド過大）

2010年代: ローコード/ノーコード
   - OutSystems / Mendix / PowerApps など
   - ビジュアル設計→コード（一部）自動生成
   - 限定的な領域では成功

2020年代後半: Tessl型 Spec-as-Source
   - 自然言語で仕様を書く
   - LLMがコード生成
   - 仕様言語の制約がない（自由な記述）
   - 「LLMが MDDの障壁を取り除く」という賭け
観点2000年代 MDDOutSystems等ローコードTessl型 SaS
仕様の書き方UML・独自DSL（厳格）ビジュアル設計（GUI）自然言語Markdown（自由）
コード生成エンジンテンプレート+ルールプラットフォーム固有エンジンLLM
適用領域制限あり（業務系で頓挫）業務アプリで成功未確定（実験中）
仕様記述コスト高い（フォーマル過ぎ）中（GUIで楽）低い（自然言語）
生成コードの再現性高い（決定的）高い低い（LLMの非決定性）
カスタマイズ余地低い中（拡張モジュール）高い（仕様の書き方次第）
📘 OutSystems経験が活きる視点: Tomさんは普段 OutSystems で「ビジュアル設計 → 自動コード生成」のパターンに慣れている。「Service Action のフローを描けば、対応するコードが自動生成される」のと、Tessl の「.spec.md を書けば src/index.ts が自動生成される」は、同じ思想の延長。OutSystems 開発者は Tessl の発想に親和性が高い。
⚠️ MDD失敗の教訓を Tessl は乗り越えられるか: MDD失敗の理由は「抽象レベルが中途半端」「カスタマイズ時にコード直接編集が必要になり、仕様↔コードが乖離する」「記述コスト＞節約コスト」。LLMで記述コストは下がったが、非決定性とカスタマイズ時の逃げ道はまだ未解決。// GENERATED FROM SPEC - DO NOT EDIT を破る瞬間がいつか来る、というのが懐疑派の主張。
✅ Tessl が MDD を超える可能性: ① 自然言語の柔軟性 ② テスト（@test）による検証 ③ Property-Based Testing 等での網羅検証（Kiroのアプローチを取り込めば） ④ MCP経由で多様なツールと連携可能。「LLMが MDD の障壁を取り除く賭け」は、検証中だが筋は悪くない。

実機で触ってみる手順

実用

Tessl Registry を Claude Code で実際に使う最小手順。5分で動くように構成した。フル Framework（v0.28）は別パスとして案内する。

🔰 Tessl の前提環境
必要なもの:
  - Node.js 22以上（v0.50系から最低要件）
  - Claude Code または Cursor（MCP対応エージェント）
  - Tessl アカウント（GitHub等でログイン）
  - 既存のプロジェクト or 空ディレクトリ
① 最短セットアップ（v0.50系・主流ルート）
# Tessl CLIをグローバルインストール
npm install -g @tessl/cli

# または npxで都度実行
npx @tessl/cli --version

# プロジェクトに移動して初期化
cd my-project
tessl init --agent claude-code
# Claude Code用のMCP設定が自動で生成される

# Tesslにログイン（ブラウザが開く）
tessl login
② SDD方法論tile + ライブラリtileのインストール
# SDD方法論をAIに教えるtileを入れる
tessl install tessl-labs/spec-driven-development

# 使うライブラリのtileも入れる（例: Express）
tessl install tessl/npm-express

# インストール済み一覧を確認
tessl list

# 何が起きたか確認:
# - .tessl/tiles/ 配下に Markdown が配置される
# - .tessl/RULES.md に AIへの指示が統合される
# - .claude/ 配下にClaude Code用のMCP設定が入る
③ Claude Code から使う
# Claude Code を起動
claude

# プロンプトの最初に「use spec-driven development」と書く
# これで方法論tileが活性化される

# 例:
"Build a REST API for managing team projects.
Use spec-driven development."

# 結果: AIがいきなりコードを書かず、要件を質問してくる
# Tessl Registry の Express tile も自動的に文脈に入る
# → API ハルシネーションが減る
📘 「use spec-driven development」が呪文: Tessl SDD tile はインストールしただけでは発動しない。プロンプトに方法論を呼び出す合図を入れることでルールが効く。逆に普通のチャットでは tile が邪魔しないので、必要なときだけ呼ぶ運用ができる。
⚠️ Frameworkフル機能（v0.28）を試すには: 上の手順とは別途、npm install -g @tessl/[email protected] でバージョン固定が必要。.spec.mdと @generate はこちらでないと動かない。開発停止のため将来サポート保証なし。研究目的・趣味のみで。
