00

境界の全体像 — read を止め embed を通す

基本

SOP(Same-Origin Policy)は「クロスオリジンへのアクセス全部」を止めるのではない。止めるのは JS がレスポンスのバイト列・DOM を読む 瞬間。リクエスト送信やリソースの埋め込み(表示・実行)はむしろ許可される。この非対称性が全ラボの軸。

操作分類クロスオリジン可否例
表示・実行委任embed✓ 許可<img> <script> <link> <video> <iframe表示>
リクエスト送信embed系✓ 許可<form> 送信 / 画像GET
レスポンス本文読取read✗ 遮断fetch().text() / XHR.responseText
DOM 読取read✗ 遮断iframe.contentDocument
ピクセル読取read✗ 遮断canvas.getImageData()
🔰 なぜ「読む」だけ止めるのか
埋め込みは Web をリンクで繋ぐ前提機能で、止めると CDN も画像も使えなくなる。一方「他サイトの中身を JS が読めてしまう」と、ログイン中の銀行残高やメール本文を悪意サイトが盗める。だから 送る・表示するは自由、中身を読むのは禁止 という線引きになった。 
attacker.example のページ
   │
   ├─ embed ──▶ bank.example のリソースを「表示/実行」  ✓ 通す
   │             （ブラウザが処理。JSは中身に触れない）
   │
   └─ read ───▶ bank.example のレスポンスを「JSで読む」  ✗ 止める
                 fetch / XHR / contentDocument / getImageData
JS — 同じ相手でも read と embed で結果が違う
// embed: ブラウザに表示を委任 → 通る（onload発火）
const img = new Image();
img.src = 'https://upload.wikimedia.org/wikipedia/commons/4/47/PNG_transparency_demonstration_1.png';
img.onload = () => console.log('embed OK: 画像は表示できた');

// read: 同じ画像URLを fetch で「読もう」とする → CORSで遮断され得る
fetch(img.src)
  .then(r => r.blob())
  .then(() => console.log('read OK'))
  .catch(e => console.log('read 遮断:', e.message));
01

fetch のレスポンス読取が遮断される

基本

fetch() のリクエスト自体は相手サーバに届く(設定次第で Cookie も付く)。止まるのは .text() / .json() で本文を読む瞬間。相手が Access-Control-Allow-Origin を返さなければ、JS はレスポンスに触れずエラーになる。

✗ Before（CORS未許可 → 読取で例外）
JS — クロスオリジンを素で読む
// 相手が CORS ヘッダを返さない場合
const res = await fetch('https://example.com/');
const t = await res.text();
// → TypeError: Failed to fetch
//   （送信は届くが本文を読めない）
✓ After（CORS許可 or no-cors埋込）
JS — 許可済みAPI or 読まない
// ① 相手が ACAO を返すAPIなら読める
const r = await fetch('https://api.github.com/zen');
console.log(await r.text()); // OK

// ② no-cors なら送れるが body は opaque（読めない）
await fetch('https://example.com/', { mode:'no-cors' });
現在: After（CORS許可APIは読める）
✓ After: api.github.com/zen は ACAO:* を返す → fetch().text() が成功し本文が読める
✗ Before: ACAOを返さないオリジンへ素のfetch → 送信は届くが .text() の手前で "Failed to fetch"。本文はJSに渡らない
02

iframe の表示は許可・contentDocument 読取は遮断

中級

クロスオリジンを <iframe> に表示するのは許可(embed)。だが親ページの JS から iframe.contentDocument や contentWindow.document で中の DOM を読むと SecurityError。表示はできても中身は覗けない。

HTML+JS — iframe表示はOK / DOM読取はNG
<!-- 表示(embed): 通る -->
<iframe id="f" src="https://example.com/"></iframe>

<script>
  const f = document.getElementById('f');
  f.onload = () => {
    try {
      // read: 中のDOMを読む → 例外
      console.log(f.contentDocument.body.innerHTML);
    } catch (e) {
      console.log('read 遮断:', e.name); // SecurityError
    }
  };
</script>
📘 例外的に通る境界: postMessage は「読む」のではなく「相手が送ってよいと判断したメッセージを受け取る」仕組みなので、クロスオリジンでも合意の上で通信できる。直接 DOM を読むのとは別物。
03

canvas 汚染(tainted) — 描画は許可・読取は遮断

中級

クロスオリジン画像を drawImage() で canvas に描くのは許可(embed)。だがその瞬間 canvas は "tainted(汚染)" 扱いになり、getImageData() や toDataURL() でピクセルを読むと SecurityError。見せてよいが盗ませない、の典型例。

✗ Before（汚染 → 読取で例外）
JS — crossorigin指定なし
const img = new Image();
img.src = 'https://他オリジン/photo.png';
img.onload = () => {
  ctx.drawImage(img,0,0); // 描画OK
  ctx.getImageData(0,0,10,10);
  // → SecurityError: tainted canvas
};
✓ After（CORS同意で汚染回避）
JS — crossorigin + 相手がACAO返す
const img = new Image();
img.crossOrigin = 'anonymous'; // 同意を要求
img.src = 'https://CORS許可オリジン/photo.png';
img.onload = () => {
  ctx.drawImage(img,0,0);
  ctx.getImageData(0,0,10,10);
  // → 読める（相手が許可した場合のみ）
};
現在: After（同意ありで読める）
✓ After: crossOrigin='anonymous' + 相手がACAOを返す → canvasは汚染されず getImageData() でピクセルを読める
✗ Before: crossOrigin未指定で他オリジン画像をdrawImage → 画像は見えるが canvasがtaintedになり getImageData() で SecurityError
04

img/script の埋込は許可される

基本

<img> はクロスオリジンでも表示される(が JS はピクセルを読めない→Lab03)。<script> は取得して実行までされる(が .js のソース文字列を JS から読むことはできない)。「実行は委任、中身の読取は禁止」が一貫した線。

HTML — クロスオリジン埋込はすべて通る
<!-- 表示される（JSはピクセルを読めない） -->
<img src="https://他オリジン/logo.png">

<!-- 取得して実行される（ソース文字列は読めない） -->
<script src="https://cdn.example/lib.js"></script>

<!-- 適用される -->
<link rel="stylesheet" href="https://cdn.example/x.css">
⚠️ 埋込の "実行委任" は信頼の前提。クロスオリジンの <script> は自オリジンの権限で実行される。CDN が改ざんされれば自サイトが乗っ取られるため、本番では integrity(SRI)属性でハッシュ検証するのが定石。
✗ Before（無検証で実行）
HTML
<script src="https://cdn.example/lib.js"></script>
✓ After（SRIで改ざん検知）
HTML
<script src="https://cdn.example/lib.js"
  integrity="sha384-…"
  crossorigin="anonymous"></script>
05

form のクロスオリジン送信は通る — CSRFの根本

中級

<form> から他オリジンへ POST を送るのは許可(embed系)。送信先の Cookie も自動で付く。レスポンスは画面遷移としてブラウザが処理し JS は読めないが、「送れてしまう」こと自体が副作用を起こす。これが CSRF の原理。

🔰 read遮断だけでは防げない理由
SOP は「レスポンスを読む」のは止めるが「リクエストを送る」のは止めない。送金APIのように送信だけで副作用が完結する処理は、レスポンスを読めなくても被害が成立する。だから SOP とは別に CSRF トークンや SameSite Cookie が必要になる。 
悪意ページ ──POST送信(Cookie自動付与)──▶ bank/transfer
                                              │
                          残高が動く（副作用は完結）
                                              │
   ◀──レスポンス── JSは読めない ✗（でも手遅れ）
✗ Before（防御なし → CSRF成立）
HTML — 攻撃側ページ
<!-- 被害者が踏むと自動送信 -->
<form action="https://bank.example/transfer"
      method="POST">
  <input name="to" value="attacker">
</form>
<script>document.forms[0].submit()</script>
✓ After（SameSite + トークン）
サーバ設定 — 防御側
# Cookieにクロスサイト送信抑止
Set-Cookie: sid=…; SameSite=Lax; Secure

# フォームに予測不能なトークン必須
<input name="csrf" value="ランダム値">
# サーバ側でトークン照合 → 不一致は拒否
06

JSONP — script実行を逆手に取った抜け道

応用

read は遮断でも、<script> の「実行までされる」性質を悪用すればデータを取れる。サーバが callback({...}) という JS を返し、ブラウザがそれを実行する——これが CORS 普及前の JSONP。SOP の境界の非対称性が穴になった歴史的事例。

HTML+JS — JSONPの仕組み
// 1) コールバックをグローバルに用意
function cb(data) { console.log('取得:', data.balance); }

// 2) script として読み込む（read遮断を回避）
const s = document.createElement('script');
s.src = 'https://api.example/balance?callback=cb';
document.body.appendChild(s);

// 3) サーバが返すのは「実行可能なJS」:
//    cb({ balance: 100 })  ← これが実行され cb にデータが渡る
🚫 JSONP は非推奨。返ってくるのは任意実行コードなので、サーバが侵害されれば即XSS相当になる。現在はクロスオリジンデータ取得に CORS(相手が明示同意する設計)を使う。JSONP は「embed の実行委任を read の代わりに使う」発想そのものが危険。
07

CORB/ORB — embed要求でも中身は渡さない補強

応用

Spectre 以降、「embed として要求されたレスポンスのバイト列がプロセス内に乗る」こと自体がリスクになった。CORB(後継 ORB)は <img> や <script> として要求されても、中身が JSON/HTML/XML 等「画像でも実行用JSでもない」ならレンダラに渡す前にブロックする補強策。

層守る対象判定基準
SOPJSがread()する瞬間オリジン一致 / CORS同意
CORB/ORBembed要求のレスポンス本文Content-Type と内容の整合(sniff)
COOP/COEPプロセス分離・SAB許可レスポンスヘッダの宣言
📘 関係整理: SOP は「JS が読む」を止める基本線。CORB/ORB は「embed と偽って中身をプロセスに引き込む」を塞ぐ補強。COOP/COEP はさらにプロセス自体を分離して SharedArrayBuffer 等の強力機能を安全に解禁する層。境界の非対称性(Lab00)を多層で守る構図。
HTTP — CORBが効く例
# 攻撃側: 機密JSONを <img> として要求
GET /secret.json
# レスポンス
Content-Type: application/json
# → CORB: 画像要求なのに中身はJSON
#   → レンダラに渡さずブロック（空扱い）
#   ＝ Spectreでも中身が読めない
