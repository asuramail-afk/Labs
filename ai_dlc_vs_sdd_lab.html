3行で違いを掴む

前提

長い比較に入る前に、本質的な違いを3行で掴んでおく。両者はAI時代の開発手法として並べられがちだが、「何を中心に置くか」と「どう人間が関与するか」がそもそも違う。

🔵 AI-DLC（AWS発・2025-）

  • 中心: 開発プロセス（Inception→Construction→Operations）
  • キーワード: Mob Work（人が同席して即決）
  • 狙い: 速度（Velocity） Boltと呼ぶ数時間サイクル

🟢 SDD（Spec-Driven Development）

  • 中心: 仕様（Spec）。仕様が真実、コードは生成物
  • キーワード: Single Source of Truth（仕様が唯一の正）
  • 狙い: 整合性（Alignment） 仕様とコードのズレを防ぐ
📘 一言で覚えるなら: AI-DLC = プロセス改革（誰が何を判断するかの再設計） / SDD = アーティファクト改革（仕様を実行可能な真実にする）。両者は対立せず補完的。実際にはハイブリッドで使われることが多い。
🔰 視覚的に並べる
AI-DLC ─ 流れ重視
  Intent → Unit → Bolt → Bolt → ... → Reflection
  「いつ・誰が・何を判断するか」を構造化

SDD ─ 文書重視
  Spec(真実) ─→ Plan ─→ Tasks ─→ Code(派生物)
                            ↓
                          Spec とコードが乖離したら
                          Spec が勝つ
01

そもそもSDDとは何か

前提

Spec-Driven Development は2026年現在、AI時代の開発手法として急速に普及している。GitHub Spec Kit（46.7k★）、AWS Kiro、Tessl などのツールが「仕様を書いてからAIにコードを生成させる」という共通の思想で実装されている。前提知識として要点を押さえる。

📘 SDDの核心: 「仕様は人間が読むためのドキュメント」だった時代から、「仕様はAIへの実行可能な契約」へ。2026年1月のarXiv論文「Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants」が学術的フレームを与えた。
🔰 SDDの3レベル（厳格度）
レベル1: Spec-First    （仕様を先に書く。コードは独立に書く）
レベル2: Spec-Anchored （仕様にコードが対応。乖離を検知）
レベル3: Spec-as-Source（仕様だけ保守。コードは毎回生成）

  ↑ 厳格度が上がるほど、仕様の精度要求が高い
  ↑ 上に行くほど、コードを「捨てて再生成」できる
代表ツール提供元形態フェーズ
Spec KitGitHubCLI + Slash Command（任意のAIエージェント）Constitution → Specify → Plan → Tasks → Implement
KiroAWS専用IDE（VS Codeフォーク）Requirements → Design → Tasks
TesslTesslSpec-as-Source指向仕様だけ保守、コードは毎回生成
BMAD-METHODOSSマルチエージェント協調独自フェーズ（汎用）
GitHub Spec Kit の典型ワークフロー
# Step 0: Constitution（憲法）= 不変の原則を最初に1回
/speckit.constitution

# Step 1: Specify = 何を作るか・なぜか（技術スタック禁止）
/speckit.specify Real-time chat with message history and presence

# Step 2: Plan = どう作るか（ここで初めて技術選定）
/speckit.plan WebSocket for messaging, PostgreSQL for history

# Step 3: Tasks = 実行可能タスクに分解
/speckit.tasks

# Step 4: Implement = AIがTasksに従って実装
/speckit.implement
✅ SpecKit と Claude Code の関係: Spec Kit は Claude Code を含む複数のコーディングエージェントから使えるCLI。uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT> で初期化すると、各エージェントのスラッシュコマンドが定義された Markdown 群がプロジェクトに展開される。
02

系譜と思想の違い

前提

両者の違いを理解するには、それぞれが「何の問題に答えようとして生まれたか」を知るのが早い。同じ「AI時代」でも、見ている課題が違う。

🔵 AI-DLC が答える問題

「AIがコードを爆速で書けるのに、なぜリリースが速くならないのか？」

  • 会議・要件調整・承認ワークフローがボトルネック
  • Sprint 2週間のリズムがAI速度と合わない
  • 従来SDLCはAIアシストでも素人自律でも品質が出ない

解: 「人間判断の高速化」を儀式化（Mob Work）し、サイクルをBolt（数時間）に圧縮

🟢 SDD が答える問題

「AIが書いたコード、動くけど意図と合ってない」

  • あいまいなプロンプトでAIが勝手に解釈する
  • 複数ファイルにまたがる整合性が壊れる
  • vibe codingの結果、技術負債が爆発（コピペ48%増・リファクタ60%減）

解: 仕様を機械可読・実行可能にし、AIへの契約として渡す

観点AI-DLCSDD
提唱元AWS（2025年7月公開）BDD・形式手法・API設計の系譜（2026年に学術化）
系譜XP（Extreme Programming）の Mob 化BDD・契約による設計（DbC）・Design-First API
主敵Agile/Scrumの長サイクルVibe Coding（雰囲気でAIに書かせる）
答えるWhy速度を上げたい整合性を保ちたい
批判される点1Boltに10〜26の人間検証ゲートがあり、モデル性能向上で過剰になる懸念小さなバグ修正には大げさすぎる（Sledgehammer問題）
⚠️ AI-DLCの「Mob Work」が見落とされがち: AI-DLC ≒ 仕様駆動開発と紹介されることがあるが、これは表層理解。AI-DLCの本質は「決定権者を物理的に同席させて、AI出力をリアルタイム検証する」というXP系の思想。仕様文書はその結果として生まれる。
📘 歴史の流れ: 2024年「Vibe Coding」流行 → 2025年「AI-assisted vs autonomous」両極の限界露呈 → 2025年7月 AWSがAI-DLC発表（プロセス側からの解） → 2025年9月 GitHub Spec Kit公開（仕様側からの解） → 2026年 両者が並立し補完関係と認識されるように。
03

フェーズ対応表で見る

構造比較

両者のフェーズを並べると、同じことを違う粒度で扱っているのがよく分かる。AI-DLCの方が「なぜ→何を→どう作る→どう運用するか」までカバー範囲が広い一方、SDDの方が「何を作るか」の解像度が高い。

🔰 フェーズ対応図
              ┌─────────────────┐  ┌────────────┐
AI-DLC →     │   Inception      │  │ Construction│  →  Operations
              │ (Mob Elaboration)│  │(Mob Const.) │
              └────────┬─────────┘  └──────┬─────┘
                       │                    │
            ┌──────────┴──────┬─────────────┴──┐  (※SDDは運用不在)
            ▼                 ▼                 ▼
SDD →   Constitution → Specify → Plan → Tasks → Implement
       (憲法)        (仕様)   (計画) (タスク) (実装)

              ↑ AI-DLC の Inception を、SDDは
                Constitution + Specify + Plan + Tasks の4段に解像
位置AI-DLC の段SDD の段（Spec Kit）主な成果物
方針CLAUDE.md / Steering FilesConstitution（憲法）不変の原則・ルール
WhyIntentSpecify（What/Whyのみ）spec.md / intent.md
How（Construction内で扱う）Plan（技術選定はここ）plan.md / design.md
DecomposeUnit分解Tasks（依存DAG付き）units/*.md / tasks.md
BuildBolt実行Implement（タスク順次）code / tests
RunOperations明示的な対応なしrunbook.md
ReflectReflectionDrift Analysis（拡張）reflection.md
⚠️ SDDに「Operations」がないのは思想的欠落ではなく、SDDが「コード生成までの正確性」に焦点を絞っているから。本番運用・障害対応・振り返りまでは別の手法（DevOps/SRE）と組み合わせる前提。AI-DLCは運用まで一気通貫にカバーする。
📘 SDDの「Constitution（憲法）」が独特: プロジェクト全体に常に適用される不変の原則を1ファイルに書き、すべてのフェーズで参照させる。例えば「TDD必須」「最大3プロジェクト構成」など。AI-DLCのCLAUDE.mdに近いが、SDDではこれを強制ゲートとして実装する点が違う。
04

成果物の役割の違い

構造比較

両者ともMarkdown中心だが、成果物の「位置づけ」が根本的に違う。AI-DLCの文書は判断ログ、SDDの文書は実行契約。同じMDファイルでも役割が違う。

🔵 AI-DLC: 判断ログとしての文書

  • 誰がいつ何を決めたかを残す
  • 過程（Mob Elaborationでのやり取り）も記録
  • 後の Reflection で読み返して学習材料に
  • 監査証跡（誰が承認した・AIがどう判断した）

例: bolt-log.md は時系列の判断記録

🟢 SDD: 実行契約としての文書

  • 仕様 = AIへの実行可能な指示
  • コードは仕様から派生する二次成果物
  • 仕様 vs コードの乖離検知が組み込み
  • 仕様は単一真実源（SSOT）

例: spec.md と code が食い違ったら spec が勝つ

観点AI-DLCSDD
主役プロセス（誰が何を決めたか）仕様（何が真実か）
コードの位置主要成果物（仕様と並列）派生物（仕様の実装結果）
文書とコードの関係並走・両方保守仕様優位・コード再生成可
仕様変更時Reflectionで意思決定を記録影響タスクが自動再起動
レガシー対応brownfield: 既存コードから semantic context を抽出既存コードから spec を抽出（リバース）
典型的な文書数多数（intent / units / bolts / reflection / runbook）少数だが厚い（spec / plan / tasks）
🔰 同じ機能を作るときの文書差（チャット機能の例）
─── AI-DLC の場合 ───────────────────────────
intent.md         「ユーザがリアルタイムで会話できる」
units/
  ├ unit-01-message.md  「メッセージ送受信」
  ├ unit-02-history.md  「履歴保存」
  └ unit-03-presence.md 「オンライン状態」
bolts/bolt-log.md   ← 各Boltの判断ログ時系列
reflection.md     ← 終わった後の学び

─── SDD（Spec Kit）の場合 ─────────────────────
specs/003-chat/
  ├ spec.md         「ユーザストーリー＋受入基準（Given-When-Then）」
  ├ plan.md         「WebSocket+PostgreSQL+Redisアーキ」
  ├ research.md     「ライブラリ比較の根拠」
  ├ data-model.md   「Message/Userスキーマ」
  ├ contracts/      「WebSocketイベント定義・REST契約」
  ├ quickstart.md   「動作確認シナリオ」
  └ tasks.md        「依存DAG付きタスクリスト」

  ↑ specs/ 配下が「契約」で、ここが正
✅ SDDの強み: contracts/ ディレクトリ: API契約・データモデル・イベント定義を独立ファイルに切り出すことで、別チームが並行実装しても整合性が保てる。AI-DLCにはこの粒度の契約管理は組み込まれておらず、必要なら自分で導入する。
05

反復粒度の違い（Bolt vs Spec単位）

構造比較

両者の最も実感しやすい違いは「何を1サイクルとするか」。AI-DLCはBolt（数時間〜数日の実装サイクル）が単位。SDDはSpec単位（1機能まるごと）で、Specifyから始めてImplementまで通す。粒度がかなり違う。

🔰 反復粒度の比較
─── AI-DLC ────────────────────────────────
1サイクル = 1 Bolt（数時間〜半日）
  ┌── Plan
  ├── Build
  ├── Self-Review
  └── Human Gate ← 毎Boltで人間承認

  Unit内で何回もBoltを回す。
  Bolt失敗 → 同Boltで再試行 → ダメならUnit再分解

─── SDD ──────────────────────────────────
1サイクル = 1 Spec（1機能まるごと、数日〜1週間）
  ┌── Constitution（プロジェクト初回のみ）
  ├── Specify
  ├── Plan
  ├── Tasks
  └── Implement ← 各Taskを順次自動実行

  Spec単位で完結。
  途中の各フェーズで人間検証ゲート。
観点AI-DLC（Bolt）SDD（Spec単位）
1サイクル時間数時間〜半日数日〜1週間
1サイクルの成果1機能の一部（実装片）1機能まるごと（仕様＋実装）
人間承認回数各Boltで承認（多い）各フェーズで承認（少なめ）
失敗時のロスト1Bolt分（小）1Spec分（やや大）
並行実行Unitが疎結合なら並行可能tasks.md の[P]マーカーで並行可能
文脈引き継ぎbolt-log.md の時系列spec.md → plan.md → tasks.md の階層
📘 Bolt粒度の哲学的理由: AI-DLCがBoltを小さくする理由は、AIのコンテキストウィンドウ制限への対応。Bolt記録をファイルに残すことで、新セッション開始時にAIが「前回どこまでやったか」を読み込める仕組み（state files）。SDDも同様の問題を抱えるが、仕様自体が状態なのでBolt記録は不要、というアプローチ。
⚠️ Spec単位の落とし穴（Sledgehammer問題）: Martin Fowlerチームの観察では、Kiroで小さなバグ修正をやると、4ユーザストーリー＋16受入基準を生成してしまう。Spec単位は機能追加には強いが、小修正には重い。AI-DLCの Adaptive Workflow （タスク規模で省略判断）の方がこの点は柔軟。
✅ 初心者の学習負荷: SDDの方がフェーズ数が少なく（Specify→Plan→Tasks→Implement）、各フェーズが明確に分かれているので最初の理解は早い。AI-DLCはBolt数を自分で見積もる必要があり、最初は粒度がブレやすい。「最初はSDD、慣れたらAI-DLC」という導入順序も有効。
06

人間関与の構造的差

構造比較

両者ともhuman-in-the-loopを掲げるが、「人間が何をするか」が違う。AI-DLCは決定者を集めて即決させる儀式化。SDDは仕様レビューに人間判断を集中するゲート化。

🔵 AI-DLC: 集合的・即時的

  • 関係者が同席（Mob Work）
  • 非同期合意ではなく口頭即決
  • 1Boltに 10〜26 の人間検証ポイント
  • 個人開発では Hat 切替で疑似Mob

哲学: 判断のスループット最大化のため、決定者を物理的に集める

🟢 SDD: 個別・段階的

  • 各フェーズ末で人間が仕様レビュー
  • 非同期可能（PR的レビュー）
  • 仕様の精度を上げることで人間関与を集約
  • "Verify, not steer"（GitHub の表現）

哲学: 仕様レビューに集中し、実装は自動化

🔰 人間関与のタイミング比較
─── AI-DLC（1日のタイムライン） ────────────────
9:00  Mob Elaboration開始（人間×AI同席で議論）
10:30 Intent と Unit を確定
11:00 Bolt 1 開始 [計画] → [承認] → [実装] → [レビュー] → [承認]
13:00 Bolt 2  「          」                       「          」
15:00 Bolt 3  「          」
17:00 振り返り、明日の計画

  ↑ 終日、人間は AI と並走している。AIが暴走しないよう
    細かく承認ゲートを通す。

─── SDD（数日のタイムライン） ──────────────────
Day 1  /speckit.specify → AIがspec.md生成 → 人間レビュー
Day 2  /speckit.plan    → AIがplan.md生成 → 人間レビュー
Day 3  /speckit.tasks   → AIがtasks.md生成 → 人間レビュー
Day 4  /speckit.implement → AIが順次実装（人間は監視のみ）
Day 5  PR作成 → 人間が最終レビュー

  ↑ 各日の終わりに集中レビュー。実装中は基本AI任せ。
観点AI-DLCSDD
関与頻度非常に高い（毎Bolt数回）中程度（フェーズ末に集中）
関与の性質議論・即決・口頭合意仕様レビュー・コメント
非同期可能性低い（同席前提）高い（GitHubのPRワークフローと相性良）
分散チーム適性低い（時差・物理同席が難）高い（時差を超えてレビュー可）
初心者一人開発Hat切替で疑似Mob可能そのまま使える（人間=自分1人で完結）
⚠️ AI-DLCの限界: Mob Work前提が「同期同席できる組織」に制約される。リモート分散チーム・グローバル組織では儀式の実施コストが高い。2025年中頃のモデル性能を前提とした設計のため、2026年の高性能モデルでは検証ポイントが過剰になる懸念も指摘されている（Zenn記事より）。
✅ SDDの強み: 仕様自体が監査証跡になり、誰がいつ承認したかをGit履歴で追える。組織のガバナンス・コンプラ要件（NIST AI RMF・EU AI Act・SOC 2）と相性が良く、規制業界での採用が進んでいる。
07

ツール実装の差

深掘り

ツールの提供形態も対照的。AI-DLCは「方法論＋緩いリファレンス実装」でツール拘束が緩い。SDDは「方法論を実装したツール群」として提供され、ツールごとに体験が違う。

項目AI-DLCSDD
主な実装AWS公式ワークフロー（Amazon Q Rules / Kiro Steering Files）／TheBushidoCollective Claude CodeプラグインGitHub Spec Kit（CLI）／AWS Kiro（IDE）／Tessl／BMAD-METHOD
提供形態Markdown規約 + （任意の）プラグイン専用CLI / IDE / Slash Command
導入の重さ軽い（CLAUDE.md書くだけでも始められる）中（CLIインストール or 専用IDE）
ロックインほぼなし（規約だけ）低〜中（ツールに依存度あり）
カスタマイズ性高い（自分でテンプレ作れる）Spec Kitは高い、Kiroは中
強制力緩い（自分が承認スキップ可）強い（フェーズゲートが組み込まれている）

🔵 AI-DLC を始めるコスト

  • Claude Code（または任意のAIエージェント）があればOK
  • CLAUDE.md とディレクトリ構造を手で作る
  • 方法論の理解に時間がかかる
  • 儀式（Mob）の運用は組織側で工夫

→ 個人で気軽に試せる。ただし規律は自前。

🟢 SDD を始めるコスト

  • Spec Kit: uvx specify init で初期化
  • Slash Command がエージェントに自動展開
  • テンプレートとフェーズ進行が固定
  • Kiro なら専用IDEを入れる

→ レール上を走れる。ただし型に従う必要。

同じClaude Codeで両方を使う場合の準備差
# ─── AI-DLC を始める（前回手順書の通り） ───
mkdir my-ai-dlc-practice && cd my-ai-dlc-practice
mkdir -p aidlc-docs/{intent,units,bolts,design,reflection}
# CLAUDE.md を手で書く（プロジェクト方針）
claude  # 起動して指示で進める

# ─── SDD（Spec Kit）を始める ───
# uv（Python のパッケージランナー）が必要
uvx --from git+https://github.com/github/spec-kit.git specify init my-sdd-project
cd my-sdd-project
# Claude Code 用の slash command が自動配置される
claude
# プロンプト上で /speckit.constitution → /speckit.specify ... と叩く
📘 AI-DLC は思想、SDD は道具という見方もできる。AI-DLCはどのツールでも実践可能（Claude Code でも Cursor でも Cowork でも）。SDDは「Spec Kit を使う」「Kiro を使う」のようにツール選択が方法論実践と紐づく。長く続けるなら思想を学ぶ AI-DLC が、すぐ動かしたいなら道具がある SDD が強い。
08

強み・弱みマトリクス

深掘り

🔵 AI-DLC が向く場面

  • 同席可能なチーム（小・中規模）
  • 速度を最大化したい新規開発
  • 運用・継続学習まで一貫させたい
  • ツール選定に縛られたくない
  • 個人開発でリズムを整えたい

🟢 SDD が向く場面

  • 分散・非同期チーム
  • API・データモデルの整合性が重要
  • 規制業界（金融・医療・公共）
  • 機能追加が中規模以上
  • 既存IDE/エージェントを活かしたい
🚨 両方が苦手な領域: ① 探索的プロトタイピング・PoC（仕様も計画も決まっていない段階） → これは vibe codingの方が速いこともある。② 緊急インシデント対応 → どちらの儀式も時間が掛かりすぎる。「全部AI-DLC/SDDで済ませる」と思わず、軽い手法も併用する判断が必要。

# Step 1: AI-DLCの儀式でSDD仕様を作る

これから AI-DLC の Inception フェーズを始めます。
ただし成果物のフォーマットは SDD（Spec Kit）形式で出力してください。

Mob Elaboration の手順:
1. Product Owner Hat で specs/001-feature/spec.md を生成
   - User Story（As a... I want... So that...）
   - Acceptance Criteria（Given/When/Then）
   - 技術スタックは書かない
2. Architect Hat で specs/001-feature/plan.md を生成
   - 技術スタック・アーキ図・主要ライブラリ選定理由
3. Developer Hat で specs/001-feature/tasks.md を生成
   - 依存DAG付きタスクリスト
   - 各タスクが AI-DLC の 1 Bolt に対応するように粒度調整

各Hatの後で私の承認を待ってください。
判断ログは AI-DLC 流に aidlc-docs/elaboration-log.md に時系列で残してください。

# Step 2: Construction は AI-DLC の Bolt サイクルで回す
#         （tasks.md の各タスク = 1 Bolt として扱う）
✅ このハイブリッドの利点: ① SDDの仕様契約が手に入る（後で他人に渡せる）② AI-DLCの判断ログとReflectionが手に入る（自分の学習が蓄積する）③ 両者の批判（SDDの「小修正に重い」「運用がない」、AI-DLCの「仕様精度が緩い」）を相互に補える。
⚠️ ハイブリッドは中級者向け: 両方の語彙と流れを知らないとどっちつかずになる。最初は片方を1〜2プロジェクト完走してから、足りないと感じた要素を他方から借りるアプローチが現実的。
📘 業界の方向性: 2026年現在、AWS自身が「AI-DLCワークフロー」をオープンソース化（Amazon Q Rules / Kiro Steering Files）し、KiroはSDDのIDEとしても位置づけられている。AWS内部でも両者は補完関係で運用されており、「どちらか」ではなく「どう組み合わせるか」が現代の実践課題になっている。
