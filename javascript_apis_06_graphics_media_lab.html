01

Canvas 2D Context — 線・塗り・グラデーションの基本

✓ iOS ✓ Android

Why exists: SVG はベクタで「図形の意味」を保持するが、写真加工やゲーム画面など ピクセル単位で大量のドット を高速に書き換える用途では DOM 操作のオーバーヘッドが致命的になる。Canvas は HTML 内に 1枚のラスタ(ビットマップ)領域 を確保し、命令で塗り潰す方式に切り替えることでこれを解決する。

💡 利用シーン
  1. 業務アプリでの簡易な手書きサイン入力欄
  2. OutSystems の Wijmo FlexGrid セルにミニチャート (スパークライン) を埋め込む
  3. レポート画面で動的に生成したダイアグラム/QRコードを画像エクスポート
    SVG (ベクタ)              Canvas (ラスタ)
   ┌──────────┐           ┌──────────┐
   │ <circle/>│ ← 図形DOM │ ●●●●●●●●│ ← ピクセル配列
   │ <line/>  │   が残る  │ ●●●●●●●●│   命令後は
   └──────────┘           └──────────┘   ただの絵
        ↓                       ↓
   後から「あの円」を       後から「あの円」は
   個別に動かせる          無い (再描画が必要)

   ─ 命令の流れ ──────────────────────
   getContext('2d') → beginPath → moveTo →
     lineTo → stroke / fill → (毎フレーム繰り返し)
📌 OutSystems文脈での旨味: Wijmo FlexGrid の formatItem で各行に Canvas を仕込めば、サーバ往復なしでセル内チャートが描ける。SVGより軽い。
⚠ Why this fails: Canvas は描いた瞬間に「図形」ではなく「色の海」になる。後から「あの線だけ消したい」はできない — 全消しして描き直す。

function lab1Run() {
  clearLog('lab1-log');
  const cvs = document.getElementById('lab1-canvas');
  const ctx = cvs.getContext('2d');           // ← 2D描画コンテキスト取得
  ctx.clearRect(0, 0, cvs.width, cvs.height);

  // 1. 線 (stroke)
  ctx.strokeStyle = '#0969da';
  ctx.lineWidth = 3;
  ctx.beginPath();
  ctx.moveTo(20, 30); ctx.lineTo(120, 30);
  ctx.stroke();

  // 2. 塗り (fill)
  ctx.fillStyle = '#1a7f37';
  ctx.fillRect(20, 50, 100, 40);

  // 3. グラデーション
  const grad = ctx.createLinearGradient(140, 0, 300, 0);
  grad.addColorStop(0, '#bf3989');
  grad.addColorStop(1, '#fb8500');
  ctx.fillStyle = grad;
  ctx.fillRect(140, 50, 160, 80);

  console.log('描画完了: 3要素');
  setBA('lab1', '(空のcanvas)', '線+矩形+グラデ');
}
02

Path2D — パスをオブジェクトとして使い回す

✓ iOS ✓ Android

Why this design: 通常の Canvas API は「命令の連続実行」スタイル。しかし同じ図形を毎フレーム何百個も描くゲームや可視化では、毎回 beginPath → moveTo → lineTo... を呼ぶのは冗長。Path2D は パスを1つのオブジェクトに保存 し、ctx.fill(path) / ctx.stroke(path) で何度でも再利用できる。SVGパス文字列("M10 10 L50 50")も受け取れる。

💡 利用シーン
  1. 地図上に同じアイコン(★)を100箇所描く
  2. SVG パスを Canvas に流し込む(svg→canvas変換ライブラリ不要)
  3. ヒットテスト: ctx.isPointInPath(path, x, y) でクリック判定
   毎回命令         vs        Path2D化
   ─────────────────────────────────────
   for (i of 100) {            const star = new Path2D();
     ctx.beginPath();          star.moveTo(...);
     ctx.moveTo(...);          star.lineTo(...);
     ctx.lineTo(...);          // ─ 1回作る ─
     ctx.fill();               for (i of 100) {
   }                             ctx.translate(...);
   ↑ 命令の文字列を              ctx.fill(star);  ← 使い回し
     パーサが毎回処理            }
📌 OutSystems文脈での旨味: Wijmo FlexGrid の数千セルにアイコンを描く場合、Path2D を ScreenAction で1度組み立て、formatItem で都度 fill するだけ。CPU負荷が目に見えて減る。

function lab2Run() {
  clearLog('lab2-log');
  const cvs = document.getElementById('lab2-canvas');
  const ctx = cvs.getContext('2d');
  ctx.clearRect(0, 0, cvs.width, cvs.height);

  // SVGパス文字列で星を1つ作る (パスは1度だけ作る)
  const star = new Path2D(
    'M 0 -20 L 6 -6 L 20 -6 L 9 3 L 13 17 L 0 9 L -13 17 L -9 3 L -20 -6 L -6 -6 Z'
  );
  ctx.fillStyle = '#fb8500';

  // 5箇所に同じ star を使い回し
  for (let i = 0; i < 5; i++) {
    ctx.save();
    ctx.translate(40 + i * 60, 60);
    ctx.fill(star);    // ← 同じパスを再利用
    ctx.restore();
  }

  console.log('Path2D を 5回 fill (生成は1度のみ)');
  setBA('lab2', '(命令を100行書く)', 'パス1つを使い回し');
}
03

ImageData — ピクセル配列を直接読み書き

✓ iOS ✓ Android

Why care: 画像処理(明度反転・グレースケール・エッジ検出)は サーバ往復なしで JS だけ で完結できる。getImageData で取得できる ImageData.data は Uint8ClampedArray で [R, G, B, A, R, G, B, A, ...] の並び。1ピクセル = 4バイト、長さ = width × height × 4。

💡 利用シーン
  1. 業務アプリで、撮影した画像を「白黒モード」で印刷プレビュー
  2. QRコード読取の前処理(コントラスト強調)
  3. サムネイルからの平均色抽出 (UIテーマ自動生成)
   ImageData.data の中身
   ┌──┬──┬──┬──┬──┬──┬──┬──┬─...
   │R │G │B │A │R │G │B │A │
   └──┴──┴──┴──┴──┴──┴──┴──┴─...
    pixel(0,0)    pixel(1,0)

   グレースケール変換:
     gray = 0.299*R + 0.587*G + 0.114*B
     R = G = B = gray

   反転 (ネガ):
     R = 255 - R
     G = 255 - G
     B = 255 - B
     (Aはいじらない)
📌 OutSystems文脈での旨味: 印刷向けにカラー画像をモノクロ化する処理を Extension (C#) で書かなくても、ブラウザ側で前処理できる。サーバCPU・帯域を節約。
⚠ Why this fails: data[i] = 300 としても自動で 255 にクランプされる(Uint8ClampedArray)。普通の Uint8Array ならオーバーフローして 44 になる — この型の選択も「なぜ」がある。

function lab3Run() {
  clearLog('lab3-log');
  const cvs = document.getElementById('lab3-canvas');
  const ctx = cvs.getContext('2d');

  // 1. グラデを描く
  const g = ctx.createLinearGradient(0, 0, cvs.width, 0);
  g.addColorStop(0, '#0969da');
  g.addColorStop(1, '#fb8500');
  ctx.fillStyle = g;
  ctx.fillRect(0, 0, cvs.width, cvs.height);

  // 2. ピクセル配列を取得
  const img = ctx.getImageData(0, 0, cvs.width, cvs.height);
  const d = img.data;
  console.log('総バイト数:', d.length, '(=' + cvs.width + '×' + cvs.height + '×4)');

  // 3. 反転 (R, G, B のみ; A はそのまま)
  for (let i = 0; i < d.length; i += 4) {
    d[i]     = 255 - d[i];      // R
    d[i + 1] = 255 - d[i + 1];  // G
    d[i + 2] = 255 - d[i + 2];  // B
  }

  // 4. 戻す
  ctx.putImageData(img, 0, 0);
  console.log('色反転完了');
  setBA('lab3', '青→橙のグラデ', '橙→青(色反転)');
}
04

Canvas → Blob / DataURL — 画像化の2方式

✓ iOS ✓ Android

Why this design: Canvas の絵を「サーバへ送る/ダウンロードさせる」には画像形式に変換する必要がある。toDataURL() は 同期 で巨大な base64 文字列を返す(メモリ食う・UIブロック)。toBlob() は 非同期 で Blob (バイナリ) を返す(効率的・推奨)。どちらも結果は同じ画像だが、サイズと API の形が違う。

💡 利用シーン
  1. サインパッドで描いた絵を OutSystems 側へ Blob 送信(File 04 の FormData/fetch と組み合わせ)
  2. レポート画面のチャートを「画像保存」ボタンでダウンロード
  3. SNS シェア用に <img src="data:..."> を即座に作る
   toDataURL()                  toBlob()
   ┌─────────────────┐          ┌─────────────────┐
   │ Canvas          │          │ Canvas          │
   └────────┬────────┘          └────────┬────────┘
            ↓ (同期・UIブロック)          ↓ (非同期・コールバック)
   "data:image/png;base64,         Blob {size: 4321, type:
    iVBORw0KG...(数百KB文字列)..." │       "image/png"}
            ↓                              ↓
   img.src= で即表示              URL.createObjectURL() or
   サイズ ≒ 元画像 × 1.33         FormData append で送信
   (base64オーバーヘッド)         サイズ = 元画像のまま
📌 OutSystems文脈での旨味: 大きな画像を toDataURL で送ると ~33%膨張 + サーバ側で base64 デコードが要る。toBlob + FormData なら無駄なし、Extension (C#) でも byte[] でそのまま受けられる。
⚠ Why this fails: toDataURL は同期なので、4K 画像で 200ms 以上 UI が固まる。toBlob はコールバックで結果を受けるか await できる。

function lab4Run() {
  clearLog('lab4-log');
  const cvs = document.getElementById('lab4-canvas');
  const ctx = cvs.getContext('2d');
  // 何か描く
  ctx.fillStyle = '#0969da';

  ctx.fillStyle = '#fff';
  ctx.font = '20px sans-serif';
  ctx.fillText('Hello', 60, 60);

  // 1) 同期 toDataURL

  console.log('DataURL長:', dataUrl.length, '文字');
  console.log('先頭:', dataUrl.slice(0, 30) + '...');

    console.log('Blob type:', blob.type);

    const ratio = (dataUrl.length / blob.size).toFixed(2);
    console.log('DataURL / Blob 比:', ratio, '(理論値≒1.33)');
    setBA('lab4',
      'DataURL: ' + dataUrl.length + '字',
      'Blob: ' + blob.size + 'B (' + ratio + '倍)');
  }, 'image/png');
}

OffscreenCanvas — DOM外で描く

✓ iOS 16.4+ ✓ Android

Why exists: 通常の <canvas> はメインスレッドでしか描けない。重い描画(数千個のパーティクル等)を回すと UI が固まる。OffscreenCanvas は DOMから切り離されたCanvasで、Worker に transferControlToOffscreen() で渡せば 別スレッドで描画できる。メインスレッドは UI に専念できる。

💡 利用シーン
  1. レポート画面の重いチャートを Worker で生成し、結果だけメインに転送
  2. サムネイル一括生成(数百枚)を Worker で並列処理
  3. ゲーム/可視化で 60fps を維持したいとき
   通常の Canvas                OffscreenCanvas
   ─────────────────────────────────────────────
   メインスレッド               メインスレッド          Worker
   ├ UIイベント                 ├ UIイベント            ├ 重い描画
   ├ 重い描画 ← 競合            └ <canvas> 表示のみ    └ ImageBitmap生成
   └ <canvas> 表示              ↑ ↓ postMessage         ↓
                                └─── ImageBitmap ←────┘
   UI が固まる                  UI なめらか
📌 OutSystems文脈での旨味: Wijmo の数千行に対する「全行サムネイル生成」のような処理を Worker に逃がせば、画面のスクロールが詰まらない。
⚠ Why this fails: transferControlToOffscreen() は 1度しか呼べない。同じ canvas を2度 Worker に渡そうとするとエラー。所有権が移譲される設計。

function lab5Run() {
  clearLog('lab5-log');
  if (typeof OffscreenCanvas === 'undefined') {
    console.log('このブラウザは OffscreenCanvas 非対応');
    setBA('lab5', '非対応', '非対応');
    return;
  }
  // メインスレッド内でも OffscreenCanvas は使える (描画 → 結果転送のテスト)
  const off = new OffscreenCanvas(320, 100);
  const ctx = off.getContext('2d');
  ctx.fillStyle = '#1a7f37';
  ctx.fillRect(10, 10, 300, 80);
  ctx.fillStyle = '#fff';
  ctx.font = 'bold 24px sans-serif';
  ctx.fillText('Drawn off-DOM', 60, 60);

  // ImageBitmap として取り出し → 表示用Canvasへ
  off.convertToBlob().then(blob => {
    console.log('Offscreen → Blob:', blob.size, 'bytes');
    const img = new Image();
    img.onload = () => {
      const main = document.getElementById('lab5-canvas');
      main.getContext('2d').drawImage(img, 0, 0);
      setBA('lab5', '(空)', 'Offscreen描画→転送完了');
    };
    img.src = URL.createObjectURL(blob);
  });
  console.log('OffscreenCanvas 320x100 を生成、描画中...');
}

<video> 制御 — play/pause/currentTime/playbackRate

✓ iOS ✓ Android

Why exists: HTML5 以前は動画再生に Flash プラグインが必要だった。<video> 要素は OS標準のデコーダを使ってブラウザネイティブで再生 する仕組みで、JS から再生位置・速度・音量をプロパティ操作で制御できる。ファイルを「読み込んで描画する」のではなく、ブラウザに任せる + フックで操る 設計。

💡 利用シーン
  1. OutSystems 製の社内研修ポータルで、章ごとにジャンプボタン (currentTime)
  2. 速度可変の再生 (playbackRate = 1.5) でレビュー時短
  3. 「次の動画へ」自動遷移 (ended イベントで次のIDをセット)
   主要プロパティ              主要メソッド・イベント
   ────────────────────        ──────────────────────────
   currentTime  : 秒(double)   .play() / .pause()
   duration     : 秒(double)   loadedmetadata: durationが入る
   playbackRate : 1.0が等速    timeupdate    : 250ms毎に発火
   volume       : 0.0〜1.0     ended         : 再生終了
   muted        : true/false   play / pause  : 状態変化

   状態遷移:
   [stopped] --play()--> [playing] --pause()--> [paused]
                              ↓
                           [ended]
📌 OutSystems文脈での旨味: 動画教材アプリで「再生済み区間」を localStorage に保存して、次回起動時に currentTime を復元するだけで進捗管理が完成。

<audio> 制御 — volume/loop/muted

✓ iOS ✓ Android

Why this design: <audio> は <video> と同じ HTMLMediaElement を継承(プロパティ・イベントが共通)。だから currentTime, play(), ended イベントの使い方は video と全く同じ — 覚えるべきAPIは1つ で良い設計になっている。違いは表示UI (controls時) のみ。

💡 利用シーン
  1. 業務アプリの「保存しました」効果音(volume小さめ)
  2. BGM ループ (loop=true)
  3. 消音切替トグル (muted切替)
   HTMLMediaElement (基底)
        ↑                 ↑
   HTMLVideoElement   HTMLAudioElement
        │                 │
        └─ 共通プロパティ ─┘
           play() / pause() / currentTime
           volume / muted / loop
           ended / timeupdate / canplay

   ボリューム関連:
   ───────────────────────────────────
   volume  = 0.0〜1.0  小さく/大きく
   muted   = true/false 一時消音(volumeは保持)
   ─────────────────
   実効音量 = muted ? 0 : volume * (デバイス音量)

08

Media events — メタデータと再生位置の発火順

✓ iOS ✓ Android

Why this design: 動画/音声の状態変化は 1イベントにまとめず段階別に分けた。loadedmetadata = duration が入る、canplay = ある程度再生可能、timeupdate = 250ms毎、ended = 再生終了。「いつ何ができるようになったか」を細かく拾える設計で、UI を段階的に有効化できる。

💡 利用シーン
  1. loadedmetadata で「シークバー長」を確定して表示
  2. timeupdate で進捗バーを更新(ただし高頻度なので注意)
  3. ended で次の動画へ自動遷移、または「視聴完了」を記録
   時系列でのイベント発火順
   ─────────────────────────────────────────
   [src設定]
       ↓
   loadedmetadata  ← duration が確定 (秒数表示OK)
       ↓
   loadeddata      ← 1フレーム描画可能
       ↓
   canplay         ← 一時的にでも再生可能
       ↓ (play())
   playing         ← 実際に再生開始
       ↓
   timeupdate × N  ← 250ms 毎 (currentTime更新)
       ↓
   ended           ← 最後まで再生完了

   ⚠ timeupdate は 250ms毎 — 重い処理を入れるとカクつく
📌 OutSystems文脈での旨味: timeupdate を全て拾わず、5秒に1回だけ進捗を localStorage に書く実装にすればパフォーマンスを保てる(throttle)。

function lab8Run() {
  clearLog('lab8-log');
  const v = document.getElementById('lab8-video');
  let tuCount = 0;

  const events = ['loadedmetadata', 'loadeddata', 'canplay',
                  'play', 'playing', 'pause', 'ended'];
  events.forEach(name => {
    v.addEventListener(name, () => {
      console.log('▶ ' + name + ' / time=' + v.currentTime.toFixed(2));
    }, { once: false });
  });

WebGL2 三角形 — シェーダ + バッファ最小例

✓ iOS 15+ ✓ Android

Why exists: Canvas 2D は CPU描画。数千〜数万の頂点を毎フレーム描くと CPU が持たない。WebGL は GPU に頂点データとシェーダ(プログラム)を流し込んで GPU側で並列計算させる。学習コストは高いが、達成可能な描画量は別世界。

💡 利用シーン
  1. 大規模散布図 (数十万点) のリアルタイム描画
  2. 3D 製品ビューワ (Three.js が内部でWebGL利用)
  3. 地図系の重ね合わせ可視化 (mapboxGL等)
   WebGL の登場人物
   ─────────────────────────────────────────
   [JS側]                       [GPU側]
   ① 頂点データ ──────────────→ Vertex Buffer
   ② シェーダソース ──compile─→ Vertex Shader
                            └→ Fragment Shader
   ③ drawArrays() ────────────→ 並列実行!

   Vertex Shader   : 頂点ごとに1回 (位置を決める)
   Fragment Shader : ピクセルごとに1回 (色を決める)

   今回の最小例:
     3頂点(三角形) → 各頂点にRGB色 → ピクセル補間
📌 OutSystems文脈での旨味: 重い可視化を OutSystems の Block 内で作る場合、Three.js (内部 WebGL) を使えばサーバ側 Extension を書かずに済む。
⚠ Why this fails: シェーダはGPU向けの「別言語(GLSL)」。型・改行・セミコロンが厳格で、コンパイルエラーが出ると getShaderInfoLog で確認しないと原因不明になる。

function lab10Run() {
  clearLog('lab10-log');
  const cvs = document.getElementById('lab10-canvas');
  const gl = cvs.getContext('webgl2');
  if (!gl) { console.log('WebGL2 非対応'); setBA('lab10','非対応','非対応'); return; }

  // Vertex Shader (位置と色を Fragment へ渡す)
  const vsrc = `#version 300 es
    in vec2 a_pos;
    in vec3 a_col;
    out vec3 v_col;
    void main() { gl_Position = vec4(a_pos, 0, 1); v_col = a_col; }`;
  // Fragment Shader (色を出力)
  const fsrc = `#version 300 es
    precision mediump float;
    in vec3 v_col;
    out vec4 outColor;
    void main() { outColor = vec4(v_col, 1); }`;

  const compile = (type, src) => {
    const sh = gl.createShader(type);
    gl.shaderSource(sh, src); gl.compileShader(sh);
    if (!gl.getShaderParameter(sh, gl.COMPILE_STATUS))
      console.log('shader err:', gl.getShaderInfoLog(sh));
    return sh;
  };
  const prog = gl.createProgram();
  gl.attachShader(prog, compile(gl.VERTEX_SHADER, vsrc));
  gl.attachShader(prog, compile(gl.FRAGMENT_SHADER, fsrc));
  gl.linkProgram(prog); gl.useProgram(prog);

  // 頂点データ (x, y, R, G, B) × 3頂点
  const data = new Float32Array([
     0.0,  0.8,  1, 0, 0,   // 上 赤
    -0.8, -0.8,  0, 1, 0,   // 左下 緑
     0.8, -0.8,  0, 0, 1    // 右下 青
  ]);
  const buf = gl.createBuffer();
  gl.bindBuffer(gl.ARRAY_BUFFER, buf);
  gl.bufferData(gl.ARRAY_BUFFER, data, gl.STATIC_DRAW);

  const aPos = gl.getAttribLocation(prog, 'a_pos');
  const aCol = gl.getAttribLocation(prog, 'a_col');
  gl.enableVertexAttribArray(aPos);
  gl.vertexAttribPointer(aPos, 2, gl.FLOAT, false, 5*4, 0);
  gl.enableVertexAttribArray(aCol);
  gl.vertexAttribPointer(aCol, 3, gl.FLOAT, false, 5*4, 2*4);

  gl.clearColor(0, 0, 0, 1); gl.clear(gl.COLOR_BUFFER_BIT);
  gl.drawArrays(gl.TRIANGLES, 0, 3);

  console.log('GPU描画完了: 3頂点 / 各頂点RGB / 補間でグラデ');
  setBA('lab10', '黒画面', 'RGB三角形');
}

⚠ HTTPS必須 ✓ iOS 14.3+ ✓ Android

Why care: MediaStream は「リアルタイムの音/映像」だが、ファイルとして保存・送信するにはエンコードが必要。MediaRecorder は MediaStream を受け取り、chunkずつ Blob を吐き出す。録画停止後に全 chunk を1つの Blob に結合 → そのままアップロードや再生に使える。

💡 利用シーン
  1. 業務アプリで「現場の声」を録音 → サーバ送信

   MediaStream → MediaRecorder → Blob
   ──────────────────────────────────────────
   stream  ┌─────────────────┐  Blob chunks

✓ iOS ✓ Android

Why exists: <audio> は「ファイル再生」専用。ゲームの効果音、ピアノ音、シンセサイザのように 音を JS で生成・加工 したい用途には不足。Web Audio API は ノードを繋ぐグラフ(オーディオの Stream API みたいなもの)で、Oscillator(発振器) → Gain(音量) → Destination(スピーカ) と連結する。

  osc.connect(gain).connect(ctx.destination);

  osc.start(ctx.currentTime);
  osc.stop(ctx.currentTime + 0.5);    // 0.5秒後に停止

  const bins = analyser.frequencyBinCount;  // = 128
  const data = new Uint8Array(bins);

  // 音量を抑えめに
  const gain = ctx.createGain();
  gain.gain.value = 0.05;

  // 接続: Osc → Analyser → Gain → Dest
  osc.connect(analyser).connect(gain).connect(ctx.destination);

  osc.start();
  osc.stop(ctx.currentTime + 3);

  // Canvas に毎フレーム描画
  const cvs = document.getElementById('lab15-canvas');
  const cctx = cvs.getContext('2d');
  let frame = 0;
  function draw() {
    if (ctx.currentTime > osc.__stopAt) return;
    analyser.getByteFrequencyData(data);
    cctx.fillStyle = '#0d1117';
    cctx.fillRect(0, 0, cvs.width, cvs.height);
    const barW = cvs.width / bins;
    for (let i = 0; i < bins; i++) {
      const h = (data[i] / 255) * cvs.height;
      cctx.fillStyle = 'hsl(' + (i * 2) + ', 80%, 55%)';
      cctx.fillRect(i * barW, cvs.height - h, barW - 1, h);
    }
    frame++;
    requestAnimationFrame(draw);
  }
  osc.__stopAt = ctx.currentTime + 3;
  draw();

  console.log('Sawtooth 220→880Hz / 3秒 + 周波数可視化');
  setBA('lab15', '黒画面', '可視化中…');
}
