なぜ生成パターンが必要なのか — 4 大症状

概観

生成パターンはどれも「new の書かれ方を整える」ためにある。 具体クラスを直接 new する状態だと、変更のたびにコード中の new を全部探して直す羽目になる。 まず「どの症状にどのパターンが効くか」の全体像を頭に入れる。

🔰 4 大症状 → 候補パターン
┌─────────────────────────────────────────────┐
│ 症状                              │ パターン  │
├───────────────────────────────────┼──────────┤
│ ① 関連するモノの整合性が崩れる    │ Abstract │
│   (Win Button と Mac Check が混在) │ Factory  │
├───────────────────────────────────┼──────────┤
│ ② コンストラクタの引数が多すぎる  │ Builder  │
│   ("thin", true, false, null...)  │          │
├───────────────────────────────────┼──────────┤
│ ③ 共通処理に new XxxImpl() が直書き│ Factory  │
│   (派生で再利用できない)          │ Method   │
├───────────────────────────────────┼──────────┤
│ ④ 重い初期化を毎回繰り返す        │ Prototype│
│   (DB アクセス、計算、etc)         │          │
├───────────────────────────────────┼──────────┤
│ ⑤ 1 つだけのはずが複数できる      │ Singleton│
│   (設定が画面ごとにバラバラ)      │          │
└───────────────────────────────────┴──────────┘
パターン何を分離するか主な目的
Abstract Factory部品のセット整合性の保証
Builder組み立て手順可読性・任意項目
Factory Method生成の一行共通フローの再利用
Prototype初期化と複製性能・状態継承
Singletonインスタンス数一意性の保証
01

Abstract Factory — 「セットの整合性」を型で守る

中級

OS 別 UI を作るとき、ボタン・チェックボックス・ダイアログをそれぞれ独立に作ると、 「Windows のボタン」と「Mac のチェックボックス」が混在する事故が起こりうる。 Abstract Factory は 「整合性」をランタイムの注意力からコンパイル時の型に格上げする パターン。

✗ Before — OS 分岐があちこち
// 利用側1: ログイン画面
const button   = isMac ? new MacButton()   : new WinButton();
const checkbox = isMac ? new MacCheckbox() : new WinCheckbox();

// 利用側2: 設定画面（同じ分岐をまた書く）
const button2   = isMac ? new MacButton()   : new WinButton();
const checkbox2 = isMac ? new MacCheckbox() : new WinCheckbox();

// 利用側3: ダイアログ画面
const button3   = isWin ? new WinButton()   : new MacButton();
//                ^^^^^ うっかり判定反転 → 不整合発生
const checkbox3 = isMac ? new MacCheckbox() : new WinCheckbox();
// → Win Button + Mac Checkbox の混在事故
✓ After — ファクトリ選択は1回だけ
interface UIFactory {
  createButton():   Button;
  createCheckbox(): Checkbox;
}

// OS 判定はアプリ起動時の1箇所だけ
const factory: UIFactory = isMac
  ? new MacFactory()
  : new WinFactory();

// 以降、利用側はすべて同じ — 整合性は型が保証
const button   = factory.createButton();
const checkbox = factory.createCheckbox();
// factory が Mac/Win を覚えているので絶対混ざらない

// 別画面でも同じ factory を使い回す
const button2   = factory.createButton();
const checkbox2 = factory.createCheckbox();
📘 Before/After の核心: Before は「OS 判定」が画面の数だけ複製され、判定ミスで混在事故が起こる。 After は OS 判定が アプリ起動時の1箇所だけ。利用側コードは具体クラスを一切知らず、 整合性はファクトリオブジェクト経由で 型システムが構造的に保証 する。
観点BeforeAfter
OS 判定箇所画面 × 部品の数だけ重複アプリ起動時に1箇所
混在事故判定ミスで起こりうる型で構造的に防止
OS 追加コスト全画面を修正LinuxFactory を1クラス追加
テスト画面ごとに OS 別テスト要MockFactory で一発置換
02

Builder — 「読めないコンストラクタ」を組み立て手順に

基本

引数が多いコンストラクタは「位置」で意味が決まるため、読めない・間違えやすい・型が通っても意味は壊れる、という三重苦。 Builder は 「位置」依存を「名前付きメソッド呼び出し」に置き換えて読みやすさを取り戻す パターン。

✗ Before — 位置引数地獄
class Pizza {
  constructor(
    dough: string, sauce: string,
    cheese: boolean, pepperoni: boolean,
    mushroom: boolean, olive: string|null,
    size: string
  ) { }
}

// これ読んで意味が分かるか？
const p1 = new Pizza(
  "thin", "tomato",
  true, false, true,
  null, "regular"
);

// うっかり順番ミス（型は通る）
const p2 = new Pizza(
  "tomato", "thin", // ← 逆
  true, false, true, null, "regular"
);
// → 実行時に「謎の生地: tomato」

// 「キノコ抜きでオリーブだけ」
const p3 = new Pizza(
  "thin", "tomato",
  false, false, false, // 全部 false 並ぶ虚しさ
  "黒", "regular"
);
✓ After — 自己説明的なチェーン
class PizzaBuilder {
  private toppings: string[] = [];
  constructor(
    private dough: string,
    private sauce: string
  ) {} // 必須はここ

  addTopping(t: string) {
    this.toppings.push(t); return this;
  }
  build() {
    return new Pizza(
      this.dough, this.sauce, this.toppings
    );
  }
}

// 各行が意図を語る
const pizza = new PizzaBuilder("thin", "tomato")
  .addTopping("cheese")
  .addTopping("basil")
  .build();

// 「キノコ抜きでオリーブだけ」も自然
const pizza2 = new PizzaBuilder("thin", "tomato")
  .addTopping("olive-黒")
  .build();
// 不要なものは「呼ばない」だけで済む
✅ Before/After の核心: Before は (true, false, true, null) という意味不明な並び。 After は各メソッド呼び出しが「何を追加しているか」を自己説明する。任意項目は「呼ばない」だけ で済むので、 null や false をプレースホルダとして並べる必要が消える。
観点Before（位置引数）After（Builder）
可読性引数の意味が読めない各行が意図を語る
順番ミス型が通れば実行時バグ名前付きで発生不能
任意項目null / false を並べるメソッドを呼ばないだけ
必須項目区別不能コンストラクタに置けば必須化
拡張引数追加で全呼出を改変メソッド追加で既存呼出は無傷
03

Factory Method — 「骨格は親、生成だけ子」

中級

共通処理の中で「具体クラスを new する一行」だけが派生先で違うとき、 共通処理ごと派生クラスにコピペすると DRY 違反。 Factory Method は 共通処理を親に1回だけ書き、生成の一行を「穴」として子に埋めさせる パターン。

✗ Before — 共通処理がコピペ
class WinDialog {
  render() {
    this.layout();           // 共通
    const btn = new WinButton(); // ★Win 固有
    btn.render();
    this.cleanup();          // 共通
  }
  layout()  { /* 共通実装 */ }
  cleanup() { /* 共通実装 */ }
}

class WebDialog {
  render() {
    this.layout();           // ← コピペ
    const btn = new HtmlButton();// ★Web 固有
    btn.render();
    this.cleanup();          // ← コピペ
  }
  layout()  { /* ← コピペ */ }
  cleanup() { /* ← コピペ */ }
}

// layout() のバグを直すと、両クラスを修正
// する必要 → 必ず修正漏れが出る
✓ After — 生成だけ子に委譲
abstract class Dialog {
  // 共通処理は親に1回だけ
  render() {
    this.layout();
    const btn = this.createButton(); // 穴
    btn.render();
    this.cleanup();
  }
  layout()  { /* 親で1回だけ */ }
  cleanup() { /* 親で1回だけ */ }
  protected abstract createButton(): Button;
}

class WinDialog extends Dialog {
  protected createButton() {
    return new WinButton();   // 穴埋め
  }
}
class WebDialog extends Dialog {
  protected createButton() {
    return new HtmlButton();  // 穴埋め
  }
}

// layout() のバグ修正は親1箇所
// → 全派生に自動反映
🔰 「穴を埋める」イメージ
親 Dialog.render() の流れ：
   ┌─────────────┐
   │ layout()    │ ← 親で実装済
   ├─────────────┤
   │ createButton│ ← 「穴」 abstract method
   │  ()         │   サブクラスが埋める
   ├─────────────┤
   │ btn.render()│ ← 親で実装済
   ├─────────────┤
   │ cleanup()   │ ← 親で実装済
   └─────────────┘
       ↑
       WinDialog: createButton → WinButton
       WebDialog: createButton → HtmlButton
📘 Abstract Factory との対比: Abstract Factory は「セット工場」を 別オブジェクトとして 持つ（コンポジション）。 Factory Method は「親メソッドの一部を子で埋める」（継承）。 前者は 複数部品の整合性 が主目的、後者は 共通フローの再利用 が主目的。
観点BeforeAfter
共通処理派生ごとに重複親で1回だけ
バグ修正全派生を直す親1箇所で全派生に反映
新派生追加render() 全体をコピペcreateButton() だけ書く
04

Prototype — 「重い初期化」を 1 回だけ

中級

DB アクセスや複雑計算を伴う初期化を、毎回 new で繰り返すとパフォーマンスが死ぬ。 Prototype は 「初期化コスト」を「メモリコピーコスト」にすり替える パターン。 Flyweight が「同じものを共有」 なのに対して、Prototype は「同じものを増殖」 が目的。

✗ Before — 毎回 DB アクセス
class CustomerProfile {
  constructor(customerId: string) {
    // 重い初期化（毎回走る）
    this.basicInfo    = db.query(...); // 100ms
    this.permissions  = db.query(...); //  80ms
    this.preferences  = db.query(...); //  50ms
    this.computedTier = computeTier(...);// 30ms
  }
}

// テスト用に 100 個のバリエーションを作りたい
for (let i = 0; i < 100; i++) {
  const v = new CustomerProfile("base-001");
  v.preferences.theme = themes[i % 10];
}
// 100 × 260ms = 26 秒
// DB に 400 回クエリが飛ぶ → 本番なら DBA に怒られる
✓ After — 雛形 1 回 + clone
class CustomerProfile {
  constructor(customerId: string) {
    // 重い初期化（1 回だけ実行される）
    this.basicInfo   = db.query(...);
    this.permissions = db.query(...);
    /* ... */
  }
  clone(): CustomerProfile {
    const c = Object.create(CustomerProfile.prototype);
    c.basicInfo   = { ...this.basicInfo };
    c.permissions = [...this.permissions];
    c.preferences = { ...this.preferences };
    return c; // DB アクセスなし
  }
}

const template = new CustomerProfile("base-001"); // 260ms 1回
for (let i = 0; i < 100; i++) {
  const v = template.clone(); // メモリコピー ≈ 1ms
  v.preferences.theme = themes[i % 10];
}
// 合計 ≈ 360ms
// DB に 4 回しかクエリが飛ばない
✅ Before/After の核心: Before は 100 個のインスタンスを作るのに 26 秒・DB クエリ 400 回。 After は 雛形を1回作って clone を100回 で、合計 0.36 秒・DB クエリ 4 回。 クラスが変わらず、利用方法も変わらないまま、コスト構造だけが激変 する。
観点BeforeAfter
100 個生成の時間≈ 26 秒≈ 0.36 秒
DB クエリ数400 回4 回
「現在の状態」を保持したコピー不可（再初期化）可能（clone 時点を継承）

Singleton — 「1 つだけ」を保証する代わりに支払う代償

注意

設定オブジェクトが複数できると「ある画面は古い設定、別の画面は新しい設定」という不整合が発生する。 Singleton は 「インスタンス数」を1に固定 するパターンだが、 テスタビリティを犠牲にする副作用がある。使うかどうかの判断こそが本パターンの肝。

✗ Before — 自由に new されてバラバラ
class Config {
  constructor(
    public env = "production",
    public apiUrl = "https://api.example.com"
  ) {}
}

// 画面 A — テストモードに切替えたつもり
const configA = new Config();
configA.apiUrl = "https://test.example.com";

// 画面 B — 別インスタンスができてしまう
const configB = new Config();
// configB.apiUrl = "https://api.example.com" のまま

// 画面 C
const configC = new Config();

// 結果:
// 画面 A だけ test URL を叩く
// 画面 B/C は本番 URL を叩く
// → デバッグで何時間も溶ける
✓ After — getInstance 経由のみ
class Config {
  private static instance: Config;

  private constructor(
    public env = "production",
    public apiUrl = "https://api.example.com"
  ) {} // ← private で外部 new を禁止

  static getInstance(): Config {
    if (!Config.instance)
      Config.instance = new Config();
    return Config.instance;
  }
}

// new Config() ← コンパイルエラー
const a = Config.getInstance();
a.apiUrl = "https://test.example.com";

const b = Config.getInstance();
console.log(b.apiUrl); // "https://test..."
console.log(a === b);  // true — 同じ実体

// 画面 A/B/C すべて同じインスタンス
// → 設定の不整合は構造的に起こらない
⚠️ Singleton の副作用: After のコードはテストで Config をモック化したいときに困る。 getInstance() はコード中のどこからでも呼べるグローバルアクセスなので、 テスト用に差し替える仕組みを別途用意する必要がある。「グローバル変数の言い換え」になりがちな点が最大の弱点。
✅ 現代的な代替: DI（依存性注入）。 クラスのコンストラクタで Config を引数として受け取れば、 本番では本物、テストではモックを 呼び出し側が選んで渡せる。 迷ったら DI を優先し、Singleton は 本当に1つでないと困るもの（OS のクロック、起動時環境変数）に限定する。 
// DI 版（推奨）
class OrderService {
  constructor(private config: Config) {} // ← 引数で受け取る
  process(order: Order) {
    const url = this.config.apiUrl;
  }
}

// 本番
const service     = new OrderService(realConfig);
// テスト
const testService = new OrderService(mockConfig); // ← 簡単に差替
観点BeforeAfter (Singleton)
インスタンス数制御不能構造的に1つ
設定の不整合起こりうる起こりえない
リソース重複接続プール多重生成リスク1つに収束
テスタビリティ○ 自由にモック作成× 差し替えづらい
依存関係の可視性○ 引数から見える× コード中に隠れる
06

使い分け即決マップ — 症状からパターンへ

総合

実務でパターンを思い出すための「症状 → 候補」逆引き。 最初から「Builder で設計する」と決めるのではなく、 「コードがこう見えてきた」という症状からパターンに到達する のが健全な使い方。

🔰 症状別 即決チャート
「コンストラクタの引数が4個以上 / null 飛ばし」     → Builder
「new XXX が画面の数だけ散らばっている」              → Factory Method
「関連する複数の部品の混在事故が起きそう」            → Abstract Factory
「インスタンスは1つだけ欲しい（が DI も検討）」       → Singleton
「重い初期化を何度もやっている」                      → Prototype

  ─────────── 判定の優先順序 ───────────
  ① まず Builder か検討（引数の見た目）
  ② new が散らばっていたら Factory Method
  ③ 部品セットの整合性が要るなら Abstract Factory
  ④ 性能問題なら Prototype
  ⑤ 最後に Singleton（できれば DI で代用）
パターン適用シグナル（こう見えたら検討）避ける場合
Abstract Factory OS / DB / テーマ など軸ごとに「セット」が必要 部品が1つだけなら Factory Method で十分
Builder boolean が4個以上並ぶコンストラクタ / null を飛ばし用に使う 引数2-3個なら普通のコンストラクタで足りる
Factory Method 共通処理の中に new XxxImpl() が1行だけある 派生が1種類しかないなら不要
Prototype 初期化が重い / 状態を持ったまま増殖したい 初期化が軽いなら普通の new で十分
Singleton OS のクロック / 起動時環境変数など本当に1つだけ テスト容易性が要るなら DI を選ぶ
📘 パターンは目的ではなく道具。 「このコードがこう変わった結果、たまたまそのパターンになっていた」が本来の使い方。 23 パターン全部を覚える必要はない。生成パターンで実務によく使うのは Factory Method・Builder・Singleton（または DI）の3つで、残りは「そういう発想がある」と知っておけば 出会った時に逆引きできる。
✅ Tom さんの実務との接続:
  • OutSystems の Server Action — 多 Input パラメータのラッパーで Builder の発想が活きる
  • Wijmo FlexGrid の列定義組み立て — Builder で可読性を確保
  • VB.NET バッチ共通基盤 — Factory Method で「ジョブ種類別の処理オブジェクト生成」を整理
  • OutSystems Extensions の DB 接続 — Singleton ではなく DI で渡すのがテスト容易
