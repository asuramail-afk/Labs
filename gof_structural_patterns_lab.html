06

Adapter — 互換性のないIFを変換する

基本

既存クラスのIFが「期待される形」と違うとき、間に変換層を挟んで使えるようにする。レガシーAPIを新規システムから呼ぶ典型場面。新規コードをOutputDeviceなどの統一IFだけに依存させ、レガシーは無傷で隔離する。

🔰 イメージ図 — 変換コンセント
新規システム                       既存レガシー
   │                                    │
   │  modernPrinter.send(text)          │
   ├──────────► ┌──────────────┐ ──────►│
                │   Adapter    │        │  printLegacy(text, "A4", false)
                └──────────────┘ ◄──────┤
              "新IFで受けて旧IFを呼ぶ"
✗ Before — レガシーIFが業務コードに漏れる
TypeScript
// 既存のレガシークラス（変更不可）
class OldPrinter {
  printLegacy(text: string, paperSize: string, duplex: boolean) {
    console.log(`OLD[${paperSize}/${duplex}]: ${text}`);
  }
}
class OldFaxMachine {
  sendFax(content: string, phoneNum: string, retry: number) {
    console.log(`FAX[${phoneNum}]: ${content}`);
  }
}

// 業務コード — 旧IFの形が染み出る
function generateInvoice(customer: string, amount: number) {
  const text = `請求書: ${customer} ¥${amount}`;
  const p = new OldPrinter();
  p.printLegacy(text, "A4", false);   // 引数仕様を覚える
  const f = new OldFaxMachine();
  f.sendFax(text, "06-1234-5678", 3); // 旧IFを直接
}
✓ After — 統一IFに変換層をかぶせる
TypeScript
// 新IF
interface OutputDevice { send(text: string): void; }

// Adapter1: 旧プリンタ → 新IF
class PrinterAdapter implements OutputDevice {
  constructor(private old: OldPrinter) {}
  send(text: string) { this.old.printLegacy(text, "A4", false); }
}
// Adapter2: 旧FAX → 新IF
class FaxAdapter implements OutputDevice {
  constructor(private old: OldFaxMachine, private phone: string) {}
  send(text: string) { this.old.sendFax(text, this.phone, 3); }
}

// 業務コード — 新IFしか知らない
function generateInvoice(c: string, a: number, dev: OutputDevice) {
  dev.send(`請求書: ${c} ¥${a}`); // 同じ呼び方
}
generateInvoice("Tom", 10000, new PrinterAdapter(new OldPrinter()));
generateInvoice("Tom", 10000, new FaxAdapter(new OldFaxMachine(), "06-..."));
観点BeforeAfter
業務コードが知るIF数旧プリンタ + 旧FAX = 2種類OutputDevice 1種類
出力先追加の影響範囲業務コード全箇所を修正新Adapter追加のみ
旧クラスの寿命業務コードと運命共同体廃止時もAdapterだけ捨てる
テスト容易性具象に依存して困難モックOutputDeviceで楽
現在: After（Adapter経由）
✓ After: generateInvoice("Tom", 10000, dev) — 統一IF 1呼び出しで「プリンタ」も「FAX」も透過的に切替可能 新しい出力先（Slack/Email）追加は Adapter を1つ書くだけ
✗ Before: 業務コードに OldPrinter.printLegacy の3引数仕様が直書き 出力先を増やすたびに引数の意味、順序、デフォルト値を毎回調べる レガシー廃止 = 業務コード全箇所の修正
09

Decorator — 機能をラップで積み重ねる

中級

継承で「機能の組み合わせ」を表現すると 2N 個のクラス が必要になる。同じIFを保ったままラッパーを「積む」ことで、N+1個の線形な拡張に変える。

🔰 ラップの積み重ねイメージ
  Espresso (300円)
    ↓ MilkDecorator がラップ → cost = 元 + 50
    ↓ SugarDecorator がラップ → cost = 元 + 20
    ↓ WhipDecorator がラップ → cost = 元 + 80

  最終: WhipDecorator(SugarDecorator(MilkDecorator(Espresso)))
       cost() = 300 + 50 + 20 + 80 = 450
✗ Before — 継承で組み合わせ爆発
TypeScript
class Espresso {
  cost() { return 300; }
}
class EspressoMilk extends Espresso {
  cost() { return super.cost() + 50; }
}
class EspressoSugar extends Espresso {
  cost() { return super.cost() + 20; }
}
// ❌ ミルク+砂糖が必要に…
class EspressoMilkSugar extends Espresso {
  cost() { return super.cost() + 50 + 20; }
}
// ❌ ホイップ追加で…
// EspressoMilkWhip / EspressoSugarWhip / 
// EspressoMilkSugarWhip ... 2^N クラス必要
✓ After — Decoratorでラップを積む
TypeScript
interface Coffee { cost(): number; }

class Espresso implements Coffee {
  cost() { return 300; }
}
class MilkDecorator implements Coffee {
  constructor(private c: Coffee) {}
  cost() { return this.c.cost() + 50; }
}
class SugarDecorator implements Coffee {
  constructor(private c: Coffee) {}
  cost() { return this.c.cost() + 20; }
}
class WhipDecorator implements Coffee {
  constructor(private c: Coffee) {}
  cost() { return this.c.cost() + 80; }
}

// 任意の組み合わせを実行時に「積む」
const drink = new WhipDecorator(
  new SugarDecorator(
    new MilkDecorator(new Espresso())));
console.log(drink.cost()); // 450
観点Before（継承）After（Decorator）
トッピング3種2³ = 8クラス4クラス（基本+3デコ）
トッピング5種32クラス6クラス
トッピングN種2N（指数）N+1（線形）
実行時の組み替え不可能自由に積める
💡 利用シーン
  • Java I/O: BufferedReader(InputStreamReader(FileInputStream))
  • HTTPミドルウェア: 認証 → ログ → 圧縮 → ハンドラ の積み重ね
  • React HOC: withAuth(withLogging(MyComponent))
  • ロギング/メトリクスの後付け: 既存IFを保ったまま横断的関心を追加
こう見えたら使える候補:
  • 機能の有無の組み合わせで継承クラスが指数的に増えている
  • 「あるメソッドの前後でログ取りたい」など横断的関心事が散らばる
  • 機能を実行時に動的にON/OFFしたい

Proxy — 本物の前に「代理」を置く

中級

本物オブジェクトと同じIFの代理を間に挟み、遅延ロード・アクセス制御・キャッシュ・ログ取得を透過的に追加する。利用側は本物を使っているつもりで Proxy を呼んでいる。

🔰 代理が本物の手前に立つ
          利用側
           │
           ▼
        ┌──────────┐
        │  Proxy   │  ← 本物と同じIF
        │ (lazy /  │     必要時に...
        │  auth /  │       ▼
        │  cache)  │   ┌──────────┐
        └────┬─────┘   │ RealImage│
             └────────►│ (重い)   │
                       └──────────┘
✗ Before — 本物に副次関心が混ざる
TypeScript
class HighResImage {
  constructor(private file: string) {
    console.log(`重い画像ロード: ${file}`); // 数秒
  }
  display() {
    // ❌ 本物クラスが認可を持つ
    if (!checkPermission(currentUser))
      throw new Error("Forbidden");
    // ❌ ログも
    log(`User viewed ${this.file}`);
    // ❌ キャッシュも
    if (cache.has(this.file)) return;
    console.log(`表示: ${this.file}`);
  }
}

// 起動時に100枚全ロード
const imgs = files.map(f => new HighResImage(f));
// 500MB消費、なのに見るのは1枚
imgs[0].display();
✓ After — 同じIFのProxyで責務分離
TypeScript
interface Image { display(): void; }

class RealImage implements Image {
  constructor(private file: string) {
    console.log(`重い画像ロード: ${file}`);
  }
  display() { console.log(`表示: ${this.file}`); }
}

// Proxy1: 遅延ロード
class LazyImageProxy implements Image {
  private real?: RealImage;
  constructor(private file: string) {} // ロードしない
  display() {
    if (!this.real) this.real = new RealImage(this.file);
    this.real.display();
  }
}
// Proxy2: 認可（同じIF）
class ProtectedProxy implements Image {
  constructor(private inner: Image, private user: string) {}
  display() {
    if (!checkPermission(this.user)) throw new Error();
    this.inner.display();
  }
}

const img = new ProtectedProxy(new LazyImageProxy("a.jpg"), "tom");
img.display(); // 認可OK→必要時にロード→表示
⚠️ Decoratorとの違い — 構造はそっくりだが意図が異なる。Decoratorは機能を「足す」（cost+50円）、Proxyはアクセスを「制御する」（lazy/auth/cache）。前者は結果が変わる、後者は結果は同じでタイミングや可否が変わる。
Proxyの種類用途実例
Virtual Proxy遅延ロードORM(Hibernate)のlazy loading
Protection Proxy認可制御ファイル/API権限チェック
Caching Proxy結果保持HTTPレスポンスキャッシュ
Remote Proxy通信スタブgRPCクライアント、Web Worker

Bridge — 抽象と実装を分離して掛け算を足し算に

応用

「2軸で増えるもの」（図形 × 描画API、通知種類 × 送信手段）をクラスの掛け算で爆発させず、独立した2階層に切り分ける。M × N 個 → M + N 個に変換するパターン。

🔰 クラス数の比較（図形3種 × 描画API3種）
【継承だけで書く】 = 9クラス
  CircleCanvas, CircleSVG, CircleWebGL,
  SquareCanvas, SquareSVG, SquareWebGL,
  TriangleCanvas, TriangleSVG, TriangleWebGL

【Bridge】 = 6クラス + 1関係
  Shape階層:    Circle / Square / Triangle    (3)
  Renderer階層: Canvas / SVG / WebGL          (3)
  Shape ──持つ──► Renderer  （実行時に組合せ）
✗ Before — 継承で2軸を表現
TypeScript
class CircleCanvas {
  draw(r: number) { console.log(`Canvas: 円 r=${r}`); }
}
class CircleSVG {
  draw(r: number) { console.log(`SVG: <circle r=${r}/>`); }
}
class CircleWebGL { /* … */ }
class SquareCanvas { /* … */ }
class SquareSVG { /* … */ }
class SquareWebGL { /* … */ }
class TriangleCanvas { /* … */ }
class TriangleSVG { /* … */ }
class TriangleWebGL { /* … */ }

// ❌ 図形3 × 描画API3 = 9クラス
// 図形を1つ追加 → 3クラス増える
// 描画APIを1つ追加 → 3クラス増える
✓ After — 2軸を独立階層に
TypeScript
// 描画API階層
interface Renderer {
  drawCircle(r: number): void;
  drawRect(w: number, h: number): void;
}
class CanvasRenderer implements Renderer { /* … */ }
class SVGRenderer    implements Renderer { /* … */ }
class WebGLRenderer  implements Renderer { /* … */ }

// 図形階層 — Renderer を「持つ」
abstract class Shape {
  constructor(protected renderer: Renderer) {} // Bridge!
  abstract draw(): void;
}
class Circle extends Shape {
  constructor(r: Renderer, private radius: number) { super(r); }
  draw() { this.renderer.drawCircle(this.radius); }
}
class Square extends Shape { /* … */ }

// ✅ 実行時に組み合わせ自由
new Circle(new SVGRenderer(), 5).draw();
new Circle(new CanvasRenderer(), 5).draw();
拡張シナリオBefore（継承）After（Bridge）
初期: 図形3 × API39クラス3+3 = 6クラス
図形をTriangle追加+3 → 12クラス+1 → 7クラス
APIをWebGPU追加（前段から）+3 → 15クラス+1 → 8クラス
図形5 × API4 想定20クラス5+4 = 9クラス
組み合わせ決定コンパイル時固定実行時切替可能

Composite — 木構造を「単体と同じように」扱う

中級

ファイルとフォルダ、UIコンポーネントとそのコンテナのように、「単体」と「集合」を同じIFで扱えるようにする。利用側は中身が単体か集合かを気にしなくてよく、instanceof 判定や再帰のひな形が消える。

🔰 同じIFを単体も集合も実装する
     FileNode (size()を持つ)
       ├── File   ── 自分のbyte数を返す
       └── Folder ── 子のsize()を全部足す
                      ├── File
                      ├── File
                      └── Folder ← 入れ子も同じIF
                            └── File
✗ Before — 利用側が型判定+再帰
TypeScript
class File {
  constructor(public name: string, public bytes: number) {}
}
class Folder {
  public children: (File | Folder)[] = [];
  constructor(public name: string) {}
}

// ❌ サイズ計算 — 利用側が型判定+再帰
function calcSize(node: File | Folder): number {
  if (node instanceof File) return node.bytes;
  let total = 0;
  for (const c of node.children)
    total += calcSize(c); // 利用側が再帰
  return total;
}

// ❌ パス列挙も同じパターンの繰り返し
function listPaths(node: File | Folder, p = "") {
  if (node instanceof File) return [`${p}/${node.name}`];
  const r = []; /* 同じ再帰のひな形を再記述 */
  return r;
}
✓ After — 単体も集合も同じIF
TypeScript
interface FileNode {
  size(): number;
  paths(prefix?: string): string[];
}

class File implements FileNode {
  constructor(public name: string, private bytes: number) {}
  size() { return this.bytes; }
  paths(p = "") { return [`${p}/${this.name}`]; }
}

class Folder implements FileNode {
  private children: FileNode[] = [];
  constructor(public name: string) {}
  add(n: FileNode) { this.children.push(n); }
  // ✅ 再帰は自分の責務として内側に
  size() {
    return this.children.reduce((s, c) => s + c.size(), 0);
  }
  paths(p = "") {
    return this.children.flatMap(c => c.paths(`${p}/${this.name}`));
  }
}

// 利用側 — 型を意識しない
const root = new Folder("root");
root.add(new File("a.txt", 100));
console.log(root.size()); // 100
観点BeforeAfter
利用側の型判定操作ごとに instanceof不要
再帰ロジックの所在利用側に分散各ノード内に1箇所
操作追加の手間ひな形再記述IFにメソッド追加
階層を深くした影響利用側で考慮必要透過的に処理
💡 利用シーン
  • React/Vueのコンポーネントツリー: 各ノードが render() を持つ
  • Wijmo FlexGrid の階層行・グルーピング（実務領域）
  • HTML DOM: Element と TextNode が同じく Node を継承
  • 組織図・カテゴリツリー: 部署も社員も同じIFで「人数」を返す

Facade — 複雑な内部に「統一窓口」を置く

基本

複数のクラスを協調させて使う必要がある複雑なサブシステムに対し、1つだけシンプルな入口を用意して利用側を楽にする。OutSystems の Server Action はまさにFacadeそのもの。

✗ Before — 利用側が手順を全部知る
TypeScript
class CPU {
  freeze() {} jump(a: number) {} execute() {}
}
class Memory { load(addr: number, data: string) {} }
class Disk { read(): string { return "OS"; } }

// ❌ PC起動 — 内部構造に密結合
function startPC1() {
  const cpu = new CPU();
  const mem = new Memory();
  const disk = new Disk();
  cpu.freeze();              // 順序を覚える
  mem.load(0, disk.read()); // アドレス0も外部知識
  cpu.jump(0);
  cpu.execute();
}

// ❌ 別箇所でも同じ手順をコピペ
function startPC2() {
  /* startPC1 と同じ4行 - バグ混入リスク */
}
✓ After — Facadeで手順を集約
TypeScript
class ComputerFacade {
  private cpu = new CPU();
  private mem = new Memory();
  private disk = new Disk();

  // ✅ 正しい手順をここ1箇所で定義
  start() {
    this.cpu.freeze();
    this.mem.load(0, this.disk.read());
    this.cpu.jump(0);
    this.cpu.execute();
  }
  shutdown() { /* 終了処理も集約 */ }
}

// 利用側 — 1行で完結
new ComputerFacade().start();
new ComputerFacade().start(); // 何度呼んでも同じ手順

// 手順変更（メモリ初期化追加など）も
// Facade内の1箇所修正で全利用箇所に反映
📘 Adapterとの違い — Adapterは「IFの形を変える」（変換）。Facadeは「複数のクラスを束ねる」（集約）。Adapterは 既存IFと新IFの1:1変換、Facadeは 複数のIFの上に新しい単純な口を作る。
🔰 AdapterとFacadeの違い
Adapter: IFの「形」を変える（1:1変換）
  [新IF: send(text)] ─Adapter→ [旧IF: printLegacy(text, "A4", false)]

Facade: 複数のIFの上に「新しい単純な口」を作る（N:1集約）
  [Facade.start()] ──┬─→ CPU.freeze()
                    ├─→ Disk.read()
                    ├─→ Memory.load()
                    └─→ CPU.execute()
💡 利用シーン
  • OutSystems の Server Action — 複数Entityアクセスをラップ
  • BFF (Backend for Frontend): 画面が必要とする処理を1エンドポイントに集約
  • SDK のトップレベル API: stripe.charges.create() 内部で複数HTTPコール
  • レガシー近代化: 古い複雑なコード群の前に新規Facadeを置く

Flyweight — 共有でメモリを節約する

応用

同じデータを大量に持つ場合、共通部分（Intrinsic State）を1つだけ作って使い回す。位置・色などの個別部分（Extrinsic State）だけ各インスタンスが持つ。文字フォントのグリフ、ゲームの弾、地図の樹木など、数万単位の同種オブジェクトで効く。

🔰 内在状態と外在状態の分離
【Before】 各Treeが重いデータを個別保持
  Tree #1 [位置(10,20) + テクスチャ4MB + メッシュ40KB]
  Tree #2 [位置(30,50) + テクスチャ4MB + メッシュ40KB]
  ...10万本 → 約400GB ✗ 即枯渇

【After】 重い部分はFactoryが1つだけ保持
  TreeType "pine" [テクスチャ4MB + メッシュ40KB] ← 1つだけ
                       ▲ 参照
  Tree #1 [位置(10,20) → TreeType]
  Tree #2 [位置(30,50) → TreeType]   ← 各Treeは位置だけ
  ...10万本 → 約5.6MB ✓
✗ Before — 各自が重い情報を持つ
TypeScript
class Tree {
  constructor(
    public x: number,
    public y: number,
    public textureName: string,
    public textureBytes: Uint8Array,    // 4MB
    public meshVertices: Float32Array   // 40KB
  ) {}
}

// ❌ 同じ松を10万本
const forest: Tree[] = [];
const tex = new Uint8Array(4 * 1024 * 1024);
const mesh = new Float32Array(10000);

for (let i = 0; i < 100_000; i++) {
  forest.push(new Tree(
    Math.random() * 1000,
    Math.random() * 1000,
    "pine",
    tex.slice(),  // ❌ 4MB × 10万 = 400GB
    mesh.slice()  // ❌ 同じく爆発
  ));
}
// メモリ即枯渇
✓ After — Factoryで共有
TypeScript
// 内在状態（Intrinsic）— 共有可能・不変
class TreeType {
  constructor(
    public name: string,
    public texture: Uint8Array,
    public mesh: Float32Array
  ) {}
  draw(x: number, y: number) { /* 共有データで描画 */ }
}

// Factory が一意性を保証
class TreeTypeFactory {
  private cache = new Map<string, TreeType>();
  get(name: string): TreeType {
    if (!this.cache.has(name)) {
      this.cache.set(name, new TreeType(
        name, loadTex(name), loadMesh(name)));
    }
    return this.cache.get(name)!;
  }
}

// 外在状態（Extrinsic）— 位置だけ
class Tree {
  constructor(public x: number, public y: number,
              public type: TreeType) {} // ✅ 参照のみ
}

const factory = new TreeTypeFactory();
for (let i = 0; i < 100_000; i++) {
  forest.push(new Tree(rx, ry, factory.get("pine")));
}
木の数Before（各自保持）After（Flyweight）
1本約4 MB約4 MB + 16 B
1,000本約4 GB約4 MB + 16 KB
100,000本約400 GB（破綻）約4 MB + 1.6 MB ≈ 5.6 MB
メモリ参照関係各Treeが独立コピー全Treeが同じTreeTypeを共有
📘 核心: 可変な部分（位置・回転・色）と不変な部分（テクスチャ・メッシュ）を分離して、後者だけ共有する——これがFlyweightの本質。「同じデータを毎回コピーしている」と気づいたら適用候補。
💡 利用シーン
  • JS文字列のinterning: V8が同じ文字列リテラルを内部共有
  • ゲームエンジン: Unityのメッシュ/テクスチャAsset参照
  • DBコネクションプール: 接続オブジェクトの再利用
  • WebGL/Canvasスプライト描画: 同じ画像を何千個配置
★

使い分け早見表 — 構造パターン7つの逆引き

総合

実務でパターンを思い出すための「症状 → 候補」逆引き。コードの匂い・症状から自然にパターンへ到達するのが健全な使い方。

症状（コードに現れるサイン）適用パターン効果の本質
古いAPIの形が業務コードに染み出すAdapterIFの形を1:1変換、レガシーを隔離
2軸（種類×実装）でクラスが指数増加BridgeM×N → M+N に変換
instanceofで再帰を書いているComposite単体=集合の透過扱い
オプション組み合わせで2NクラスDecorator線形（N+1）に削減、実行時組替可
内部の正しい呼び出し順序が散らばるFacade1箇所に集約、利用側を簡素化
同じデータを大量複製してメモリ枯渇Flyweight共通部分を共有、位置だけ可変
重い初期化/認可/キャッシュを本物に書きたくないProxy同じIFで仲介、副次関心を分離
🔰 7パターンの3グループ俯瞰
構造パターン = クラス・オブジェクトの「組み立て方」を整える

┌─ A. 包む系 ──────────────────────────────────┐
│  Adapter    形を変える（旧IF→新IF）           │
│  Decorator  機能を足す（cost+50円）            │
│  Proxy      アクセスを制御（lazy/auth/cache）  │
└──────────────────────────────────────────────┘
       ↑ 全て「同じIFを保ったまま中身をラップ」

┌─ B. 切る系 ──────────────────────────────────┐
│  Bridge     2軸を独立階層に（M×N → M+N）       │
└──────────────────────────────────────────────┘

┌─ C. まとめる系 ──────────────────────────────┐
│  Composite  木構造を単体扱い                   │
│  Facade     複雑な内部に統一窓口               │
│  Flyweight  重複データを共有して軽量化          │
└──────────────────────────────────────────────┘
✅ パターンは目的ではなく道具。「このコードがこう変わった結果として、たまたまそのパターンになっていた」が本来の使い方。最初から「Decoratorで設計する」と決めるのではなく、if-elseやnewの散乱、クラス爆発、メモリ枯渇といった症状から逆引きで到達するのが健全。
⚠️ 似ているパターンの混同に注意:
・Adapter vs Facade: 形変換(1:1) vs 集約(N:1)
・Decorator vs Proxy: 機能を足す vs アクセスを制御する
・Bridge vs Strategy: 構造の分離 vs アルゴリズム差替（こちらは振る舞いパターン）
