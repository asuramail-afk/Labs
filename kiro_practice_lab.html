00

全体像と所要時間

準備

Kiro は AWS が提供するSDD（仕様駆動開発）専用の独立IDE。Code OSSベースでVS Code的に使え、Specs/Steering/Hooksの3つのペインで仕様駆動を完結させる。本Labは前回のSpec Kit手順書と同じ題材（最小TODO CLI）を Kiro で完走することで、両者の体感差を実機で掴むことが目的。

🔰 全体フロー
┌── インストール（Lab 01〜03） ────────┐
│  ダウンロード → インストール             │
│  → ログイン → VS Code設定インポート（任意）│
└────────────┬─────────────────┘
             ▼
┌── プロジェクト準備（Lab 04〜05） ────┐
│  Open Folder で空ディレクトリを開く      │
│  Steering ファイルを整える               │
│  （product.md / tech.md / structure.md） │
└────────────┬─────────────────┘
             ▼
┌── Spec Mode 3フェーズ（Lab 06〜09） ──┐
│  Requirements → Design → Tasks → Run    │
│  各フェーズで人間レビュー（GUIで）       │
└────────────┬─────────────────┘
             ▼
┌── 応用（Lab 10〜11） ──────────────┐
│  Bugfix Spec / Hooks / 運用Tips         │
└────────────────────────────────┘
段階所要時間主な作業
Lab 01〜0315〜30分ダウンロード・インストール・ログイン
Lab 04〜0515〜20分UI把握とSteering準備
Lab 06〜0960〜90分Spec → Design → Tasks → Run
Lab 1030〜60分Bugfix Specの体験
合計2〜3時間初回1本完走
📘 本Labの題材: 最小TODO CLI（Python）。Spec Kit手順書と意図的に同じにしてある。終わったら同じ題材で両者を比較できる。Kiroの強み（GUI・Bugfix Spec・PBT）が、どこで効くかを体感できる。
⚠️ 本Labのバージョン前提: Kiro v0.10系（2026年2月以降）。Requirements-First / Design-Firstの2ワークフロー、Bugfix Spec、Property-Based Testing（PBT）が利用可能。古い記事ではこれらの機能がない場合がある。
01

動作要件と費用感の確認

準備

インストール前に、自分の環境で動くか・どれくらいの費用がかかるかを確認する。Spec Kitと違ってKiroは独立アプリなので、OS要件と業務PCへのインストール可否を最初にチェック。

項目要件
WindowsWindows 10 or 11（64bit）。ARMは未サポート
macOSIntel / Apple Silicon 両対応、最新のセキュリティ更新適用済み
Linuxglibc 2.39以上（Ubuntu 24+ / Debian 13+ / Fedora 40+ など）
ディスク容量約170〜273MB（インストーラサイズ、プラットフォーム別）
認証方式GitHub / Google / AWS Builder ID / AWS IAM Identity Center のいずれか
AWSアカウント不要（個人利用なら GitHub or Google だけでOK）
📘 費用感（2026年4月時点）: Free は月50credits（永続）+ 初回30日間500 bonus credits。Pro $20/月で1,000 credits、Pro+ $40/月で2,000 credits、Power $200/月で10,000 credits。クレジット単位は超過時 $0.04/credit。日本の請求先住所には消費税が加算される。
⚠️ 業務PCに入れる場合の確認事項: ① 会社のソフトウェアインストール承認が必要か ② Code OSSベースなので、社内ポリシーが「VS Code限定」と書いていると弾かれる場合あり ③ Microsoft専有のVS Code拡張は動かない（Pylance、Remote Development、GitHub Copilot拡張など）。個人PC・自宅環境で試すのが最も安全。
✅ 初回30日トライアルの活用: 500 bonus credits は本Lab全体（最小TODO CLI 1本 + Bugfix Spec体験）には十分足りる。有料化判断は1〜2機能を完走してからで良い。
🔍 事前確認
  1. OSバージョン（Windowsならwinver、Macなら「このMacについて」）
  2. ディスク空き容量 1GB以上
  3. 使えるアカウント（GitHub or Google）の有無
  4. 業務PCの場合、社内ソフトウェア導入ポリシー

Kiro IDE のインストール

準備

公式サイト（kiro.dev）からインストーラをダウンロードして導入する。App Store や winget では配布されていないので、必ず公式サイトから取得する。

① ダウンロード
# 公式ダウンロードページ
https://kiro.dev/downloads/

# 自分のOSに合うインストーラを選ぶ:
#  - Windows: Kiro-Setup-x.x.x.exe
#  - macOS Apple Silicon: Kiro-x.x.x-arm64.dmg
#  - macOS Intel: Kiro-x.x.x.dmg
#  - Linux: .deb / .rpm / .AppImage
② Windows でのインストール
# 1. Kiro-Setup-x.x.x.exe をダブルクリック
# 2. AWS Customer Agreement と IP License に同意
# 3. インストール先を選択（デフォルトでOK）
# 4. デスクトップ・スタートメニューショートカットを作るか選択
# 5. Install をクリック → 完了まで数分
# 6. Launch にチェックを入れて Finish
③ macOS でのインストール
# 1. .dmg をダブルクリックでマウント
# 2. Kiro.app を Applications フォルダにドラッグ
# 3. Launchpad または Spotlight から Kiro を起動
# 4. 初回起動時「開発元を確認できません」と出たら
#    システム設定 → プライバシーとセキュリティ → 「このまま開く」
📘 Kiro CLIも別途あり: GUIだけでなく kiro-cli というCLIも公式提供されている（macOS/Linux）。本Labは IDE が主体だが、慣れたら CLI で自動化することも可能。
⚠️ 非公式ダウンロードサイトに注意: 「Kiro download free」で検索するとTechSpotなど第三者サイトが上位に出る。必ず kiro.dev からダウンロードすること。第三者サイトは古いバージョンや改変されたバイナリの可能性がある。
🔍 インストール確認
  1. デスクトップ or アプリ一覧に Kiro アイコンが追加されたか
  2. 起動するとスプラッシュ画面が表示されるか
  3. 「Sign in to Kiro」のログイン画面が出るか
03

初期設定とログイン

準備

初回起動時のオンボーディングを進める。VS Code設定インポート・テーマ選択・シェル統合の3点を順に設定する。5分程度で終わる。

🔰 初回起動の4ステップ
Step 1: ログインプロバイダ選択
  ├─ GitHub        ← 個人開発に最も簡単（推奨）
  ├─ Google
  ├─ AWS Builder ID（無料・AWSアカウント不要）
  └─ AWS IAM Identity Center（業務向け）

Step 2: VS Code 設定インポート（任意）
  └─ 既にVS Codeを使っているなら ON にすると拡張・テーマが移行される

Step 3: テーマ選択
  └─ Kiro Dark / Kiro Light など

Step 4: シェル統合の許可
  └─ Kiro がターミナルで pip / npm 等を実行できるようにする
     （許可しないと自動実装ができなくなるので ON 推奨）
💻 実際の流れ
  1. 初回起動でログイン画面が出る
  2. 個人で試すなら GitHub でログイン（ブラウザが開いて認証）
  3. 戻ってきたら「Import from VS Code」ダイアログ → 拡張を引き継ぐなら Yes
  4. テーマ選択（Tomさんは普段 Light 系なら Kiro Light を推奨）
  5. シェル統合を有効化（後で実装フェーズで必須）
  6. 「Welcome to Kiro」画面に到達 → セットアップ完了
💡 コツ: 業務PC兼用なら、VS Code拡張インポートはスキップしてクリーンな状態から始めると、Open VSX非対応拡張で混乱しない。
📘 初回30日トライアル: ログイン直後に「500 bonus credits（30日有効）」が付与される。Free tierの50 creditsとは別枠。トライアル期間中はPro相当の機能をフルに試せる。本Labはトライアル期間内に完走することを推奨。
⚠️ AWS IAM Identity Center を選ぶと: 業務組織のSSO経由になり、コンテンツ収集オプトアウトなど企業向け設定が変わる。個人学習目的なら GitHub or Google or AWS Builder ID が手軽。
🔍 ログイン確認
  1. 右下のステータスバーにアカウント名が表示されているか
  2. 左サイドバーに Kiro 専用ペイン（Specs / Steering / Hooks 等）が表示されているか
  3. 右下のクレジット残高表示に「500 bonus + 50 free」相当が出ているか

UI構成を理解（Specs / Steering / Hooks）

準備

Kiroの中核は左サイドバーの Kiro ペイン。Specs / Steering / Hooks / Powers / MCP の5つに分かれている。本Labで主に使うのは Specs と Steering。

🔰 Kiro ペインの構成
┌─ 左サイドバー: Kiro ペイン ─────────────────┐
│  ▼ Specs            ← 機能仕様（本Labのメイン）   │
│    [+] New Spec     ← ここから機能を作る         │
│    └ feature-name   ← 機能ごとにフォルダ          │
│       ├ requirements.md（または bugfix.md）       │
│       ├ design.md                                 │
│       └ tasks.md                                  │
│                                                  │
│  ▼ Steering         ← プロジェクト全体ルール    │
│    ├ product.md     ← 何を作っているプロダクトか │
│    ├ tech.md        ← 技術スタック・規約          │
│    └ structure.md   ← ディレクトリ構造ルール     │
│                                                  │
│  ▼ Hooks            ← ファイル変更で自動発動    │
│    （Lab 11で扱う）                              │
│                                                  │
│  ▼ Agent Powers     ← 専門化されたツール群      │
│  ▼ MCP Servers      ← 外部ツール統合            │
└────────────────────────────────────────┘

中央: エディタ（VS Code風）
右: チャット（vibeまたはspec文脈）
機能役割本Labで使う
Specs機能仕様の作成・実行（核心）Lab 06〜10で多用
Steeringプロジェクト全体の不変ルールLab 05で準備
Hooksファイル変更で自動発動するエージェントLab 11で軽く触れる
Powers専門化されたツール群（ドメイン知識）使わない（応用編）
MCP Servers外部ツール統合（Apidog等）使わない（応用編）
Chat（右側）vibe coding風の自由対話補助的に使用
📘 「Spec モード」と「vibe モード」の違い: Kiroの右側のチャットは2モードある。vibeは普通のAIチャット、spec文脈は #spec で特定機能を参照しながらの対話。本Labでは Specs ペインから機能を作り、必要なら #spec で参照する流れ。
💻 練習用フォルダを開く
  1. 事前にOSのファイラで空のフォルダを作る（例: C:\Users\user\KiroProjects\my-todo-kiro）
  2. Kiroで File → Open Folder でそのフォルダを選択
  3. Trust the authors を聞かれたら Yes
  4. 左サイドバーの Kiro ペイン（旗のようなアイコン）を開く
  5. Specs / Steering / Hooks のセクションが空の状態で表示される
💡 コツ: このタイミングで git init をターミナルで打っておくと、Spec Kitと同じく機能ごとに自動でブランチが切られる流れに乗れる。
🔍 UI確認
  1. 左サイドバーの Kiro ペインを開けるか
  2. Specs セクションに + ボタンが見えるか
  3. Steering セクションが空（or プレースホルダ）か
  4. 右側にチャットペインが開けるか（vibe モードがデフォルト）
05

Steering ファイルを整える

Specモード実践

Spec を作る前に Steering（操舵）でプロジェクト全体のルールを書く。これは Spec Kit の constitution.md に相当するが、Kiroは用途別に複数ファイルに分割する設計。本Labでは標準の3ファイルを準備する。

🔰 Steeringの3標準ファイル
.kiro/steering/
├── product.md     ← 何を作っているか・対象ユーザ・差別化要素
├── tech.md        ← 技術スタック・コーディング規約・禁止事項
└── structure.md   ← ディレクトリ構造・ファイル命名・配置ルール

  これらは全ての対話で自動的にAIの文脈に含まれる
  ↓
  毎回「Pythonで」「型ヒント必須」と言わなくて済む
💻 Steeringの作り方（GUI）
  1. Kiro ペインで Steering セクションの + をクリック
  2. 「Generate Steering Documents」を選ぶと、Kiroが現状コードを分析してテンプレを生成
  3. or 手動で .kiro/steering/ 配下に product.md 等を作成
  4. 本Labは新規プロジェクトなので、AIに生成させる方が速い
右側チャット（vibeモード）に貼る指示
このプロジェクトは Python 3.12 で作る最小TODO CLI です。

.kiro/steering/ 配下に以下の3ファイルを作成してください:

## product.md
- プロダクト名: minimal-todo-cli
- 対象ユーザ: 個人開発者（自分1人）
- コア機能: コマンドラインでタスクを追加・一覧・完了・削除
- 差別化: ログイン・サーバ・DB不要、即起動

## tech.md
- 言語: Python 3.12
- 標準ライブラリ優先、外部依存は必要最低限
- 型ヒントを全関数に付ける
- パッケージ管理: uv（pyproject.toml）
- テスト: pytest（標準的な使い方）
- CLIフレームワーク: argparse

## structure.md
- src/todo/ 配下にモジュール（task.py / storage.py / cli.py）
- tests/ 配下にテストファイル（test_*.py）
- 1ファイル100行を目安に分割
- README.md にCLI使い方を必ず書く

各ファイルは Markdown で、なぜそのルールが必要かの理由も1行ずつ添えてください。
✅ Steering と Spec Kit constitution の違い: 同じ目的だが、Kiroは関心ごとに分かれているので後でメンテしやすい。tech.md だけ更新すれば技術スタック変更が反映され、product.md には触らない、のように。Tomさんが慣れたOutSystemsのSettings Module分割と同じ発想。
⚠️ Steeringを書きすぎない: 全フェーズで毎回ロードされるので、長すぎるとAIの応答が鈍重になる。合計500行以下を目安。詳細な決定は個別Spec内で書けばよい。
🔍 Steering完了の判定
  1. 左サイドバーのSteeringに3ファイルが表示されている
  2. 各ファイルを開いて、内容が自分の意図に合っているか
  3. 「これでSteeringとして十分か、抜けがあれば指摘して」とチャットで自己評価させる
  4. git add .kiro/ && git commit -m "Add steering files" でコミット
06

Spec作成（Requirements-First）

Specモード実践

ここからSpecモードの本番。Specs ペインから新規Specを作り、Requirements-First ワークフローで進める。これは「ユーザ視点の要件から始める」標準的なフロー。

💻 New Spec を作る
  1. Kiro ペインで Specs セクションの + をクリック
  2. または右側チャットで「Generate spec」と入力
  3. 「Feature or Bugfix?」と聞かれる → Feature を選択
  4. 「Requirements-First or Design-First?」と聞かれる → Requirements-First を選択
  5. 初期プロンプトを入力する画面になる
💡 コツ: Specs設定で「default workflow」を Requirements-First にしておくと、毎回選ばなくて済む。Settings → Kiro → Specs から変更可。
初期プロンプト（Spec作成時に入力）
最小のTODO CLI を作ります。

ユーザがコマンドラインで以下を行えるようにしたいです:
- タスクを1行で追加できる（タイトルのみ）
- 全タスクを一覧表示できる（未完了/完了が一目で分かる）
- IDを指定してタスクを完了状態にできる
- 完了済みのタスクをまとめて削除できる
- データはローカルファイルに永続化される（再起動しても残る）
- 1人で使う前提（マルチユーザ・認証は不要）
- インストール後すぐに使えること（DB・サーバ不要）

成功の定義:
- ターミナルで5回コマンドを叩いてTODO管理が完結する
- 自分が3日連続で使う

スコープ外:
- 期限・優先度・タグなどの拡張属性
- リモート同期
- TUI / GUI
📘 Kiroが裏でやること: ① .kiro/specs/minimal-todo-cli/ ディレクトリを作成 ② Gitブランチを切り替え（minimal-todo-cli ブランチ） ③ requirements.md を EARS記法で生成 ④ 中央エディタで開く ⑤ Specs ペインに進捗インジケータ（Requirements/Design/Tasks の3段）を表示。
⚠️ 技術スタックを書かない: 「Pythonで」「argparseで」と書きたくなるが我慢。それはtech.md（Steering）に既に書いてある。requirements.md はWhat/Whyだけの世界。技術が混じると、要件と設計が癒着して柔軟性が失われる。
🔍 Spec作成の確認
  1. 左サイドバーに minimal-todo-cli Spec が現れた
  2. 進捗バーが「Requirements」フェーズで停止している
  3. 中央エディタに requirements.md が表示されている
  4. requirements.md が EARS記法（WHEN ... THE SYSTEM SHALL ...）で書かれている
  5. Gitブランチが minimal-todo-cli に切り替わっている
07

requirements.md レビュー

Specモード実践

Kiroが生成した requirements.md を必ず読んで承認するのがSDDの命。Spec Kitの /speckit.clarify 相当の曖昧解消は、Kiroではrequirements.mdに対する追加対話で行う。

🔰 EARS記法の典型出力（Kiroが生成）
## Task Management

### Add Task
WHEN a user runs `todo add "<title>"` with a non-empty title
THE SYSTEM SHALL create a new task with status "pending"
  and persist it to local storage

WHEN a user runs `todo add ""` with an empty title
THE SYSTEM SHALL display "Title cannot be empty" and exit
  with status code 1

### List Tasks
WHEN a user runs `todo list`
THE SYSTEM SHALL display all tasks with their ID, status,
  and title in a readable format

WHILE there are no tasks
THE SYSTEM SHALL display "No tasks found" instead of an empty list

### Complete Task
WHEN a user runs `todo complete <id>` with an existing ID
THE SYSTEM SHALL change the task's status to "completed"

IF the user provides a non-existent ID
THEN THE SYSTEM SHALL display "Task not found: <id>"
  and exit with status code 1
...
💻 レビューと修正
  1. requirements.md を上から読み、抜け・誤解がないか確認
  2. 気になる点があれば、右側チャットで指摘:
    「requirements.md にデータ永続化の場所（ホームディレクトリ vs カレント）が明記されていない。追加して」
  3. 追加したい異常系を指示:
    「同じIDが複数回 complete されたケースの挙動を追加して」
  4. EARS記法に違和感があれば「WHILE は使わず WHEN ベースに統一して」のように指示
  5. OK なら右側チャットで LGTM または「次のフェーズに進む」と入力
💡 コツ: Kiroの公式ドキュメントが LGTM（Looks Good To Me）と言うだけで次フェーズへ進むことを推奨している。短い承認語が認識される。
📘 requirements.md の修正は何度でも可: design.md 生成後でも、requirements.mdを編集して「Refine」ボタンを押せば design.md と tasks.md が自動再生成される。仕様駆動の真価はこの整合性の自動維持にある。Spec Kitだとここは手動で言わないといけない。
⚠️ EARSは慣れが必要: 「WHEN ... THE SYSTEM SHALL ...」が窮屈に感じる場合、自然言語のメモを # コメントとして添えても良い。Kiroは混在を許容する。大事なのは曖昧さの除去であって、形式の遵守ではない。
🔍 Requirements完了の判定
  1. すべての主要機能（add/list/complete/clean）がEARS記述されている
  2. 異常系（空タイトル・存在しないID等）が記述されている
  3. データ永続化の場所が明示されている
  4. 承認後、進捗バーが「Design」フェーズに進んだ
  5. git add .kiro/ && git commit -m "Add requirements"
08

design.md 生成と確認

Specモード実践

Requirementsを承認すると、Kiroはdesign.md を自動生成する。これは Spec Kit の plan.md / data-model.md / contracts/ に相当する内容を1ファイルに集約したもの。Mermaidシーケンス図やコンポーネント図が含まれることが多い。

🔰 design.md の典型構造
## Architecture Overview
- 高レベルのコンポーネント図（mermaid）
- データフロー

## Components
- src/todo/cli.py     ← argparse parser、エントリポイント
- src/todo/task.py    ← Task dataclass
- src/todo/storage.py ← JSON I/O

## Data Model
- Task の構造（id / title / status / created_at）
- JSON保存形式
- ファイルパス: ~/.todo-cli/data.json

## Sequence Diagrams
- todo add のシーケンス（mermaid）
- todo list のシーケンス
- todo complete のシーケンス

## Error Handling
- 永続化失敗時のリトライ
- 破損ファイルの検知

## Implementation Considerations
- ファイルロック（複数同時起動）
- トランザクション境界
📘 Preview モードで読みやすく: design.md は Mermaid 図を含むので、エディタ右上の「Preview」ボタンでレンダリング表示すると読みやすい。シーケンス図やコンポーネント図が視覚化される。
💻 design.md レビューのコツ
  1. Preview で全体像を把握
  2. requirements.md と矛盾がないか確認（特にデータモデルと永続化場所）
  3. Steering（tech.md）の制約を満たしているか:
    ・標準ライブラリ優先 ✓
    ・型ヒント全関数 ✓
    ・1ファイル100行 ✓
  4. 不安な点があればチャットで:
    「storage.py のファイルロック実装方針が曖昧。fcntl使うのか tempfile経由でアトミック書き込みするのか明記して」
  5. requirements.mdの修正が必要になったら:
    requirements.md を編集 → design.md の右上「Refine」ボタン → 自動再生成
  6. OK なら LGTM で次へ
💡 コツ: design.md の出力が薄いと感じたら「Implementation Considerations にエッジケース対応を追加して」と指示。AIは指示すればより詳細を出してくれる。
✅ Spec Kit との実感差: Spec Kit だと plan.md / data-model.md / contracts/ / research.md / quickstart.md が分散して生成される。Kiroは1ファイルで読みやすいが、API契約が大きいプロジェクトでは Spec Kit の分散方式の方が探しやすい場面もある。題材依存。
⚠️ 「過剰な設計」に注意: 最小TODOなのに大規模システム並みの設計を出すことがある。「これは過剰。最小TODO なのでシンプルに3モジュール構成で十分」と削減指示。Sledgehammer問題はKiroでも起きる。
🔍 Design完了の判定
  1. design.md にコンポーネント図とシーケンス図がある
  2. requirements.md の全要件が design.md でカバーされている
  3. Steering（特に tech.md）の制約を満たしている
  4. 承認後、進捗バーが「Tasks」フェーズに進んだ
  5. git add .kiro/ && git commit -m "Add design"

tasks.md 生成と実行

Specモード実践

design.md を承認すると、Kiroは tasks.md を自動生成する。Kiroの最大の差別化ポイントは、tasks.md の各行に 「Start Task」「Run all tasks」 ボタンが表示されGUI実行できること。Spec Kit の /speckit.implement をボタン化したイメージ。

🔰 tasks.md の表示（Kiro特有のUI）
┌── tasks.md（Kiroのエディタで開く） ────────────┐
│  ## Phase 1: Foundation                          │
│                                                  │
│  ☐ T001 Project skeleton                        │
│      Files: pyproject.toml, src/todo/__init__.py │
│      [Start Task]   ← クリックで実行              │
│                                                  │
│  ☐ T002 Task dataclass + tests                  │
│      Files: tests/test_task.py, src/todo/task.py │
│      Depends-on: T001                            │
│      [Start Task]                                │
│                                                  │
│  ## Phase 2: Storage                            │
│                                                  │
│  ☐ T003 [P] Storage JSON I/O                    │
│      ...                                         │
│                                                  │
│  [Run all tasks]   ← 全タスク順次実行             │
└────────────────────────────────────────┘
📘 Kiroのタスク実行UI: 公式ドキュメントによると「Kiroはtasks.md ファイルにタスク実行インターフェースを提供。リアルタイムのステータス更新が表示される」。タスクが in-progress / completed と動的に更新される。進捗が視覚的に把握できるのがCLIのSpec Kitとの最大の体感差。
💻 タスクを段階的に実行
  1. tasks.md を Preview ではなく Edit モードで開く（ボタンが押せる）
  2. Phase 1 の T001 の Start Task をクリック
  3. Kiro がコード生成・テスト記述を始める。中央エディタにファイルが順次作成される
  4. 完了するとチェックマークが付く
  5. そのファイルを開いて目視レビュー
  6. OK なら次のタスクの Start Task
  7. Phase 1 が全部完了したらターミナルで pytest 実行
  8. 全テスト通過なら git add . && git commit -m "Phase 1 done"
  9. Phase 2 以降も同様に
💡 コツ: 慣れてきたら「Run all tasks」で全自動実行できる。ただし最初は1タスクずつ進めて、AIの挙動を観察するのが安全。クレジット消費も把握しやすい。
🚨 暴走したと感じたら止める: AIが想定外のファイルを大量に作ったり、Steering tech.mdに違反する依存（例: 標準ライブラリ縛りなのに requests 追加）を入れたら、即「Stop」ボタン。git checkout . で戻す。Phase ごとにコミットしておくと退避が楽。
✅ 「コワーカーが既に実装済み」のタスク検出: Kiro特有の便利機能として、「Check which tasks are already complete」とチャットで指示すると、コードベースをスキャンして既存の実装と一致するタスクを自動でチェック済みにマークしてくれる。brownfield や中断再開で効く。
🔍 Implement完走の判定
  1. tasks.md の全タスクがチェック済みになっている
  2. ターミナルで pytest が全PASS
  3. 実際に python -m todo add "test" など手動コマンドで動く
  4. requirements.md の受入基準を1個ずつ手動確認
  5. git log で Phase 単位のコミットが残っている
  6. 右下のクレジット残高を確認（だいたい消費された量も把握）

Bugfix Spec を試す

応用

Kiroの差別化機能の1つ Bugfix Specを体験する。完成したTODO CLIに意図的にバグを混入させて、それをBugfix Specで修正する流れ。Property-Based Testing（PBT）の威力も体感できる。

💻 まず意図的にバグを仕込む
  1. src/todo/task.py を開く
  2. Task に complete() メソッドがあるはずなので、わざと2回呼ぶと例外を出すように改変
    （または、空タイトルチェックを外して空タイトルでも追加できるようにしてしまう）
  3. git add . && git commit -m "Introduce intentional bug" で記録
  4. これがBugfix Specのインプットになる
💻 Bugfix Specを作る
  1. Specs ペインの + をクリック
  2. 「Feature or Bugfix?」で Bugfix を選択
  3. 初期プロンプトでバグの状況を説明（次のコードブロック参照）
  4. Kiroが bugfix.md を生成（current/expected/unchanged 構造）
Bugfix Spec の初期プロンプト
同じタスクを2回 complete すると例外が発生します。

現状の挙動:
  $ todo complete 1
  $ todo complete 1
  Traceback... AlreadyCompletedError

期待する挙動:
  2回目以降は何もせず正常終了する（idempotent）。
  既に完了済みのメッセージを表示するだけ。

変えてはいけない挙動:
  - 存在しないIDを指定したときはエラー（status 1）のまま
  - add / list / clean の振る舞いは一切変更しない
  - データファイルのフォーマットは変更しない
🔰 bugfix.md の構造（Kiroが生成）
## Current Behavior
- todo complete <id> を同じIDで2回呼ぶと
  AlreadyCompletedError が発生
- スタックトレースが表示される
- exit status: 例外による終了

## Expected Behavior
- 2回目以降は冪等（idempotent）に成功
- 「Task <id> is already completed」と表示
- exit status: 0

## Unchanged Behavior（最重要）
- 存在しないIDの挙動は維持
- add コマンドの全挙動を維持
- list / clean の全挙動を維持
- data.json のJSONスキーマを維持

## Property-Based Test Cases
1. 既存バグを検証するPBT
   - 任意のIDで complete を2回呼ぶと例外が出る（バグ存在を確認）
2. 修正後の挙動を検証するPBT
   - 任意のIDで complete を N 回呼んでも例外なく完了
3. 変えない挙動を保護するPBT
   - 存在しないIDは引き続きエラー
   - add → list の冪等性
📘 「Unchanged Behavior」がブレイクスルー: AIが「ついでに直す」傾向を、仕様レベルで明示的にブロックする仕組み。これがあると、サージカル（外科的に最小範囲の）修正が保証される。Spec KitやAI-DLCには対応する組み込み機構はなく、運用で工夫する必要がある。
✅ PBTの効き方: Kiroは Python なら hypothesis、JSなら fast-check を使ったPBTを生成する。「任意の整数IDで complete をランダム回数呼んでも例外なし」のような性質ベースのテスト。具体例だけのテストでは見つからない副作用を捕まえる。
💻 残りの流れ
  1. bugfix.md をレビュー → LGTM
  2. design.md（修正設計）が生成 → レビュー
  3. tasks.md（surgical fixのステップ）が生成 → 実行
  4. PBTが実行され、3カテゴリのテストが通ることを確認
  5. 「Unchanged Behavior」のPBTが通っていることが特に重要
  6. git commit -m "Fix complete idempotency"
🔍 Bugfix完了の判定
  1. 修正前のバグを再現するPBTが、修正後は通らなくなっている
  2. 修正後の冪等性を検証するPBTが通る
  3. 「変えない挙動」のPBTがすべて通る（add/list/cleanが壊れていない）
  4. tasks.md にあったタスク以外のファイルに変更が入っていない（git diffで確認）

Hooks・運用Tips・限界

応用

初回完走後の継続運用のためのTipsと、Kiro特有のHooks（自動化）機能の紹介。本Labは詳細実装はしないが、何ができるかを把握しておく。

🔰 Hooksの典型的な使い方
.kiro/hooks/
├── on-save-test.md
│   トリガー: テストファイル保存時
│   アクション: 該当テストを自動実行してカバレッジ確認
│
├── on-spec-update.md
│   トリガー: requirements.md 変更時
│   アクション: design.md と tasks.md の整合性チェック
│
└── before-commit.md
    トリガー: コミット直前
    アクション: Spec と実装の乖離スキャン
📘 Hooks の作成: Kiro ペインの Hooks セクションで + をクリック、または .kiro/hooks/ 配下に Markdown ファイルを置く。AIが内容を解釈して自動発動する。Spec Kit には組み込みの対応物がない（Git Hooksで自前実装が必要）。
症状原因と対処
クレジットがすぐ尽きるSpecの再生成（Refine）を多用するとクレジットを消費。Free 50 + Trial 500 で2〜3機能が目安。Pro $20/月への昇格を検討
VS Code拡張が動かないKiroは Open VSX のみ対応。Microsoft専有拡張（Pylance等）は使えない。代替を Open VSX で探す
tasks.md のボタンが効かないシェル統合が無効になっている可能性。Settings → Terminal → Integrated → Shell Integration を有効化
EARS記法が窮屈で書きにくいrequirements.md を直接編集して自然言語のメモを # で添える。Kiroは混在を許容する
Bugfix Specが大げさすぎる初期プロンプトに「これは1行修正レベル。最小限のPBT 1つで十分」と明記
Sledgehammer問題（小機能に重い）右側の vibe チャットで普通の対話で対応する。Specsを使わない判断もアリ
⚠️ Kiroの限界: ① クレジット制なので「使った分だけ」見えるが、busty usage（特定の月に集中）で予想より高くつく ② Open VSX制限で開発体験が狭まる場合あり ③ チームの分散ワークフローでは、IDEを揃える必要があり導入ハードル高 ④ 規制業界では監査ログを別途確保する必要がある（Kiroの証跡だけでは不十分な場合）。
✅ SpecをClaude Codeに持ち込む（前回比較Labのパターン①）: Kiroで作った requirements.md / design.md / tasks.md は、Spec Kitプロジェクトに変換可能。Claude Codeで実装したい場合や、業務PCにKiroを入れられない場合の脱出口になる。
