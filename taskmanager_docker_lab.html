全体像と3つの実装バリアント

概念

2フェーズで進めた。フェーズ1＝React+Vite+LocalStorage（1人用・サーバ無し）、 フェーズ2＝保存先を Docker 上の PostgreSQL に移して複数ユーザ共同利用。 さらに「ソースとDockerをどこに置くか」で 3つの方式を作り、すべて競合なく同時稼働させた。 

# 推移（保存先と配信が段階的に変わる。UIコードは最後まで無変更）
フェーズ1            フェーズ2(開発)              フェーズ2(共有)
1ブラウザ完結   →    DB+API化(viteは生)     →    全コンテナ化(他端末公開)
LocalStorage         PostgreSQL/Docker           PostgreSQL/Docker
# 3バリアント（フォルダ / Compose名 / どこでビルドするか）
1) WSL版      taskmanager        /home/user/TaskManager      （全部WSL内）
2) Win版・方式B taskmanager-win   C:\…\TaskManagerWin         （rsyncでWSLへ転送→build）
3) WinA版・方式A taskmanager-wina  C:\…\TaskManagerWinA        （/mnt/c を直接build）

02

フェーズ1：Vite 生成と「保存の窓口」

フェーズ1

Vite+React を生成し、データ保存を taskRepository.js 1ファイルに隔離した。 UI は localStorage を直接触らず、必ずこの窓口経由。これがフェーズ2で「中身だけ差し替え」を可能にする要。 

# プロジェクト生成
npm create vite@latest TaskManager -- --template react
cd TaskManager && npm install
// src/repository/taskRepository.js（フェーズ1：LocalStorage版）
const STORAGE_KEY = 'taskmanager.tasks.v1'

// 防御的read: 空/壊れたデータでも例外を投げず必ず配列を返す
function read() {
  try {
    const parsed = JSON.parse(localStorage.getItem(STORAGE_KEY) ?? '[]')
    return Array.isArray(parsed) ? parsed : []
  } catch { return [] }
}

// ★関数はすべて Promise を返す（非同期IF）→ フェーズ2で fetch にしても await が変わらない
export async function addTask({ title }) {
  const task = { id: crypto.randomUUID(), title: title.trim(),
    done: false, createdAt: new Date().toISOString() }
  const tasks = read(); tasks.push(task); write(tasks); return task
}
🔰 「窓口を1つに隔離」とは
UI から保存先への呼び出しを1ファイルに集約しておくと、後で保存先を差し替えても「触る場所はそこだけ」で済む。 
UI (App/TaskForm/TaskList)
      │  getTasks() / addTask() ...  ← 呼び方は常に同じ
      ▼
 taskRepository.js  ←★ここの中身だけ後で差し替える
      │
  [LocalStorage]  →（フェーズ2）→  [fetch → API → DB]

フェーズ1：UI 実装と検証

フェーズ1

App が状態を持ち、操作後は必ず refresh() でリポジトリから取り直す。検証は ロジックは Node 単体テスト、永続化（リロード）はブラウザ目視に分けた （LocalStorage はブラウザ専用で curl では確認できないため）。 

// src/App.jsx（抜粋）操作 → リポジトリ → 取り直し
async function handleAdd(title) {
  await taskRepository.addTask({ title })
  await refresh()
}

npm run test:repo   # Node単体テスト（localStorageをシムで差し替え, 8件）
npm run build       # 全コンパイル確認（21 modules transformed）
npm run dev         # http://localhost:5173/ で起動
04

設計の背骨（なぜ UI を変えずに済むか）

設計

フェーズ2移行が「1ファイルの差し替え」で済んだ理由は4つ。 ①窓口の隔離 ②最初から非同期IF ③相対URLで同一オリジン ④返り値の形と並び順を厳守。

フェーズ1：LocalStorage
export const STORAGE_LABEL =
  'ブラウザの LocalStorage'

export async function getTasks() {
  return read().sort(...)
}
フェーズ2：fetch（UI無変更）
export const STORAGE_LABEL =
  'データベース（PostgreSQL）'

export async function getTasks() {
  return handle(await fetch('/api/tasks'))
}
🔑 相対URL /api/tasks がポイント。dev では vite proxy、共有では nginx が同じパスを backend へ転送するので、 同一オリジン扱い＝CORS不要。リポジトリのコードは環境非依存のまま。
現在: After（フェーズ2・DB）
画面フッター表示： 保存先: データベース（PostgreSQL / Docker・フェーズ2） ← STORAGE_LABEL を import して表示。リポジトリを差し替えると自動でこの文言に切替わる。
画面フッター表示： 保存先: ブラウザの LocalStorage（フェーズ1） ← 以前は文言をハードコードしていたため、差し替え時に直し忘れが2回発生。STORAGE_LABEL 化で解決。
05

フェーズ2：backend（Express + PostgreSQL）

フェーズ2

/api/tasks の CRUD を Express+pg で実装。id/createdAt はサーバが採番。 起動時に CREATE TABLE IF NOT EXISTS＋接続リトライでDB準備を待つ。 

// backend/src/server.js（要点）
// created_at を camelCase の createdAt に別名付け（UIのソート前提を維持）
const TASK_COLS = 'id, title, done, created_at AS "createdAt"'

app.get('/api/tasks', async (_req, res) => {
  const { rows } = await pool.query(
    `SELECT ${TASK_COLS} FROM tasks ORDER BY created_at DESC`) // 新しい順＝Phase1と同じ
  res.json(rows)
})
⚠️ 起動順レース: compose の depends_on は「コンテナ起動」を待つだけで、Postgres が 接続を受け付ける状態は別。→ healthcheck ＋ 接続リトライの二重保険で回避した。
06

フェーズ2：docker-compose（db / backend / 共有nginx）

フェーズ2

3サービスを定義。db（名前付きvolumeで永続化＋healthcheck）、backend、 frontend（profile: share で共有時のみ・nginxがdist配信＋/api転送）。 

# docker-compose.yml（要点・WSL版の例）
services:
  db:
    image: postgres:17-alpine
    volumes: ["db-data:/var/lib/postgresql/data"]   # ★永続化
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U taskuser -d taskmanager"]
  backend:
    build: ./backend
    depends_on: { db: { condition: service_healthy } }   # ★healthy待ち
  frontend:
    profiles: ["share"]                # 共有時のみ起動
volumes: { db-data: {} }
開発時はフロントを vite dev（生）で動かし HMR で快適に。他端末へ配るときだけ --profile share で nginx コンテナを足す。backend / db は両モードで共用。
07

リポジトリ差し替え＋プロキシ配線

フェーズ2

taskRepository.js を fetch 版に差し替え、UI は1行も変えずに DB 接続へ。 dev は vite proxy、共有は nginx が同じ /api を backend へ転送する。 

// vite.config.js（開発時：/api を backend の公開ポートへ転送）
server: {
  port: 5173,
  proxy: { '/api': 'http://localhost:3000' }
}
# nginx.conf（共有時：/api を backend サービスへ転送）
location /api/ {
    proxy_pass http://backend:3000;
}
location / {
    try_files $uri $uri/ /index.html;   # SPA fallback
}
08

方式A と 方式B（デプロイの違い）

デプロイ

「デプロイ」＝ソースをイメージに COPY で焼き込み、docker compose up -d --build。 Windows の C: ソースを WSL の Docker に渡す経路で 方式A / 方式Bに分かれる。 

# パス対応（同じ実体）
C:\Users\user\ClaudeCode\...   ⇔   /mnt/c/Users/user/ClaudeCode/...
方式A：/mnt/c を直接ビルド
# rsync なし・1コマンド
wsl -d Ubuntu -- bash -lc \
 "cd /mnt/c/Users/user/ClaudeCode/TaskManagerWinA \
  && docker compose up -d --build"
# 手軽 / 但し /mnt/c 読込で遅め
方式B：rsync 転送してからビルド
# WSLネイティブへ複製 → そこでビルド
rsync -a --delete --exclude node_modules \
 /mnt/c/Users/user/ClaudeCode/TaskManagerWin/ \
 /home/user/TaskManagerWin/
cd /home/user/TaskManagerWin
docker compose up -d --build
# 速い / C:と完全分離・本番に近い
⚠️ どちらも node_modules は持ち込まない（.dockerignore / rsync --exclude）。 Windowsの node_modules は Windows用バイナリを含み、Linuxコンテナに入れると壊れる。コンテナ内で npm install させる。
💡 バインドマウント（volumes）は「実行時ライブリンク」で開発用。デプロイとは別物。 /mnt/c のバインドは inotify が効きにくくホットリロードが不安定なので採らず、両方式ともイメージ焼き込みにした（更新＝再ビルド）。

検証方法（自動でできる／できない）

検証

フェーズで検証の性質が変わる。LocalStorage はブラウザ専用でサーバから確認不可。 DB はサーバ状態なので CRUD も永続性も curl で自動検証できる。React 描画だけ目視。 

# API の自動検証（backend/test/api.test.mjs ＝ fetch統合テスト7件）
node backend/test/api.test.mjs    # health/CRUD/400/404/createdAtキー

# 永続性＝コンテナ作り直してもボリュームに残るか
curl -X POST .../api/tasks -d '{"title":"MARKER"}'
docker compose down && docker compose up -d   # 名前付きvolumeは保持
curl .../api/tasks                # → MARKER が残っていれば永続OK
🚫 curl の 200 を「UI が動く」と誤解しない。/api/tasks → 200 はプロキシ疎通の証明で、React 描画の確認ではない。 描画・LocalStorageのリロード永続化は必ずブラウザ目視に回す。
⚠️ リポジトリを fetch 化したら、Phase1 の repository.test.mjs（localStorage前提）は壊れる。 差し替えと同時に削除（デッドコードのまま緑表示になる事故を防ぐ）。実際これを2回踏んだ。

つまずきポイント（実際に踏んだ）

教訓

Windows × WSL × Docker の境界で起きた4つの罠と回避策。次回の自分のための記録。 

# ① PowerShell から $ を含む bash ワンライナーは変数展開が干渉
#   → 複雑なものは .sh に書いて wsl bash で実行する

# ② UNC(\\wsl.localhost) 経由で書いたファイルは root 所有になり user で rm 不可
#   → ディレクトリ削除は Windows 側の Remove-Item で行う

# ③ nvm 初回導入：Windows側 tar/xz が PATH 漏れで展開失敗
#   → /mnt/* を PATH から除外して回避。さらに $HOME 展開ミスで
#     "C:Usersuser"(U+F03A=コロン代替)という文字化けフォルダが誤生成（掃除済み）

# ④ WSL の background プロセスは wsl コマンド終了で消える
#   → Docker は up -d(detached) / dev server は harness の background 実行で保持
✅ 設計の改善として、フッター文言を STORAGE_LABEL 定数化（リポジトリから export）。 差し替えでラベルも自動で切替わり、「文言の直し忘れ」を構造的に解消した。

運用コマンド集（3環境）

運用

起動・停止・再デプロイの早見表。down はデータ保持、down -v はデータも削除。 

# 起動（db+backend）。共有フロントも出すなら --profile share を付ける
docker compose up -d                      # 通常
docker compose --profile share up -d --build   # 他端末公開（nginx 8081/8082/8083）

# 停止
docker compose down        # コンテナ削除・データ(volume)は残る
docker compose down -v     # データも完全削除

# 再デプロイ
#  方式A: /mnt/c で1コマンド
cd /mnt/c/Users/user/ClaudeCode/TaskManagerWinA && docker compose up -d --build
#  方式B: rsync 再転送 → 再ビルドの2手
rsync -a --delete --exclude node_modules /mnt/c/.../TaskManagerWin/ /home/user/TaskManagerWin/
cd /home/user/TaskManagerWin && docker compose up -d --build
# 各環境のフォルダ（ここで docker compose を実行する）
WSL版    /home/user/TaskManager                         （5173/3000/5432/8081）
方式B    /home/user/TaskManagerWin                      （5174/3001/5433/8082）
方式A    /mnt/c/Users/user/ClaudeCode/TaskManagerWinA   （5175/3002/5434/8083）
