00

全体像と所要時間

準備

Spec Kit はGitHub公式の仕様駆動開発（SDD）ツールキット。Claude Code に /speckit.* というスラッシュコマンドを追加し、Constitution → Specify → Plan → Tasks → Implement の流れを自動化する。本LabではHello World規模の練習題材を1本完走するところまで導く。

🔰 全体フロー（このLabで通すもの）
┌── 環境準備（Lab 01〜02） ────────┐
│  Python 3.11+ / uv / Git / Claude Code │
└─────────────┬──────────────────┘
              ▼
┌── プロジェクト初期化（Lab 03〜04） ──┐
│  specify init my-project --ai claude    │
│  → .specify/ と .claude/commands/ 生成    │
└─────────────┬──────────────────┘
              ▼
┌── 仕様駆動の5+1ステップ（Lab 05〜10）─────┐
│  /speckit.constitution  プロジェクト憲法     │
│  /speckit.specify       何を作るか           │
│  /speckit.clarify       曖昧さの追加質問     │
│  /speckit.plan          どう作るか           │
│  /speckit.tasks         タスク分解           │
│  /speckit.implement     実装実行             │
└─────────────┬──────────────────┘
              ▼
       完走（Lab 11 はトラブル対処）
段階所要時間目安主な作業
Lab 01〜0215〜30分環境構築（既にClaude Codeあれば短い）
Lab 03〜0410分プロジェクト作成と構造把握
Lab 05〜0960〜90分各スラッシュコマンド実行・成果物レビュー
Lab 1030〜90分実装（題材次第）
合計2〜4時間初回1本
📘 本Labで使う題材: 「タスクをコマンドラインで追加・一覧・完了できる最小TODO CLI（Python）」。Spec Kitの強みは中〜大規模機能だが、初回は完走することが目的なので意図的に小さくする。Tomさんが業務で慣れたOutSystems的な大物は2回目以降で。
⚠️ 本Labのバージョン前提: Spec Kit v0.7.x（2026年4月時点の最新リリース系列）。コマンド名は /speckit.specify 形式。古い記事では /specify と書かれているが、現行は speckit. プレフィクス付き。

準備

Spec Kit を Claude Code で動かすために必要な前提を確認する。Tomさんの環境（Windows業務PC）を念頭に、Mac/Linux両対応の手順を併記する。Python 3.11以上、uv（パッケージランナー）、Git、Claude Codeの4つが揃えばOK。

Claude Codev1.0以降claude --version
uv0.5以降uv --version

# すべて出ればこのLabはスキップ可
python --version

uv --version

📘 uv とは: Astral 社が作る Python のパッケージマネージャ＋ランナー。uvx はインストール不要でPython製CLIを単発実行できる仕組み。Spec Kitは uv tool install（永続インストール）と uvx（単発実行）の両方をサポートしている。本Labでは永続インストール側を採用する。
⚠️ Windows: PATH反映の罠: uv インストール後、PowerShellを再起動しないと uv コマンドが認識されない。エラーが出たら一度ターミナルを閉じてやり直す。Claude Code内のターミナルを使う場合も再起動が必要。
🔍 セットアップ確認
  1. 4つの --version がすべてエラー無く表示されるか
  2. Pythonが 3.11.x 以上か（3.10系だと一部機能で警告が出る）
  3. Claude Codeで一度認証済みか（初回ブラウザ認証が必要）
  4. git config user.name と user.email が設定されているか（Spec Kitは内部でブランチを切る）
02

uvとSpec Kitのインストール

準備

uvが入ったら Spec Kit 本体をインストールする。インストール方式は2通り。(A) 永続インストール（specify コマンドが常時使える）と (B) 単発実行（uvx で毎回実行）。本Labは(A)を推奨。

(A) 永続インストール（推奨・初心者向け）
# GitHubから直接 specify-cli をインストール
# （特定リリースを固定するなら @v0.7.2 のようにタグを付ける）
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git

# インストール確認
specify --version
specify --help

# 必要なツールが揃っているかをSpec Kit自身がチェック
specify check
(B) 単発実行（uvxを使うパターン）
# インストール不要で実行できる代わり、毎回ダウンロードが走る
uvx --from git+https://github.com/github/spec-kit.git specify --help

# プロジェクト作成も同様
uvx --from git+https://github.com/github/spec-kit.git specify init my-project --ai claude
✅ specify check の役割: 環境前提（Python・Git・対応AIエージェント）が揃っているかを自動診断する。最初に1回走らせておくと、後の specify init で詰まるリスクが激減する。
方式長所短所
(A) tool install毎回 specify だけで起動・速い更新は uv tool upgrade が必要
(B) uvx 単発常に最新が使える・更新不要毎回ネットアクセスが走る・遅い
⚠️ PyPIの偽パッケージに注意: PyPIに specify-cli という同名パッケージがあるが、これは公式と無関係。必ず --from git+https://github.com/github/spec-kit.git を付ける。これは公式 README にも明記されている安全注意点。
📘 バージョン固定のすすめ: 業務利用や教材化を考えるなら @v0.7.2 のようにタグ固定推奨。main から取ると未リリース変更が混じる場合がある。最新タグは GitHub Releases で確認できる。
🔍 インストール確認
  1. specify --version でバージョン番号が出るか
  2. specify check が「すべてOK」相当の出力になるか
  3. uv tool list に specify-cli が載っているか
  4. 使用中の Claude Code が listed agents（claude）に出ているか
03

specify init でプロジェクト初期化

準備

実際にプロジェクトを作る。specify init はディレクトリ構造とテンプレート、Claude Code用のスラッシュコマンドファイルを一括展開するコマンド。これでClaude Codeから /speckit.* が使えるようになる。

① 新規プロジェクトとして作る場合
# 練習用のディレクトリ名（好きな名前でOK）
specify init my-todo-spec --ai claude

# Windowsで PowerShell を使うなら（Bashスクリプトの代わりに .ps1 を生成）
specify init my-todo-spec --ai claude --script ps

# プロジェクトに移動
cd my-todo-spec
② 既存ディレクトリで初期化する場合
# 既存プロジェクトに後から導入したいとき
cd existing-project
specify init . --ai claude
# または
specify init --here --ai claude
📘 主要オプション: --ai claude（エージェント指定。他は copilot / gemini / cursor / codex など）／ --script sh|ps（自動化スクリプトをBashかPowerShellか）／ --no-git（git init をスキップ）／ --ignore-agent-tools（ツール存在チェックを飛ばす）。
⚠️ Windowsでの注意点: --script ps を付けないとデフォでBashスクリプトが配置される。Git Bashが入っていればBashでもOKだが、ピュアPowerShell運用なら明示指定推奨。
✅ 初期化中のインタラクティブ選択: --ai を省略すると、矢印キーでエージェントを選ぶUIが立ち上がる（claude / copilot / gemini / cursor など）。Claude Code のターミナル内から実行するとここで詰まることがある（issue #267）ので、OS本体のターミナルから実行するのが安全。
💻 実際にやる
  1. OS本体のターミナル（PowerShell or Terminal）を開く
  2. 練習用の親ディレクトリへ移動（例: C:\Users\user\ClaudeCode\）
  3. 上記コマンドで specify init my-todo-spec --ai claude を実行
  4. 初期化中のメッセージで「Claude Code commands installed to .claude/commands/」相当が見えるか確認
  5. cd my-todo-spec で入る
💡 コツ: プロジェクト名は my-todo-spec のように半角英数字とハイフンで。日本語や空白は後段のスクリプトで罠になる。
🔍 初期化成功の判定
  1. 新ディレクトリ my-todo-spec/ が作成されたか
  2. その中に .claude/commands/ ディレクトリがあり、speckit.*.md ファイルが並んでいるか
  3. .specify/ ディレクトリと memory/、templates/、scripts/ が見えるか
  4. git log --oneline で初期コミットが残っているか
04

生成ファイル構造を読む

準備

specify init 直後の構造を理解しておくと、後で何が生成されているのか・どこを直せばいいかが分かる。Claude Code が読むのは .claude/commands/*.md。Spec Kit本体は .specify/ 配下。

🔰 ディレクトリ構造（typical）
my-todo-spec/
├── .claude/
│   └── commands/                ← Claude Code が読む slash command 群
│       ├── speckit.constitution.md
│       ├── speckit.specify.md
│       ├── speckit.clarify.md
│       ├── speckit.plan.md
│       ├── speckit.tasks.md
│       └── speckit.implement.md
├── .specify/
│   ├── memory/
│   │   └── constitution.md      ← Lab05 でここに「憲法」が生成される
│   ├── templates/               ← spec.md / plan.md / tasks.md のひな型
│   └── scripts/                 ← 内部で動く .sh / .ps1
├── specs/                        ← Lab06 以降、機能ごとに作られる
├── .gitignore
└── README.md（テンプレ的なもの）
場所役割編集する？
.claude/commands/Claude Codeへの命令テンプレ基本ノータッチ
.specify/memory/constitution.mdプロジェクト憲法Lab05で生成→以後たまに更新
.specify/templates/各ステップのMarkdownひな型カスタマイズ可
.specify/scripts/ブランチ作成等の自動化基本ノータッチ
specs/NNN-name/spec.md機能の仕様書Lab06で自動生成→人間レビュー
specs/NNN-name/plan.md技術計画書Lab08で自動生成→人間レビュー
specs/NNN-name/tasks.mdタスクリストLab09で自動生成→人間レビュー
📘 specs/ は機能ごとにフォルダが切られる: /speckit.specify を実行するたびに specs/001-todo-cli/、specs/002-add-priority/ のような連番フォルダが作られ、Gitブランチも自動で切られる（例: 001-todo-cli ブランチ）。これがSpec Kitの「Spec単位 = ブランチ単位」の運用思想。
初期化直後の確認コマンド
# Windows / Mac 共通
ls -la .claude/commands/
ls -la .specify/

# Claude Code が読み込めるか確認
claude
# プロンプトに「/」を入れると候補に speckit.* が出るはず
⚠️ スラッシュコマンドが見えないとき: Claude Code を Spec Kit 初期化前に既に開いていた場合、コマンド一覧をリロードしないと表示されない。一度 /exit で終了→ claude で起動し直すのが確実。
🔍 構造確認
  1. .claude/commands/ に6個前後の speckit.*.md がある
  2. .specify/memory/constitution.md はこの時点では空 or テンプレ状態
  3. Claude Codeを起動して / を打つと /speckit.constitution 等が候補に出る
  4. specs/ はこの時点ではまだ空
05

Step 1: /speckit.constitution（憲法）

5フェーズ実践

最初のステップは「憲法（Constitution）」を書くこと。プロジェクト全体に常に適用される不変の原則を1ファイルに定めて、以後すべてのフェーズで参照させる。これがあると AI が勝手に過剰な抽象化やフレームワーク導入をしなくなる。

📘 憲法に書くべきこと: ① コーディング原則（TDD必須・最小依存・型を書く等）② アーキテクチャ制約（最大3プロジェクト等）③ ライブラリ方針（フレームワーク機能を直接使う・ラッピング禁止）④ レビュー・テストポリシー。「将来揺らがないルール」だけ書くのがコツ。題材ごとの細かい要件は spec.md に。
Claude Code で実行
# プロジェクトディレクトリで Claude Code を起動
claude

# プロンプトで以下を打つ
/speckit.constitution

このプロジェクトは Python 3.12 で作る最小TODO CLI です。
以下を不変原則として明文化してください:

1. テストファースト（実装前にpytestを書く）
2. 標準ライブラリ優先、外部依存は必要最低限
3. 型ヒントを全関数に付ける
4. 1ファイル100行を目安に分割
5. README に使い方を必ず書く
6. CLI は --help で全機能が分かる設計
⚠️ AI出力をそのまま受け入れない: スラッシュコマンドはAIに高品質な出力を促すが、Spec Kitの設計者は「Verify, not steer」と書いている通り、毎フェーズで人間が読んで承認するのが大前提。憲法は特に後で外しにくいので、初回は時間をかけて読み直す。
💻 実際の流れ
  1. 上のプロンプトを claude で実行
  2. AIが .specify/memory/constitution.md を生成・更新
  3. エディタ（VS Code など）でそのファイルを開いて必ず読む
  4. 過剰なルール・抽象的すぎるルールがあれば「5番目のルールを削除して」「3番目をもっと具体的に」と修正指示
  5. OK なら git add . && git commit -m "Add constitution"
💡 コツ: 1回目は短めに5〜7条で。「TDD必須」「型必須」あたりだけでも十分機能する。長いほどAIが守りきれず無視されることもある。
🔍 Step 1完了の判定
  1. .specify/memory/constitution.md が更新され、Markdown形式で読める
  2. 原則が箇条書きで5〜10条程度に収まっている
  3. 各原則に「なぜそれが必要か」の短い理由が添えられている
  4. あなたが3ヶ月後に読んでも違和感ない内容になっている
06

Step 2: /speckit.specify（仕様生成）

5フェーズ実践

ここからが本番。/speckit.specify はWhat/Why（何を作るか・なぜか）を仕様書にまとめさせるコマンド。How（技術スタック）は書かないのが鉄則。Pythonとか言わず「ユーザがコマンドラインで…」のような利用者視点だけ書く。

Claude Code で実行（題材: 最小TODO CLI）
/speckit.specify

最小のTODO CLI を作ります。
ユーザがコマンドラインで以下を行えるようにしたいです:

- タスクを1行で追加できる（タイトルのみ）
- 全タスクを一覧表示できる（未完了/完了が一目で分かる）
- IDを指定してタスクを完了状態にできる
- 完了済みのタスクをまとめて削除できる
- データはローカルファイルに永続化される（再起動しても残る）
- 1人で使う前提（マルチユーザ・認証は不要）
- インストール後すぐに使えること（DB・サーバ不要）

成功の定義:
- ターミナルで5回コマンドを叩いてTODO管理が完結する
- 自分が3日連続で使う

スコープ外:
- 期限・優先度・タグなどの拡張属性
- リモート同期
- TUI / GUI

技術スタックは指定しません（Plan で決めます）。
✅ このコマンドが裏でやること: ① specs/001-minimal-todo-cli/ のようなディレクトリを作る ② 同名のGitブランチを作って切り替える ③ テンプレートに基づいて spec.md を生成（ユーザストーリー・受入基準・スコープ等を埋める） ④ Review & Acceptance Checklist を末尾に付ける。
⚠️ 技術用語を書きそうになったら止まる: 「Pythonで」「argparseで」「JSONで保存」と書きたくなるが我慢。それはLab08の /speckit.plan のテリトリー。Specifyに技術が混じると、AIが「実装を意識した抽象的な仕様」を出してしまい、本来の柔軟性が失われる。
💻 spec.md レビューのコツ
  1. 生成された specs/001-*/spec.md を必ず開く
  2. 末尾の Review & Acceptance Checklist を Claude Code に渡す:
    「spec.md のレビューチェックリストを読み、各項目について満たすかどうか判定し、満たすものだけ✓を入れて。理由も1行ずつ書いて」
  3. 受入基準が Given/When/Then 形式で書かれているか確認
  4. 曖昧な箇所は次のLab07で /speckit.clarify を使う
  5. OK なら git add . && git commit -m "Add spec for todo-cli"
💡 コツ: 「これでspecとして十分か、抜けがあれば指摘して」とAIに自己評価させると、追加で3〜5個の質問が出てくることが多い。それに答えながらspecを育てる。
🔍 Step 2完了の判定
  1. specs/001-XXX/spec.md が生成され、ユーザストーリーがAs a/I want/So that形式で書かれている
  2. 受入基準が Given/When/Then 形式で複数（5〜10個）書かれている
  3. spec.md 内に技術スタック（Python・JSON・SQLiteなど）の言及がない
  4. Gitブランチが 001-XXX に切り替わっている（git branch で確認）
07

Step 3: /speckit.clarify（曖昧解消）

5フェーズ実践

/speckit.clarify は仕様の曖昧さをAIが質問形式で洗い出すコマンド。Plan に進む前にここで詰めておくと、後段でAIが勝手に解釈して暴走するリスクが減る。初回は必ずやることをおすすめ。

Claude Code で実行
/speckit.clarify

spec.md に対して、実装前に確定すべき曖昧な点を質問として出してください。
特に以下の観点を重点的に:

- 入力バリデーション（タイトルの最大長・空文字許容など）
- データ永続化の場所（ホームディレクトリ？カレント？）
- IDの採番方式（連番？UUID？）
- エラーケースの挙動（存在しないID指定時など）
- 複数同時起動時の挙動（ファイルロック）

質問は番号付きで出してください。私の回答後、spec.md を更新してください。
📘 Clarify が効く理由: Specify 段階で書いた仕様は意図せず曖昧なことが多い。「タスクを追加できる」と書いても、「空文字でも追加できるか？」「絵文字は？」「同じタイトルの重複は？」など決めるべきことが残る。Plan に進む前にここを潰すと、tasks.md の精度が劇的に上がる。
⚠️ 質問は5〜10個に絞る: あまり多いと回答に疲れて適当に答えてしまい、結果的に仕様精度が下がる。本当に決めないと実装できないことに絞ってAIに指示する。
💻 やり方
  1. 上のプロンプトを実行
  2. AIが質問リストを出す（例: 「タイトルの最大長は？」「データファイルの場所は？」）
  3. 1問ずつ答える（「タイトル200文字まで」「~/.todo-cli/data.json」など）
  4. すべて答えたら「これで spec.md を更新して」と指示
  5. 更新された spec.md を読み、納得できればコミット
💡 コツ: 答えに迷う質問が出たら、その場で決めずに「これは Plan で決めるべき技術的な話なのでスキップ」と返してOK。Clarify はあくまで仕様レベルの曖昧解消。
🔍 Step 3完了の判定
  1. spec.md に「Edge Cases」「Constraints」セクションが追加 or 拡張されている
  2. 受入基準（Given/When/Then）に異常系のシナリオが追加されている
  3. 残った疑問点が「Open Questions」として明示されているか、または全て解消されている
  4. spec.md の更新分が git diff で確認できる
08

Step 4: /speckit.plan（技術計画）

5フェーズ実践

ここで初めて技術スタックを決める。/speckit.plan は spec.md と constitution.md を読み、技術選定・アーキテクチャ・データモデル・コントラクト・クイックスタート手順を一気に生成する。複数ファイルに分かれて出力される。

Claude Code で実行
/speckit.plan

Python 3.12 / 標準ライブラリのみ で実装します。
- 永続化: JSON ファイル（~/.todo-cli/data.json）
- CLI: argparse
- テスト: pytest（標準的な使い方）
- パッケージ管理: uv（pyproject.toml）

constitution.md と spec.md を踏まえ、以下を生成してください:

1. plan.md（アーキテクチャ概要・モジュール分割・依存・主要決定事項）
2. data-model.md（Task のデータ構造とJSONスキーマ）
3. quickstart.md（クローンから動作確認までの手順）
4. research.md（argparse vs click のような検討メモ・採用理由）

constitution の「テストファースト」「型ヒント全関数」「1ファイル100行目安」を守ること。
✅ Plan の威力: plan.md 単体ではなく、関連する data-model.md・contracts/・research.md・quickstart.md を芋づる式に生成する。これらすべてが「契約」として後段の tasks.md 生成に効く。Spec Kit の真価はこの多層成果物の連動にある。
📘 Researchが必要な技術には追加指示: 急速に変わるライブラリ（フロントエンドFW・新興AIライブラリなど）を使うときは、Plan 後に「research.md を見直し、不足している最新情報を Web で調べて補強して」と追加で指示できる。Claude Code の Web 検索能力をここで活用する。
⚠️ Plan が大きすぎると感じたら止める: 小規模題材なのに巨大な研究ドキュメントが出てきたら、「これは過剰。最小TODO CLI なので plan.md と data-model.md だけで十分」と削減指示。Spec Kit は Sledgehammer 問題（小タスクを大げさに扱う）が知られているので、人間側でブレーキを掛ける必要がある。
💻 Plan レビューのコツ
  1. 生成された全ファイルを開いて目を通す（plan.md / data-model.md / research.md / quickstart.md）
  2. constitution.md と矛盾がないか確認（「TDD必須」と書いたのに plan.md でテスト後回しになっていないか等）
  3. spec.md の受入基準が plan.md でカバーされているか
  4. 気になる点を Claude Code に伝えて修正させる
  5. OK なら git add . && git commit -m "Add implementation plan"
💡 コツ: 「constitution と spec と plan に整合性があるか自己レビューして」とAIに依頼すると、自分で気づかない矛盾を3〜5個指摘してくれる。
🔍 Step 4完了の判定
  1. specs/001-XXX/ 配下に plan.md と関連MDが揃っている
  2. plan.md に技術選定の理由が書かれている（単なる選定リストでなく根拠つき）
  3. data-model.md にデータ構造が JSON Schema 風に書かれている
  4. quickstart.md を読めば、他人が手順通りに動かせそうか
09

Step 5: /speckit.tasks（タスク化）

5フェーズ実践

/speckit.tasks は plan.md を実行可能な単位タスクのリストに分解する。各タスクは依存関係順に並び、並行実行可能なものには [P] マーカーが付く。各タスクには触るファイルパスまで含まれる。

Claude Code で実行
/speckit.tasks

plan.md と data-model.md を踏まえ、tasks.md を生成してください。

要件:
- 各タスクは1〜2時間で終わる粒度
- 依存関係を明示（後続タスクは前提タスクのIDを参照）
- 並行実行可能なものに [P] マーカー
- TDDに従い、テストタスクは実装タスクの前に置く
- 各タスクに触るファイルパス（フルパス）を明記
- ユーザストーリー単位でフェーズ分け
🔰 tasks.md の典型構造
## Phase 1: User Story 1（タスクを追加・一覧）
T001    Project skeleton 作成
        files: pyproject.toml, src/todo/__init__.py
T002    Task データクラス + テスト
        files: tests/test_task.py, src/todo/task.py
        depends-on: T001
T003 [P] Storage 層 + テスト（JSON I/O）
        files: tests/test_storage.py, src/todo/storage.py
        depends-on: T001
T004 [P] CLI: add コマンド + テスト
        files: tests/test_cli_add.py, src/todo/cli.py
        depends-on: T002, T003

## Phase 2: User Story 2（完了マーク・削除）
T005    CLI: complete コマンド
T006    CLI: clean コマンド
...

  ↑ [P] が並行可能。T003 と T004 は依存関係的に同時に進められる。
📘 Spec Kit のタスク粒度設計: 「ユーザストーリー単位でフェーズ分け」「各フェーズ内で依存DAG」「並行可能なものをマーク」「ファイルパス明記」の4点が組み込まれている。これは AI-DLC の Bolt 設計と類似だが、Spec Kit の方がメタデータが構造化されている分、自動実行に向く。
⚠️ タスクが多すぎたら止まる: 最小TODOで20個以上タスクが出てきたら過剰。「これを10個以内に統合して、1タスク1コミットを目安にして」と再生成依頼。後の implement ステージで疲れるのはここの粒度設計ミスが原因。
💻 tasks.md レビューのコツ
  1. tasks.md の最初のタスクから読む
  2. 各タスクが「何を作って何で確認するか」が1文で言えるか確認
  3. 依存関係が循環していないか（A→B→Aは禁止）
  4. 並行 [P] のマークが妥当か（実は密結合で並行できないものに付いてないか）
  5. OK なら git add . && git commit -m "Add task breakdown"
💡 コツ: tasks.md は次のステップで「順次実行」される設計図。ここで違和感があれば必ず直してから進む。間違ったタスクをAIに実行させて後戻りするより安い。
🔍 Step 5完了の判定
  1. tasks.md がユーザストーリー単位のフェーズで分かれている
  2. 各タスクに ID（T001など）と触るファイルパスがある
  3. 依存関係が明示され、並行可能タスクに [P] が付いている
  4. テストタスクが対応する実装タスクの前に置かれている
10

Step 6: /speckit.implement（実装実行）

5フェーズ実践

ついに実装。/speckit.implement は tasks.md を順次実行し、各タスクのファイルを生成・テストを書いて走らせる。ここが「AIが自走する」最大のフェーズ。人間は要所で監視と承認をする。

Claude Code で実行（小さく始める）
/speckit.implement

tasks.md の Phase 1（User Story 1）のタスクから実装してください。

ルール:
- 各タスクの実装後、必ずテストを実行して結果を報告
- 1タスク完了ごとに私の承認を待ってから次へ
- constitution.md の原則を厳守（型ヒント・1ファイル100行目安）
- 触ると tasks.md に書いていないファイルには手を出さない
- Phase 2 にはまだ進まないでください
✅ 「Phase ごとに区切る」のが安全: いきなり /speckit.implement だけ叩くと全タスクを順次走らせる。最初は怖いので明示的にPhase 1だけと指示する。慣れたらフルで走らせてもOK。
⚠️ 「触らないファイル」を毎回明示: AIは指示の隙を見つけて「ついでに直す」傾向がある。tasks.md に書いていないファイルへの編集は確実に禁止と書く。これを怠ると、Spec Kitが管理する仕様契約とコードの整合性が崩れる。
📘 テスト駆動が組み込まれる: constitution.md に「TDD必須」と書いておくと、implement フェーズで AI が必ずテストを書く→失敗を確認→実装→テストを通すの順で進める。これは Spec Kit のテンプレートで構造的に強制されている。
💻 実装フェーズの進め方
  1. Phase 1 を実行依頼
  2. 各タスク完了時にAIが報告する → ファイルを開いて目視レビュー
  3. テスト結果（pytest出力）を確認
  4. 気になる点があれば「T002 のテストにX観点が抜けている。追加して」と指摘
  5. Phase 1 が全部終わったら一度動かして手動確認（quickstart.md の通り）
  6. git add . && git commit -m "Implement Phase 1"
  7. Phase 2 を依頼…という流れ
💡 コツ: 全Phase終了時に「spec.md と plan.md と実装に乖離がないかレビューして」と最終チェック依頼。これが Spec Kit の「Drift Detection」相当を擬似的に実現する。
🚨 暴走したと感じたら止める: AI が想定外のファイルを大量に作ったり、tasks.md にないライブラリを導入したら、即 Esc や Ctrl+C で中断。git checkout . で戻して、tasks.md を見直してから再実行。戻れる場所を毎Phaseでコミットしておくのが命綱。
🔍 Step 6完了の判定（プロジェクト完走）
  1. quickstart.md の手順通りにクローン直後から動作確認できる
  2. すべてのテストが通る（pytest 実行で全 PASS）
  3. spec.md の受入基準（Given/When/Then）が全て満たされる
  4. git log を見て Phase 単位でコミットが残っている
  5. 残ったタスクや既知の制限が tasks.md or plan.md に記録されている

トラブル対処と更新・小ネタ

運用

初回完走後によく出る問題と、Spec Kit を継続的に使うための運用Tips。ハマったときに参照する逆引き集として活用できる構成にしている。

症状原因と対処
Claude Code起動時に /speckit.* が出ない初期化前に開いていた可能性。/exit → claude で再起動。.claude/commands/ にファイルがあるか確認
specify init がCLIから対話で固まるClaude Codeの内部ターミナルで実行している可能性。OS本体のターミナルで実行する（issue #267）
Windowsで.shが動かない--script ps 付きで初期化。または Git Bash を使う
ブランチが勝手に切り替わって戸惑うSpec Kit は /speckit.specify で機能ごとにブランチを作る。これが Spec単位 = ブランチ単位 の思想。git branch で現在地を確認する習慣をつける
uvxで毎回ダウンロードが遅いLab02の(A) uv tool install 永続インストールに切替
Implement中にAIが暴走Esc/Ctrl+Cで中断 → git checkout . で戻し → tasks.md の粒度を見直して再実行
Spec Kit の更新
# CLI ツール本体の更新
uv tool upgrade specify-cli

# プロジェクトのテンプレートを最新版に更新（既存プロジェクト内で）
cd my-todo-spec
specify init . --ai claude --force
# --force は scripts/ と templates/ を上書き。specs/ 配下は触らない設計

# constitution.md をカスタマイズ済みの場合、必ずバックアップしてから --force
cp .specify/memory/constitution.md /tmp/constitution_backup.md

✅ AI-DLCとのハイブリッド再考: 前回比較Labで提示した通り、Spec Kit の specify → plan → tasks の3つを AI-DLC の Inception フェーズで使い、Construction は Bolt 形式で回す、というハイブリッドが現実的。Spec Kit の構造化された出力 + AI-DLC の細かい人間ゲートでいいとこ取り。
